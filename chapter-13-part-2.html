Chapter 13 — Streaming compaction and safe reclamation

Part 2 — Install new owners, then reclaim old names

Part 1 established the complete-prefix rule and output forecast. This part implements the two distinct operations. compact_prefix creates and installs replacement tables. Only a later collect_obsolete considers deletion. An exception during the first operation must not turn its speculative outputs into authority; an error during the second must not turn current input files into garbage.

All code below extends the completed Part 1 state. The allocation remains 4.0 implementation hours for the whole chapter, not four hours per part. The implementation and test hooks remain synchronous and nonreentrant. In particular, a hook must not call back into the same database, capture views, or run collection.

A source needs both object identity and persistent identity

Chapter 12's retention slots count distinct source objects using stable owner addresses. That is sufficient for admission accounting, but a directory listing contains persistent file IDs and suffixes, not TableReader* addresses. Record both identities in the same bounded registry. Do not add a second owning registry that accidentally keeps every retired source alive forever.

A table source records its .sst identity. A frozen memtable source records its .wal identity, even though reads come from its arena. Preserving that WAL name while its generation is retained gives one conservative policy for both source kinds. Every source admitted by Database::snapshot must have a nonzero ID.

Apply these declaration changes to read_view.hpp. file_id is plain metadata; the shared pointers remain the owning edges. Slot::references still counts admitted states, not copies of a ReadView handle.

Inside namespace read_detail in src/storage/read_view.cpp, replace the complete Context::check_admission and Context::retain definitions. The former checks the new invariant before any rotation. The latter stores persistent identity only when a previously unseen owner acquires a slot. Existing release clears the whole slot with {} at its final reference, including the added fields.

After namespace read_detail has closed, but before the file's final namespace strata::storage closing brace, add this qualified definition:

A cursor owns its state even after it reaches end-of-range. Exhaustion describes iteration, not object destruction. Resetting the last handle destroys the state, which unregisters its sources. Standard shared ownership destroys the managed object only when its final owning handle goes away; see the C++ draft's shared_ptr destructor. Our registry records which persistent names that live state protects. It does not infer safety from an arbitrary use_count() value or from whether a cursor is currently positioned on a row.

Enumerate first, remove second

Deleting while advancing a directory stream makes enumeration behavior harder to reason about. Instead, collect one bounded list of numbered files under the already-held directory lock, close the stream, and then process the list. Chapter 11 already caps the entire directory at 4,096 non-dot entries. Reserve at most that many NumberedFile records with the shared budget before enumeration.

The vector contains metadata, not table contents. Its requested capacity charge is 4096\,\mathrm{sizeof}(\texttt{NumberedFile}) bytes on the current C++ ABI; sizeof may include padding, so do not hard-code a purported portable byte count. Allocation failure occurs before any deletion. The existing strict checks on reserved entries still reject symlinks, nonregular files, and multiple hard links. Foreign names are counted toward the directory bound but never returned for collection.

Replace Directory::scan in src/io/directory.cpp with this definition. Its default null output pointer preserves the constructor's inventory-only scan. The owned DIR* is destroyed on normal return and on exceptions; descriptor ownership transfers to fdopendir only after successful creation.

Append these definitions inside namespace strata::io, before its final closing brace. remove_numbered can construct only a reserved numbered filename. It cannot express MANIFEST, LOCK, a parent path, or notes.txt. It rechecks the entry before one unlink attempt and reports an absent entry as already gone.

The database must still decide eligibility; this low-level method is not that policy. We assume a trusted local directory and cooperating users of the lock, as in Chapter 11. A check followed by unlinkat is not a defense against an adversary who can replace directory entries between those calls. No such hostile concurrent mutation is admitted by this course's file boundary.

A successful unlink removes a name, not necessarily the last live storage reference. Apple's archived unlink(2) manual explains why an already-open file can remain usable after its name disappears. Consequently, a test that only reads an old cursor can miss premature unlink. We will also assert that retained source names remain present. removed_file_bytes will mean the summed logical lengths of successfully unlinked files, not measured filesystem blocks or immediately recovered physical space.

Expose bounded operations and scoped measurements

Create this header. A call may produce at most max_output_files files and at most max_output_bytes completed output bytes. The manifest's remaining slots impose an additional cap. Each file also obeys its TableOptions::file_limit, block count, and metadata limits. The total cap is a bound on this operation's new table outputs, not an operating-system reservation or a database-wide disk cap. Old inputs, retained generations, newer files, logs, and manifest temporaries can coexist with it; actual disk-full errors remain possible.

The distinction between the measurements is intentional:

Field Meaning
input_entries Stored entries advertised by selected, validated input tables
output_entries Rows successfully appended so far, including an uninstalled attempt
selected_file_bytes Logical sizes of selected files, including their metadata
merge_read_bytes Successful transfers on selected input readers during this operation
output_write_bytes Successful transfers on new output descriptors, including partial failures
completed_file_bytes Sizes of finished output tables, even if installation later fails
installed The manifest transition and nonthrowing owner publication completed

The read meter excludes earlier table opening, output verification, WAL work, and manifest traffic. Cache hits may avoid input transfers. These are not total engine I/O counters, device-sector counters, a throughput benchmark, or process memory measurements. A saturated counter must not be treated as exact.

Replace database.hpp with the following complete header. The trailing & on mutating methods retains the earlier lvalue-only API. The base argument to open_table selects stricter key/value rules but permits compacted-away sequence endpoints; ordinary flushes continue calling it with the default false.

Reopen the meaning, not just the bytes

A valid checksum proves neither uniqueness nor coverage. Replace Database::open_table in src/storage/database.cpp. It retains exact file-length checks, charged shared ownership, and full-table verification. For a base partition it additionally requires puts only, strictly increasing user keys, and at least one row. Every row's sequence must still belong to the declared interval. A delta must still witness both endpoints of its interval.

previous is an optional user key, not an internal key. Two versions of the same user key therefore fail the base check even though they would be valid in an ordinary sorted delta. Empty bases are represented by zero files, so dereferencing first_key and last_key for a successfully opened base partition is safe.

Replace recover as follows. Adjacent base partitions must satisfy \operatorname{last}(i-1)<\operatorname{first}(i) under KeyLess. This is both nonoverlap and increasing manifest order. Reordering two otherwise valid base records and recomputing the manifest checksum must still be rejected.

Current point reads still search newer deltas before the base. Searching base partitions in reverse is harmless because their user-key ranges are disjoint; at most one contains a key. Snapshot scans already merge any bounded source set by internal order. Neither mechanism needs an in-memory map of all compacted keys.

Replace snapshot to supply persistent IDs alongside each owner. All Chapter 12 admission, rotation, and activation ordering is retained. No file identity is looked up by dereferencing a possibly retired pointer.

Stream a replacement through the existing heap

Create src/storage/compaction.cpp from the following segments in order. The first segment contains all includes and local helpers. The meter destructor bodies perform no new transfers or synchronization; they only collect already-recorded counters. Releasing their owner members can still perform the existing nonthrowing descriptor cleanup. The read meter retains the selected reader owners until it has measured them, including when the serving array has been swapped. The write meter is declared after its file owner, so it reads that owner's final counters before the file object is destroyed.

The eligibility predicate for cleanup is deliberately separate from the retention query. A file can be live in the current manifest even when no user snapshot exists. A temporary manifest candidate is never authoritative merely because it has a high number or valid-looking bytes.

Begin the compaction method. The selected count indexes the leading table records, not a sequence number. It must be nonzero and at least the existing base-file count: all of that base, optionally plus newer deltas. A base-only rewrite does not advance base_end; it can repack small partitions into larger files. When no base exists, base_count == 0 and any nonempty oldest prefix is eligible.

If K tables are selected and U newer tables remain, the maximum output count is \min(\texttt{max_output_files},16-U). This accounts for the unselected owners that must remain in the manifest. next_manifest checks epoch exhaustion before file effects. Statistics are reset after this preflight; a rejected invalid selection leaves the previous operation's statistics unchanged.

This segment deliberately ends inside the method. Append the next segments without adding a closing brace here. Database is already a friend of ReadView, so it may construct a private view over the selected sources. This temporary state is not activated as an admitted user snapshot: it cannot escape and no collector can run concurrently or reentrantly. Its shared owners still keep all inputs alive. The ordinary heap scan does the difficult work from Chapter 12, including consuming every older version of each key and copying the output row before invalidating a borrowed input span.

The new array of shared readers is fixed-size. candidate.tables is rebuilt, while its logs and flushed boundary remain copied from the current manifest. base_end becomes the selected prefix's end, not the latest log sequence. Only after the input scan and workspace exist do we mark the database poisoned and begin output effects. Earlier preparation failures need not poison it.

Continue with the output loop:

The cursor advances only after a row is appended successfully. A negative forecast leaves that row available for the next file. If the first row cannot fit, rows == 0 rejects the operation rather than creating empty files forever. With 300-byte files, eight event results become four 286-byte files; two account results share a 254-byte file. The five outputs total 4\cdot286+254=1398 bytes. The total output cap can make the last file's effective cap smaller than 300.

Builder buffers are destroyed before allocating the new reader's metadata. The file is synchronized and checked-closed before it is opened for serving. The new reader is fully validated before the manifest may name it. This conservative verification rereads outputs; it is not included in merge_read_bytes, and it costs work. The meter remains outside the builder scope so successful header and block writes are counted even if a later allocation, append, sync, or open fails.

A failure after poisoned_ = true leaves all artifacts in place and disables serving through this database facade. An earlier read view may still read its unchanged sources. Reopen determines authority; a subsequent explicit collection can remove uninstalled outputs. This intentionally broad failure policy avoids pretending that a partially executed maintenance operation rolled back its I/O.

Finish the method:

Only install(candidate) changes authority. Chapter 11's ordering still applies: output contents are synchronized, dependency names are synchronized, a new manifest is written and synchronized, the manifest name is replaced, and the directory and authority are stabilized. No old input is removed on this path. The remaining array swap, trivial statistics changes, and owner releases cannot allocate. There is no post-install reader construction that could leave the manifest committed while serving owners are missing.

The empty-output case skips the entire loop, installs positive base_end with zero base files, and retains any newer tables and logs. A later delta after that boundary is still contiguous. An old view that needs a deleted value continues using its old files; the new base need not retain that value for it.

For N stored input entries in K selected sources, the existing heap uses O(N\log\max(2,K)) comparison work, plus the initial source setup. Its dynamic storage is bounded by the source count: one position/pin per source, the heap, and one owned result row. Output adds one builder workspace at a time and bounded metadata/owner storage for completed outputs. Retained old states, the cache, and those new allocations all use the shared budget. A small budget can therefore reject compaction even though no collection of all N rows is allocated. Fixed stack arrays and ordinary process/runtime overhead remain outside the charged-allocation promise from Chapter 9.

Fence identities before erasing their evidence

Suppose a failed operation left s-00000000000000001000.tmp, but the installed manifest still says next_id == 40. Reopen sees ID 1000 and raises the in-memory high-water mark. Simply deleting the orphan would erase the only persistent evidence of that ID. Another reopen could then allocate 40 onward and eventually reuse 1000. That contradicts our permanent identity discipline.

Before deleting anything, install a manifest whose next_id is greater than every observed numbered identity. install itself consumes a temporary ID, then writes the resulting next-ID value, so its own temporary is covered too. An uncertain fence installation poisons the database and performs no deletion. If the highest ID is the maximum unsigned value, fail explicitly: there is no representable next ID.

Append the final segment of compaction.cpp:

Enumeration and any high-water manifest installation precede unlink attempts. The current manifest is checked first, the retained-source registry second. Only files failing both checks are candidates. Idle cached byte copies are trimmed, but a cache pin alone is not a file owner: it retains its own immutable allocation, not a descriptor or a right to reopen a removed file. Every database cursor that can advance to another block retains its state and source owner, which the registry protects.

The result distinguishes failure to remove a file from failure to synchronize the namespace afterward. Failed individual deletions remain discoverable by a future scan; the collector continues with other eligible files. The original error code is retained when available. A test-hook exception without an errno is represented by EIO. Ordinary cleanup failure does not poison a database whose current dependencies were never eligible for deletion.

Directory synchronization runs even when zero files were removed. This permits a retry to resolve a previous cleanup-sync failure after all names are already absent. In full-device mode, the existing explicit device-flush request follows the directory synchronization. Apple's archived fsync(2) discussion distinguishes a host flush from F_FULLFSYNC; issuing that request is not a measurement of hardware persistence. Do not infer power-loss correctness from our process-exit tests. SQLite's atomic-commit discussion, particularly sections 9.2 and 9.5 is useful context on flush assumptions and recovery-file lifetime; this implementation does not use SQLite's rollback-journal algorithm.

Follow one retirement to its final release

A sequence-1 snapshot owns an arena/log source. Flush creates a table; that old snapshot still owns the log. A second snapshot owns the table. A cursor from the second snapshot owns its state. Compaction later installs five new base files. The first log and old table are now absent from current authority, but both are retained. Neither may be unlinked by our policy.

Reset the first snapshot: the old log becomes eligible. Reset the second snapshot but keep its cursor: the old table remains ineligible. Exhaust the cursor: still ineligible. Reset the cursor: its state's last owner disappears, its retention slot is released, and the next collector may remove the table. This is a state transition controlled by ownership, not by a timer or a guess that a query should have finished.

The collector requires a live database facade. When only an escaped view remains, it continues holding the directory lock and sources, but performs no background cleanup. After it releases them, a later database reopen can enumerate leftovers and collect them. No filesystem operations are hidden in a custom source deleter.

Part 3 exercises these transitions, checks a completely deleted prefix, and interrupts installation and cleanup in separate native processes.
