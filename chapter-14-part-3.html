Chapter 14 — Owned batches and a streaming query pipeline

Part 3 — Boundary, retention, and refill checks

The complete batch and operator code from Part 1 and Part 2 is the prerequisite. This final part stays within the chapter's 3.5-hour implementation allocation. It adds one CTest entry and keeps all nineteen storage/foundation entries: twenty tests in the cumulative suite.

The expected results below are explicit values, not answers generated by the operator under test. Test-only vectors and temporary-directory cleanup are outside the engine's allocation ledger. No database library, Python query implementation, or SQL engine computes the result.

Assemble one runnable fixture

Create tests/query_pipeline.cpp by appending the following segments in order. The compile-time assertions check compatible batch interfaces, noncopyability, and nonthrowing plan moves. The runtime check stays active in Release.

expect<Error> catches only the requested family. A test expecting FormatError therefore does not accidentally pass because its fixture exhausted the budget. A thrown exception escapes to main unless the test specifically expects it.

The temporary directory is declared before the database and query owners that use it. Its destructor removes fixture files through the error-code overload; it does not throw during cleanup. The tiny cache is smaller than an event frame, so disk reads use the charged bypass path instead of letting a warm cache hide the later file-corruption check.

The seed matches the five-event example. Storage receives both account and event mutations in one committed batch; the query receives one snapshot of that state. The two explicit expected vectors describe filtering only. Event 103 is still a valid filtered result even though its account will not match the future join.

Append the plan constructor and consumer:

drain checks Pull::end before reading rows. A zero-row batch is recorded and followed by another pull. Its hundred-call guard is a fixture diagnostic against an accidentally nonprogressing source, not an arbitrary production query limit. After end it calls once more with valid output to verify absorbing completion.

The consumer copies each event into a test-owned result vector before refilling output. That vector is an oracle convenience only. A bounded production sink would process rows incrementally; it must not collect an entire query merely because this tiny fixture does.

Test the complete ownership state, not only the values

Begin the first check. A capacity-three EventBatch charges exactly 84 bytes. An injected failure at each of its four replacement allocations must leave the original capacity, rows, and existing borrowed spans unchanged.

The test reacquires column spans after moving the owner. It intentionally does not dereference the previous borrow after that successful move, even though the underlying allocation transferred without changing address. A named-owner contract is easier to reason about than relying on whichever object happens to keep an allocation alive.

After clear, zero rows still cost 84 bytes. After successful replacement with capacity two, the cost becomes 56 and the rows are empty. Filling both slots and attempting a third append must preserve the two existing rows. These tests would catch “increment the count first” errors that an address sanitizer need not find.

Continue the same function with scan/account construction, cross-ledger moves, and invalid capacity checks:

A scan batch has five allocations, so failing its fifth acquisition must destroy all four already-built event columns. The account replacement fails at its second acquisition while the first candidate column is live. Both paths return charges without losing the previous batch's values.

The cross-ledger move is important. The destination initially owns storage charged to other; afterward that ledger is zero and the destination owns the source's arrays under budget. Moving a pointer without its matching allocator would make one ledger leak charges and the other underflow at destruction.

The overflow case passes a capacity one greater than SIZE_MAX / 36. It must fail before acquiring a partial five-column batch. A zero-capacity or null-ledger owner is rejected rather than introduced as a special uncharged output mode. A moved-from batch can have zero capacity internally, but cannot serve as a valid pull target until reconfigured.

Make an empty first result observable

The next check first selects day 4 at capacity three. Its first result must be a zero-row batch, followed by the event 104. Only afterward do we compare the one-row and three-row day-3 executions.

The same test checks two empty filtered steps when no days match, an empty day interval, and ordered account scanning. A source that stops on the first empty filtered result loses event 104; a source that crosses the relation bound may try to decode account bytes as events.

Before the first pull, a capacity-three plan and output must add exactly 300 column bytes. Reserve all remaining ledger headroom, then execute: the lazy cursor cannot allocate. The current output stays empty and the outer plan becomes terminal. Releasing the reservation does not authorize retrying that plan. Continue the function:

The fourteen deterministic construction failures are ten scratch-column allocations plus four output-column allocations. They do not assume the size or allocation count of an implementation-defined shared-pointer control block: the cursor has not been created yet. Every failed construction returns to the same baseline of retained storage.

The final two misuse cases are different from execution failure. An output that is too small, or belongs to another budget, is rejected by the outer preflight without changing its sentinel row or consuming upstream input. A subsequent valid output still receives the complete expected relation.

Exercise true emptiness and exact exhaustion

An empty relation must end directly, rather than repeatedly return empty batches. A relation containing only accounts must not appear as event data. Six live events with capacity three must give exactly two full batches and then end. The maximum day must fit a half-open interval without overflow.

The original empty snapshot remains empty after writes. That check distinguishes a query over an immutable read state from a query that silently asks the mutable database for a new view on each pull. The 64-bit interval endpoint includes every possible 32-bit day; the rejected endpoint above that bound is a configuration error, not a wrapped predicate.

Pause queries while storage changes beneath their owners

This is sequential interleaving, not a concurrency test. The first plan reads from a retained memory source and pauses after three output rows. A second plan later pauses over table sources. Between pulls, the database accepts updates, flushes, compacts, and tries to collect obsolete files.

The older query still sees event 101 at 250 cents and event 102 alive. The newer query sees event 101 at 900 and no event 102. Old and new account scans observe regions 1 and 3 respectively. The result does not combine one snapshot's account row with another snapshot's event row.

The borrowed held.columns() view survives maintenance because its batch is neither mutated nor destroyed during those operations. It does not borrow the memtable or table storage. Separately, source ownership keeps the old WALs and tables protected from collection until their read states disappear. Owning decoded output and retaining snapshot inputs are different lifetime obligations.

After the inner scope releases all plans/views, reclamation reports no retained obsolete files. An exhausted plan can still retain its view until destruction; end-of-stream is not an implicit promise to release the snapshot's entire lifetime.

Let the database and root handle disappear first

A plan can escape the database's scope because its scan owns the read state. A completed output batch can then outlive the plan because it owns its fields and its budget handles. Use a weak pointer only as a test observation of when the last owning handle disappears:

The first pull occurs after the database and caller's budget handle are gone. After releasing the plan, output still contains the three decoded events. At that point it needs no file or directory lock, only its own column allocations and their ledger. Resetting the final output releases storage before the last budget owner; the weak pointer then expires. A dangling borrowed Budget& would not satisfy this destruction order.

Reject malformed rows and abandon a failed refill

Start the final check with invalid visible-entry shapes. The decoder rejects an unsupported record version, a disagreeing key, a tombstone, a zero sequence, and an account key mismatch. These checks exercise the query decoder directly rather than relying on corruption that some earlier storage validator already catches.

For an actual pull failure, write eight events to a table and successfully consume one row. Then alter one byte in a later data frame. The frame is not retained by the deliberately undersized cache. This is a controlled fixture violation of the engine's immutable-file assumption, not permission for applications to edit open tables.

Each event entry uses 22 bytes of table entry framing plus 30 bytes of encoded payload. A 128-byte data payload holds a four-byte count and two such entries. The complete frame therefore occupies

12 + 4 + 2(22 + 30) = 120\text{ bytes}.

The header occupies 24 bytes. The third frame starts after two 120-byte frames; its payload begins after its eight-byte frame prefix. The injected byte offset is

o_{\mathrm{damage}} = 24 + 2(120) + 8 = 272.

Those are this fixture's verified format/layout choices, not arbitrary offsets to use on a differently configured table. Finish the test file:

The failed refill has room for four rows, so the source can consume some input before it encounters the damaged frame. The query must discard that in-progress refill and reject later calls even after the fixture restores the byte. The separate earlier batch still owns event 100. A freshly constructed query over the same view reads all eight repaired rows, each checked independently.

The file edit is visible to ordinary reads in the current process; the test makes no durability claim and does not require a sync to simulate physical power loss. It checks decoding, terminal state, cleanup, and the distinction between earlier successful output and a failed current refill.

Expected diagnostic, also observed under the sanitizer build:

The defective branch has no invalid memory access. It gives the caller a false completion signal after the first three rejected rows and silently loses event 104. A sanitizer cannot prove this protocol. The explicit future-live-row fixture can. Restore the original unconditional Pull::batch return, rebuild, and run the whole suite again before continuing.

Other symptoms point to different boundaries. A nonzero ledger after an allocation failure suggests a partially constructed column owner or a mismatched allocator. Old output changing after a storage advance suggests that encoded bytes escaped instead of being decoded and copied. A full final batch repeating forever suggests that the scanner did not advance or did not preserve its ended state. A different answer after compaction suggests a source-lifetime or snapshot-selection error, not a reason to patch the filter predicate.

For a small variation within the implementation allocation, use capacity two. The day-3 batch sizes should be 2, 2, 0; the day-4 sizes should be 0, 0, 1. The same plan plus output then holds 200 column bytes, not a smaller capacity charge when only one row passes. Predict these results before adding the checks. Do not turn this logical call-count comparison into an unsupported throughput claim; useful timing and workload controls come later.

Boundary reached

The engine now has owning charged column batches, a synchronous pull protocol, event and account snapshot scans, stable filtering, and narrow projection. Output owns its values independently of the current storage cursor; operators retain the source generation for their lifetime. Empty progress and permanent completion have different results. Refill failure clears the candidate batch and requires a fresh query rather than guessing how much input to retry.

These operators do not sort, join, aggregate, schedule threads, or provide a whole-query success artifact. They establish the data and ownership contracts those mechanisms need.
