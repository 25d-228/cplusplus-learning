Chapter 13 — Streaming compaction and safe reclamation

Part 3 — Observe retained names, bounded outputs, and restart behavior

The completed Part 1 and Part 2 are the prerequisites for these checks. All three parts form one chapter with one 4.0-hour implementation allocation. The tests add no database library or execution framework. Their std::map is an independent expected-result model, not the engine's compaction implementation.

The central fixture has five committed batches. The first three are selected; the fourth table and fifth batch remain newer than the compacted boundary.

Batch Changes
1 Events 0–7, amounts 10 + key, account 10/day 3; accounts 10→region 1 and 20→region 2
2 Delete event 0; event 1→901 cents; account 10→region 3
3 Event 2→702 cents; event 8→808 cents/account 20; account 20→region 4
4 Reinsert event 0→1,000 cents; delete event 3; account 10→region 5
5 Event 9→909 cents/account 20; delete event 4

The first three tables contain 10+3+3=16 stored versions. At boundary 3 there are eight live events, keys 1–8, and two accounts: ten results. Event 0's selected tombstone must not resurrect its sequence-1 value. But batch 4's newer reinsertion must still be visible to a current reader. An old boundary-1 view must continue seeing the original ten rows. These are three different correct answers, not three views of a mutable global map.

Build one explicit test program

Create tests/compaction.cpp by concatenating the following segments in order. The first opens an unnamed namespace and defines the small assertion helpers. check remains active in Release, unlike a disabled assert. expect catches only the named exception family; an unrelated exception fails the test.

A temporary directory owns the whole test namespace and removes it only after database/view owners in the test scope have been destroyed. This fixture cleanup is not the production reclamation policy. Tiny 128-byte blocks and two cache slots force interesting transitions with a small amount of data; output tables are capped at 300 bytes.

The independent model applies each committed mutation in batch order. The structured binding in matches names the map entry's key and value without copying them, as in the earlier language chapters. Point reads, range order, row bytes, original sequence numbers, and absence are all compared. Merely comparing row counts would miss a wrong surviving version.

These are the complete fixture builders. commit(..., false) leaves the new batch active; normal calls rotate and flush it. seed creates consecutive flushed generations, not one file containing precomputed query answers. The file-name helper uses the production naming rule only to inspect existence; it does not choose collection eligibility.

Check an exact cap and a partial transfer

The first test uses a 286-byte cap, where two event rows fit exactly. It offers a third row without advancing an input cursor, observes rejection, and finishes the two-row file. It then uses Chapter 10's WalFileOps backend to allow four bytes of a nine-byte write before failure. The name of that test backend does not limit it to WAL framing; it implements the same FileOps boundary used here.

The interruption flags exercise retry without double counting. Moving the file moves its accounting history. The last addition tests saturation near the unsigned limit without attempting an enormous allocation or transfer.

Check the complete version-2 envelope

This synthetic manifest fills all 16 table and four log slots. The test checks each of 668 single-bit corruption positions and each shorter prefix. It then tries structurally invalid but otherwise ordinary manifest objects. These checks validate the codec; they do not claim that fictitious table IDs have real files. Real-file key-range validation is exercised later.

The zero-file example preserves coverage through sequence 10 and keeps one active log beginning there. The 84-byte image is valid without a table that pretends to contain a value at sequence 10.

Retain the old WAL, then only the old cursor

This test exercises the whole lifetime trace. It captures an arena-backed view, flushes, captures a table-backed view and cursor, and then creates a view through batch 3. Compaction must not rewrite any of those states. Their owning handles are released in a deliberate order so that eligibility changes are observable.

The first collection reports four retained obsolete sources: the first log and three old tables. After releasing the views, only the cursor's first table remains. Even after that cursor is exhausted, the filename must exist. Its final reset permits exactly that last retained file to be removed. A foreign text file survives every collection.

The later call compacts the whole base plus batch 4, but not batch 5's newer log. This tests repeated base extension, not only the first version-1-to-version-2 transition. Charge returns to zero after all database and read owners leave scope, then a fresh database reconstructs the same current result.

Repack a full base instead of trapping the writer

A capacity bound is incomplete when maintenance cannot make progress at the bound. Thirty-two event rows split into sixteen two-row files fill every table slot. A newer sealed log cannot flush. Repacking the same complete base with a larger per-file cap produces one file at the same sequence boundary; the pending flush can then proceed. This is why a base-only selection is allowed. It is not permission to select an arbitrary subset of the base.

The old view keeps all sixteen original partitions alive while the current manifest uses the repacked file and a later delta. Repacking reduces serving slots, not necessarily immediate disk usage: retained snapshots still have a cost. If format, output, or memory caps genuinely cannot accommodate the live base, report capacity failure; no automatic guarantee of unbounded ingestion is being made.

Let all selected values disappear

The next test creates a put followed by its erase. The correct output is zero files with a nonzero covered boundary, not an empty table and not an unchanged zero boundary. An older view must still see the put. After reopening, a new batch can extend that empty base and compact normally.

Inject failure at observable boundaries

The hook's erased void* points to a Cut object whose scope outlives the database. Only checkpoint converts it back to its actual type. A cut is armed after setup, fires once, and either throws a controlled error or calls std::_Exit(73). _Exit deliberately skips stack unwinding; it is not a simulation of loss of kernel caches or device power. The other hook mode arms the next charged allocation only after manifest-closed, allowing us to test the nonallocating publication tail.

The cleanup test first injects a pre-unlink error and then a cleanup-sync error. Both must be reported without poisoning an otherwise valid serving set. It then adds an unreferenced high-ID file to expose the identity-fence requirement. A failed fence must leave that file present and require reopen. Successful cleanup must preserve the high-water value after the orphan name has disappeared.

Injecting before unlink checks policy/error reporting, not an actual filesystem permission or media failure. The native path still executes real enumeration, normal unlink, and synchronization. Do not relabel the injected exception as an observed disk failure.

The allocation sweep rebuilds the same fixture for each failure ordinal. It covers charged state/control storage, input pins, output buffers, metadata, and new reader owners without assuming one implementation's exact allocation count. After any failure, an old view must remain usable. A fresh reopen must see a whole valid serving state, and collection must handle any leftover output.

The three capacity failures differ: output-file slots, aggregate output bytes, and a per-file cap too small even for one event row. They leave partial artifacts and an uninstalled result. The final budget lease consumes all remaining charged capacity, so directory-list admission fails before any new manifest epoch.

Finish the file with its native-process interface and main. The native fixture uses batches 1–4; the in-process test above additionally exercises active batch 5. The inspect action compares all current rows against the independent model and creates no new mutations.

Decode the files independently

Create scripts/check_compaction_fixture.py from the following segments. It imports only frame, make_filter, and need from Chapter 8's complete scripts/check_table_fixture.py, which must remain beside it. Those helpers parse a framed checksum, construct expected Bloom bytes, and raise a test failure. They do not invoke the C++ reader. Python is an independent fixture oracle, not a dependency of the engine or its bounded-memory path.

The table decoder walks every data block, checks directory endpoints and exact consumption, and reconstructs Bloom bytes from decoded user keys. It uses ordinary Python lists because these disposable fixtures are small; this is not a claim that the verification script is a bounded production reader.

The manifest decoder independently handles both header lengths. For base files it checks the shared temporal boundary, 300-byte fixture cap, absence of tombstones, and globally increasing unique user keys. For deltas and logs it retains the older contiguous-interval rules. File existence and size are checked against the authority, not guessed from the highest numbered filename.

Expected base rows are calculated directly from batches 1–3. The two accounts and eight events preserve their actual winning sequence numbers. Their value bytes are independently encoded using Python struct, including format and relation bytes, so a self-consistent bug in the C++ encoder and decoder cannot alone make the oracle pass.

Begin main. Each case gets a copy of a closed seed directory, so neither live file descriptors nor a copied locked process are involved. The normal case verifies all five base files, unchanged newer dependencies, and that collection leaves only currently authoritative numbered files.

Continue the same function with the interruption campaign, then the module entry point. There are 13 compaction cut points, each tested once by an exception and once by abrupt process exit: 26 interruptions. The process-visible manifest changes at rename; every fresh inspector must nevertheless return the complete same logical current database. Two more process exits interrupt cleanup. A checksummed swap of base records and a missing required file must fail reopening.

The campaign observes real process termination and reopening on the same running operating system. It does not erase volatile kernel state, reorder persisted writes, simulate every possible short sector write, or test physical power loss. Before rename the old manifest remains authoritative; afterward the new one is visible to these fresh processes. A failed operation may have committed its maintenance transition, which is why the old facade stops rather than claiming rollback.

Build and run from the learner root

Append this block to the existing CMakeLists.txt; do not replace earlier targets or add a second copy of the read_view.cpp source. The Python interpreter was already found by the previous native-fixture tests.

Use the compatible native C++20/CMake tools established in Chapter 1. No new compiler-version gate or macOS-version assumption is added. The target is still native ARM64 on the M4 Mac mini; inspect the actual architecture and toolchain instead of relying on the machine model alone.

Run address/undefined-behavior instrumentation in a separate build. Use the sanitizer facilities available in the native toolchain. Linux leak-detection settings are not mandatory flags for Apple's toolchain.

Read the measurements without changing their meaning

For the selected three fixture files, their logical lengths total 1,594 bytes. The completed replacements total 1,398 bytes. Define I as selected-file bytes and W as successful new-output write bytes. The local rewrite ratio is

R=\frac{W}{I}=\frac{1398}{1594}\approx0.877.

This does not mean compaction had negative cost. It performed 1,398 additional write bytes while old and new files coexisted. The smaller final representation removed six stored versions but paid for five separate headers, filters, directories, and footers. The measured 746 input-transfer bytes are smaller than I because the phase excludes opening/verification and some blocks were already cached. Do not substitute W/746 and call it a disk write-amplification factor.

Whole-engine write amplification would need an explicit denominator of accepted logical input bytes and a numerator including WAL, flush, compaction, and chosen metadata traffic. These operation-local counters do not yet measure all of that. Repeated base-only repacking demonstrates extra writes without new logical data; its cost is visible even when the row count and base boundary do not change. After a failed attempt, output_write_bytes can be positive while installed is false. Later cleanup reports logical lengths successfully unlinked. Do not subtract those lengths from write traffic: deletion does not undo previous writes.

Diagnose the boundary, not just the exception name

Symptom Likely boundary to inspect
Deleted key reappears An arbitrary partial source set was fed to the tombstone-suppressing cursor
Second output loses its first row Cursor advanced after a negative can_append result
A 286-byte cap rejects two event rows Metadata/frame/footer accounting was omitted or counted twice
Empty compaction cannot reopen Base coverage was derived from an actual output row instead of base_end
Reads work but retained names vanish Registry protection was skipped; open descriptors mask early unlink
High orphan ID is reused after restart Its name was removed before the manifest high-water fence
Reopen rejects swapped checksummed base records Correctly detected nonincreasing or overlapping user-key partitions
Repacking cannot allocate despite small logical rows Old pins/states, output workspaces, and owner metadata coexist under the shared budget

For a small variation, change the 286-byte forecast test to cap 285. Predict the second admission result, then update that isolated test to finish after its first row and check the 234-byte file. Restore the original fixture afterward. The one-byte cap change exposes a real framing boundary, not a timing difference.

Completion boundary and next mechanism

The database now rewrites a complete older prefix into bounded immutable files, installs their authority before changing serving owners, and leaves retained snapshots on their original generations. It can represent an empty base, extend one, or repack it without advancing visibility. Collection protects live and retained files, persists identity high-water before deletion, reports partial cleanup failure, and remains retryable after process exit.

The next chapter builds owned column batches and a pull-based scan/filter/project pipeline on these snapshots. It must preserve the distinction between an empty filtered batch and end-of-stream and must charge batch capacity. It does not yet add external sorting or concurrency.

References used for the boundaries

The C++ working draft's shared_ptr destructor rules were used for final-owner lifetime. Apple's archived unlink(2) and fsync(2) manuals were read for name removal versus open-file lifetime and host versus device-flush requests. These are archival references, not evidence of native execution on the reader's installed macOS. SQLite's atomic-commit discussion, sections 9.2 and 9.5 provides additional context on persistence assumptions and recovery-file lifetimes; its rollback-journal protocol is not copied here.
