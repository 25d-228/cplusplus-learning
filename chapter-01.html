Chapter 1 — From C files to a native C++ program

Strata will eventually have separate implementations for files, indexes, recovery, query operators, and scheduling. Before those parts can cooperate, their declarations must agree, their object files must be linked, and a failed check must actually make the program fail. This chapter establishes that working cycle with an accumulation function small enough to inspect one statement at a time.

The program summarizes three unsigned integers. It returns a count and a sum; {10, 20, 12} produces count=3 sum=42. An empty input produces two zeros. There is no engine code to start from. Basic C functions, arrays, pointers, and shell commands are sufficient prerequisites.

Learning objectives

Separate a header declaration from a function definition and a linked program; use a namespace and an initialized aggregate; explain a pointer's valid range; select and probe a native C++20 toolchain; build and test with CMake/CTest; distinguish a compilation error, a linkage error, and an incorrect result; inspect a live call with LLDB.

The implementation allocation is 2.0 hours, including the small experiments: 0.5 for tool observation and probes, 0.5 for the program, 0.5 for CMake/CTest, and 0.5 for debugger and failure diagnosis. Reading is separate. An already configured machine may make setup shorter; a long explanation is not additional coding time.

Describe the result before writing the loop

#ifndef, #define, and #endif form an include guard. The first inclusion in a translation unit defines the guard's name; another inclusion in that same unit skips the guarded text. It prevents repeated definitions of the structure within that unit. It does not arrange linking or prevent every cross-file one-definition error.

The standard header <cstdint> supplies fixed-width integer type names in namespace std. Here std::uint32_t is an unsigned 32-bit integer and std::uint64_t an unsigned 64-bit integer. These exact-width types are available on the target toolchains; the header specification marks them optional on implementations that cannot supply the corresponding representation. The feature probe will also check the byte sizes we use.

A namespace neither allocates an object nor creates a runtime wrapper. Inside its body, the short name Stats already refers to this declaration. Avoid a header-level using namespace std;: a header should not inject an entire library's names into every source file that includes it.

A struct introduces a type; Stats can be used as a type name without C's struct Stats spelling or a separate typedef. Its members are public. This particular structure is an aggregate: brace initialization can give values to its members in declaration order. The = 0 on each member provides a default initializer, so a member omitted from an aggregate initializer starts at zero. The aggregate initialization rules specify that behavior.

What the pointer promises, and what it cannot prove

The parameter const std::uint32_t* values points to integers that this function may read but not modify through that pointer. It does not own those integers. The caller must keep the array alive for the call and supply a length that fits that actual array. Passing an address does not copy the array.

For a positive length, the readable range is values[0] through values[length - 1]. A null pointer is accepted for an empty range, where the function must perform no dereference and no pointer arithmetic. A null pointer with a positive length, or a length longer than the allocation, violates the interface's precondition. Raw pointers carry no allocation-length information that this function could use to validate that claim. We will not manufacture such an invalid access as a normal test.

This is an internal range interface, not a parser for untrusted input. Chapter 2 will place pointer and length together in a view and teach the associated lifetime rules. A view still cannot make dead storage live again.

Choose a numeric range that makes the loop exact

This foundation function deliberately limits both an element and the element count to 32 unsigned bits, while accumulating into 64 bits. It accepts no negative values. This narrow domain lets us prove that every permitted sum fits, instead of adding an exception or overflow-status mechanism before those have been taught.

Let n be the element count, x_i the value at zero-based index i, and S_k the sum after consuming k elements. The result we want is

S_0 = 0, \qquad S_{k+1} = S_k + x_k, \qquad S_n = \sum_{i=0}^{n-1} x_i.

Both n and every x_i are at most 2^{32}-1. Values are nonnegative, so no partial sum is greater than the final sum. Its maximum is bounded by

S_n \leq (2^{32}-1)^2 = 2^{64} - 2^{33} + 1 < 2^{64}.

An unsigned 64-bit integer represents zero through 2^{64}-1, so the sum fits. The count increments at most n times and fits its own type. At the maximum length, the loop index reaches length and stops; it never needs to increment past that value. The integer-type rules define unsigned arithmetic, but our bound avoids relying on wraparound.

This is a range proof, not a claim that a four-billion-element array fits the machine. Actual arrays must still exist. Nor is it a general replacement for checked arithmetic: the engine later accepts 64-bit amounts, for which a 64-bit accumulator needs explicit overflow checks. Do not widen this exercise's input type or count type and silently keep the old proof.

Turn the recurrence into one complete function

Create exercises/chapter-01/stats.cpp:

Include the function's own header first. The compiler now sees its declaration and definition together and can diagnose disagreements in this translation unit. The namespace is reopened, so this body defines strata::summarize, not an unrelated global function with a similar name.

result is a local value whose initialized fields hold the state. On entry to iteration i, result.count equals i and result.sum equals S_i. The first statement adds the current element; the second records that one element has been consumed. At the next loop test both fields describe the same prefix. Inside the body, between those two statements, the sum has advanced before the count. That intermediate state is useful to recognize in the debugger.

The left operand of += has type std::uint64_t; the 32-bit element is added in the wider unsigned arithmetic type on the target. This matters. Computing a 32-bit addition first and only then assigning its result to a 64-bit field would not repair an overflow that had already occurred.

For the three-element fixture, the concrete states are:

Point in execution Next index Count Sum
Before the loop 0 0 0
After reading 10 1 1 10
After reading 20 2 2 30
After reading 12 3 3 42

Each array element occupies four bytes on the intended platform. If the first one is at address A, element i begins at A + 4i. values[i] expresses the correct element step without handwritten byte-address arithmetic. The array payload occupies 12 bytes; the two scalar result fields and any structure padding are separate. We do not serialize the structure's object representation or assume it has no padding.

For length == 0, the first comparison is false, the loop body never runs, and result stays zero. This is why the empty case works with nullptr, C++'s null pointer literal. No special zero-sized C array is needed.

return result; returns a value, not a pointer to a dead local object. The caller obtains the two fields as its own result object; the implementation may eliminate a physical copy. Neither field refers into the input array. There is no dynamically allocated storage or file to clean up here, and the function performs no I/O. All source-array storage stays with the caller.

At the first call, the array expression values converts to a pointer to its first element. The 3 is a count of elements, not bytes. const prevents accidental mutation of the local fixtures. Adding it twice gives 8,589,934,590, which does not fit 32 bits but does fit 64. A mistakenly narrow accumulator can pass the 42 fixture and still fail this one.

The one-zero fixture distinguishes “one element whose value is zero” from “no elements.” Both sums are zero; their counts differ. The checks are ordinary control flow, not a call hidden inside assert. Defining NDEBUG disables assert evaluation; it does not disable these function calls or their failure returns. Assertions can document internal invariants later, but required test work must remain observable in Release.

Compile pieces, then link a program

A source file plus the text included into it, after preprocessing, forms the input for a translation unit. In our conventional header-based build, each .cpp is compiled separately. The header participates in both compilations; it is not a third executable component. The language's separate-translation model permits these units to be translated and later linked.

For this program, the build has the following shape:

An object file contains generated code/data and information about symbols it defines or still needs. The body of strata::summarize is in stats.o. main.o contains a call that needs that definition. The C++ compiler driver selects the appropriate standard-library and runtime linkage when it performs the final link. Use clang++, not a direct invocation of ld or an improvised list of C++ runtime libraries.

The -I option adds a header search directory. Because our quoted header is beside both source files, their local include search also finds it; a future consumer in another directory will need the advertised include path. The warning options ask the compiler to diagnose suspicious constructs, nonstandard extensions, and conversions that can change a value or its sign. An include guard is not a linker fix

Now deliberately omit the object that contains summarize. Do not alter the source files or the working executable:

Compilation of main.cpp already succeeded: its header supplied a declaration with the correct type. The final link cannot supply the called function's body. On macOS, look for an undefined-symbol diagnostic mentioning strata::summarize; the spelling of the integer types may reflect their underlying implementation types. The test succeeds as an experiment when linking fails for that missing symbol, not merely for any unrelated command error.

Repair the link by including stats.o, as in the successful command. Including stats.cpp from main.cpp is not the repair. If that body is also compiled separately, it can create a duplicate non-inline definition. Our intended organization is one ordinary function declaration visible to callers and one linked ordinary function definition. The one-definition rules also permit matching class definitions in multiple translation units under specified conditions; that is why a guarded structure definition belongs in this header. Templates and inline functions have further rules, introduced when we need them.

Similarly, writing the body outside namespace strata would define a different function. A linker error is not an instruction to change strata::summarize's declaration until a differently named symbol happens to match. Compare the intended signature, definition, namespace, and actual linked objects.

Probe the language and library that later chapters need

The statistics function uses only a small portion of C++. It can compile even when a later required library facility is missing. Before adopting the toolchain, compile a separate capability probe for C++20 concepts and std::span.

Two small pieces of syntax appear here before their deeper treatment. In template <std::integral T>, T names a type parameter and std::integral restricts it to integer types. Calling echo_integer(10) selects the version with T equal to int; its parameter and return value are both int. This is a language constraint, not a runtime tag test.

std::span<const int> is a library type that refers to a contiguous range of read-only integers without owning them. Its constructor can obtain the length from the local array, .size() reports that length, and [i] reads an element. In this probe the array stays alive for the entire use of the span. Chapter 2 will develop borrowing and invalidation; Chapter 5 will develop templates and constraints. No engine design depends on learning those subjects from this probe alone.

Give the build graph to CMake

Repeating the manual commands explains the machinery, but hand-maintaining every object dependency will become unreliable as the engine grows. CMake describes a graph of targets. The build tool then compiles changed inputs and links their consumers. CTest runs the registered executable tests; it is not the compiler.

Create the root CMakeLists.txt. The following two blocks, in order, are the complete file. There is no generated file to edit and no future target to add.

project(... LANGUAGES CXX) enables C++ toolchain detection. The first target is a static library: an archive of compiled objects, not a running service or a new implementation dependency. CMake compiles stats.cpp once into that library and links its needed code into foundation-01.

target_include_directories advertises the header location. The quoted ${CMAKE_CURRENT_SOURCE_DIR} expands to the directory containing this root CMake file; it does not depend on which directory the build tool uses later. PUBLIC means the requirement applies both to this target and to targets that consume it. Thus foundation-01 acquires the include directory and the C++20 minimum through target_link_libraries. PRIVATE on that link says that the executable uses the library without making a public interface promise to further consumers.

CMake's cxx_std_20 meta-feature requests a compiler mode at least as new as C++20. It does not guarantee each library facility; that is why the probe remains a target. CMAKE_CXX_EXTENSIONS being OFF requests a non-extension language mode rather than, for example, a GNU dialect. It is not a proof that every extension would be rejected.

add_test(NAME ... COMMAND ...) accepts an executable target name and substitutes its built path. Do not hard-code an absolute binary path from this machine. enable_testing() makes the root build tree testable. We use the process return status as the check, not a fragile search for the words “passed” in its output.

Prove that the check can fail in Release

A test system that has only ever displayed green output has not yet demonstrated its failure path. Make one temporary change in main.cpp: in check_stats("three values", actual, {3, 42}), change only the expected sum from 42 to 41. Keep the function and input unchanged. Save the file.

Both selected CTest runs must report a failure, and the direct executable must return status 1. CTest's own nonzero exit code need not equal the executable's 1. The executable's diagnostic should be:

This failure is useful precisely because the algorithm is still correct. We changed the oracle and observed its control over the process status. The compiler may optimize the implementation, but it cannot replace this required failure with success while preserving the program's behavior. No assert macro controls the check.

Locate a failure at the right layer

These symptoms suggest different first investigations:

Symptom Likely boundary First useful action
stats.hpp is not found Header lookup Check the filename, source location, and actual include search path.
A type or member is unknown Compilation Read the first diagnostic and compare the included declaration with its use.
strata::summarize is undefined Linkage Confirm that the definition has the right namespace/signature and that its object or library is linked.
A duplicate definition is reported Linkage Look for a .cpp included as text and also compiled, or a non-inline function body repeated in headers.
The wide-sum fixture fails Arithmetic Inspect the accumulator's type and where widening occurs, not only the printed 42 example.
CTest finds no tests Test discovery Check the build-tree path and root enable_testing(); do not accept an empty run.
A known wrong expectation still passes Build/test selection Confirm the saved source, successful rebuild, chosen binary, and configuration.
LLDB cannot inspect useful locals Debug configuration Use the current Debug binary with debug information, and verify breakpoint/source locations.

Do not begin with a blanket reinstall or deletion of every build directory. Read the first meaningful error, identify the stage, and change the smallest relevant input. A compiler's successful exit, a linker's successful exit, and a test's successful exit answer three different questions.

A legal subrange and an empty range

For the final variation, predict the result of starting at the second element of {10, 20, 12} and consuming two elements. Insert these checks in main, after the existing checks and before the successful std::cout output:

values + 1 advances by one element, or four bytes under the verified layout. The available suffix is {20, 12}, so the result is count two and sum 32. The second call has a non-null pointer but consumes no elements, again producing zeros. The function's empty-range behavior depends on the count, not on the pointer being null.

values + 2 with length two would exceed this array. Do not execute that call and hope a passing run validates it. The pointer/length precondition must be established by the caller. Rebuild and run Debug and Release after adding the legal variation; successful output remains the same. This small extension is inside the chapter's implementation allocation.

What carries forward

Keep the five source/build files, including the two variation checks. You now have a repeatable native compilation, a static-library link boundary, an active runtime check, a C++20/library probe, and a debugger path from an input pointer to a returned value. No files, threads, or dynamic buffers are owned by the accumulator; there is nothing for its caller to free.

The roadmap places values, references, containers, and views next. That chapter will add a separate exercise and retain these targets. Its starting code is exactly the five files specified here, not a future storage engine or an unpublished helper library.
