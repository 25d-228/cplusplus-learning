Chapter 12 — Immutable snapshots and merged reads

Part 3 — Retention, failure, and ownership checks

Parts 1 and 2 supplied the owners and merge. Now test their claims at the boundaries where a superficially correct implementation usually fails: a flush replaces the database's source but not a view's source; a tombstone must hide an older value; a failed next() must not leave a plausible partial position; and the final cursor may be destroyed long after the database and the caller's budget handle.

This is the final part of the chapter's 4.5-hour implementation allocation. Keep all earlier tests. The new fixture adds one CTest entry; the complete suite has seventeen. None of the new tests requires a server or starts a reader thread.

Update the existing database fixture without weakening its assertions

Database now requires a std::shared_ptr<memory::Budget> rather than a borrowed budget. Its internal context needs real ownership; fabricating a shared pointer with a no-op deleter would leave a dangling object when the original scope ends. Standalone arenas, WAL owners, and readers still have their existing borrowed budget contracts. Do not change those constructors.

In each of the three budget-owning scopes of tests/database.cpp, change the stack budget to an owning handle plus a reference. Pass the handle only to Database; keep the reference for every existing charge/fault assertion. The following one-time edit performs that exact migration and refuses an unexpected input. Run it from the learner source root, not the book package:

A typical migrated scope reads Database db{budget_owner, ...} followed by unchanged checks such as budget.used() == 0. The reference does not own anything; the handle and, while necessary, the context do. The root budget's small bootstrap allocation remains outside its own accounting, as explained in Part 1. This does not waive charging of reader, source, state, or scan allocations.

Give the test its own temporary directory

Create tests/read_view.cpp. Its filename-labelled blocks below append in reading order. The test's directory helper creates a fresh private name and removes its fixture at scope exit. It uses the nonthrowing std::filesystem::remove_all overload that reports through std::error_code: a cleanup failure must not throw from a destructor while another exception is active. This is test cleanup, not the engine's future file-reclamation policy. The directory object is declared before the engine handles, so those handles normally release first.

The library uses bounded storage; this test may use an ordinary map and vector as an independent oracle. Those test-only containers are not included in engine memory accounting. The tiny cache intentionally cannot admit a complete event frame, exercising Chapter 9's charged bypass instead of silently making every read a cache hit.

expect<Error> catches only the expected category. An unrelated exception propagates to main and fails the executable. This matters when a test is intended to prove a retention-limit rejection: an allocation failure must not accidentally count as success.

The next helper answers the roadmap's small query: for day 3, match each event to its account and group the event count and amount by region. It performs a point lookup for each event using the same view that supplies the scan. Using Database::get instead would let later account updates contaminate an old event scan. The four-region fixed array and at-most-2000-cent fixture are deliberate bounds, not a general join or an unchecked production aggregation API. The external join and aggregation engine comes later.

There are five initial events. Event 103 has no matching account and event 104 belongs to day 4. Before the batch, region 1 contains events 100 and 101 for 500+250=750 cents; region 2 contains event 102 for 700 cents. After the batch, region 3 contains events 100 and 101 for 500+900=1400 cents; event 102 is absent.

The complete test captures both boundaries, flushes both memtables, and checks all three source arrangements: an old retained arena, a newer view of two arenas, and a newly captured pair of tables. The next listing starts the function; the block following it completes the same function.

The second empty-active capture must not rotate again. Its epoch check is not merely a performance assertion: unnecessarily sealing an empty generation would consume bounded log slots and manufacture maintenance for a read boundary that already exists.

The range [101,104) must yield 101 and 103 only. The erase hides 102, and the exclusive bound excludes 104. An empty interval succeeds with no rows; a reversed interval is an input error. Invalid relation tags are rejected instead of reaching an ordering function that was never specified for them.

Compare multiple retained boundaries against a separate model

A merge tested only with disjoint keys cannot expose incorrect version priority. Build an independent current-state map whose update rule is simpler than the engine: a put replaces one entry and an erase removes it. Copy that map whenever a view is captured. The model stores the sequence as well as the payload, so a result with the right bytes but the wrong internal version still fails.

std::map::lower_bound is used only by this oracle. The engine's range implementation remains the hand-written source heap from Part 2. std::ranges::equal, introduced in the earlier tests, compares the counted byte ranges rather than their addresses.

Each generation has three batches. Each batch touches 32 event keys and 32 account keys once, giving 8\times3\times64=1536 stored versions. Multiplication by five permutes the 32 key positions because five and 32 have no common factor other than one; the round offset changes insertion order without introducing duplicate keys inside a batch. The modulo-seven erase schedule mixes newer tombstones with older puts. None of these choices depends on random-generator implementation details.

Capture before each flush. A saved view therefore combines prior disk tables with that generation's retained arena. Later flushes change the live database, not the saved source arrays. This creates actual mixed-source merges rather than eight copies of a single final table.

For each of eight boundaries, compare 64 point lookups and six ranges. The ranges include a cross-relation boundary, a missing starting key, and an absent upper bound. Their totals are 8\times64=512 point checks and 8\times6=48 ranges. A range assertion verifies both contents and termination; returning all expected rows followed by an extra obsolete version must fail too.

Distinguish handle count from retained-source count

Set the snapshot-state limit to one. Copying its view is allowed because both handles share one state. Creating a cursor from it also shares that state. After both view handles are reset, the cursor still prevents another state from being admitted—even after it has reached the end. Exhaustion releases its current row and source positions, but does not silently reset the public cursor owner.

Before a rejected capture, record the manifest epoch, current sequence, file count, and charged bytes. Admission must fail before a new WAL, sealing, or state allocation changes any of them. Resetting the cursor then releases the final state, allowing the identical capture to succeed. A second scope isolates the distinct-source limit: retained arena M_1, its replacement table T_1, and new arena M_2 require three distinct source slots, even though the new view itself needs only two.

A practical diagnosis follows directly. When capture reports exhausted retention, inspect outstanding cursors as well as view variables; then inspect whether a flushed generation is still retained as an arena. Increasing only the cache size cannot resolve either ownership limit. The test's budget->used() == 0 is checked after every engine owner in the scope has been destroyed, not while a legitimate view still owns storage.

Separate rejection from an uncertain installation

The hook has the same borrowed, synchronous, nonreentrant contract as Chapter 11. It can either throw immediately after manifest rename, or arm the next charged allocation at manifest-closed. Neither action emulates a physical power failure. The latter action tests a precise property: returning a newly installed snapshot must not allocate after that checkpoint.

Sweep allocation failures from the first charged allocation until a capture completes. Construct a fresh directory each time, so one failed installation cannot change the next ordinal's prerequisites. The state allocation precedes rotation: its failure leaves the old database healthy, the directory unchanged, and no retention registered. A later failure inside rotation follows Chapter 11's stricter rule: stop the old database object and recover from authoritative files.

The ordinal is a test seam, not an allocator ABI. The fixture requires at least two failing preparation points and eventual completion; it does not insist that every standard library produce exactly the Linux run's allocation count.

Continue the same function. First arm an allocation failure after installation. The capture must return successfully; a deliberately separate charged vector allocation must then consume the still-armed failure. If snapshot publication allocated, the capture itself would throw instead.

Next retain that old view and interrupt a later capture after manifest rename. The candidate state was never admitted. The old view still answers its immutable sequence after the failed database is destroyed. Only after releasing that view can the test reopen the directory: the shared context intentionally retains the exclusive lock. Reopen follows the installed manifest, not the failed facade's old in-memory diagnostics.

Make a failed scan terminal, not partially resumable

The next test first rejects allocation of a scan object, then reserves all remaining budget to exercise the capacity error separately. Neither failure creates another snapshot state. A cursor owns an existing state; it does not register a new one.

The table payload budget is 128 bytes. With the existing record layout, an event row occupies 52 bytes, so two rows fit and a third does not. Scan construction consumes row 0's version group and leaves row 1 at the source head. The next call consumes row 1, then attempts to load the next block. Injecting a failure at that load exercises failure after an input cursor has advanced, rather than only failure before any work begins.

The candidate row for that unsuccessful call is not published. valid() becomes false, entry() rejects, and another next() cannot resume midway through the group. The immutable view is still usable; a freshly constructed cursor can retry from an explicit lower bound. Already delivered rows are not rolled back.

This is why a successful prefix followed by an exception is not a complete query answer. A future materializing operator must discard or mark its partial output on failure. A streaming consumer must report the failure to its caller. Silently turning every read error into end-of-range would make corruption or memory pressure look like a valid smaller result.

Let the last cursor outlive every obvious owner

std::weak_ptr observes shared ownership without keeping the object alive. Its expired() query becomes true when no shared owner of the object remains. It does not prove that the weak control block itself has been deallocated, nor is it a synchronization mechanism for access to Budget. Here it lets the test detect a lifetime cycle or a missing owner without extending the budget's life itself. See the weak-pointer observer rules.

Declare the escaped view and cursor outside the database scope. Inside, reset the caller's last explicit budget handle before destroying the database. Afterwards, the view must still perform a new lookup and construct a new table cursor. Merely reading previously copied bytes would not test the cache/budget/file dependency chain. Then release the view but retain the cursor, check that a competing open cannot take the directory lock, and advance that cursor once more.

The second key is UINT64_MAX. An absent upper bound must include it without computing an overflowing key + 1 sentinel. Releasing the final cursor must destroy the context and budget without a cycle; reopening with a different budget must then succeed.

The lock assertion is intentionally stronger than merely preserving open table file descriptors. Retaining the context prevents another cooperating writer from reopening the database and changing its namespace while these old readers are alive. This conservative policy is acceptable for this single-writer local engine. A design that allows reopening alongside detached views would need a different cross-instance lifetime and reclamation protocol; it is not obtained by dropping the lock member early.

Finish the file with its exception boundary. No assertion depends on assert, so Release builds run the same logical checks.

A wrong comparator can remain perfectly memory-safe

Temporarily replace Scan::before with the following diagnostic version. It adds one early condition before the two correct internal-key comparisons; identical internal keys still use the original source-index tie breaker.

This still orders user keys correctly. It still forms a valid heap. Every pointer can remain within its allocation. But the first eligible row in a group is now the oldest one, so newer values and tombstones lose. Rebuild and run only the read-view test in Debug, Release, and the sanitizer configuration. The observed failure was read-view: new fixture answer in all three, with no sanitizer memory error. The semantic test catches what memory instrumentation cannot.

Restore the original Scan::before from Part 2 and rerun all seventeen tests before continuing. The canonical listings contain the correct comparator, not the defect. Do not invert the complete comparison: reversing user-key order would test a different failure and obscure the version-priority lesson.

Completion boundary

The finished chapter has a real immutable serving set, not a mutable database pointer plus a sequence label. Capture either rejects before rotation, completes publication without allocation after installation, or follows the existing uncertain-owner stop/reopen rule. Views and cursors retain the resources they actually use, with limits on admitted states, distinct retained sources, and charged allocations. Range reads own one output row and bounded source positions; they do not collect the database into a map.

Before advancing, explain why a cursor at end-of-range still occupies a retention slot; why two handles to one view do not consume two state slots; why a flushed arena and its table count as two retained sources; and why copying a candidate before source.next() is necessary even though the final public row owns bytes. Use the existing tests to answer each question by observing ownership or output, not by adding elapsed hours to the estimate.

No file is deleted by this chapter. Snapshot lifetime supplies one prerequisite for safe reclamation, not a complete reclamation policy. The next chapter builds streaming compaction and connects obsolete-file cleanup to installed authority and remaining readers. It must not use this public, tombstone-suppressing cursor for a partial-source compaction that still needs tombstones to hide unmerged older data.

References used for the ownership checks
