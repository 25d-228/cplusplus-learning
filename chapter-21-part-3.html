Chapter 21 — Reproducible workloads and independent answers

Part 3 — Force old, new, canceled, and reopened answers

Sequential commands can validate reopening, but they cannot demonstrate a query retaining its old sources while ingestion and maintenance change current authority. Two writer processes are not the answer: the directory lock excludes that arrangement. The scenario below uses one Engine, two query workers, and the dedicated maintenance worker in one process.

Prerequisite code: Chapter 20 and Parts 1 and 2 of this chapter. Keep the tiny configuration and the default 120-event input for the controlled scenario. Smaller or differently filtered input may not reach a spill-pass checkpoint; the scenario then fails rather than claiming to have exercised cancellation during spilling.

Give the controller an observable boundary

There are two gates. The old query pauses after capture, keeping its original snapshot alive. The canceled query pauses at a spill-pass boundary, after it has created runs. A gate owns its mutex, condition variable, and two booleans. arrived_ announces that the worker reached the boundary; open_ permits it to continue. Both predicates are observed under the same mutex. Notify calls alone are not the state.

The callback's void* context borrows a Gate. We keep both gate objects outside the executor's scope so the borrowed pointer outlives every worker. The first matching checkpoint waits; after release, future matching checkpoints pass immediately because open_ remains true. Thirty-second waits are watchdogs for an invalid fixture or stuck implementation, not the mechanism establishing ordering.

An exception in the controller must not strand a worker behind a gate while the executor destructor waits to join it. Release is declared after the executor, so reverse destruction opens both gates before destroying the executor. This is a small application of the lifetime discipline from Chapters 3 and 18. The gates themselves are declared earlier and remain alive during both operations.

submit does not keep a second request owner. It takes the handle, asks the executor to accept the request, and returns the handle. On rejection the local unique owner destroys the unsubmitted request before the helper throws.

The scenario uses a new root containing db, spill, and out. It checks that base and delta seeds agree and sets the snapshot-state limit to two. After base import and maintenance, the old query reaches captured. Only then does the controller apply the delta and request compaction. With the defaults, these boundaries are sequences 5 and 6.

The old query consumes one whole-query reservation while paused. The canceled query uses the other; neither leaves room for another query reservation. The maintenance worker uses its separate allowance. This is why resource ownership rather than just worker count matters to the scenario.

The sentinel file represents a previous completed result. Its write and close must themselves be checked; otherwise a later cancellation could appear to preserve a file that was never successfully created.

When the canceled query is paused in a spill pass, two snapshot states are retained. A direct third capture must fail with the retention-limit error, without installing a different manifest epoch. This isolates snapshot retention from the executor queue's own admission. Release and cancellation are separate: requesting stop does not magically release this test gate, so the controller must open it as well.

After cancellation frees its reservation, submit the fresh query. Releasing the old query allows both successful executions to finish. Both answers are checked for their sequence boundaries, both sorts must have at least two materialized passes, and terminal cleanup must have released the owners. The controller then collects obsolete names, stops the engine, and destroys its owners before opening a new Database object on the same directory.

The scenario checks sequence and resource invariants in C++. The Python test below independently computes the entire old and new answers and performs a further query after reopen. That division matters: an internally consistent but wrong C++ answer must still fail the test.

Point in the default run Retained states Required observation
Old query paused after capture 1 Its boundary is sequence 5
Writer applies delta and compacts 1 Current boundary becomes 6; old state survives
Canceled query pauses in spilling 2 Third capture rejects without changing epoch
Canceled task becomes terminal 1 Previous output survives; spill owners are gone
Old and fresh queries finish 0 Old answer is sequence 5; fresh answer is 6
Engine owners die and database reopens 0 Recovered sequence is 6

This fixture establishes ownership overlap, not a throughput comparison. It uses no sleeps, no second writer process, and no claim that every possible thread schedule was explored.

A handwritten oracle before a generated one

Create the test script. Three literal inputs supply answers simple enough to calculate without the generator. The first batch has two matches. The second changes account 10's region and event 1's amount while deleting event 2. The third deletes account 10 and inserts another referencing event: the inner join must now be empty. A zero region is not a tombstone.

The subprocess helper captures both output streams and includes the command, arguments, and status when a stage fails. Its timeout is a harness watchdog. The child that tests a low descriptor limit changes only its own inherited limits, not the controller's. This use of preexec_fn is confined to the single-threaded Python harness; it is not a pattern for the threaded engine.

The reference test then covers 18 seed/size combinations: three seeds, including the maximum unsigned 64-bit value, and six sizes spanning empty, partial-period, exact-period, and multiple-period cases. Forced-hot settings are 0, 70, and 100; batch sizes are 1, 32, and 256. Each case compares replay with the independently computed formula for both phases. Repeated generation checks actual bytes, not merely equal row counts.

Seven malformed answer files also check the CSV comparator itself, including wrong width, missing/extra rows, noncanonical numbers, a changed value, and an unterminated quoted field. The trillion-event check changes only metadata and evaluates the formula. It checks the multiplicity derivation against one full period without writing a trillion-event input or building a trillion-entry dictionary.

The next test makes input rejection a shared external contract without sharing the parser. It supplies 22 invalid forms to both C++ and Python. A truncated terminator, an oversized count, a duplicate key, an out-of-range unsigned field, and a malformed END must not become a plausible different workload.

The preflight tests request more free space than the filesystem reports and launch a child with a soft descriptor limit of 128. Python's resource documentation describes the soft/hard tuple and its Unix availability. The harness lowers both limits in the child, then exits; it never tries to raise the parent limit.

The native test first exercises the handwritten history, a repeated-apply rejection, and a malformed second batch. Notice that it reopens the failed import and queries the committed prefix. Merely seeing a nonzero importer exit would not establish what survived.

The next two databases separate valid maximum integers from invalid arithmetic. One event has the maximum ID, account ID, amount, day, and region. A half-open interval ending at 2^{32} must include that day. Another database has two matching events with cents 2^{64}-1 and 1. Import is valid; their aggregate is not. Both the engine and Python must reject the query, and the previous completed CSV must remain unchanged.

The generated native fixture then checks both complete phases through the actual driver and compares them with both oracle modes. It requires multiple materialized passes in both sorts and confirms an empty spill parent after completion. These assertions would catch a preset that accidentally made every query in-memory.

Finally, run the in-process scenario and compare every emitted group. The additional reopened query is a new process invoking the regular driver, after the scenario has released the directory lock. The canceled output is checked byte-for-byte against its sentinel. None of these checks derives expected totals from C++ counters.

Connect the driver to the existing build

Append this block to the learner root CMakeLists.txt. strata-workload links the existing core rather than copying it. PUBLIC propagates the core's include path and thread dependency to the driver. The tests use the already configured Python interpreter. No new package manager or third-party runtime is needed.

The cumulative engine suite now has 34 entries. The three added names are workload-reference, workload-native, and workload-scenario. A focused rerun is ctest --test-dir build-debug -R '^workload-' --output-on-failure; retain the full run before declaring the chapter integrated.

Use a separate sanitizer directory so instrumented and uninstrumented objects are not mixed. The compiler must support the selected sanitizer for the target; there is no required compiler-version label beyond the features actually used.

ThreadSanitizer is a separate build, not an additional flag on the address- sanitized build. Use Chapter 18's supported compiler/runtime procedure and run workload-scenario. Do not treat an unsupported runtime or startup failure as a successful race check. Also keep the logical oracle: absence of a race report says nothing about whether an account tombstone changed the answer correctly.

Scale past the workspace, not past the implemented catalog

The larger check uses 200000 events and 257 accounts, with 256 operations per batch and the stream preset. Its base logical input is

200000(30)+257(14)=6003598\text{ bytes}.

This exceeds each sort's 2 MiB workspace. Selecting all eight days yields \lceil200000/2048\rceil=98 initial event runs, below the 128-run cap. With fan-in eight, the two materialized passes are 98\rightarrow13\rightarrow2. The group sort also spills. This demonstrates bounded processing of data larger than a workspace; it is not a claim that the input exceeds total machine RAM or that the query allocation peak equals RSS.

The base ends at sequence 783. Its query consumes 200000 events, joins 200000, and emits 32 groups. The delta has 41870 operations and 931465 logical bytes, ending at sequence 947. Its query consumes 184600 surviving events, joins 180200 after account deletions, and still emits 32 groups. The latter sorts start with 91 event runs and 88 joined runs; both make two materialized passes. A constant number of groups does not imply unchanged values—the oracle compares every count and cents total.

In the Linux Release check, the base sorts wrote 16863048 and 19263048 spill bytes; the updated sorts wrote 15564648 and 17355948. These are each sort's reported write traffic, including materialized runs, not database disk size. The corresponding query ledger peaks were 784870 and 767390 bytes in that build, with zero final charge. Those allocation-size observations are not portable thresholds or performance claims. No timing or M4 memory measurement is inferred from them.

Make a wrong answer fail without relying on a sanitizer

Temporarily change the tombstone branch in Input::operation: for an account tombstone, return Mutation::put(Account{id, 0}) instead of Mutation::erase. Keep event tombstones unchanged. Build and run only workload-native. The handwritten third phase should be empty, but the defect retains account 10 in region zero and emits an extra answer row. The Python comparator must fail. This is a semantic defect with valid memory accesses; a sanitizer need not report it. Restore the original branch and rerun the full suites.

The normal Chapter 21 source and the cumulative 34-test suite were checked in Linux Debug, Release, and AddressSanitizer/UndefinedBehaviorSanitizer builds with Clang 17. The temporary account-delete defect failed the expected logical comparison in all three configurations and was restored before the final passing runs. The focused workload-scenario test also passed a separate GCC 14.2 ThreadSanitizer build; this was not a full ThreadSanitizer suite. The larger 200000-event run was checked in Release against both phase formulas. These are correctness and resource-owner checks, not native macOS execution or physical power-loss tests.

Diagnose the stage, not just the last error line

Symptom Likely boundary to inspect Useful next check
base-sequence mismatch A file was repeated, applied to the wrong history, or a prior import stopped after commits Inspect recovered sequence and reported last_acknowledged; do not automatically replay
Import fails after a valid first batch The file, not the batch, was assumed atomic Query the reopened committed prefix; inspect the rejected batch's terminator
Scenario arrival watchdog Selected input never spills, or a worker failed before the requested boundary Run the corresponding ordinary query and inspect the named task error and run counts
Extra group with region zero A deleted account became a value, or a tombstone was ignored Run the handwritten third phase before inspecting generated totals
Formula agrees at 1000 but not 1001 Tail multiplicity is wrong Lane 0 occurs twice; every other lane once
Run-descriptor limit Row count exceeds chunk_rows * max_runs Keep the test within the documented preset, or explicitly redesign the catalog; do not just increase the input
Completed CSV plus cleanup error Publication and temporary-file deletion have different outcomes Preserve the completed answer and inspect remaining spill owners/names

As a useful variation, set --hot-percent 100 --update-every 0 --delete-every 0 and use the full day range. Event payloads then all target account 1, but account updates/deletions still follow their separate rule. Predict the number of join matches before running; then compare both replay and formula. Another variation is batch size 1: the final values stay the same, while snapshot sequence numbers and maintenance frequency change. Read metadata rather than hard-coding 5 and 6.

The completed chapter leaves a reproducible input format, two independent answer paths, a bounded C++ adapter, and a thin driver over the real engine. Chapter 22 will use these interfaces for recovery and resource-pressure experiments. Normal command completion and a clean reopen here do not establish the outcomes of a crash or simulated persistence failure.
