Chapter 7 — An arena-backed skip-list memtable

Part 1 — Stable storage and ordered search

Suppose the in-memory index contains event 10 and event 30. A batch adds event 20, adds event 25, and deletes event 10. Allocating and publishing each operation in turn is unsafe: a later allocation failure could leave only half the batch visible. Keeping every allocation alive is not sufficient either. Incorrect link updates can make a fully allocated node unreachable.

We will implement two connected mechanisms. An arena supplies stable, aligned storage under a byte cap and can abandon everything allocated during one preparation. A skip list orders versions of records and publishes an entirely prepared batch without allocating. The link algorithm, allocation policy, rollback, and structural checks are ours; no standard ordered container sits inside the engine.

Begin with the restored Chapter 6 workspace, including its second part and all eight passing CTest entries. Keep Chapters 1–5's independent foundation programs. We reuse Key, KeyLess, the Event and Account value types, 30/14-byte codecs, and checked size arithmetic. No preceding file is replaced.

Learning objectives

Allocate aligned storage without relocating existing nodes; separate storage from object lifetime; roll back a preparation without losing old values; derive skip-list search and insertion; order versions and deletion markers; publish interacting nodes without throwing; distinguish stable addresses from snapshot semantics; verify every level against a reference order.

The allocation remains 4.5 implementation hours: arena 1.0, index and batch preparation 2.5, and structural tests/debugging 1.0. Reading is separate. This chapter has two complete parts with that single allocation. Part 1 develops storage, record entries, and search. Part 2 finishes publication, diagnostics, tests, and the build. Implement both before advancing; the source files continue across the two pages.

The files and the ownership boundary

Create the directories, retaining the native C++20 compiler already selected:

File Responsibility
include/strata/memory/arena.hpp Capped storage and one rollback transaction
src/memory/arena.cpp Chunk acquisition, aligned bump allocation, rollback
include/strata/storage/entry.hpp Internal keys, owned mutations, borrowed entries
include/strata/storage/memtable.hpp Index, cursor, prepared-batch interfaces
src/storage/memtable.cpp Search, preparation, link publication, invariants
tests/memtable.cpp Lifetime, failure, version, and reference checks

All filename-labelled blocks for a file append in reading order, first this page and then Part 2. A later CMake block appends to the existing root file. There is no new dependency or unfinished future target.

MemTable owns its arena. The arena owns chunks, and chunks provide storage for nodes and their encoded values. A Cursor or EntryView borrows those objects; it owns no chunk. A prepared-batch token temporarily controls an arena checkpoint and the lifetimes of unpublished nodes. It must be destroyed or committed before the table can be frozen, and must never outlive the table.

The entire layer is single-threaded or externally exclusive. Even an otherwise read-only lookup must not overlap link publication in another thread. A later snapshot layer will share frozen tables, not turn these ordinary pointer writes into lock-free operations.

An arena gives addresses a longer life than a vector

A vector can move its elements when capacity grows. That is unacceptable for a node referenced by many other nodes. Instead, acquire independent chunks and never move them. Each chunk holds 4096 payload bytes. A bump cursor advances inside the newest chunk; a new chunk is acquired when the remaining suffix cannot hold the next aligned request. We do not search old holes or individually free committed nodes.

The payload is a genuine bounded array of std::byte, not a one-element array followed by out-of-bounds indexing. alignas(std::max_align_t) makes its base suitable for the fundamental alignments this arena supports. alignof(T) asks for a type's alignment, whereas sizeof(T) asks for its complete object size. An over-aligned type is rejected rather than silently misaligned. See the alignment rules and the special role of byte arrays that provide object storage.

Start the arena header:

ArenaFull means the configured storage cap prevents another chunk. It differs from std::bad_alloc, which can represent allocator failure or our test seam. Both are exceptions; neither permits partial publication. This distinction lets later admission code react to a full memtable without pretending the system allocator failed.

Chunk::previous links ownership history, not search order. used is an offset into its own byte array. The array is not initialized by new Chunk; its bytes must be written or used to construct an object before reading them. Pointer and offset members have explicit default initializers.

We charge sizeof(Chunk), not merely 4096. This includes the link, offset, member padding, payload, and any trailing padding. A partially filled chunk costs the same as a full one. The allocator's hidden bookkeeping is not included.

Give rollback one exclusive owner

The nested class Arena::Transaction may access private arena members, but it still needs an actual Arena&; nesting does not manufacture an owning instance. It records the current chunk, that chunk's cursor, and the total used bytes. Only one transaction may be active. Deleting both copy and move operations prevents multiple guards from believing they own the same rollback point. The nested-class access rules explain the access permission, not a lifetime extension.

Continue the open Arena declaration:

On normal scope exit without commit, the transaction discards new chunks and rewinds the original chunk. On commit, it stops owning that rollback obligation. Objects constructed in the abandoned storage must be destroyed before the transaction releases or rewinds it. This arena deliberately does not maintain a hidden destructor registry; its caller owns object lifetimes.

Complete the header:

reserved_bytes() is the sum of complete live chunk charges. used_bytes() is the sum of consumed payload prefixes, including alignment padding. The arena object itself, the memtable's head pointers, stack scratch space, and operating system memory are outside this local cap. Chapter 9 will compose subsystem charges; this is not yet a whole-process or whole-engine budget.

fail_on_chunk(k) arms a one-based countdown for new chunk acquisition, not every small allocation and not every allocation in the process. A request that fits the existing chunk does not consume the countdown. Cap rejection precedes the seam. A triggered failure disarms itself; unused countdown progress is observational test state, not something rollback promises to restore.

Rewinding storage without rewinding old objects

Let a checkpoint contain head H, its used offset u, and total consumed payload U. A transaction can append bytes to H and prepend new chunks. To abandon it, delete chunks until the head is again H, restore that chunk's cursor to u, and restore the aggregate to U. Older chunks were never changed. A null H means the arena was initially empty, so every acquired chunk is new.

Create the implementation:

If a nested transaction is attempted, its constructor throws before setting the active flag. The first guard remains responsible for its checkpoint. For a successfully constructed guard, the destructor handles both ordinary abandonment and stack unwinding. The comparison of head pointers is a comparison of chunk identity, not an attempt to order unrelated addresses.

The checkpoint only rolls back allocations. It cannot undo a caller writing through a pointer to old data. Our memtable will keep old values immutable and avoid changing links until preparation is complete. That caller discipline is what makes arena rollback useful for a strong state guarantee.

drop_head releases a complete Chunk with ordinary delete; it does not delete arena-constructed nodes individually. Its caller knows a head exists. The decrement is valid because each head was previously charged once. The transaction restores the aggregate consumed-byte count after dropping all new chunks; destruction of the whole arena no longer needs that counter.

Destroying an arena with an outstanding transaction is a lifetime contract violation. std::terminate() makes that misuse fail immediately rather than leaving a guard pointing into a destroyed owner. This is not an ordinary resource-pressure outcome. A table is likewise nonmovable so an outstanding token cannot quietly start referring to a different owner address.

Complete the small fault-control operations:

Changing the seam while a transaction is active is rejected. It would otherwise make an in-progress operation's test policy depend on unrelated activity. The same guard makes the seam unusable as a hidden callback during commit.

Derive alignment before doing pointer arithmetic

Let C=4096 be the payload capacity, u the current used offset, a the requested alignment, and n the requested nonzero byte count. The base is aligned to every supported a. The padding needed to reach the next aligned offset is

p = (a-(u\bmod a))\bmod a.

This also returns zero when u is already aligned. Require a>0 before the modulo. For u=5, a=8, and n=16, padding is 3, the returned offset is 8, and the new cursor is 5+3+16=24. Bytes 5 through 7 are padding, not part of the new object. With u=4090, a=8, and n=8, padding is 6 but the request cannot fit: no bytes remain after alignment.

Avoid computing an unchecked u + p + n. First require

p\leq C-u,\qquad n\leq C-u-p.

Only then advance the cursor. The loop invariant is 0\leq u\leq C. The first test protects the second subtraction. A positive power of two has exactly one set bit, so a & (a - 1) is zero; the zero-alignment test must precede that expression. We support only such alignments no greater than max_align_t.

Begin the allocation function:

try_chunk is a local lambda. [this, bytes, alignment] borrows this arena through this and copies the two request sizes. The explicit -> void* fixes the return type because one branch returns nullptr and another returns a byte pointer. It is used only during this call. It neither escapes nor allocates.

A void* denotes an address without a pointed-to object type. Returning it separates storage allocation from construction. No Node has been constructed merely because this function advanced the cursor. The successful arithmetic is bounded by one payload. Aggregate used bytes cannot overflow either: consumed payload never exceeds the sum of charged live chunks, which fits the cap.

Finish the function and namespace:

Let B be the configured cap, R current reserved bytes, and K=\operatorname{sizeof}(\text{Chunk}). The maintained invariant R\leq B allows the admission check K\leq B-R without overflowing R + K. new Chunk can throw, but until it returns, no ownership pointer or charge has changed. After acquisition, linking the chunk and updating the charge cannot fail.

The second call to try_chunk must succeed: the new chunk has offset zero, a suitably aligned base, and the request was already checked against 4096. The last chunk's unusable tail remains charged. This is intentional fragmentation, not lost accounting. Our arena favors predictable lifetime and rollback over packing every free byte.

The condition if (void* result = try_chunk()) declares a local pointer and tests whether it is nonnull. Its scope is that if statement. It is not a cast from integer truth to an address.

Construct an object; do not merely cast to one

The language requires enough suitably aligned storage and completed initialization for an object's lifetime to begin. A cast alone does not run a constructor. Placement construction places an object in storage already owned elsewhere. A placement new expression uses an address rather than acquiring its own allocation; C++20's std::construct_at expresses that operation through <memory> and returns a pointer to the constructed object. The relevant sources are object lifetime, placement new, and construct_at.

For our node the concrete operation will be:

The allocator returns suitably sized storage. static_cast<Node*> gives that address the type needed by construct_at; construction, not the cast, creates the initialized node. We retain the pointer returned by construction rather than relying on a stale pointer from an earlier occupant of the same storage. The empty argument list value-initializes this concrete node, including null links. It does not initialize a disk format.

std::destroy_at(node) invokes the destructor without freeing the containing chunk. This pairs with placement construction, whereas delete node would attempt to release storage not independently acquired by new Node. Destroy nodes before releasing their chunks. The library specifies this distinction in destroy_at. Part 2 includes a nontrivial counted object so this lifetime step is observable, rather than relying only on nodes whose destructor currently does no work.

Represent versions, not overwrites

A storage key is the pair (relation, primary). Its order is already defined by Chapter 6's KeyLess. An internal key adds a positive batch sequence. For equal storage keys, a larger sequence sorts earlier, placing newest versions first. Different storage keys still sort ascending. No subtraction participates in the engine comparator, so the full unsigned range is usable.

For one key, versions at sequences 9, 7, and 4 appear as 9, 7, 4. A lookup visible through sequence 8 starts at internal key (key,8) and finds sequence 7. A lookup through zero finds none, because committed sequences are positive. Sequence gaps are valid; wrapping or reusing a sequence in one table is not.

An erase is a stored tombstone, not the absence of a node. If sequence 7 is an erase, a lookup through 8 returns that erase. It must not fall through to the put at sequence 4. A later merged reader needs the distinction to suppress an older value in another source.

Create the entry header:

EntryView owns a copy of the key and kind, but only a span into the value bytes. Copying this view does not keep a memtable alive. A put carries exactly its relation's encoded row; an erase carries no row bytes. Sequence and operation kind are storage metadata, not silently added to Chapter 6's codec.

Requests own their input image

We could accept a span into a temporary encoded array, but that would make lifetime errors easy. A Mutation instead owns a fixed 30-byte array, enough for either schema, plus a logical length. Account images use the first 14 bytes. Factories are static member functions: call Mutation::put(event) without an existing mutation object. Overload selection distinguishes an event from an account by argument type.

These factories make the usual path correct, but their public fields are not a trust boundary. A caller can still fabricate an inconsistent key or length. Validate the entire request before allocating nodes. A repeated storage key within a batch is rejected later, even when one operation is a put and another an erase. That policy avoids an implicit "first wins" or "last wins" rule.

The length guard precedes .first(length). An erase with nonzero length is rejected; a put must decode with the expected relation, version, and exact byte count. The decoded row's key must equal the metadata key. Otherwise a point lookup could find a value that claims to belong to a different row.

FormatError remains the codec's malformed-image error. Invalid operation metadata uses invalid_argument. Either error happens before the index changes. The unused suffix of an account's owning array is not copied into the memtable.

A skip list is several ordered lists sharing nodes

Level zero contains every version. A node with height h participates in levels 0 through h-1. At each level it points to the next node participating there; its height is not the number of following rows to skip. Higher levels bypass some lower-level work without creating copies of the records.

This is the probabilistic search-and-splice structure introduced by William Pugh, Skip Lists: A Probabilistic Alternative to Balanced Trees, first two pages. Our versioned ordering, arena rollback, and batch publication policy are additional design decisions. We do not implement physical deletion of individual nodes; an erase adds another version, and a whole generation is reclaimed later.

Consider this illustrative shape, ignoring sequences because all keys differ:

To seek 25, begin at the highest level. Advance to 20, but not beyond the end. At level 1, 40 would overshoot, so stay at 20 and descend. At level 0, 30 would also overshoot. The next node at level zero is therefore the lower bound, 30. Seeking exactly 20 must stop before 20, so the horizontal comparison is strictly less than, not less than or equal to.

Bounded towers without pretending a one-element array is larger

We choose a maximum height of 16 and give every node a real std::array of 16 link pointers. Only the first height slots participate; the remaining slots stay null. This spends extra memory for a simple, portable object layout. It is not the variable-length trailing-array technique seen in some implementations.

The node also has a separate pending-chain pointer. Before publication that chain owns the inventory of constructed nodes. It must not reuse next[0], whose meaning changes during publication. Node payloads live in separately allocated regions of the same arena, so tombstones need no payload allocation.

Start the memtable header:

The fields in an arena node are ordinary C++ objects; InternalKey, spans, and link arrays may contain implementation padding. None is written directly to storage. The static payload limit and complete node size are checked in the constructor implementation below.

We keep one head pointer for each level instead of inventing a sentinel key smaller than every possible unsigned key. A null predecessor means "use the head pointer at this level," not an actual node with an invalid relation tag.

A cursor borrows; a preparation owns a pending change

The two nested interfaces have different responsibilities. A cursor holds one borrowed node pointer and can advance at level zero. A prepared token holds the rollback guard and unpublished-node chain. Their constructors are private so only MemTable can produce a valid one. The explicit friend class MemTable permits the enclosing class to call those private constructors; outer classes do not automatically gain access to nested classes' private members. See friend declarations.

table_ is a reference, so the token does not own or extend its table's lifetime. transaction_ is declared before the pending pointers. The token's destructor body will destroy unpublished nodes first; automatic member destruction then runs the transaction's rollback. The copied generator state belongs to the candidate until commit.

The token is deliberately neither copyable nor movable. That is compatible with returning a freshly constructed token by value, as Part 2 explains. It also avoids a move-assignment case that might unexpectedly abandon an unrelated prepared batch.

Continue with the public operations:

A default visible argument means the largest representable sequence. Explicit values allow boundary tests and future merged reads. The ref-qualified const & accessors borrow from an lvalue table; their const && counterparts are deleted to reject obvious borrowing from a temporary. This is a useful restriction, not a lifetime proof for every possible caller.

size() counts versions, including tombstones, not distinct live keys. freeze() only seals this table against later preparation. It does not flush, create a durable snapshot, synchronize threads, or transfer ownership.

Finish the private state:

Declare the arena before the index state so it is destroyed last. The table's destructor body will traverse level zero while all node storage is still alive. No head array or cursor owns a node separately. fixed_height is a deterministic test configuration: zero chooses generated heights; 1 through 16 force one height for every node. It is not an adaptive performance setting.

Begin with construction and whole-generation destruction

The type traits with suffix _v are compile-time Boolean queries from <type_traits>. is_nothrow_default_constructible_v<Node> checks that empty node construction cannot throw, and is_trivially_destructible_v<Node> checks that node destruction is trivial. See the type-property specifications. These assertions guard this concrete representation; they do not say that arbitrary placement constructors cannot fail.

Create the source file:

Nonthrowing node construction makes the interval between obtaining node storage and registering its lifetime in the pending chain safe. Later payload allocation can still fail and must be covered by that chain's cleanup.

Destruction saves next[0] before ending the current node's lifetime. Reading that member afterward would use a dead object. The arena then releases its own chunks automatically after the table destructor body finishes. Values are byte regions owned by those chunks; there is no separate heap payload to delete.

The zero generator seed is rejected because the chosen shift/XOR recurrence would remain zero forever. The fixed-height upper bound is validated once rather than checked at every link access.

Search by preserving the predecessor invariant

The mutable helper returns Node*&: a reference to a pointer slot, not just a copied pointer. Assigning through it updates either a node's actual outgoing link or the actual head slot. The const helper returns a borrowed pointer value and cannot expose a mutable link. These overloads share the sentinel-free head policy.

At the start of each horizontal step, previous is null or has an internal key strictly before the target. Moving to next preserves that invariant. When the next key is not before the target, descending one level keeps the same valid predecessor and examines finer links. A node reached at a higher level also participates at all lower levels, so its lower links exist.

The outer loop starts at 16 and decrements inside the loop before use. It visits levels 15 through 0 without testing an unsigned variable against zero with >=, which would never become false after wraparound. Once level zero is finished, its next link is the first key not before the target, or null at end.

begin returns the first level-zero node. It is raw internal iteration, not a query that collapses old versions. Both cursor operations and lookup are small enough to keep the borrowing behavior explicit:

entry() returns a new view object, not a node reference. At end it throws out_of_range; next() at end is an idempotent no-op. The lookup checks the storage key after lower bound because the next node can belong to another key. An equal key with an erase kind is returned as a present tombstone. A missing optional and a tombstone are intentionally different results.

A previously returned value span remains valid across later insertions because old arena storage does not move or get overwritten. A cursor resumed after insertion can nevertheless see changed forward links. Therefore iteration must not span a commit when a stable result is required. Freeze first, and keep the whole table alive for the entire read. Stable addresses are not by themselves snapshot semantics.

Heights: a useful model, not a worst-case promise

With ideal independent promotion probability 1/2, a node reaches height at least h with probability 2^{-(h-1)}. For maximum height H, its expected participating height is

\mathbb{E}[h]=\sum_{j=1}^{H}2^{-(j-1)}=2(1-2^{-H}).

For H=16, that is approximately 1.99997 participating levels. With n nodes, level i has expected membership n/2^i. Sixteen nodes would have expected memberships 16, 8, 4, 2, 1 in the first five levels; an actual fixture need not match those numbers.

These calculations describe an idealized distribution, not memory allocation: our node always stores 16 pointers, even when its height is one. Nor is a fixed height cap an asymptotic logarithmic guarantee for arbitrarily large n. The top level still has roughly n/2^{15} nodes in this model, and an all-height-one list has linear search. Chunk caps bound practical table sizes; generated heights provide a useful expected search shape, not an adversarial performance guarantee.

Use a reproducible 32-bit shift/XOR generator. A generated zero bit promotes; stop at the first one bit or at the height cap:

The three shifts update a local 32-bit unsigned state. Every shift count is smaller than 32. Copying that state into a preparation makes a failed attempt leave the table's future height sequence unchanged. This simple generator is not cryptographic, and this implementation does not claim its bits satisfy the independence assumptions of the probability model. The test seed makes failures repeatable; forcing heights 1 and 16 exercises both structural extremes without waiting for a rare generated tower.
