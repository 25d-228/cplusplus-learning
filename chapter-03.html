Chapter 3 — Lifetime, RAII, and move-only owners

A buffer holding a disk block can outlive the function that read it, but it cannot outlive its last owner. A query can borrow the block without becoming responsible for freeing it. Moving that responsibility to another object need not move even one payload byte. These are different relationships, and a useful resource type must make each one explicit.

This chapter builds a fixed-size, move-only byte buffer. It transfers {4, 5, 6} without allocating another payload, releases an already-owned destination before replacing it, leaves a distinct moved-from source empty, and makes self-move a no-op. Allocation counters and a separate lifetime trace make those promises observable. The same reasoning will later govern file handles, pinned blocks, arenas, and spill-file cleanup; this exercise is not the engine's allocator.

Starting code: retain the complete programs and root CMake configuration from Chapter 1 and Chapter 2. Their three passing CTest entries stay in place. You need references, const, arrays, vectors, spans, and Chapter 1's active check pattern. No engine files or future chapter code are required.

Learning objectives

Separate storage, object lifetime, ownership, and borrowing; define classes with constructors, destructors, and private invariants; prefer member-owned resources and the rule of zero; distinguish move construction from move assignment; implement a documented moved-from state; account for destruction, self-move, early return, and vector relocation without double release.

The allocation is 2.5 implementation hours: 1.0 for the owner and lifetime exercises, 1.0 for move paths and container integration, and 0.5 for checks and diagnosis. Reading is separate. The fixtures are deliberately small; their purpose is an exact state trace, not a throughput result.

Storage is not an object, and an object is not its payload

Storage is a region of memory with a size and alignment. An object has a type, initialization, and a lifetime in suitable storage. For the ordinary class objects in this chapter, completed initialization establishes a usable object; starting its destructor ends its lifetime in the formal language sense. Construction and destruction have special rules that still permit their member accesses. Merely retaining an address does not keep an object alive. The object-lifetime rules distinguish these concepts more generally, including storage reuse cases we are not using here.

Consider a local owner that contains a pointer to three dynamically allocated bytes. There are at least three separate things to track:

Thing Where its storage comes from What ends its useful lifetime here
Local owner object Automatic storage for a local variable Leaving its scope
Dynamically allocated byte array An array allocation Its owning pointer resets or is destroyed
Local std::span value Automatic storage for another local variable Leaving the span's scope; its borrow can become invalid sooner

The pointer member belongs to the owner object, but the pointed-to array is not a member subobject. Destroying a bare pointer does not release its pointee. Destroying an owning smart pointer does. A span stores access information; it does not participate in release responsibility.

We will not use placement new, casts from untyped storage, or manual destructor calls in this chapter. Those would mix the question of who releases a resource with the different question of which objects exist in raw storage. The later arena implementation will need the latter distinction explicitly.

Constructors establish state; destructors finish a scope

A class, like a struct, defines a type with data and functions. Its default member access is private; a struct's is public. We write public: for callable operations and private: for internal state. Private access prevents a caller from casually breaking an invariant; it does not make an incorrect constructor or member function correct.

A constructor has the class's name and no return type. A destructor uses that name preceded by ~, takes no arguments, and has no return type. The expression following a constructor's colon initializes members before its body runs. A reference member must be bound there or by a member initializer; assignment inside the body cannot go back and initialize an unbound reference.

Prefer an existing owner before writing special members

Resource Acquisition Is Initialization, or RAII, binds a resource's release responsibility to an object's lifetime. A successful construction gives you an owner; destruction releases what it still owns. The resource might be an allocation, file descriptor, lock, or temporary file, not just memory. RAII is not garbage collection, and it does not require the owner itself to be on the heap.

std::vector already owns its element storage. std::unique_ptr<T> represents exclusive release responsibility for a separately allocated T; moving it transfers that responsibility. For an array, use std::unique_ptr<T[]>, whose default deletion uses the array form of deletion. Neither form is a reference count. Copying a unique pointer is prohibited; its interfaces are specified in unique ownership.

Before introducing our cross-member invariant, compare two small aggregates:

std::byte, from <cstddef>, represents a byte without treating it as an ordinary arithmetic integer. Write a known byte value as std::byte{4}. For printing a numeric value, std::to_integer<unsigned int>(value) converts explicitly; see byte operations. The fixed three-element array here lets UniqueRecord avoid a second length member.

Neither aggregate declares a destructor, copy operation, or move operation. This design is often called the rule of zero: let well-chosen member types supply those operations instead of duplicating their resource management. ValueRecord can copy its vector into independent storage. UniqueRecord cannot copy its unique pointer, but the generated move transfers that member. The copy/move constructor rules describe memberwise generation and when a generated copy is deleted.

std::move permits a transfer; it does not perform one

A named object expression such as source is an lvalue: it designates an existing object. std::move(source) produces an expression that permits selection of an operation accepting an expiring value, conventionally a T&& parameter. It does not allocate, copy payload bytes, destroy the source, or itself remove ownership. The selected constructor or assignment operator performs the work. The move helper's specification describes a cast, not a transfer algorithm.

An rvalue reference parameter is written T&&; it is not two levels of pointer. The parameter still refers to an object. Once that parameter has a name inside the function, using its name is again an lvalue expression. This is why a custom move constructor must explicitly move the source's owning member rather than assume every access to the parameter will move automatically.

std::make_unique<T>(arguments) allocates and constructs a T and returns its unique owner. Here T is one std::array, not an unknown-length array. The empty source.payload is a documented consequence of the unique-pointer move constructor, not a universal property of moving. The standard library generally permits a valid but unspecified moved-from state unless a type gives a stronger guarantee; see moved-from library objects. A user-defined type does not become correct merely because it has a T&& constructor. We must establish and document our own source state.

An invariant that needs a custom move

Our ByteBuffer has two coupled fields: an owning pointer and a byte count. The public boundary invariant is:

  • Empty means a null pointer and count zero, with no allocation.
  • Nonempty means exclusive ownership of an array of exactly the advertised number of accessible bytes; every byte has been initialized.
  • A move between distinct owners preserves the array's address and contents, and leaves the source empty. A self-move preserves the original state.

Let p denote the stored pointer and n the byte count. The empty-state part is

n = 0 \quad\Longleftrightarrow\quad p = \mathrm{nullptr}.

The other half of the contract cannot be proved from those two values alone: a nonnull pointer with count three must actually own a live three-byte array. We arrange that by making fields private and allowing acquisition only through the constructor. A span does not validate this ownership for us.

Why not generate every move? A defaulted move would move the unique pointer but copy the scalar length. A source that originally held three bytes would then contain a null pointer and length three. Each member would individually be in a legal state, but the combined object would violate our invariant. The rule of zero works best when the chosen representation makes memberwise operations correct; it is not a command to accept an invalid state.

The buffer also records successful payload acquisitions and releases. Define A as acquisitions, R as releases, and L as currently live payload arrays. For this finite, single-threaded fixture, at completed public operations,

L = A - R.

Moving to a fresh owner changes neither A nor R. Replacing an already-owning destination releases one array, so R increases by one and L decreases by one. These counters count arrays owned by ByteBuffer only. They do not count stream allocations, vectors' element storage, allocator bookkeeping, the earlier standard-owner exercise, or process memory usage. They are not a thread-safe memory budget and are not intended for an indefinitely running counter service.

Read the interface before its implementation

A default constructor takes no arguments. = default asks the compiler to generate that operation using the members' declared initializers. = delete instead makes an attempted call ill-formed. We explicitly delete both copying operations because copying this type must not silently allocate a second payload or manufacture a second release obligation.

ByteBuffer(ByteBuffer&&) constructs a new object from a source. ByteBuffer& operator=(ByteBuffer&&) changes an already-existing object and returns a reference to that destination. The two operations have different cleanup requirements. A destructor, copy constructor, copy assignment, move constructor, and move assignment are the five special operations whose interaction you must consider here; “consider all five” does not mean implement all five as permitted operations. The assignment rules explain generated and deleted assignments.

The view accessors have another qualifier: bytes() & is callable on an lvalue owner, while bytes() const & supplies read-only elements when the owner is observed as const. We delete the corresponding && overloads, preventing a call such as ByteBuffer(3).bytes() from borrowing a temporary that is about to die. These are ref-qualified member functions; the qualifier belongs to the object on which the method is called, not to its returned span. See member-function qualifiers. This blocks one easy mistake, not every dangling borrow.

size() const can inspect but not change ordinary members through that access path. Its returned integer owns its value and needs no lifetime restriction. A static member function, allocations(), has no particular buffer as its target; call it as ByteBuffer::allocations(). The inline static data member supplies one shared counter object, rather than a counter in every buffer. inline here permits the definition in the class; it is not an instruction to inline machine code. The static-data-member rules cover these declarations. Returning counts by value prevents a caller from modifying the instrumentation through the result.

An explicitly declared destructor or copy operation changes which move operations are implicitly supplied. Do not add a logging destructor to an otherwise rule-of-zero type and assume that its move behavior is unchanged. Here all five choices are visible rather than left to accidental generation.

Acquire once, and make release idempotent

Define construction outside the class. ByteBuffer:: identifies the member being defined, just as a namespace qualifier identified a function in Chapter 1.

The conditional expression selects exactly one initializer. A size of zero uses an empty unique pointer and performs no array allocation. Otherwise, std::make_unique<std::byte[]>(size) value-initializes the array, so every byte starts at zero. The creation functions specify this array initialization. ByteBuffer(0) and ByteBuffer{} therefore reach the same empty representation; we do not depend on how a zero-length new[] allocation might be represented.

Acquisition is counted only after initialization succeeds. The size-taking constructor is deliberately not noexcept: allocation can fail. No counter is incremented before the allocation, and the remaining constructor body only updates the counters. If a constructor fails before completion, the complete object's destructor is not the cleanup mechanism; its fully constructed member subobjects are cleaned up. Making the resource a smart-pointer member puts that release responsibility in a constructed subobject. The construction-failure rules underpin this behavior. Chapter 4 will add explicit handling and deterministic failure tests; these tiny successful allocations are not an allocation-failure experiment.

data_.reset() releases its currently owned array and makes the pointer empty. Our outer reset() also updates the length and instrumentation. Calling it twice is safe: the second call observes no pointer, releases nothing, and leaves length zero. This property is called idempotence: repeating the operation has the same final state as doing it once.

Do not substitute data_.release(). The similarly named smart-pointer operation detaches and returns a raw pointer without deleting the resource. Ignoring that return value would leak the array. Nor should a borrower call delete[] on data_.get(): the owning pointer would still believe it must delete the same array. The unique-pointer modifiers and array interface distinguish observing, releasing responsibility, and destroying a resource.

The destructor calls our reset once; after its body, member destruction still runs. data_ is then empty, so its destructor has no second array to release. There is no throwing callback, allocation, or stream output in this cleanup path. A real file's successful flush is different from merely releasing its handle: important completion errors need an explicit operation, not a destructor that tries to report success by throwing.

A view exposes bytes, not release authority

Append the size and view operations:

get() observes the stored pointer; it transfers nothing. A mutable owner gives out a writable span. A const access path gives out a span of const bytes. Constness of a unique pointer by itself would not make its pointee const; our chosen return type supplies the read-only access contract.

The explicit empty branch returns a default empty span. It requires no pointer arithmetic and no attempt to describe three elements through a null pointer. For the nonempty case, the constructor-established pointer/count invariant makes the range valid. This accessor does not perform a separate allocation check.

A caller may keep the span only while the particular array it refers to is alive. Resetting or destroying its current owner invalidates that borrow. Replacing an owning destination invalidates views into the destination's old array. In contrast, moving our pointer/count pair to a different owner leaves the same array alive, so a view into the transferred array remains valid. This is a property of our implementation and contract, not a promise that any operation named “move” preserves every kind of view.

Deleting rvalue accessors is only a guardrail. A span obtained from a named local can still be returned from a function that then destroys that owner. A caller can also keep a span and reset the owner. Neither mistake becomes safe because the original bytes() call was permitted by the type system.

Transfer both fields, not just the pointer

The source of a move is still a live object and will eventually have its own destructor called. The move must leave it with no responsibility for the transferred allocation. std::unique_ptr handles that obligation for its member; we must also handle the length.

std::exchange(object, replacement), from <utility>, stores the replacement and returns the old value. For a length of three, std::exchange(other.size_, 0) returns 3 and leaves other.size_ equal to zero. This is not an atomic operation; see the exchange specification. Its role here is to make the old-value/new-state transition explicit.

Append the complete move constructor:

The members initialize in declaration order: the destination's data_ receives the source's owning pointer, then size_ receives the source's previous count. The source has become (nullptr, 0) by the time construction completes. No payload loop, array allocation, or counter adjustment is needed. There are brief internal intermediate states between those initializers, but nothing in this single-threaded code observes them or invokes a callback. Our invariant is promised at operation boundaries, not after every machine instruction.

The std::move on other.data_ is necessary. Merely writing data_(other.data_) would try to copy a unique pointer, because the named expression is an lvalue. Deleting that copy is a useful compile-time failure, not a reason to add a raw pointer escape hatch.

Move construction has no old destination resource. Move assignment does:

this is the pointer to the object receiving the member call. &other is the address of the source object. *this names the destination object; returning it as ByteBuffer& returns a reference, not a new owner. A call destination = std::move(source) selects this function when both have the appropriate types.

The identity check handles aliases: other may be another reference to the very same destination. If so, we preserve the object, payload, and counts. Without that check, our reset-first algorithm would erase the object before trying to move it from itself. That might avoid a double deletion, yet it would still violate our stronger no-op self-move contract.

For different objects, reset destroys the destination's previous allocation and accounts for the release. Only then do we take the source's pointer and length. The unique-pointer assignment already knows how to release its old pointer; our explicit reset also maintains the enclosing buffer's counters and invariant. After reset the pointer is empty, so the member assignment has no second old allocation to release.

A swap-based assignment is another possible policy. It would leave the source owning the destination's old payload until later cleanup, rather than empty. That can be valid, but it is not the policy promised here. “Moved from” describes an operation that happened; it is not a complete state specification.

Why these moves can honestly be noexcept

They transfer a default-deleter unique pointer, assign scalar fields, and possibly release a byte array. None of those operations needs a new allocation or a throwing element destructor. This reasoning, not the attractiveness of a faster container path, justifies the declaration.

When a vector needs new element storage, it must construct elements there while preserving its specified failure behavior. A nonthrowing move gives it a transfer path that cannot fail after some old elements have been moved from. For some copyable types a potentially throwing move motivates copying instead; a move-only type has no such fallback. The vector capacity contract and insertion guarantees specify the relevant exceptions rather than promising that every move-looking expression is cheap.

Add compile-time checks using standard type traits: the _v forms are boolean questions about a type, not function calls on a buffer. static_assert rejects the translation unit when a condition is false. The type-property specification defines these queries.

These checks verify the type's declared interface, not that a body never leaks or violates an invariant. A wrongly written noexcept function can still terminate. Runtime state checks are still necessary.

Empty objects and reusable moved-from sources

A valid empty state is useful only if normal operations handle it. Test default construction, size-zero construction, moving from empty, assigning empty over a nonempty destination, reusing a previously moved-from object, and repeated reset. No view from this test survives an operation that releases its array.

In zero = ByteBuffer(3), the right side is a temporary owner. Its allocation is transferred by assignment; the temporary is empty before its destruction at the end of that full expression. The subsequent move into empty transfers that same allocation again. Neither transfer creates another array.

Notice the difference between assigning from a temporary and borrowing from it. Taking ownership before it dies is safe. Returning a span to its bytes without transferring ownership would not keep those bytes alive; the deleted rvalue accessors reject that particular spelling.

A return statement still crosses the lifetime boundary

Append a function with an early-return branch and a success branch, followed by a check of both:

The returned boolean is evaluated before local cleanup. It is an independent value, not a reference to scratch. Both paths destroy the local owner; neither returns its allocation. The same discipline applies when a future parser rejects a malformed record halfway through its work.

Do not generalize scope cleanup into a crash-recovery guarantee. Normal returns and exception unwinding toward a handler can run destructors; abrupt termination, process killing, and power loss are different events. Nor does releasing a buffer undo a disk write. The storage chapters will need a durable recovery protocol rather than an assumption that cleanup always executes.

Relocating owners is different from relocating their arrays

A std::vector<ByteBuffer> owns storage for its buffer objects. Each buffer in turn owns a separate byte array. If vector growth relocates the buffer objects, references to those objects are invalidated. Our buffers' move constructors nevertheless keep their separately allocated arrays alive at the same addresses. A view to those bytes is therefore a different dependency from a reference to a vector element.

Append a forced relocation check. As in Chapter 2, request more than the observed capacity rather than assuming a particular growth factor:

A successful reserve leaves our view usable. A future owner that stores bytes inline, rather than separately allocating them, would need a different promise.

There is no timing claim here. Counting payload acquisitions tells us which mechanism ran; it does not measure allocator overhead, cache behavior, or total process memory. Those measurements need larger, controlled workloads later.

What this owner does and does not promise

The buffer has exclusive ownership, a known empty state, initialized payloads, nonthrowing transfer and cleanup, and restricted view creation. A distinct move empties its source; self-move preserves the value. Existing destinations release their old arrays. Borrowers observe the array, not release authority. The checks make each transition visible without deliberately dereferencing dead storage.

This is not a replacement for std::vector, an engine memory allocator, a shared cache pin, or a transactional update. Ordinary values with independent member invariants should continue to use the rule of zero. Here custom special members were justified by the pointer/count relationship and accounting. Do not copy this single-threaded instrumentation into a concurrent engine and call it a memory budget.

The next chapter introduces error categories and exception handling, then builds a replacement before committing it. That will answer a different question: when acquiring a proposed new resource fails, how do we preserve the old value without leaking either resource?
