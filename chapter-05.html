Chapter 5 — Templates, concepts, and ordering contracts

Two sorted inputs can be merged without sorting them again. The visible result looks simple: {1, 4} and {2, 4} become {1, 2, 4, 4}. The interface is more interesting. Who owns the inputs? What does “before” mean? Which copy of an equivalent key comes first? What survives if a comparison throws after the result already contains two elements?

We will implement the merge loop ourselves, parameterize its element and comparison types, and return an owned vector. A C++20 concept will reject an argument that cannot be called as a comparator. Separate runtime checks will expose comparators that compile but do not describe a coherent ordering. The same distinction will matter when a skip list, sorted table, or compaction loop relies on an ordering it cannot prove from a function's type.

Start from the restored workspace of Chapter 4, including all earlier CMake targets. Chapter 2 supplies values, references, vectors, and spans; Chapter 3 supplies ownership and moves; Chapter 4 supplies exceptions, optional values, and prepare-then-commit. No engine source exists yet. This chapter does not include an earlier .cpp file or assume an unwritten utility header.

Learning objectives

Write and instantiate a function template; explain callable objects and lambda captures; constrain expressions with a concept; distinguish syntactic checks from ordering laws; implement a stable merge over borrowed inputs; identify the copies, allocations, and exception boundary of an owned result.

The allocation is 2.0 implementation hours: 0.5 for syntax experiments, 0.75 for the merge, 0.5 for ordering checks, and 0.25 for the expected-failure compilation. Reading is separate. This exercise deliberately materializes its result; it is not yet the bounded-buffer merge used for disk runs.

Decide what merging promises

Call the left input L and the right input R. Their lengths are n and m; valid element indices are 0 through n-1 and 0 through m-1, respectively. The predicate a \prec b means “the comparator says that a comes before b.” It is not automatically the built-in integer < operator.

Both inputs must be sorted under that same predicate. The algorithm keeps indices i and j at the first unconsumed elements. When both are available, choose the right element only if R_j \prec L_i. Otherwise choose the left one. This “otherwise” includes equivalent keys, so ties prefer the left input. After one side is exhausted, copy the remaining suffix of the other side.

For the numeric fixture, the merge decisions are:

Before the decision Comparison Element appended Remaining inputs
i=0, j=0 2 < 1 is false Left 1 {4} and {2,4}
i=1, j=0 2 < 4 is true Right 2 {4} and {4}
i=1, j=1 4 < 4 is false Left 4 Empty and {4}
Left exhausted No comparison Right 4 Both empty

This is a merge, not a set union: both occurrences of 4 survive. Each input's internal order also survives. To state stability across inputs, imagine their concatenation as left followed by right; equivalent elements retain that order. The standard merge specification gives a useful reference for stable merging. Here we implement the index loop rather than delegate it to std::merge.

The ownership contract is equally explicit. Inputs are borrowed read-only spans whose elements remain alive and unchanged throughout the call. The output owns newly constructed element values. The comparator is borrowed only until the call returns and is never retained. Input spans may overlap because this algorithm does not write through them. Another alias, callback, or thread must not change their values or invalidate their storage during the call.

For the numeric and tagged records in this chapter, copying an element copies all its data. Generic copying does not promise a deep clone of arbitrary pointer members: a vector of pointers would own pointer values, not the objects they point at. We are making the result's element ownership clear, not granting ownership of everything an element can reach.

A callable object is an object with a call operation

Begin the executable with its headers, check helper, and a concrete comparator:

Number is an alias for std::uint32_t, not a new numeric type. NumericLess is a class with a public operator(). For an object named less, the expression less(a, b) invokes that member, just as less.operator()(a, b) would. The final const means calling it does not require mutable access to the comparator object. This comparator owns no state. noexcept is appropriate here because comparing the two unsigned integers cannot throw.

A function object is a convenient way to package behavior with state when state is needed. It does not require virtual functions, inheritance, dynamic allocation, or a std::function wrapper. Our template will use its actual type. Lambda expressions will give us shorter ways to construct such objects, but first separate type parameters from ordinary function parameters.

This is compile-time selection, not a runtime test of which type an object contains. It also does not promise one emitted machine-code copy per specialization: optimization and linking can change emitted code without changing semantics.

The unconstrained example assumes that before(a, b) makes sense. Passing the integer 7 as before does not. Instead of discovering that only while instantiating the body, put the callable requirement at our real interface.

Read the definition from the inside out. The parameters after requires are names used to describe expressions; they do not construct a comparator or execute a comparison. They ask whether a call through a const comparator reference with two const element references is valid. The braces around before(a, b) introduce a compound requirement. The arrow constrains the expression's type; it is not a lambda return-type declaration here.

std::same_as<bool> requires the call expression to have type bool in this case. An integer three-way comparison result is deliberately rejected, as is a bool& result. We are not treating “negative means before” as truthiness: a negative and a positive integer would both convert to true. The concept is narrower than accepting every Boolean-convertible proxy. That narrowness makes this interface unambiguous without teaching a proxy-reference framework.

The requires expression evaluates to a compile-time Boolean when its template arguments are substituted. It does not run the function to see whether a particular answer is correct. The compound-requirement rules specify that the expression is unevaluated. We did not write a noexcept requirement, so a throwing comparator is allowed.

The name BooleanComparator describes only this callable shape. It does not claim that a comparator obeys ordering laws. a <= b has the required type but is unsuitable for a strict ordering. We will demonstrate that mismatch safely rather than pass it to a library sort whose requirements it violates.

Validate counts without overflowing first

The result needs space for n+m elements. Let M be the result vector's max_size(), measured in elements rather than bytes. Before computing the sum, require n \le M and m \le M-n:

n + m \le M \quad \Longleftrightarrow \quad m \le M-n \qquad \text{when } 0 \le n \le M.

This is a check on representable size, not a claim that an allocation of that size will succeed. For M=10, left length 7 leaves room for right length 3; right length 4 must be rejected. Check left length 11 before trying to subtract it from 10, because unsigned subtraction would wrap.

This linear scan does not establish that the comparator is a strict weak ordering. It cannot turn a cyclic predicate into an ordering, and its local checks do not prove global sortedness without the ordering laws. Nor can it check that a borrowed span denotes live memory. Those are separate obligations.

Implement the stable merge

Append this definition and the header's closing lines:

The first constraint is std::copy_constructible<T>. We read const T elements and construct output values from them, so move-only ownership is not supported by this interface. The library concept includes construction requirements and a semantic expectation that copying preserves the source's value; it does not promise that copying is cheap or nonthrowing. See copy_constructible. A different merge that consumes move-only inputs would need writable inputs and a different failure contract. It is not obtained by adding std::move to this read-only algorithm.

std::remove_cvref_t<T> is a type transformation from <type_traits>: it strips references and top-level const/volatile qualifiers. Requiring it to be the same type as T keeps the owning vector's element type unqualified. Pass Number, not const Number, as the template argument; read-only access already comes from span<const T>. This check does not cast away qualifiers or change an object. The remove_cvref definition is a reference for the type transformation.

Inside the function, using Size = typename std::vector<T>::size_type; names the vector's size type. This is another use of typename: it marks a dependent qualified name as a type. The name depends on T, unlike the already-known std::size_t. Use this explicit spelling rather than treating a nested type as a runtime member. C++20 can infer type names in some type-only contexts; that does not make typename a cast or a value declaration. See template name resolution.

There are three distinct preparation steps: check the total, validate the left/right sortedness, then reserve capacity. reserve(total) changes capacity, not size; no output elements exist yet. It reserves at least the requested capacity, not necessarily exactly that much. During the subsequent appends, size never exceeds the reserved total, so those appends do not reallocate the vector's element storage. Element copying can still allocate internally or throw for other element types. The relevant rules are in vector capacity.

The main loop uses before(right[j], left[i]). Only a strictly earlier right element wins. If the answer is false, left wins even when the elements are equivalent. The two suffix loops need no comparisons because each input is already sorted. Every index increment follows the corresponding successful push_back; no iteration consumes an element without first constructing its output value.

The loop invariant explains both the result and its bound

At the top of each merge iteration:

0 \le i \le n,\qquad 0 \le j \le m,\qquad \operatorname{size}(\text{result}) = i+j.

The result is the stable merge of exactly the consumed prefixes L[0,i) and R[0,j). The half-open notation means that the end index is excluded. Initially both prefixes and the result are empty. Choosing the earlier remaining head appends the next valid element; choosing left for equivalence preserves the left-before-right tie rule. Incrementing its index extends exactly that consumed prefix by one. Thus the invariant is preserved. When both suffixes are exhausted, i=n and j=m, and the result has exactly n+m elements.

For nonempty inputs, the main loop makes at most n+m-1 comparisons: each comparison consumes one element, and the loop must stop with at least one element left for a suffix when it has consumed n+m-1 elements. With either input empty it makes zero comparisons. Our validation adds \max(n-1,0)+\max(m-1,0) comparisons on successful inputs. If C is the number of main-loop comparisons, the total callback count is:

C_{\text{total}} = \max(n-1,0)+\max(m-1,0)+C.

For two inputs of length two, validation costs one call per input; the trace above costs three merge calls. The observed total must therefore be five, not three. Each of the four values is copied into the result exactly once. The algorithm has linear element work, but the time taken by a comparison or an element copy still matters; generic syntax does not make these operations constant-cost for every possible type.

Returning ownership does not require forwarding machinery

left[i] and right[j] are const lvalue expressions. Of the vector's push_back(const T&) and push_back(T&&) overloads, the copy-taking operation is the applicable one here. Casting one of those expressions with std::move would preserve its constness and would not create permission to consume a move-only owner. These overloads are specified in vector modifiers.

The local result is different: it is a non-const owner that the function is finished using. return result; allows construction directly in the caller's result object or the applicable move when elision is not performed. It does not return a reference to the local vector or copy a span pointing into it. Do not write return std::move(result); as a ritual; the ordinary spelling already enables the intended return behavior. See return statements.

Our comparator parameter is const Compare&, not a forwarding reference. The algorithm synchronously borrows it and invokes it as a const lvalue. A temporary such as NumericLess{} lives through that call. No comparator is stored for later execution. We do not need Compare&&, std::forward, type erasure, or a custom callable hierarchy merely to select one comparison operation.

Definition visibility and deduction are different questions

The header contains the complete template definitions so an including translation unit can instantiate them with its actual element and comparator types. Moving those definitions to a separately compiled .cpp and exposing only declarations would not, by itself, arrange instantiation for arbitrary caller-defined comparator types. Explicit instantiation can support a known finite set, but it is not our extensible interface. This is different from Chapter 1's non-template statistics function, whose one compiled definition could be linked from a library. See implicit instantiation.

Deduction happens earlier, when a call is matched to the function template. The merge's input parameters are std::span<const T>, not std::array<T,N>. In the C++20 interface used here, deduction does not first convert an arbitrary array or vector into a span in order to discover T. Use either of two clear call forms:

Call form What supplies the types
ordered_merge<Number>(left_array, right_array, less) T is explicit; array-to-span conversions then apply; Compare is deduced
ordered_merge(left_view, right_view, less) Both views already have type std::span<const Number>; types can be deduced

A span with mutable elements or a static extent can likewise be a different pattern from our const-element, dynamic-extent parameter. Avoid relying on a conversion to solve template deduction: use the explicit element type or construct the exact views. See function-call template deduction.

This is also a useful distinction in diagnosing overload selection. A call can fail because deduction could not match the parameter shape, because a constraint made a candidate nonviable, or because code inside a chosen specialization is invalid. These are not interchangeable “template errors.” Adding casts indiscriminately can hide the first symptom without fixing the interface.

Count calls with a lambda that borrows a counter

A lambda expression creates a callable object with an unnamed closure type. auto can name a variable of that type without knowing its spelling. Empty brackets [] mean no local captures; [&calls] means the closure borrows the local calls variable. The parameter list and body have their usual meanings. Without mutable, the ordinary lambda's call operator is const; mutating a referenced external counter does not mutate the closure's stored state. See closure types.

The lambda increments the referenced counter and always returns the ordinary a < b answer. The counter remains alive for the complete merge call. Its value is diagnostic state, not part of the ordering. This custom interface permits such diagnostics and will not roll them back on failure. It still requires consistent answers for the same unchanged values whenever comparisons return normally. const access to the closure is not a promise that it cannot affect anything reachable through references.

The final mutation sets the first element of one result to 99. Neither input nor the independently constructed second result changes. We have tested the ownership boundary, not just the sorted integer sequence. The check helper uses ordinary control flow, so the checks remain active with NDEBUG in a Release build.

For this fixture there are four logical output elements. With the 32-bit Number representation checked in the earlier foundations, their nominal payload is 4\times4=16 bytes. Allocated element capacity may be larger than four; allocator bookkeeping, stack objects, and input storage are separate. For these ordinary element types, capacity K corresponds to K\,\mathrm{sizeof}(T) bytes of element storage, not total process memory. Do not apply that formula to the specialized vector<bool> representation or to the extra allocations an owning element may make.

This in-memory result grows with the total input size. It does not enforce the engine's later memory budget or replace a streaming spill merge. Reusing its tie rule does not require reusing its materialization strategy.

Exercise empty, overlapping, and oversized inputs

Append the boundary checks:

An empty span has zero elements; neither validation nor a suffix loop indexes it. When just one input is empty, the other is copied in order. A large reserve or a special empty sentinel is unnecessary.

The overlap case uses two valid views into {1,2,3}: the first two elements and the suffix beginning at index one. The value 2 is intentionally in both inputs, so {1,2,2,3} is correct. The input owner is unchanged throughout the call. This would need a different contract for a merge that wrote back into either input.

The remaining checks use only scalar counts. maximum - 2 plus 2 is accepted; maximum plus 1 is rejected before addition; left count 11 against limit 10 is rejected before subtraction. We do not create a maximum-length span or try to allocate that many elements. These checks establish arithmetic behavior, not available-memory behavior. Chapter 4 already supplied a deterministic allocation-failure seam without requiring machine exhaustion.

The (void) casts explicitly discard a return value in paths where the expected observation is an exception. They do not suppress exceptions or change control flow. Each catch records that the expected exception occurred; an unexpected exception will reach main and fail the program.

Equivalent keys are not identical records

The duplicate integer 4 cannot reveal which input supplied it. Attach a small payload tag and compare only the key:

The nested braces initialize an array of small aggregates. Each Tagged contains a key and a character; no packed binary layout or disk encoding is implied. The lambda has no captures and reads only key. Thus {4,'b'} and {4,'y'} are equivalent under this comparator even though their tags differ.

For any comparator before, define equivalence by:

a \sim b \quad\Longleftrightarrow\quad \neg(a\prec b)\;\land\;\neg(b\prec a).

The symbol \neg means “not,” and \land means “and.” Equality of all fields is not required. Among the key-4 records, the merge must emit left tags b,c before right tags y,z, preserving each input's order. The complete tag order is therefore a,x,b,c,y,z.

A loop that instead chooses the left element only when before(left,right) is true will choose the right element on ties. Its numeric result can look perfect, but these tags reveal the lost left-before-right stability. This is why verifying only sorted keys is not enough to verify a merge contract.

In the later engine, key ordering and version precedence will be explicit parts of a record comparator. “Left wins ties” is not a substitute for defining which sequence number is newer. This exercise establishes stable mechanics without silently specifying the engine's version-resolution policy.

Captured state becomes part of the ordering contract

A captured value and a captured reference behave differently. Append this complete check:

Both closures are created when descending is true. The value capture stores that value in its closure. Changing the original variable to false does not change the stored copy, so copied_direction(4,1) remains true. The reference capture still refers to the original variable, so borrowed_direction(1,4) now returns true instead. See the lambda capture rules.

The ternary expression selects between a > b and a < b; its result is Boolean in either branch. The two descending inputs {4,1} and {4,2} match the copied comparator's direction, so their result is {4,4,2,1}. Changing comparator state after sorting inputs can make those inputs unsorted under the new state. Changing it during merging is worse: there is no single relation under which the loop can be reasoned about.

The borrowed-direction closure is used only while its referenced variable is alive. Returning it from this function would not extend that variable's lifetime. A captured pointer or span has the same limitation: copying a view into a closure does not copy or retain its underlying storage. Later tasks that outlive their submitting scope will need an explicit ownership policy.

Our concept requires const-callability. A lambda marked mutable ordinarily has a non-const call operator and would not satisfy that interface. There is no need to make this lambda mutable merely to increment the earlier referenced counter. Conversely, accepting a const-callable object is not a complete purity or lifetime check.

The laws the compiler cannot establish for you

A strict weak ordering is a relation that orders equivalence classes while allowing different objects to share a class. The required implications are:

Law Meaning
Irreflexivity No value comes before itself: \neg(a\prec a)
Asymmetry If a\prec b, then \neg(b\prec a)
Transitivity of order If a\prec b and b\prec c, then a\prec c
Transitivity of equivalence If a\sim b and b\sim c, then a\sim c

Asymmetry follows from irreflexivity and transitivity, but checking it separately produces a simpler two-value diagnostic. For numeric <, the equivalence classes are individual numeric values. For our tagged comparator, all records with the same key form one class regardless of tag.

The standard's strict_weak_order concept has semantic requirements beyond call-expression validity. The ability to instantiate a concept expression does not let the compiler prove those laws for arbitrary function bodies. The standard also distinguishes stable, equality-preserving behavior from merely callable expressions; see equality preservation. We use our explicitly syntactic BooleanComparator for the diagnostic tool, not a standard constrained algorithm whose semantic requirements are knowingly violated by the test predicates.

Consider three failures on values 0,1,2. The predicate a <= b says 0 <= 0, so irreflexivity fails immediately. A cycle saying 0 before 1, 1 before 2, and 2 before 0 has no self-edge or two-way edge, but 0 before 1 and 1 before 2 do not imply 0 before 2. Finally, “before only when the gap exceeds one” relates 0 to 2, but leaves 0 equivalent to 1 and 1 equivalent to 2. That fails transitivity of equivalence. Testing only self-comparisons would miss both of the latter defects.

A bounded sampler returns a counterexample, not a proof

Add the diagnostic result types to the executable:

The three indices identify positions in the sample, not copied payload values. For a one-value failure they are the same; for a two-value failure the unused third position repeats the second. std::optional<OrderViolation> will represent either an observed counterexample or absence of one.

The sampler below accepts at most eight values. For a sample of length s, it constructs a Boolean matrix B with logical shape [s,s]:

B_{ij} = \operatorname{before}(\text{values}[i],\text{values}[j]).

It stores that active matrix in a fixed 8\times8 nested array; unused cells are irrelevant. Building the matrix takes s^2 callback invocations. Checking triples takes at most s^3 iterations. This small cubic diagnostic belongs in the fixture, not in the merge's normal input path.

Append the complete sampler:

The size guard executes before any matrix indexing. less[i][j] first selects row i from the outer std::array, then element j from that row. The aggregate initialization {} starts every Boolean cell as false; the fill loop overwrites every cell that will be read. This is a fixed stack object, not vector<bool>.

The first scan checks the diagonal. The second looks for paired true entries across the diagonal. The triple loop checks the two transitivity implications: B[i][j] && B[j][k] && !B[i][k] is precisely an order counterexample. The local equivalent lambda derives equivalence from the already-filled matrix, so checking it makes no additional callback calls. Its borrowed less array outlives the lambda's use.

The sampler invokes no sorting, merging, binary search, or associative-container operation. Its own contract permits arbitrary defined Boolean answers; such answers are the data being inspected. A predicate may violate ordering laws without violating this sampler's preconditions. The predicate must still be safe to call on every pair in the sample, must not invalidate the sample, and may propagate an exception. No test harness can make an out-of-bounds predicate safe merely by calling it a comparator.

Passing the sampler means only that this table of observed answers contains no counterexample. It does not cover values outside the sample, prove stable answers on repeated calls, or verify a borrowed object's lifetime. An empty sample has no counterexample regardless of the predicate. Even on a nonempty sample, a time-varying predicate might happen to produce a consistent table once. Use sampling to find bugs, and use the relation's definition and domain to justify correctness.

Make each bad relation fail for a concrete reason

Append the law checks:

decltype(non_strict) names the type of that lambda variable without executing it. The compile-time assertion deliberately confirms that <= satisfies the syntactic concept. The assertion for int confirms that an integer is not a callable comparator. A static_assert checks a constant expression during compilation, unlike the runtime check calls that evaluate particular values.

For the cycle, the expected witness indices are (0,1,2): 0 precedes 1, 1 precedes 2, but 0 does not precede 2. For the gap relation, the same indices witness 0 ~ 1 and 1 ~ 2 but not 0 ~ 2. The expression a < b && b - a > 1 computes the subtraction only when a < b; it avoids unsigned wraparound in the gap calculation. The != predicate supplies a separate asymmetry failure on any two distinct sample values.

The optional is checked before its fields are accessed with ->. A returned witness is an ordinary owned value; it does not retain the sample or the comparator. The sample cap is tested with nine actual elements, not a made-up length. None of these four invalid predicates is passed to ordered_merge or to a standard ordering algorithm.

Throw after two output elements, before installing the result

An exception can come from validation, vector allocation, an element copy, or the comparator. Our algorithm never publishes its partial vector. Its local owner destroys any constructed elements and releases its storage during unwinding. Under the stated read-only input and value-copy contracts, input values remain unchanged. This says nothing about rolling back comparator counters, logging, or arbitrary external side effects.

The local candidate is initialized only after ordered_merge completes. On the injected failure, that initialization never completes, installed.swap is not reached, and the old vector retains both its contents and its element address. The old span remains valid. The callback's reference to calls remains valid through the exception and the catch. The counter intentionally remains five; it is outside the protected result state.

The retry uses a nonthrowing numeric comparator and commits by swapping two vectors with their ordinary standard allocators. This swap exchanges their storage without copying elements. Be precise about the old view: swap alone does not destroy the old payload. After this swap, old_view refers to the payload now owned by candidate, not to installed's new elements. When candidate is destroyed at function exit, that old view becomes unusable. The program does not access it afterward. This is the same resource reasoning as Chapter 4's replacement, but the old candidate's lifetime is visible here. See the container swap and reference-validity requirements.

We do not claim this is a rollback facility for arbitrary user code. A comparator that writes input elements through another alias violates the read-only contract. A copy constructor that steals from a const source violates the intended value-copy contract even if a declaration looks callable. An allocation failure or a well-behaved throwing copy still releases the local result through its vector owner; this chapter's runnable failure fixture specifically injects a comparator exception, not allocator failure.

What carries forward

Keep the complete ordered_merge.hpp, normal merge_demo.cpp, isolated non_callable.cpp, and appended foundation-05 target. The template returns an owned value from read-only borrowed inputs, uses one const-callable Boolean comparator consistently, validates representable counts and input order, and prefers the left input on equivalence. It does not retain inputs or comparator state. The ordering sampler remains a small diagnostic in the executable, not a mandatory cubic step in the merge.

The first five chapters now supply native builds, values and views, lifetime and RAII, moves, failure-safe preparation, and constrained generic interfaces. They do not yet supply a database. The next section of the roadmap starts the engine's record encodings and dependable file boundary. Its byte arithmetic, resource owner, and failure reporting will build on these foundations rather than hide those mechanisms behind a storage library.
