Chapter 8 — Indexed immutable tables

Part 3 — Verification and native checks

Continue from Part 2. The table header and implementation are complete. Now create the deterministic test program and independent Python byte checker, then append the CMake targets. Keep the earlier chapters' files unchanged. These checks belong to Chapter 8's single 5.0-hour implementation allocation, not an additional allocation.

The tests separate four questions: are bytes encoded as specified, does a seek return the correct version, do corrupt inputs stay within bounded reads and allocations, and does failure leave a file or cursor in its documented state? A sanitizer can help with memory mistakes; it cannot answer all four questions.

Build a deterministic file backend large enough for tables

Create tests/table.cpp. The helpers throw on failure in both Debug and Release. expect_error catches only the named exception type; a different failure must escape rather than accidentally satisfy the test.

The fixture owns a preallocated 512 KiB byte array through a vector. This test-only allocation is not engine storage and is never used by the native implementation. install copies an image only while no file is open. image deliberately copies the used prefix so corruption tests can own and edit it independently.

The virtual operations below allocate nothing. They can therefore implement the Chapter 6 noexcept backend interface without hiding allocation failures inside an exception-to-error adapter. Every offset is compared with a size before it is converted to size_t and used for indexing.

accepted counts successfully written bytes; fail_after makes a later call return EIO. A successful partial call does not also return an error, matching the earlier Transfer contract. transfer_limit=3 forces the real File loops to assemble frames across many calls. One injected EINTR checks retry without counting bytes that were not transferred. The fixture must be declared before its owning File or reader so it outlives their destructor calls.

Construct the eight-version trace explicitly

The three input batches create this sorted history:

User key Versions, newest first
events 10 erase at 3; put amount 22 at 2; put amount 10 at 1
events 20 put amount 23 at 3; put amount 20 at 1
events 30 put amount 30 at 2
accounts 100 put region 7 at 3; put region 1 at 1

There are eight versions, four distinct user keys, and three latest live rows because events 10 is deleted. The table builder stores all eight, including the tombstone. At a 64-byte data payload limit each occupies a separate block. We will also test a larger block size because one-row blocks can conceal a wrong sparse-search implementation.

Freeze the bit conventions, then measure false positives

The checksum test has three independent expectations: empty input, a standard fixed message, and incremental versus concatenated processing. The Bloom test pins its byte-level format with events key 42, checks every one of 100 inserted keys, and prints the result of 10,000 known-absent probes. The exact printed positive count is not a statistical acceptance condition. A filter returning true for an absent key is permitted; returning false for an inserted key is not.

For this deterministic implementation the observed sample is 97 positives out of 10,000, or 0.97%. That is an observation about this fixture, not a hardware speed measurement, universal false-positive rate, or guarantee matching the idealized 0.76% calculation. Enlarging the filter can improve selectivity without changing answers; clearing bits after inserting a key can break correctness.

Test visibility at block boundaries and retain an owned answer

The three visibility checks for events 10 must each read exactly one data frame. The first returns an erase, and the other two return different put versions. Visibility zero finds no qualifying version; missing keys before, between, and after the stored range exercise different search boundaries. The lower_bound gap check bypasses the Bloom filter entirely, so a negative filter cannot conceal a broken directory search.

The two simultaneous cursors prove that one cursor's advance does not overwrite the other's block. The injected next-read failure makes the advancing cursor terminal. The owning result retained survives both the cursor used by find and the reader's entire scope; decoding it afterward would expose a returned borrow into a destroyed block buffer.

The empty fixture finishes at 120 bytes with no data frames. Finishing twice is an error; observing end and advancing end are normal operations. verify_all works without special caller handling for an empty table.

Compare with a structurally different reference

These test helpers copy complete entry values and express ordering with a tuple, not with the production InternalLess:

For an unsigned sequence s, UINT64_MAX - s reverses its order without a signed conversion. Tuple comparison then gives relation ascending, primary ascending, and sequence descending. The full-range std::equal overload compares both length and bytes; equal prefixes with different lengths do not count as equal rows.

The next fixture creates 200 batches and 600 versions. One event key family repeats, one creates distinct keys, and the account keys repeat independently. Some updates are tombstones. This makes the test sensitive to relation tags, long histories, keys inside blocks, and the numeric 255/256 boundary.

Continue check_oracle after writing the table. The point-reference path scans all expected versions and chooses the largest sequence not exceeding visibility. That is intentionally different from the production directory and lower-bound algorithm, so they are less likely to share the same indexing defect.

There are 2\times320\times6=3840 point queries: two relations, 320 primary keys, and six visibility values. The complete ordered stream must also match all 600 reference entries. A typical run here uses 122 blocks, a metadata vector capacity of 6,148 bytes, and a cursor frame capacity of 268 bytes. Those capacities are observations of the tested standard library, not mandated vector growth behavior. The code does not time these runs or claim performance on the M4.

Corrupt semantics even when the CRC still matches

A checksum-only test can be satisfied by a parser that does no semantic validation. We need both damaged CRCs and deliberately repaired CRCs around invalid content. The repair helper is test code, not a repair policy for a database file.

reject_image requires the reader to close its adopted file on every exception. It calls verify_all because a corruption in an unvisited data block need not be found by opening alone. The native reader path remains unchanged; only its backend supplies bytes from memory.

The lambda captures the small fixture by reference and creates a fresh owned copy for each experiment. It changes one field, optionally recomputes the containing CRC, and demands rejection. This keeps experiments independent: an early checksum failure cannot mask a later malformed-length case left over from another test. The large frame length is read only into the bounded buffer; a wrong tag cannot be accepted merely because the checksum was recomputed.

Continue check_corruption with excessive metadata, a wrong total count, and a logically invalid filter:

The zeroed, recomputed filter shows the lazy-verification boundary explicitly: find skips the data and returns absent, but verify_all detects a stored key that the filter rejects. This is a deliberately forged logical inconsistency, not a valid table that legitimately has a Bloom false negative.

Now set extra bits instead. An all-one filter is semantically safe, though useless for pruning. Its positive answer must still be followed by a real search. Then try every incomplete prefix of the valid 970-byte fixture.

All 970 proper prefixes are incomplete tables and must be rejected. Appending one trailing byte must also fail, even when the caller passes the original length. Unlike a future log-recovery rule, this table reader does not ignore a torn last block and return the preceding rows as a complete file. A standalone table requires its complete footer and consistent extents.

Failure does not mean that the output stayed empty

Start the write-failure tests:

With failure after 34 accepted bytes, the 24-byte table header is complete, as is the first frame's eight-byte header, and two payload bytes have arrived. That is an observable partial effect. The builder's failure state prevents finish from reporting success; destruction frees memory but does not erase those file bytes. The last-footer failure similarly produces no usable result. Short transfers without an actual error must instead produce a byte-identical 970-byte file.

Continue with duplicate keys, resource caps, and existing-file protection:

The block-cap and file-cap configurations are valid but too small for this nonempty fixture; they must throw length_error, not silently drop rows or grow without limit. A nonempty file is rejected before its bytes change. The builder is intended for newly created outputs, not an in-place replacement protocol.

Exercise an actual file and clean up only what this call created

native_fixture uses File::open(create_new) rather than trusting the emptiness probe alone. The created flag is set only after exclusive creation succeeds. On failure, local file/reader owners unwind before the outer handler attempts to remove the temporary path. A collision with an existing file must not remove it.

The nonthrowing std::filesystem::remove overload accepts an error_code output. We report a cleanup failure separately and rethrow the original problem. This helper assumes its caller supplied an exclusively owned temporary path; it is not a safe deletion protocol against another actor replacing that pathname concurrently. The Python runner below supplies such a private temporary directory.

The explicit file synchronization and checked close are observed operations, not a claim about a power-cut experiment. A successful table is retained for the Python decoder. A failure after creation removes only this fixture output when cleanup succeeds. No manifest, rename sequence, directory synchronization, or log installation is being performed.

Finish tests/table.cpp with its entry point:

The normal test sequence uses the deterministic backend. --fixture PATH selects the real positional-I/O implementation. Both modes convert a standard exception into a nonzero exit code and a visible diagnostic, including under NDEBUG.

Inspect native bytes with a separate implementation

Create scripts/check_table_fixture.py. It uses Python only as an independent fixture checker: the table construction, indexing, searching, checksums, and filter implementation under test remain C++. Python's standard zlib.crc32 provides a separate CRC implementation; struct decodes explicit little-endian fields without calling our C++ helpers. The collection type annotations require Python 3.9 or newer; a compatible maintained Python 3 installation is sufficient.

Python integers do not naturally wrap at 64 bits. Mask after each multiplication in mix and the FNV loop. For positions we can use unbounded start + probe * step and then modulo the power-of-two bit count; Part 1 showed why this yields the same result as the C++ unsigned wrap. Omitting masks from the mixer itself would be a different hash, not “higher precision.”

This checker is intentionally for the fixed tiny fixture, not a second general storage engine. It first requires exactly 970 bytes and the expected header and metadata choices. It independently checks every extent and CRC before decoding its one-entry data blocks.

Continue the same verify function. Construct the expected row encodings directly with struct.pack and compare the complete ordered history, not just a few selected fields. Rebuild the filter from the set of expected user keys to check its exact bytes as well.

The script can check an existing fixture path or invoke the executable itself. The latter mode gives CTest a private output directory, then attempts exclusive creation again and confirms that the original bytes survived the rejection.

A codec bug can sometimes make a writer and its matching reader agree with each other. Comparing their actual output with separately constructed bytes makes that symmetry harder to hide. This is why the fixture checks its eight complete rows, not only the file length or one returned amount.

No invalid pointer is required for this bug: it simply skips a block whose first key precedes the target but whose last key does not. A memory sanitizer cannot prove the indexing contract.

Check memory behavior separately from logical correctness

For a focused instrumented run, compile the complete dependencies, not only the test translation unit:

Use the selected compatible clang++, not an unrelated architecture or toolchain just to match a version number. The normal deterministic tests and native fixture passed AddressSanitizer and UndefinedBehaviorSanitizer in the Linux environment; Linux leak detection was enabled there. Supported sanitizer combinations and leak detection differ by platform, so do not infer target support or target results from that authoring run.

Symptom Likely cause and concrete check
A new table fails its header CRC Check version/reserved bytes and CRC coverage [0,20); do not include the CRC in itself.
Some old versions disappear only with larger blocks Check the sparse search's last key and descending sequence comparison; run the 3,840-query oracle.
A filter rejects a tombstone-only key Ensure erase entries call bloom_add, and hash the user key, not kind or sequence.
Reopening fails only after writing several blocks Compare directory offset/complete frame length with actual emitted bytes; remember the 12-byte frame overhead.
entry() after an I/O error throws The cursor is intentionally terminal. Do not keep using a pre-error borrowed row or silently retry it.
Correct results accompany growing memory Count readers and live cursors and their vector capacities; one-block-per-cursor is not a global admission policy.

Two small variations that change understanding

First change the bulk fixture's block payload size from 256 to 512, leaving the 600-version oracle unchanged. Predict fewer directory entries, a larger cursor buffer, and identical query answers. Run it and record the actual block count and capacities. Do not change the tiny native fixture's options: its 970-byte oracle intentionally fixes a format example. Restore the bulk size afterward so the published sample output remains easy to compare.

Next change only the standalone Bloom experiment's 128-byte filter to 256 bytes. All inserted keys must still pass; the absent-probe result is a new observation, not a reason to hard-code a percentage. Explain why more versions of an already inserted user key would not have the same effect as more distinct keys. Restore the original size before the next chapter. These variations belong within the chapter's testing allocation, not an extra benchmark project.

You now have independently readable immutable tables, a bounded streaming writer, a sparse numeric index, a portable implemented checksum/filter, and explicit cursor/result ownership. Nothing yet shares cached blocks, admits work against a global byte budget, or installs these files in a recoverable database. Chapter 9 adds memory budgets and a pinned block cache on top of these finite buffers and lifetimes; the table format and standalone checks remain the foundation.
