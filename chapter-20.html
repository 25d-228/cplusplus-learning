Chapter 20 — Concurrent readers, ingestion, and maintenance

Part 1 — Share lifetimes, not mutable readers

A query can keep a valid snapshot while the writer commits another batch. That alone does not make the database concurrent. A disk reader updates counters and cache recency while it reads. The final snapshot owner might release an arena on a query worker. A compaction may finish after the writer has installed a new log. Each of these operations touches a different kind of shared state.

This chapter connects the real writer, query executor, and maintenance path. An old query will retain sequence 1. While a compaction of the prefix through sequence 2 is paused, the writer will commit sequence 3 and rotate its log. Installation must preserve that newer log set. A fresh query must see sequence 3, not an accidental combination of the two snapshots.

Learning objectives Publish one coherent source set; distinguish immutable nodes from mutable reader bookkeeping; keep final-owner cleanup safe on another thread; build maintenance output without the writer mutex; revalidate selected inputs rather than rejecting every changed epoch; and stop a backpressured writer without losing acknowledged batches.

Prerequisites: the complete engine through Chapter 19, including Chapter 18's synchronization exercises. In particular, keep Chapter 11's manifest installation, Chapter 12's owning views, Chapter 13's prefix compaction and retirement, and Chapter 19's query admission and cancellation contracts. The standalone Database remains a synchronous API; the new Engine is its concurrent coordinator, not an instruction to call old methods from arbitrary threads.

Implementation: 3.5 hours across all three parts. Preserve the roadmap split: publication/locking 1.25 hours; maintenance/backpressure 1.0; controlled overlap and shutdown tests 1.25. Reading is separate. Record actual implementation time rather than treating these estimates as minimum durations.

Choose an owner for every mutation

A shared ownership count answers when an object may die. It does not serialize operations on that object. The standard's shared-pointer rules concern the pointer/control machinery, not a lock around the pointee; see shared ownership. We therefore retain immutable source objects but do not share mutable disk readers across query workers.

State Ownership and synchronization in this chapter
Database, current WALs, manifest, namespace creation and retirement One Engine mutex; one serialized writer
Frozen memtable nodes and encoded payloads Immutable after publication; owning parent view keeps storage alive
Query disk readers, cache recency, pins, and read counters Private to one query worker; no concurrent calls on the same reader/cache
Maintenance disk readers, cache, and builder buffers Private to the maintenance job while it builds
Shared storage allocation ledger Internal budget mutex, including final-owner deallocation
Snapshot-retention registry Internal registry mutex; new snapshot admission also serialized by the engine
Maintenance results, failure, and writer-wait counts Engine mutex; returned as value snapshots
Stop signal observed during unlocked work Atomic Boolean; does not publish the manifest

The original cache's pinned-bypass and admission algorithm is unchanged. There is no duplicate-admission race within a cache, because one worker owns it. Two queries may cache the same disk block twice in different budgets. That is a real efficiency cost, not a race to resolve with an uncharged shared entry. Parallelism is obtained by isolating mutable readers, not by locking a global cache around a disk read.

The engine mutex still covers WAL synchronization, manifest installation, and bounded namespace cleanup. These calls can be slow. It does not cover bulk table scanning, compaction encoding, output verification, query sorting, or CSV execution. This is not a lock-free writer or a claim of bounded commit latency.

Repair the ledger before owners cross threads

Suppose a query is the last owner of an old arena. Its worker releases the arena while the writer reserves space for a new batch. The old Chapter 9 counters would be read and written concurrently even though neither thread touches the same payload. Protect the ledger, not the payload.

Let r be reserved bytes, a be allocated bytes, and L be the immutable budget limit. A reservation for n bytes succeeds only when

0 \le r+a \le L,\qquad n \le L-(r+a).

The subtraction form avoids overflowing an unchecked sum with n. Checking and increasing r must occur under one lock. For example, with L=1000, r=100, and a=700, two simultaneous reservations of 150 cannot both pass. The first produces (r,a)=(250,700); the second sees only 50 free bytes.

Apply the header changes. mutable permits a const observer to acquire its bookkeeping mutex without treating the observation as a logical value change. limit_ never changes after construction, so limit() needs no ledger lock.

Replace src/memory/budget.cpp with the following two blocks. Each lease still has exactly one owner. Protecting the budget does not permit two threads to move or reset the same lease object simultaneously.

A committed allocation transfers bytes from r to a without changing r+a. The native allocation remains outside the ledger lock: its reservation already prevents another thread from spending the same bytes. Allocation failure unwinds the lease and returns the reservation.

reserve must not call the newly locking used() while already holding the same nonrecursive mutex. It reads the protected fields directly. The observer methods acquire their own lock only when called from outside that critical section. Mutex acquisition after an earlier unlock provides the synchronization we need; this is the rule in the mutex requirements, not a property of std::size_t.

The failure countdown is also serialized. In a concurrent run, “allocation 7” means the seventh admitted call reaching that countdown, not a deterministic choice of thread. Use single-threaded fault injection or controlled gates when an exact failing operation matters.

The cleanup methods retain their nonthrowing contracts. An exceptional failure to acquire their internal mutex is an unrecoverable invariant/runtime failure, not an allocation rejection to retry. Ordinary budget exhaustion still throws before the requested allocation. Budget destruction requires all leases and allocations gone and no concurrent callers; a mutex does not extend its own lifetime.

A final snapshot release is a registry mutation

Snapshot capture checks capacity and later activates a state. In between, it may prepare a replacement writer. We do not hold the registry mutex over that I/O. Instead, the engine mutex serializes all new admissions, while internal registry locking allows concurrent releases. A release can only reduce pressure between check and activation; it cannot consume an unreserved slot.

Add the forward declarations, friendships, registry mutex, and private isolation entry point. Friendship grants access to these explicitly cooperating classes; it is not synchronization and does not make the methods public.

The registry's slot_for helper remains nonlocking and private: its callers already hold that mutex. A collector acquires the engine mutex, checks the registry briefly, then removes only an unreferenced name. A query releasing its last parent takes only the registry and budget locks; it never tries to acquire the engine mutex. This direction is important to avoiding a lock cycle.

A C++ lifetime ending can conflict with accesses to that storage; retaining the last source owner is therefore part of the concurrency proof, not merely a memory-leak concern. The relevant definition is data races and lifetime.

Share frozen nodes; reopen mutable readers

Chapter 19's immutable fixture required every source on disk. Live capture may contain a recently sealed memtable. Its nodes, towers, and payloads are now immutable: rotation installed a different active writer before the view escaped. We can share that generation without copying all its rows.

Replace ReadView::isolate_disk with this delegating wrapper. The frozen fixture retains its stricter disk-only contract; the live engine will opt into frozen memory explicitly.

Add the next function before the final namespace closing brace in the same file. It first validates the complete parent, then allocates one private read context. Disk sources reopen by stable file identity and get private cache IDs. Memory sources copy only an owning source handle. Their mutable WAL I/O and writer methods are never called through this read path.

The parent state remains anchored inside IsolatedRead. That parent protects file names during all read-only opens and protects memory until every cursor is gone. A failed third reader construction destroys the first two private readers and releases the parent normally. Nothing is registered twice in the storage retention registry.

The shared Directory object has a deliberately narrow concurrent use here: its read-only open branch uses the stable directory descriptor and does not change its inventory. Creation, replacement, enumeration, and deletion remain coordinated. This is a property of our Chapter 11 implementation, not permission to call every Directory method concurrently.

A copied ReadView still shares its private reader state. Give one isolated view to one query worker. Do not share that same view between independently running queries; capture another isolated view for the other query instead.

Admit for a stable upper bound

An executor must know its descriptor requirement before it captures a live snapshot. Sampling “currently two source files” at submission is unsafe: the writer can create additional generations before admission. Introduce a small provider interface whose source_count() means a lifetime-stable upper bound. The fixed fixture can return its exact immutable count. The live engine will return read_detail::max_sources, which is 20.

virtual and override use the same interface mechanism as the file backend in Chapter 6. The virtual destructor permits ownership through the base type. The interface abstracts the capture boundary, not indexing, query algorithms, or storage implementation.

The executor keeps the provider owner rather than an unowned reference. A new captured checkpoint occurs only after the immutable view and its sequence exist; it gives our tests a precise old-snapshot pause without sleeps. All previous checkpoints and admission behavior remain in force.

For the fixture, each sort declares three descriptors. Add the provider bound and Chapter 19's three other query descriptors:

F_q=20+3+3+3=29.

The test admits two queries at once, so its executor allowance is 2F_q=58. These are software allowances, not 58 preopened kernel descriptors. Keeping the bound conservative prevents later capture from exceeding what admission promised. Existing FrozenInputs tests still use their smaller exact bound.

Reserve a separate route for maintenance

Do not make the maintenance worker acquire a query permit while every query permit belongs to work waiting for storage progress. Give storage, maintenance workspaces, and admitted queries separate budgets. Let S be the storage limit, M the maintenance limit, P the query pool, and C_s,C_m,C_i their current charged bytes. Then our tracked dynamic allocations obey

C_s\le S,\qquad C_m\le M,\qquad \sum_i C_i\le P, \qquad C_s+C_m+\sum_i C_i\le S+M+P.

The test uses S=64 MiB, M=2 MiB, and P=4 MiB: a 70 MiB aggregate charged ceiling, not a claim that 70 MiB is resident. Thread stacks, allocator overhead, fixed controller objects, library runtime memory, and the operating system's file cache are not made into an RSS cap by this equation. Resident table-reader metadata belongs to storage; temporary builders and private maintenance readers belong to maintenance.

For at most 16 private input readers and O precreated output files, reserve

F_m=16+O+1

maintenance descriptors. The final 1 covers authority installation. An output writer closes before its replacement reader opens, so they do not add two slots for the same output. With O=4, the test requires 21. Existing storage readers, WALs, the directory lock, and query allowances are additional. Leave operating- system headroom; an allowance cannot prevent an external descriptor shortage.

Separate pools prevent queries from consuming maintenance's allowance. They do not guarantee progress with an undersized storage budget, permanent I/O failure, or snapshots retained forever. Those conditions must fail visibly or reject admission, not silently allocate beyond the configured bound.

Separate preparation, build, and installation

A MaintenanceJob has three ownership phases. Construction runs under the engine mutex: capture input identities, retain immutable sources, reserve output IDs, and exclusively create a bounded set of output names. build runs without that mutex. install reacquires it and validates that the selected inputs are still the authoritative prefix or oldest sealed log.

Only one split job may exist in an engine. Collection is forbidden until that job is destroyed, including after failure or stale rejection. This rule protects its selected input names and precreated output names without pretending they are already user snapshots or manifest dependencies.

Add the narrowly scoped database friendship:

Create the complete job header. database_ is an identity check, not a pointer that the unlocked build may dereference. context_ and workspace_ are real owners. Fixed arrays bound output metadata even before any file is written. Phase prevents a failed or consumed job from being rebuilt or installed twice.

Start the source file with preparation. Flush retains the oldest sealed memtable. Compaction selects a complete table prefix, including every existing base partition. The selection rule is the same tombstone-elision proof as Chapter 13; we are changing when the work runs, not weakening its coverage.

An output creation failure can leave earlier newly created names behind. Their IDs have already advanced and must not be reused. Ordinary member cleanup closes the descriptors; later collection or reopening handles the nonauthoritative names. The existing manifest never references an incomplete output merely because its pathname exists.

The private compaction State is intentionally not activated in user retention. The coordinator's no-collection rule is therefore essential. A second arbitrary collector thread would violate this protocol even though all shared pointers were individually valid.

Validate each output before it can become authoritative

The output transfer counter is computed from the job's file owners. A closed File preserves its byte counters, so a partial output remains observable after failure. Completed-file bytes and installed authority remain separate facts.

An output is synchronized and closed, then reopened through a new reader with no shared cache. Its resident metadata is charged to the storage budget; its builder has already been destroyed. Full verification and a semantic scan check the interval, row kind, key ordering, and base-partition boundaries before that reader is placed in the prepared owner array.

For a flushed interval (b,e], its minimum sequence must be b+1 and its maximum must be e. For a compacted base through e, surviving rows may have older sequences, but each must be a put with 0<s\le e and strictly increasing user keys. An entirely deleted prefix produces no output reader; the manifest still records its coverage boundary in Part 2.

output_files counts verified prepared files here. output_write_bytes includes partial writes as well. merge_read_bytes below counts private input-reader traffic, including their metadata reads; it does not count output verification reads, directory metadata, WAL traffic, or physical device amplification. Do not label it total engine I/O.

Reuse the ordered scans and bounded builder

Flush has no sorting step. The frozen skip list already supplies the required internal-key order. Its cancellation boundary occurs between rows; the file layer also checks at block I/O boundaries. A hook may throw after a row to test failure cleanup, but it must not reenter the engine.

Compaction reopens private disk readers and uses the existing bounded heap merge. One output builder exists at a time. can_append includes directory, Bloom, and footer costs from Chapter 13; it is not a test of row bytes alone.

The local ReadTraffic object is a small scope guard: its destructor collects counters on both success and exception. Its source span borrows from local, which was constructed first and therefore outlives the guard. The cursor is constructed last and dies first. No heap allocation is needed to record these fixed-size observations.

If D is the total output-byte allowance and d the completed bytes so far, the next file has limit \min(L_f,D-d), where L_f is its individual file cap. Each completed file fits the remaining allowance, so the subtraction is valid. If even one row cannot fit, fail; do not create an infinite series of empty runs.

Complete the build wrapper. It closes precreated but unused writers, leaving their names explicitly nonauthoritative. Its state becomes built only after the final test hook returns. Append the installation function in Part 2 before closing this namespace; this source file is intentionally continued there.

At this boundary the output is valid, but the database still serves its original source set. The writer may already have advanced. We have prepared a candidate, not acquired permission to overwrite newer history.
