Chapter 23 — Profiling, optimization, and the final demonstration

Part 2 — Remove work without changing the answer

Part 1 makes equivalent query shapes observable. This part adds two independent controls: optional instrumentation to locate checksum work, and an optimized checksum recurrence that preserves every format byte. It then supplies the measurement harness. Keep the Part 1 files and all Chapter 22 prerequisites.

Start with a hypothesis, not a preferred speedup

Every table frame and spill frame uses the same CRC-32 routine. With bounded blocks, a query repeatedly validates existing frames, creates new ones, and verifies intermediate replacements. The bitwise routine performs eight state updates per input byte. This makes it a plausible CPU cost, not proof that it is the dominant cost on every workload.

On a native Mac with Instruments available, use a RelWithDebInfo build, select the Time Profiler template, choose strata-measure as the executable, and supply the same database, temporary directory, output directory, variant, and numeric arguments used below. Record several repetitions. Inspect the interval covering query work, not only program launch. Use the call tree to distinguish a function's own work from work attributed through its callees. A CPU profile alone does not count exact invocations or explain elapsed time spent blocked. Apple's execution-frequency tutorial explicitly separates those questions.

For command-line discovery, inspect the installed tools rather than assuming a particular Xcode release or an Instruments installation:

The Apple command-line reference identifies xctrace as the trace recording/export tool and directs users to its installed manual. The course's ordinary command-line build does not require installing full Xcode solely to reproduce a screenshot. The scoped timer below provides an additional reproducible, narrower measurement.

On Linux, an available GNU gprofng can sample the same optimized executable:

The GNU manual explains sampling, inclusive/exclusive metrics, and these commands. Check the experiment header before interpreting its function table. In the Linux check accompanying this chapter, the collector warned that its interval timer changed to zero. Its displayed percentages were not accepted as reliable attribution. A large number in a profiler window does not override the profiler's own warning.

Use separate observations for separate questions: sampling for likely CPU paths; scoped timings for a bounded region; allocation counters for ownership costs; file-transfer counters for I/O volume; and waiting/rendezvous state for resource admission or locks. A large elapsed-minus-CPU gap is a clue, not proof of disk waiting: scheduling and unrelated contention can also create it.

Make instrumentation optional and thread-local

Add these declarations to table.hpp. CrcProfile is a copyable observation, not an owning resource. Reset and read it on the thread running the measured synchronous query. No cross-thread aggregation is promised.

The following exact table.cpp patch adds the profiling helper and the selectable CRC implementation. Read its three mechanisms separately.

First, thread_local gives each calling thread its own counters. It does not make a returned snapshot a live cross-thread view. CrcTimer records a steady_clock point at entry and updates saturating counters at destruction. No allocation or stream output occurs in the timed path. The saturation flag turns an unusable observation into an explicit failure in the driver.

Second, make_crc_table is a constexpr function: the initialized array can be computed during translation. Each entry applies the old eight-step recurrence to one possible byte. The array occupies 256\times4=1024 read-only data bytes; it is not charged heap storage. [[maybe_unused]] avoids a warning when the baseline build does not reference it. This attribute does not remove correctness checks or change object lifetime.

Third, preprocessing selects one recurrence. STRATA_CRC32_TABLE=0 retains the original eight bit steps; =1 uses one table lookup per byte. STRATA_PROFILE_CRC=0 removes the clock/counter path. Part 3's CMake options define both macros as numeric 0 or 1. These controls are independent.

A scope timer measures elapsed time including any descheduling during the scope. Clock reads and counter updates have costs. Consequently its sum is not an exact CPU-time partition, and an instrumented binary is not one of the unprofiled timing-comparison builds. The harness rejects an instrumented record. The code uses one start/end pair per CRC call, not per input byte.

Derive the table recurrence

Let s be the current unsigned 32-bit internal state, b the next input byte, and P=\texttt{0xedb88320} the reflected polynomial already used by the file format. One bit update is

f(x)=(x\mathbin{\gg}1)\mathbin{\oplus} \begin{cases} P,&x\mathbin{\&}1=1,\\ 0,&x\mathbin{\&}1=0. \end{cases}

Here \gg is logical right shift, \oplus is bitwise exclusive-or, and \& is bitwise and. The old byte step is f^8(s\oplus b), where f^8 means applying f eight times. Define a 256-entry array by T[i]=f^8(i) for byte values 0\le i<256.

Write s\oplus b=(s\gg8)2^8+i, with i=(s\oplus b)\mathbin{\&}255. During those eight shifts, the original upper 24 bits move down eight positions. Their original low eight bits are zero, so they cause no feedback on these first eight steps. The feedback from i is exactly T[i]. Exclusive-or is linear over these bit operations, giving

s'=(s\gg8)\oplus T[(s\oplus b)\mathbin{\&}255].

For an initially empty checksum, the internal state is 0xffffffff. The first ASCII byte of "123456789" is 0x31. Its index is 0xce, and the generated entry is T[0xce] = 0x7cdcefb7. Thus

The initial and final xor remain 0xffffffff. A caller passing the previous returned checksum therefore resumes the same internal state. Empty inputs and split-buffer chaining are unchanged. CRC still detects certain accidental changes; it is neither authentication nor a repair mechanism. Do not remove checksums, persistence barriers, or required-file validation to obtain a faster number.

Define the experiment before running variants

Create scripts/measure.py. The workload is Chapter 21's documented periodic recipe: by default 20,000 events, 257 accounts, ten days, eight regions, seed 23, 60 percent hot-account lanes, and 256 operations per input batch. Query days are [2,7). The generator also writes a delta, but the timed comparison loads only the base. Final-demo scenarios exercise the delta separately.

With chunk capacity C=512, the first sort receives 10,000 selected rows in the early plans and 20,000 in the late plan. Their initial run counts are

R_{\mathrm{early}}=\lceil10000/512\rceil=20,\qquad R_{\mathrm{late}}=\lceil20000/512\rceil=40.

For fan-in four, the materialized passes reduce 20\to5\to2 or 40\to10\to3. The remaining two or three runs stream into the next operator. Both sorts therefore genuinely spill, even though this is a deliberately small reproducible experiment. The account stream exceeds its configured batch capacity.

The run catalog still allows at most 128 initial runs. The harness checks the unfiltered row count against 128C because the late plan sorts every event. This bound is necessary, not sufficient: memory, disk, source metadata, and compaction limits can reject a configuration earlier. The executable's maximum chunk parameter does not promise that every allowed parameter fits its budget.

The first block imports the independent formula and defines the empirical nearest-rank percentile. For n sorted observations and integer percentile p,

k=\lceil pn/100\rceil,\qquad Q_p=x_{k-1}.

The array index is zero-based. With five observations, the empirical 95th percentile is simply the maximum because \lceil4.75\rceil=5. It is not evidence of a stable production tail. All summaries retain the sample count.

Capture actual build settings and a representative compilation command. The experiment requires CMAKE_EXPORT_COMPILE_COMMANDS=ON; a directory name such as release is not evidence of its flags. Equivalent compilers are allowed, but two builds compared for one code change should otherwise use matching flags.

Run commands as argument arrays without a shell. Time the parent-observed process interval separately from the query's internal interval. Keep stdout, stderr, return code, and argument values when a command fails; never continue as though a missing answer were a fast query. Python's subprocess.run contract describes timeout handling and reaping of the immediate child. The timeout is a diagnostic bound, not an asynchronous job service or a performance target.

Parse exactly one JSON line. A profiling run with multiple repetitions is not silently averaged here. Reject failed charge invariants and instrumentation-enabled records before they enter a comparison. RSS conversion is an explicit parameter; null normalized bytes with rss_unit="raw" means the unit was not established, not zero memory.

The experiment generates, loads/settles, explicitly compacts, and reopens in separate commands. load-and-settle includes parsing, WAL synchronization, concurrent maintenance, settlement, shutdown, and process overhead. Its throughput is a named end-to-end ingestion measure, not the speed of one memtable loop. The explicit compaction command prints that process's job traffic. Earlier loading may have performed several jobs; its last_job counters are not their sum and must not be advertised as total write amplification.

Warmup and measured rounds both execute all build/variant pairs. A seeded shuffle changes their order per round rather than always giving the same variant the warmest cache. Each child starts with a fresh private engine cache. The operating-system cache is not cleared: call these repeated, OS-cache-uncontrolled runs, not cold-device tests. Do not use privileged cache-dropping commands as a hidden prerequisite.

Answer comparison and spill-directory inspection happen after the timed child returns. Every sample must have the expected sequence and group count, no residual spill names, and nonzero initial runs in both sorts. Reducing a filter until the whole answer fits in memory would no longer satisfy this experiment's stated purpose.

The report is saved incrementally with complete=false. A later failure retains prior observations but produces no success claim. A report is ordinary measurement data, not a publication journal. The summary below excludes every warmup.

Finish argument validation and the entry point. A fresh output directory is required so a rerun cannot overwrite its prior evidence or a completed database. perf_counter_ns avoids floating subtraction of large absolute timestamps; it does not guarantee nanosecond physical resolution. The Python clock documentation also supplies the queried implementation and resolution fields recorded here.

The report contains both process elapsed time and internal query elapsed time. Subtracting the latter from the former does not isolate a single subsystem: startup, opening, shutdown, JSON output, scheduling, and parent overhead remain. Use the separately measured open_seconds to discuss reopening, while keeping its verification work distinct from crash recovery correctness.
