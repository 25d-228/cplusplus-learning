Chapter 20 — Concurrent readers, ingestion, and maintenance

Part 3 — Force publication, failure, and shutdown boundaries

We will not infer overlap from a fast wall-clock result. A gate will hold the maintenance worker outside the writer mutex, and the writer must commit and rotate before that gate is released. Another gate holds an old query after capture. A third holds a query at a real spill pass so cancellation must clean actual files without publishing partial output.

Complete Part 1 and Part 2 first. All blocks named tests/engine.cpp below concatenate into one complete program. No mock query replaces the Chapter 17 two-sort join/aggregation pipeline.

Construct small but structurally demanding data

Create the test file with its imports, ordinary throwing checks, temporary namespace owner, and text reader. TemporaryDirectory is a test owner only; production cleanup failures remain visible through the engine and task reports. The test removes its private root during cleanup and never targets a caller's existing directory unless the explicit fixture mode is selected.

Use small blocks and three-row sort chunks so the input must spill. The two accounts initially map to regions 1 and 2. Event IDs are 100+i for 0\le i<60, amounts are i+1, and every third event belongs to account 20. Thus all values and expected answers remain small enough to inspect manually.

TaskHandle::wait_for is a test watchdog, not a claim about production latency. A terminal task must report zero charged query bytes and no unresolved spill or result cleanup. We still read the output files independently; an empty resource ledger does not prove a correct query answer.

For region 2, the amounts are 1,4,7,\ldots,58: twenty values. Their total is

20(1+58)/2=590.

All sixty amounts total 60\cdot61/2=1830, leaving 1830-590=1240 for the forty region-1 events. At sequence 2, account 10 moves to region 3, event 101 changes from 2 cents to 900, and event 102's 3 cents are deleted. Its new count is 39 and total is 1240-2+900-3=2135. At sequence 3, account 20 moves to region 4 and a new 100-cent event adds one row: count 21 and total 590+100=690.

The query must select one account/event snapshot together. Reading the new accounts with old events would produce plausible numbers under the wrong region IDs, so comparing only the grand total would miss the error.

Establish the pause, then perform the competing operation

The Gate owns its mutex and condition variable. A callback announces arrival while holding the gate mutex, then waits on a predicate that releases it. The controller observes that arrival before performing the competing action. The timeouts report broken rendezvous; no sleep is used to guess whether the other thread has reached a boundary.

ReleaseGates is created after the engine/executor owners. During unwinding it releases their borrowed callbacks before those owners try to join workers. A test assertion must not strand the very worker that a destructor is joining.

Hooks borrow their context pointers. Keep the gate or failure object alive until every worker using it has joined. Maintenance build hooks run without the engine mutex; installation hooks run inside the authority critical section. Neither is a general-purpose reentrant extension point. In particular, do not call engine.stats() from an installation hook that already owns that mutex.

Run the complete overlap fixture

The executor has three worker threads but permits only two simultaneous full query reservations: 2\times2 MiB and 2\times29 descriptors. The old query and cancelable query occupy that entire pool while both are paused. Maintenance must still install its prepared compaction and flush the later log.

The sequence is explicit: flush sequence 1, hold its query, commit/flush sequence 2, pause compaction, commit/rotate sequence 3, and hold another query at a spill pass. Only then release maintenance. Check its result before releasing either query. This tests progress independent of the query pool, not just different threads running at unrelated times.

Both successful queries process sixty events, but their answers differ. Each sort creates twenty initial runs. With fan-in two, materialized counts are 20\to10\to5\to3\to2: four passes, followed by the final streaming merge. The canceled query has also created more than one run before cancellation, so its cleanup is not an empty-input shortcut.

While the old query remains paused, collection must report retained obsolete sources. After terminal results release the views, explicit collection must leave zero retained snapshot states and zero maintenance workspace bytes. Reopening then checks sequence 3 and the actual updates and tombstone, not just the CSV files.

The CSV sink preserves cancel.csv's previous completed contents. Cancellation is not translated into a new empty result. The test also verifies that neither successful query leaves spill files behind.

Test revalidation without relying on a lucky schedule

Use the split job directly under a single controlling thread to exercise three precise changes between build and install: a newer log set, a replaced selected prefix, and a newer unselected table suffix. There is still at most one split job alive; no collector runs while it exists. The synchronous compaction used to make the stale case is deliberate and fully completed before the stale job tries to install.

The first and third jobs must rebase successfully despite an epoch change. The middle job must reject because its selected records are no longer current. Its second installation attempt throws: stale is a terminal phase, not permission to try the same candidate repeatedly. Finally, deleting both keys checks a zero- file base with nonzero coverage through sequence 4.

Stop while a writer cannot make progress

Pause the first flush, then create three sealed generations and one active generation under a one-batch threshold. The fifth writer enters the actual condition-variable wait. await_writers(1) confirms that state before stop is requested.

The local JoinWriter guard requests engine stop before joining the external writer. This order remains valid if an assertion or watchdog throws. Without that request, the guard could wait forever for a slot that the paused maintenance worker is not allowed to free.

Stop abandons the not-yet-installed flush. Its files may exist as orphans; they are not adopted on reopen. The authoritative WALs still recover all four acknowledged batches, and event 5 must be absent. Shutdown is therefore a tested state transition, not a blanket request to discard every buffered object.

Make worker failure visible without revoking old readers

One failure hook throws during output construction. Another throws after manifest rename, where authority may already have changed. Arm the second only after the rotation needed by capture, otherwise the test would fail the wrong operation.

The already captured view contains frozen memory. Both failure cases must leave it readable, stop new writes, make await_idle and explicit finish report the stored exception, and reopen to the one acknowledged sequence.

A construction failure is not an uncertain commit, while a rename-stage failure requires reopening authority. The engine deliberately stops after either kind of maintenance failure rather than silently continuing with no worker. An existing view is independent of that decision because its state has already been captured and its source ownership is complete.

Release the last owner on a different thread

A snapshot cap of one rejects the second capture before changing the manifest epoch. Then destroy the engine and the caller's query-budget handle while keeping one isolated view. The directory lock must remain held; an attempted reopen fails until that view is released.

The final release is performed by a new thread. This exercises the registry, arena/table releases, shared allocator control storage, and directory lock through their actual transitive owners—not merely a standalone atomic counter.

The weak budget handle is only an observation. It does not keep the private query budget alive. Its expiration after the release thread joins establishes that the last shared-control allocation no longer owns that budget either. The join orders the subsequent check after the release; the test never reads ordinary shared state while that release is still running.

Stress the ledger and reject an impossible allowance

Six threads each perform 500 independent reservation/allocation/release cycles. At most six pairs of a 200-byte lease and a 64\cdot8=512-byte vector coexist: 6(200+512)=4272 bytes, within an 8192-byte limit. A smaller observed peak is expected when their lifetimes do not fully overlap; do not assert a particular scheduler interleaving.

The thread-start loop also joins a partially started set if a later creation throws. This is the same lifetime rule taught in Chapter 18, applied to test code rather than ignored there.

A 64-byte maintenance budget cannot fit the job and its control storage. The worker must fail visibly, release its charge, and stop the engine; it must not borrow from query memory. A descriptor configuration of one is rejected at configuration validation, before trying to open the already locked database. The normal entry point runs every check. Fixture mode leaves its outputs in an explicitly supplied disposable root for the Python oracle.

Read failures as ownership and progress evidence

Symptom First boundary to inspect
Writer cannot commit while compact-build is paused Engine mutex accidentally spans job->build; gate is not outside the critical section
Fifth writer never wakes after stop Stop does not notify changed, or the wait predicate ignores stopping/error
New CSV uses old regions or old amounts Account/event scans did not share one captured sequence, or installation discarded newer dependencies
ThreadSanitizer reports a cache/counter race A private reader/view was shared between workers; do not merely make its owner count atomic
Final query charge or storage retention remains nonzero Terminal task retained a plan/view, or final allocator/control storage still owns its budget
Snapshot limit rejection changes epoch Admission was moved after rotation, violating the no-side-effects pressure check
Maintenance loops forever with 16 tables A base-only repack cannot free a slot; report capacity failure instead of retrying unchanged work
Reopen fails after a maintenance error Distinguish valid orphan files from a missing/corrupt authoritative dependency; preserve Chapter 11's strict policy

collect_obsolete remains bounded by the directory inventory limit, but its metadata operations run under the engine mutex. The file system can block that mutex for a substantial time. Measurements in later chapters should distinguish this from bulk compaction, which runs unlocked; a single “maintenance time” number would hide the tradeoff.

Verified boundary and remaining limits

The cumulative 31-test suite passes Debug, Release, and AddressSanitizer/UndefinedBehaviorSanitizer builds with Clang 17 on Linux. The four focused executor/live-engine tests pass a separate GCC 14.2 ThreadSanitizer build. The overstrict-epoch mutation fails its logical assertion in all four configurations without a sanitizer report, and the correct implementation is restored before the final passing runs. The Linux race-check build used -fno-pie/-no-pie for that runtime; these are not prescribed native macOS flags.

These tests establish the demonstrated code paths, not freedom from every possible interleaving. Native M4/macOS execution and Apple full-device synchronization remain unverified. Ordinary reopen after joined shutdown is not a power-loss experiment. Budget counters are not RSS; descriptor allowances are not kernel reservations; long-lived snapshots deliberately retain resources.

The engine now coordinates real concurrent queries, ingestion, and maintenance with explicit lifetime, admission, failure, and publication boundaries. It still has one serialized writer, one maintenance worker, fixed table/log limits, and per-query reader/cache isolation. Do not replace those explicit bounds with an unbounded queue of frozen generations to hide pressure.

References used for this chapter

The implementation above is self-contained with its named prerequisites. These primary references clarify the C++ rules behind its synchronization choices:

  • C++ working draft: mutex requirements, particularly lock/unlock synchronization and noncopyable mutex lifetime.
  • C++ working draft: shared ownership pointers, particularly final-owner destruction and the distinction between pointer machinery and accesses to the pointed-to object.
  • C++ working draft: condition variables, particularly atomic unlock-and-wait, re-locking, predicate waits, and destruction.
  • C++ working draft: data races, particularly conflicting lifetime operations, happens-before, and relaxed atomics.

These draft pages can include facilities beyond C++20; this chapter uses only its already established C++20 baseline. It does not require newer signatures shown elsewhere on those pages.
