Chapter 19 — Bounded execution and cooperative cancellation

Part 3 — Force the waiting and publication boundaries

The scheduler's contract is not "the test eventually prints two answers." We need to observe a worker waiting for resources, cancel a request behind the blocked queue head, show that the caller still owns a rejected request, and cancel on both sides of the result-publication gate.

This completes the same 4.0-hour chapter begun in Part 1 and continued in Part 2. Use the exact prerequisite amendments before building. All test helpers below are included; no unseen test framework or scheduling service is required.

A small answer with genuinely spilling execution

The fixture has accounts 10 and 20 in regions 1 and 2. Event index i runs from 0 through 59. Its account is 20 when i is divisible by 3, otherwise 10; its day is 3 and its cents value is i+1. Region 2 therefore receives the 20 values 1,4,7,\ldots,58:

\text{region 2 total}=20(1+58)/2=590.

All 60 events total 60\cdot61/2=1830 cents. Region 1 has the remaining 40 events and 1830-590=1240 cents. The expected CSV is thus independently calculable, not extracted from a previous C++ query run.

Each sort admits only three input rows per initial run. Sixty rows require \lceil60/3\rceil=20 initial runs. With merge fan-in two, materialized passes reduce that count through 20\to10\to5\to3\to2. The final two-way merge streams into its consumer, so the expected materialized-pass count is four for each sort. Small row and block buffers force the real spill/cleanup paths while keeping the fixture inexpensive.

Create tests/executor.cpp. Begin with imports, assertions, the temporary owner, and ordinary file helpers:

TemporaryDirectory owns only the test root. Its destructor uses the error-code overload of removal so a diagnostic exception cannot cause another exception during unwinding. The runtime's own cleanup is asserted before this fallback removes the fixture. It must not hide a missing runtime unlink.

Configure tiny operator buffers and create a disk-only database before any worker exists:

rotate and flush_oldest complete outside the executor. The ordinary setup budget must return to zero after the local database dies. Only then does FrozenInputs recover and retain the immutable sources. Reopening here also exercises the existing manifest authority, table decoding, and directory lock instead of substituting a vector of fake query rows.

The result helper checks normal teardown before returning the copied report. The separate deletion-refusal test will intentionally bypass its clean-spill expectation. A fifteen-second completion wait is a diagnostic watchdog, not the means of coordinating threads.

Use a gate to hold workers immediately after admission. The controller waits until the exact number of arrivals has been observed under a mutex. No sleep is used to guess that a worker has started. Hook and gate lifetimes extend until the executor has joined; the timeout path reports a broken test rather than leaving a permanently blocked worker.

The gate callback runs on a worker and borrows Gate. Its counters and flag use one mutex. release publishes the open flag before notification. Although two arrivals are required, the scheduler does not depend on this gate at all; it is only a way to observe a stable intermediate state.

Prove overlapping admission and ownership-preserving rejection

Append the two-query check:

At the gate, both requests are running and their allowances sum to 4 MiB and 20 file descriptors. A duplicate a.csv descriptor remains at its original address after output_busy. Once released, both queries must complete with sequence 1, two groups, and the exact CSV. Each must exercise both spilling sorts. finish then returns only after the diagnostic live-thread count is zero.

The CSV names differ, so the two workers do not race to replace one destination. The input names are shared but immutable; the readers/caches and output owners are distinct. The final rejected submission also proves that closing does not silently consume late work.

Cancel behind a head that cannot fit

Append the independent memory-pressure and descriptor-pressure check:

Call this twice. With files == false, memory permits one running query; with files == true, descriptor capacity permits one. In both cases a second worker is observed waiting and B/C remain queued. Cancel the tail C first. If the scheduler checks only the head's resource predicate, C's wait times out even though it needs no resources to become canceled. Cancel B next, then release A.

The test also covers impossible and full submissions while preserving the exact caller-owned pointer. Checking that no canceled queued destination exists helps catch an implementation that captures a snapshot or starts a sink too early. The invariant still comes from the code path: queued cancellation never calls execute.

Stop at a boundary, then stop too late

Two borrowed hook contexts let the worker itself request cancellation at a precise point. CancelAt uses the ordinary checkpoint path; LateCancel runs inside the sink after the final checkpoint has already passed.

For the block case, the thirtieth block checkpoint avoids limiting the test to the first metadata read. The spill-pass case requires at least twenty created runs, so cancellation really owns temporary files to unwind. At the final gate, both groups have been staged but the old destination must remain unchanged.

The late hook sets the same stop flag immediately before rename, inside the masked finish scope. The result must be completed and the new file must be complete. This deterministic interleaving exposes a logical race in outcome classification even when every individual memory access is properly synchronized.

A cancellation that races with a different exception has no universal precedence in this design. The path actually observed decides: a Canceled exception gives canceled, a different exception gives failed, and successful publication gives completed. We do not relabel outcomes afterward by sampling the flag.

Failure is local to one query

Append a sink error and the first twenty-four charged-allocation failures:

The captured sink exception is rethrown on the controller and checked by type. The old completed CSV survives. The allocation loop is a targeted early-failure campaign, not a claim that every allocation site in every plan was exhaustively failed. All twenty-four selected ordinals must produce bad_alloc, return their working ownership, and leave no run directory.

A 512-byte query fits the scheduler's pool claim but cannot construct the private read context and plan. It is accepted, then fails locally. The later normal query must succeed. If it remains queued, inspect reservation return; if it allocates through a dead ledger, inspect escaped read/statistics ownership. Neither problem is fixed by catching and discarding the original exception.

A cleanup report must not pretend the disk is empty

Append the deliberate unlink refusal:

Cancellation at the first spill pass now encounters an unlink hook that always fails. The result has zero charged working bytes and the executor has returned its memory/descriptor allowances, yet live_files, disk_reserved, cleanup errors, and the directory path remain observable. Those facts are compatible: closing a file descriptor does not remove its name or reclaim its disk contents.

Only this test explicitly removes its known fixture directory after terminal completion. Production cleanup should operate on the reported, controlled spill namespace and surface failure; it must not recursively delete arbitrary user paths. No automatic retry service is implemented here. A result-sink cleanup error is separately reported by result_cleanup_error.

The remainder of the check proves that cancellation before submission persists across a rejected closed return and a later accepted submission. Rejection must not invent a terminal owner. Uppercase names are rejected to preserve the executor's bounded lowercase output namespace.

Unwind the controller and partially started constructors

Append shutdown tests and the complete main:

The first loop fails before launching worker 0, 1, or 2. Every already-started thread must be joined before the constructor exception reaches the caller. The second case accepts ten requests, then deliberately throws from the controller's scope. Some requests may finish before cancellation; others may be canceled. Both outcomes are legal. An unresolved handle, escaped worker, failed query, or remaining spill directory is not.

TaskHandle values remain outside the executor's scope. Their completion data are still readable because they own only their controls, not a raw executor pointer. Cancellation after executor teardown is safe as well: the weak wakeup may be empty, while the task's completed result remains unchanged.

The executable's --fixture ROOT mode runs only the successful overlap check and leaves its two completed CSV files for an independent process to examine. It does not leave spill runs or a running thread.

Sanitizers cannot replace this state-machine assertion. Restore result.state = TaskState::completed;, rebuild, and rerun the normal checks before proceeding.

As another reasoning exercise, move snapshot capture above scheduler admission on paper and count the retained owners when the queue fills. Even if only two workers execute, queued snapshots could pin old generations and allocate caches before any query allowance exists. The requirement is not merely a worker count; it is the precise point where ownership is admitted.

Diagnosis follows the boundary that failed

Symptom First boundary to inspect
Canceled tail times out behind a large head Cancellation scan before resource admission; cancel mutex handshake
Idle workers repeatedly wake without requests Test-observation notifications incorrectly using the worker condition variable
final_bytes is nonzero Escaped stats/read view/cache owners or a charged allocation that lacks cleanup
Two queries trigger a race in cache or budget A shared parent reader/context was served instead of a private isolated state
Published file exists but handle says canceled Stop flag sampled after the publication gate
Query fails and the next task never starts Allowances not returned on the failed path
Memory is returned but spill directory remains Explicit cleanup error/path report; do not confuse close with unlink
Destructor blocks indefinitely A blocked native call, unreleased test gate, or a forbidden descendant wait

A watchdog failure deserves a trace of states and owners, not a larger sleep. Start with queued, running, waiting, and the two reservation totals. Check which mutex protects each observation. Then inspect the query's last boundary and cleanup report. The executor does not offer forced termination of a running thread, and destroying its memory while it is blocked would not be a repair.

Executed checks and limits

The complete cumulative learner program passed 29 CTest entries in Debug, Release, and AddressSanitizer/UndefinedBehaviorSanitizer builds with Clang 17 on Linux. A separate GCC 14.2 ThreadSanitizer build passed the focused runtime and native CSV checks. The deliberately wrong post-publication classification failed the intended logical assertion in all four configurations without a sanitizer memory/race report; the correct assignment was restored before the final runs.

The checks include independent memory/descriptor waits, queued-tail cancellation, five running cancellation boundaries, successful publication after a late stop, twenty-four allocation positions, insufficient local workspace, sink failure, observable cleanup refusal, pre-submission cancellation, partial thread startup, and controller unwinding. They exercise real two-sort plans and native table, spill, and CSV files. They are not an exhaustive schedule exploration.

Native M4/macOS execution remains unverified. The immutable fixture is not concurrent ingestion. Cooperative cancellation is not interruption of a blocked filesystem call. Charged allocations are not RSS, descriptor allowances are not kernel reservations, per-sort disk caps are not a global disk quota, and completed CSV publication is not power-loss durability.

The next chapter adds coordinated live reads, one writer, and background maintenance. Keep this chapter's boundaries: admit before capturing, do not share mutable read bookkeeping accidentally, return owners before terminal completion, and join before destroying shared state.
