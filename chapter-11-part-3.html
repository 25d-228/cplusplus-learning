Chapter 11 — Flush installation and database reopening

Part 3 — Failure cases across process lifetimes

Part 1 made the manifest and directory boundary explicit. Part 2 built the installation protocol and serving owners. Now test the difference between bytes that exist, a catalog that names them, and an object that may safely serve requests. This is the final part of the same 5.5-hour chapter, not a second implementation allocation.

The C++ executable has two jobs. With no arguments it tests the bounded manifest codec and the strict sealed-log boundary against an in-memory file backend. With a command and directory it performs a small native database operation. The Python driver launches that executable repeatedly, decodes the manifest with independent struct and zlib operations, damages disposable copies, and starts a genuinely separate lock contender. It does not implement the engine.

The tests must not erase a real database. The Python driver creates and owns its entire temporary directory tree. Manual commands below create a new directory and leave it available for inspection. Never point a corruption exercise at your only copy of useful data.

Check format semantics independently of checksums

Create tests/database.cpp. It reuses the complete WalFileOps test backend from Chapter 10's tests/wal_file_ops.hpp; do not substitute the native backend for these deterministic sealed-tail checks. No other test helper is missing.

format_failure accepts only the expected FormatError. A bad_alloc, a native I/O error, or failure to throw is not a passing corruption check. That distinction prevents a test from “passing” merely because something unrelated went wrong.

The smallest manifest has zero tables and one active log. Its length is 48+24+4=76 bytes. The full bounded manifest has sixteen table records and four log records: 48+16\cdot32+4\cdot24+4=660 bytes. Each single-bit mutation below is restored before trying the next byte position. The test is 660 mutations, not all possible corruptions and not all eight bit positions per byte.

The mutation at offset 56 changes the first table's base. Recomputing the CRC makes its checksum correct while its history coverage is wrong: a first interval starting at 1 omits the required boundary at 0. The decoder must reject that image for its semantics. Tests also reject duplicate file identities, a gap between sources, a nonzero active end, the wrong flushed boundary, exhausted high-water admission, an excessive table count, and epoch zero.

The filename exercise reaches UINT64_MAX without overflowing decimal parsing. A larger decimal value must fail rather than wrap into an existing identity. notes.txt is foreign to the reserved namespace; zero and malformed reserved identities are errors, not filenames to silently skip.

A sealed prefix cannot be repaired as an active tail

The next test writes two complete account batches, then freezes the writer. It records the boundary after the first batch so the test does not depend on a hardcoded account-frame size. Reopening as sealed must recover exactly sequence 2 and retain a frozen memtable. Removing a complete last batch is just as invalid as removing one byte from that batch.

There are two independent assertions after a failed sealed constructor. The storage image remains unchanged, including the truncate-call count; the failed owner also closes its descriptor and releases every charged allocation. Merely throwing eventually would be insufficient if replay had already shortened a sealed dependency.

The final active-log open uses the same partial bytes but a different contract. It is allowed to discard the incomplete final frame and recover sequence 1. Treating these two modes identically would silently discard manifest-authorized history. The distinction is a recovery invariant, not a different checksum algorithm.

Make interruption observable without changing the algorithm

The installation callback receives a borrowed Cut through the void* context introduced in Part 2. The cast is valid because this driver always passes the address of that exact type and keeps it alive longer than the database. No callback starts another database operation. armed remains false while opening so an injection intended for rotation does not accidentally fire during initial creation or recovery.

The exception path throws after a completed boundary and runs normal C++ cleanup. The abrupt path flushes the diagnostic stream and calls std::_Exit(73): no stack unwinding, database destructor, or normal stream cleanup is relied on. These are two different process behaviors. Neither removes the running kernel's page cache, reorders device writes, or models a power interruption.

At manifest-closed, a separate mode arms the next charged allocation instead of interrupting. After the operation returns, a one-byte probe must still trigger that failure. This checks that publication after durable installation did not perform another charged allocation. It does not intercept allocations outside our Budget allocator or prove the absence of every possible library allocation.

The data fixture is deliberately small but crosses both relations in each batch. Sequence s writes account 10's region as s and event 100's amount as 400+100s, except that sequence 3 writes an event tombstone. Holding the keys constant forces newer generations to override older sources.

The driver checks decoded values, not only the manifest counters. After a tombstone has moved into an installed table, the older event must remain absent. A catalog that looks plausible while get resurrects that event fails here. orphans_at_open() is the inventory observed when this process opened; it does not update after each operation. The next process may therefore print one more orphan even though no additional mutation occurred between the two outputs.

Keep the native command boundary small

The driver uses an existing directory and an explicit create/recover choice. --allocation N accepts an ordinal from 1 through 128. std::stoull can throw; the final main reports conversion and range errors through the same exception boundary. Numeric parsing is test infrastructure, not an engine format parser.

Cut and Budget outlive Database. Failure injection is enabled only after construction, and the old epoch/sequence are copied before the operation. A post-install exception may leave a newer manifest on disk, yet this poisoned object must not pretend its old serving set is current. Diagnostics may inspect the old state; public reads and writes may not continue.

The exception cases have distinct exit codes so the Python driver cannot mistake an expected installation failure for a successful command. Code 3 means a checkpoint exception, 4 an injected charged-allocation failure, and 5 a bounded slot-admission rejection. Ordinary construction or format errors reach main and produce code 1. The abrupt path uses 73 and cannot check in-process cleanup.

length_error is expected only for the deliberate pre-effect generation caps in these fixtures. It must leave the object healthy. By contrast, the chosen allocation injections occur inside the conservative uncertain maintenance region and must poison it. The outer scope checks zero charged bytes after destruction on every normally unwound path.

Decode native authority with a separate implementation

Create scripts/check_database_fixture.py. The decoder below does not import C++ layouts or call back into the executable for metadata. The little-endian format strings derive directly from Part 1's byte table. In "<8sIIIIQQQ", 8s reads eight bytes, each I four bytes, and each Q eight bytes, with no native padding. zlib.crc32 provides an independent check on our CRC implementation.

This is a small-fixture decoder. Its read_bytes() calls are not the engine's bounded streaming path, and it does not replace the C++ table validator. The native executable separately verifies table framing, row ordering, checksums, and sequence coverage while opening.

For every table, the decoder checks the actual referenced file length. For every log, it checks the native header's base against the manifest. The active log has an open end of zero; sealed intervals advance the boundary. Missing references are errors rather than permission to adopt another file from the directory.

The next blocks continue the same file and the same main function. Preserve indentation across blocks. run launches a fresh process with a 60-second test timeout and requires both its exit status and an identifying output substring. A timeout is a failing test, not a reason to retry an operation against the same possibly changed database.

The original fixture is sequence 2 in log 1, with a one-log manifest whose next unused identity is 3: temporary manifest 2 consumed an identity even though its name became MANIFEST. clone copies only closed fixture trees; no running writer owns a copied directory. Each subsequent case receives its own path and lock inode.

The successful lifecycle rotates first, commits sequence 3 into the new active log, flushes the older generation, then rotates and flushes the tombstone's generation. Reopening must still return absence for event 100. An empty active memtable makes rotation a true no-op, including unchanged manifest bytes.

Now interrupt at every named install boundary. There are ten common stages and one operation-specific stage: log-ready for rotation or table-ready for a flush. Two operations, eleven stages, and two interruption modes give

2\cdot11\cdot2=44

cases: 22 exception cases and 22 abrupt process exits. The live kernel has not crashed. Therefore a completed rename is immediately observable by the next process, even at a checkpoint before directory synchronization. The test expects the old epoch before rename and the new epoch after it. That observation must not be reused as a power-loss recovery rule.

Each reopened database completes whichever maintenance work remains, then checks its values again. This catches a protocol that reopens once but cannot safely continue after an interrupted rotation or flush.

The allocation sweep starts from a fresh copy for each ordinal. It requires a poisoned operation failure, unchanged manifest bytes, and a successful reopen. The first ordinal beyond the operation's actual allocation count succeeds and ends the sweep. Counts are observations of this implementation and standard library, not a portable API contract. No failure is allowed to silently evade the reopen check.

Reject attractive but unauthorized recovery paths

A valid orphan manifest candidate does not repair a corrupt authoritative MANIFEST. Likewise, an old WAL retained after a flush does not replace a missing or corrupt table that the current manifest names. The checks below keep those tempting fallback inputs in the directory and still require failure.

The two native sealed-log cuts remove either the entire last batch or its last byte. This fixture has two 100-byte cross-relation frames after a 32-byte header, so its length is 32+100+100=232 bytes. Cuts at 132 and 231 must leave the damaged file untouched. A four-byte incomplete active-frame header, by contrast, is a permitted active tail and is removed before serving.

The next cases check namespace rules and bounded admission. Observed orphan IDs 900 and 901 push the next log to 902, the temporary manifest to 903, and the persisted next-ID value to 904. Their file contents are deliberately useless; only their names affect high-water admission. Neither becomes recovery data.

A symlink in the reserved namespace is refused. The generation tests then fill four log slots and sixteen table slots, respectively. These are format/resource bounds, not a request to overwrite the oldest live dependency. Flushing the oldest sealed log frees a log slot; this chapter has no compaction operation to free a table slot, so table-cap rejection remains the correct result.

The lock check is not two Directory objects in one process. A child announces locked only after it has opened the database and retained its lock. A separate child must fail to open. The holder then receives a line on standard input, returns normally, and releases the descriptor; the following open succeeds. LOCK remains the same inode throughout. Removing and recreating it would allow cooperating processes to lock different objects under the same pathname.

Diagnose a logical recovery defect

Temporarily remove the following guard from WalMemTable::replay in src/storage/wal.cpp and put (void)required_end; in its place. The cast only suppresses an unused-parameter warning; it does not perform a check.

Rebuild strata-database-tests in Debug, Release, and the sanitizer configuration, then run it with no arguments. For the complete-boundary truncation, the broken reader accepts sequence 1 even though the manifest required sequence 2. The expected test result is exit status 1 and database: expected format rejection. The test is reporting a missing format rejection, not confirming one.

That deliberate defect produced the same logical failure in all three tested configurations, with no sanitizer report. The memory operations can be legal while the recovery decision is wrong. Restore the complete guard before continuing, rebuild all configurations, and rerun the entire CTest suite. Never leave the diagnostic edit in a source tree used to open a persistent database.

Troubleshooting by violated boundary

Observation Check first Do not “repair” it by
Second process cannot acquire LOCK Whether the first process still owns its descriptor Unlinking or replacing LOCK
authoritative MANIFEST missing in recover mode The exact directory and explicit create/recover intent Creating an empty database over numbered files
Manifest CRC or interval validation fails The authoritative bytes and their provenance Selecting the largest .tmp filename
Sealed WAL end mismatch Manifest (base,end], exact complete-frame boundary, and file length Applying active-tail truncation to the sealed log
Installed table is missing or damaged The specific manifest dependency and copied fixture Falling back to a retired WAL
Failure after rename poisons the old object Reopen using the one authoritative manifest Retrying writes through the old serving owners
Flush exhausts the shared budget Old/new reader overlap, builder workspaces, and candidate image Releasing a live recovery source before publication
Log or table slots are exhausted Whether ordered flush or later compaction can free the intended slot Overwriting a live file or inflating format counts
Synchronization request fails Filesystem/device support and the exact failing operation Downgrading the requested guarantee silently

A database directory containing foreign files is not automatically invalid; notes.txt is preserved. A file in the reserved s- namespace, however, must obey the naming and regular-file rules, including the one-link requirement. The directory cap counts foreign entries too so enumeration remains bounded. This is a cooperating-process, trusted-local-directory model, not a hostile multi-user sandbox.

What is now implemented

A caller can create a database in an existing directory, commit atomic batches, rotate an active log, flush sealed generations in order, close the process, and reopen from a bounded checksummed manifest. All serving owners are prepared before successful publication. Uncertain maintenance stops the old owner; reopening decides authority. Unreferenced files are recognized without reuse or adoption, and retained rather than reclaimed prematurely.

Current point reads resolve the latest value or tombstone across those owners. They are not immutable multi-call snapshots, and there is no merged range cursor or concurrent access yet. Chapter 12 will give those serving generations an explicit snapshot lifetime and merge order. That work must preserve the sealed end boundary, durable identity high-water, and separation between removing a source from authority and reclaiming its file.

References used in this chapter

The format, interval policy, and installation state machine are implemented here; they are not claims that any one system call supplies a complete database transaction. The following primary references supply the underlying contracts.

  • Apple flock(2), Apple open(2), and Apple rename(2): advisory locks, creation/open flags, and pathname replacement. These are archived manual pages; the native feature checks and actual filesystem behavior still matter on the target machine.
  • Apple fsync(2) and Apple fcntl(2): synchronization requests and the distinct F_FULLFSYNC request. The discussion here keeps device behavior and successful-call assumptions explicit.
  • Linux fsync(2), open(2) / openat, and opendir(3) / fdopendir: directory synchronization, descriptor-relative opens, and directory-stream ownership used in the authoring-platform implementation.
  • C++20 draft N4861, shared-pointer creation, shared-pointer assignment, and construction/destruction during exception handling: allocator-aware owner construction, nonthrowing owner transfer, and cleanup when a database constructor does not complete.
