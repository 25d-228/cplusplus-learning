Chapter 22 — Recovery and resource-pressure experiments

Part 1 — Separate bytes, names, and acknowledgements

A process can terminate without losing the kernel's cached file contents. A synchronization call can report an error even though the bytes survive. A newly installed manifest can be readable while one of the names it references is missing from the persisted directory. These are different experiments. A test that treats every failure as “discard everything since the last successful call” cannot distinguish them.

We will put the existing database behind a small, explicit persistence model, then run a separate native child-process campaign. The model calls the real Database, WAL decoder, table reader, installer, and collector. It does not reimplement their decisions. A parent-side acknowledgement ledger determines which recovered histories are allowed. Finally, native spilling queries will encounter quota pressure, injected no-space errors, cancellation, and refused cleanup without replacing an earlier completed result.

Learning objectives State a crash model's assumptions; separate file contents from namespace bindings; preserve acknowledged batch history rather than merely row count; distinguish permitted tail repair from corruption; freeze an injected crash image despite host-language unwinding; coordinate a real process kill without sleeps; and follow pressure failures through ownership and cleanup.

Prerequisites: the complete implementation through Chapter 21, especially Chapter 6's FileOps, Chapters 10–13's recovery and manifest rules, and Chapters 19–21's executor, spill hooks, and workload presets. This chapter adds six test or script files, six narrowly scoped prerequisite-file edits, and a CMake append. The production default remains native I/O. The threaded engine does not use the synchronous test backend.

Implementation: 4.0 hours across all three parts. Allocate 1.25 hours to the persistence model and boundary, 1.25 to the crash campaigns, and 1.5 to pressure, diagnosis, and integration checks. Reading is separate. Reuse existing codecs, fixtures, and resource machinery; do not build another storage engine inside the test. Record actual implementation time.

Create these files. Concatenate successive blocks for a new filename in reading order; the six diff blocks are exact edits to prerequisite files, not new files.

Part 2 constructs allowed histories and crash images. Part 3 implements native process control, resource pressure, and complete run commands.

A recovered state is not a subset of old keys

Let B_i denote the complete mutation batch with sequence i. Let D_i be the logical database after applying B_1 through B_i in order. An update replaces an old value; a tombstone removes a key. Consequently, preserving acknowledged history does not mean retaining every key that ever appeared in an acknowledged batch. It means recovering the correct state of that history.

Let A be the highest sequence acknowledged outside the instance that will crash. Let R be the recovered sequence. These tests have at most one attempted but unacknowledged batch, B_{A+1}. With no such attempt, require R=A. With that attempt, allow

R\in\{A,A+1\},\qquad \text{recovered rows}=D_R.

The second condition matters as much as the first. Reporting sequence 3 with half of batch 3's updates is a failure. Returning sequence 2 with resurrected batch-1 values is also a failure. Conversely, recovering all of an unacknowledged batch can be legitimate: its synchronization might have completed before the caller learned the result. A definitely rejected batch never enters this set.

The fixture's second batch changes account 10's region to 4, replaces event 1's amount with 11, deletes event 2, and inserts event 3. Its third batch removes account 20 and event 3, replaces event 1 with amount 13, and inserts account 30 and event 4. Thus sequence 2 and sequence 3 both contain four live rows. A row count cannot distinguish them.

The ledger will live outside the simulated database object, or in the Python parent outside the killed child. It is not reconstructed from MANIFEST or the WAL. The native parent is still on the same powered machine: this is an external process-lifetime observer, not a durable distributed client or a production retry/deduplication protocol.

Specify the model before implementing it

For inode i, keep volatile bytes and length V_i, plus synchronized bytes and length S_i. A successful modeled file sync performs S_i\leftarrow V_i. Separately, let N_v map current names to inodes, and N_s map synchronized names to inodes. A successful directory sync performs N_s\leftarrow N_v. Syncing an inode does not create its directory binding; syncing names does not invent missing file contents.

A crash image chooses bytes and names independently. We exercise synchronized contents, current contents, correct append prefixes, and a deterministic mix that keeps current bytes for even-numbered inodes. Namespace choices include synchronized names, current names, and a third image that retains a completed manifest rename without unrelated unsynchronized creates or deletions. That last choice exposes a dependency-ordering bug that an all-old/all-new namespace model can miss.

This is a bounded test model, not an APFS implementation. It has one preexisting root with a durable LOCK, one exclusive owner at a time, 64 inode slots, 64 handles, and at most 16 KiB per file. A successful sync is an ideal persistence barrier for the selected object. File and full-device sync modes share that abstraction here; the model cannot validate the physical meaning of either native operation. Existing synchronized bytes are not damaged by a later append. Workloads append to WALs, build new immutable files, or shorten an incomplete WAL tail; they do not overwrite an acknowledged prefix in place.

The model assumes an intact old or new manifest binding, not a half-decoded rename. Its survival profiles are selected examples, not all subsets of all writes, all sector layouts, concurrent filesystem histories, device failures, or malicious modifications. One additional test creates a complete frame with wrong bytes and requires fail-closed behavior. It does not promise automatic salvage of arbitrary corruption. These limits are part of the result, not reasons to omit the experiment.

SQLite's atomic-commit discussion, Section 8 provides a useful primary example of testing recovery through a simulated file interface. Its rollback-journal algorithm and crash model are not the algorithm implemented here. We use the testing principle, while stating this model's narrower assumptions explicitly.

Keep simulated handles out of native descriptor owners

File already dispatches through FileOps, but Directory currently performs native namespace operations directly. Add a small optional directory backend. It returns ordinary OpenedFile objects, whose File borrows the same backend's FileOps subobject. Directory retains a shared owner of the backend until all its dependent files have been released through the existing context graph.

The abstract base has a virtual destructor because a shared owner can hold it through the base type. acquire/release describe exclusive context ownership; release must not throw. An unsuccessful acquire must leave no acquisition to release. scan may allocate through its caller-provided charged vector. Native Descriptor must never receive one of the model's small integer handle indices: calling the operating system's close on such an integer could close an unrelated real descriptor.

The default argument is an empty shared_ptr, so every existing constructor call still chooses the native path. A simulated constructor acquires first, then scans. If scanning throws, the constructor itself releases the acquisition: the destructor of a not-fully-constructed Directory will not run. In a completed object, the destructor releases the acquisition while the backend owner still exists. The native directory_ and lock_ members retain their original RAII cleanup when no backend was supplied.

Keep component-name validation, exclusive-create inventory accounting, and numbered-file restrictions in Directory. Delegation is only the operation boundary, not permission to bypass those contracts.

Pass the optional owner through DatabaseOptions into read_detail::Context. The context already outlives retained sources and their files. The explicit owner also prevents a test from returning a File whose virtual dispatch target has already been destroyed. These changes do not make Database concurrent, and the diagnostic backend below must not be supplied to concurrent workers.

No installer ordering or recovery rule changes in these edits. A test backend is valuable precisely because it reaches the same implementation. Replacing install with a separate simulated installer would allow the test to prove the wrong program correct.

Represent identity separately from reachability

A name holds a small inode index; a handle holds the same index plus access mode. Removing a name does not invalidate existing handles. Conversely, keeping file bytes without a name does not make those bytes discoverable during reopening. Slots are not recycled within one short campaign. This deliberately avoids an inode-reuse simulation while leaving production file-ID fencing under test.

PersistenceModel implements two independent interfaces using public inheritance. DirectoryBackend supplies namespace operations; FileOps supplies positioned byte operations. There is no common virtual base and no diamond. shared_ptr<PersistenceModel> converts to shared_ptr<DirectoryBackend> while retaining the original object's control ownership; File::adopt(*this, index) selects the FileOps base by its parameter type.

Image is a value describing one restart. current_names=false selects the synchronized namespace; rename_only=true overrides that choice with the shadow rename image. prefix is a byte count, not a percentage. write_allowance is optional: absence means no injected byte limit, while zero requests immediate no-space failure.

The overridden file calls are noexcept because Chapter 6's byte boundary reports numeric errors. Namespace methods may throw system_error; they already feed the database's maintenance failure path. Keep the return conventions different rather than letting an exception escape a noexcept override.

The two fixed byte arrays in every node are the test machine's simulated disk, not engine workspaces. Their payload alone is

64\times 2\times 16384=2097152\text{ bytes}.

Names, handle records, lengths, and object/control overhead are additional. This harness allocation is deliberately outside memory::Budget; each tested database has a separate 8 MiB budget. A zero engine charge proves that its tracked owners released, not that the entire process uses zero memory.

Freeze effects, not C++ cleanup

The model begins with one stable LOCK binding. It permits cloning only after all owners and handles are gone. A clone is a full value copy of this bounded machine, not a copy of a live database connection. Short-circuit name checks avoid treating unused slots as strings.

arm(k) counts persistent effects from a known point. After the kth effect, crashed_ becomes true. Later reads and writes return EIO; namespace operations throw. Closing handles and releasing host-side owners remain legal and cannot change the frozen byte/name image. Thus the real database can unwind in the test process without accidentally synchronizing or deleting its way out of the crash.

This is a simulation technique, not a claim that destructors run on a killed process. The native campaign in Part 3 uses actual termination without normal C++ unwinding. Acknowledgement is also a counted boundary: the external ledger is updated before calling checkpoint, so cutting there must preserve the newly acknowledged batch.

Restart chooses a namespace first, then bytes. For a correct append prefix, let s be the synchronized file length, v the volatile length, and p the selected extra-byte count. When v\ge s, the chosen length is

\ell=s+\min(p,v-s).

The prefix reuses the actual written bytes, not zeros. For a shortening operation (v<s), this profile chooses the old synchronized contents; the current profile chooses the shortened contents. The alternating profile varies by inode, not by write call, and therefore does not claim exhaustive reorder coverage. The torn profile is a separate corruption experiment: it retains current bytes and flips one newly appended byte when such a byte exists.

Once selected, the image becomes the next boot's stable baseline. Fault controls reset, while inode identities and chosen bytes remain. restart rejects live owners; it is not a method for changing persistence underneath running queries. The following helpers permit deliberate damage only with no live handles. The name append_garbage describes zero extension, not a valid WAL tail; Part 2 will overwrite it with bytes from a real encoded batch for the repair scenario.

Open, sync, rename, and unlink are different effects

Scanning reports the same numbered-name grammar as the native directory. It does not inspect contents to decide whether an unreferenced file is authoritative. open(create_new) first allocates an inode and binding, records the creation, and only then installs a handle. A cut immediately after creation can therefore leave a name without returning a File to the caller. No descriptor is leaked because the handle has not yet been published.

A directory sync error may occur with or without persistence. The flag controls that uncertainty independently of its return value. The shadow namespace starts at the last successful name barrier. On a manifest rename it receives the new MANIFEST binding, but not unrelated current names. This yields a concrete counterexample image: a new manifest survives while a newly created log's name does not. The correctly ordered installer prevents that combination by syncing the dependency names before the rename can happen.

Removal changes only reachability. The returned size belongs to the removed binding's inode, and open handles continue to point there. EACCES is injected before removal; a crash cut is injected after removal. Those cases must not be reported identically. The collector can confirm a refusal, but a cut after unlink leaves the surviving namespace undecided until restart chooses an image.

Short transfers expose the existing retry loops

Reads and writes transfer at most seven bytes. This is a deliberate test limit, not a sector size or a native performance choice. File::write_all must advance both its buffer and its offset after each successful short write. If an allowance of 19 bytes remains, transfers of 7, 7, and 5 succeed; the next attempt returns ENOSPC.

At a crash cut the model may copy bytes and then return zero progress with an error. That reproduces the uncertainty at the caller boundary: observing an error is not evidence that no side effect happened. After crashed_ latches, subsequent attempts cannot modify the frozen image.

A successful file sync copies contents and length, not names. An injected failed sync either performs that copy or leaves the synchronized version alone. Truncation changes only the volatile length until an appropriate sync. This is why replay must sync a repaired active tail before publishing its recovered owner. Close merely releases a handle; neither byte durability nor namespace persistence is smuggled into destruction.

The backend is now complete. It has enough state to ask whether a manifest's bytes, its binding, and its dependencies survive independently. The next part uses explicit batch states to decide which combinations must reopen successfully and which damaged images must be rejected.
