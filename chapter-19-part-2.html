Chapter 19 — Bounded execution and cooperative cancellation

Part 2 — A terminal result owns no running query

Part 1 made a query safe to run on one worker: its read-side state is private, its allocation cap is real, and cancellation unwinds its existing owners. Now we decide which worker may start it, how the caller observes completion, and how shutdown resolves every accepted request.

This is the second part of the same 4.0-hour chapter, not another allocation. The code operates against FrozenInputs; it must not capture a mutable database inside an arbitrary callable. No job may submit a blocking descendant to this same pool. A pool with all workers waiting for their own queued children would be deadlocked even if every mutex were correctly used.

A task handle is an owner of the answer, not the work

Use these state transitions:

A rejected submission stays created and remains with its caller. An accepted request is uniquely owned by the queue or by one worker. A separate shared control object survives through any copied handles. That control object contains the stop flag, state, completion statistics, and an exception reference. It does not contain a read view, output batch, or private query budget.

std::exception_ptr retains the caught exception beyond the catch block. std::current_exception() captures it while handling the error; the caller can later use std::rethrow_exception after checking the pointer is non-null. An exception is not magically thrown on the caller's thread. The ownership and capture behavior is specified in exception propagation. Capture can itself substitute an allocation-related exception, so do not promise perfect error-text preservation under global memory exhaustion. Query and diagnostic exceptions must not smuggle borrowed rows or private allocator-backed owners to the caller.

The completion control needs to wake a scheduler that may already have been destroyed by the time a handle is used. Store a weak_ptr to a small Wakeup object, not a raw pointer to Executor. Calling lock() yields a temporary strong owner or an empty pointer atomically; it does not extend the executor's lifetime. This operation is defined in weak ownership observers. The weak-pointer member itself is accessed under the task mutex while submission binds it and cancellation reads it.

Begin include/strata/runtime/task.hpp with the result and synchronization owners:

SortStats is copied by value after the plans die. Its fixed arrays preserve spill-directory names and cleanup reports without preserving a query allocator. staged_groups is not an acknowledgment of result publication. final_bytes will be sampled after every query-owned charged allocation has been released; the normal invariant is zero.

There are two condition variables in Wakeup. changed wakes workers after new work, cancellation, capacity release, or closure. observed wakes only a controller-side test waiting to see blocked workers. Combining those channels would let idle workers notify one another merely for entering the wait state, creating a wake/recheck cycle with no useful work.

Finish the header with the caller handle and fixed descriptor:

The descriptor has a bounded basename and a fixed-size query configuration. handle() copies only the control owner. submit will accept a reference to a unique_ptr<Request> and move it only on success, preserving Chapter 18's rejection-ownership contract.

The public hooks are diagnostic borrows, not a general task API. Configure them before submission and keep their contexts alive until terminal completion. Do not modify a submitted descriptor through a saved raw pointer. A checkpoint hook that pauses at a rendezvous must eventually be released by its test controller; the executor cannot cooperatively interrupt arbitrary user callback code.

Cancel a resource waiter without losing the wakeup

The scheduler will examine stop flags while holding its mutex and then wait on changed. Storing an atomic flag and calling notify_all() alone is insufficient: the notification could occur after the predicate check but before the worker actually enters its wait.

Use a short mutex handshake. Cancellation stores the flag, obtains a strong Wakeup owner under the task mutex, releases that mutex, then locks and unlocks the scheduler mutex before notifying. Consider a worker that has already read "not canceled" while holding that mutex. Cancellation cannot finish the handshake until the worker releases the mutex as part of entering its wait. The following notification then wakes it. Conversely, if the handshake completes first, the worker's next predicate check sees the stop request.

The condition-variable wait atomically releases its associated mutex and blocks, then reacquires the mutex before returning; it may wake spuriously. Those rules come from condition variables. Our complete predicate loop, not the notification, decides permission.

Create the beginning of src/runtime/task.cpp:

Submission and worker dispatch sometimes hold the scheduler mutex and then take a task mutex. Cancellation deliberately releases the task mutex before taking the scheduler mutex. Holding both in the opposite order would create a deadlock cycle. The otherwise empty lock scope is therefore meaningful synchronization, not redundant locking.

Pre-submission cancellation is also legal. Its stop flag stays set. If submission wins first, it binds the wakeup under the same task mutex; if cancellation wins first, submission's own notification wakes workers to observe the already-set flag. Neither interleaving leaves accepted canceled work asleep indefinitely.

State inspection and completion waits use only the task mutex:

Waiting on a never-accepted descriptor throws instead of waiting forever for an owner that does not exist. wait_for returns an empty optional on timeout; it does not cancel the task and does not establish a query deadline. The complete result is copied while holding the mutex, after a terminal-state predicate has succeeded. Do not expose references into Control::result after unlocking.

The constructor validates a result basename, then copies it into a zero-filled array. Leave one byte for the terminating zero. Restrict names to lowercase ASCII letters, digits, dot, dash, and underscore, with a letter/digit first. This avoids treating simple case variants as distinct concurrent destinations on a case-insensitive filesystem. It is not a sandbox against hostile directory changes. One executor must exclusively control its output namespace, with no other publisher replacing those names.

The executor prevents matching names only while requests are queued or running. Later intentional reuse replaces the completed file. A retained handle is an immutable record of that task's outcome, not a permanent snapshot of a pathname that future tasks may replace.

Keep scheduler storage fixed and query storage private

Create include/strata/runtime/executor.hpp:

queue_ has 64 physical slots and a configured logical capacity no larger than that. Removing a middle canceled descriptor shifts at most 63 unique pointers; this bounded linear operation makes the cancellation rule explicit. We do not need a general lock-free queue.

running_ contains non-owning pointers protected by the scheduler mutex. The corresponding worker's Dispatch owns each request. The pointer is installed before execution and cleared before request destruction. Shutdown uses it only to set the atomic stop flag. It never follows it into a query's private data.

Every member is constructed before any worker starts. threads_ is declared last, but declaration order alone would not join it: the destructor body must request termination and join while all earlier members still exist. Only the controller calls finish() or destroys the executor. Do not race two joins, call finish() from a worker, or destroy the executor while another thread is calling its public methods. Task handles have a separate safe lifetime.

Start a partial set of workers, or clean up all of it

Begin src/runtime/executor.cpp:

A failed constructor does not run ~Executor. The catch is therefore essential: it closes admission, requests cancellation, wakes any already waiting workers, and joins each successfully created thread before member destruction. The optional injected ordinal exercises exactly that ownership path without needing the operating system to run out of threads.

[this, i] captures a borrowed executor pointer and a copied worker index. The object cannot move or disappear while that callable executes. Destruction uses cancel-and-join rather than detach. A successful join waits for thread completion and synchronizes with it; the thread-handle object itself still needs controlled access. See thread members. A synchronization infrastructure failure in this noexcept shutdown path is fatal; silently detaching would leave dangling access and is not a recovery.

The next functions implement whole-query permission and ownership transfer:

fits subtracts current reservations from the configured caps. Subtraction is safe because all updates preserve used <= cap under the same mutex. Checked addition in files_for rejects unrepresentable descriptor totals before taking ownership. The request's configuration is immutable after acceptance, so its validated claim cannot grow while queued.

Submission is nonblocking. full is transient caller backpressure: retain the descriptor, perform other work, then retry or discard it. impossible requires a smaller claim or a larger pool. output_busy requires waiting for the conflicting operation or choosing a different name. closed will not become open again. No return value silently destroys the caller's request. Invalid null/reused requests throw as programming errors.

Accepted work waits internally for resources. Admission is FIFO among noncanceled requests. A large head can delay a smaller follower even if the latter fits; that deliberate head-of-line policy avoids a hidden best-fit scheduler and has no operating-system fairness guarantee. Cancellation of any queued descriptor is processed without requiring its resource claim to fit.

Dispatch only after reserving every allowance

Append the queue removal and worker acquisition functions:

Walk a pressure example with two workers, a 2 MiB pool, and 2 MiB requests A, B, and C. A is running. B and C are queued; the spare worker cannot admit B and waits. Cancel C. The wakeup returns the worker to the top, where the scan removes C before checking B's resource claim. C becomes canceled without ever opening a table, result file, or spill directory. Cancel B next and it also resolves. A can then finish normally. Repeating this test with plentiful memory but a 10-file allowance exercises descriptor pressure independently.

An admitted dispatch updates reservations, running count, peaks, the raw running pointer, and task state under the scheduler mutex. It moves the request out before releasing that lock. A canceled dispatch has no allowance and leaves its state queued until terminal publication; another caller can observe that brief intermediate state, but never a fabricated running state.

The wait is deliberately inside an explicit loop because there are several predicates and actions. Closure ends an idle worker only when the queue is empty. If accepted work remains, close drains it; a running worker's later resource release wakes any resource-blocked colleagues. No operator executes under this mutex.

Destroy query owners before publishing completion

Append result publication and the worker loop:

execute returns only after its local plans, views, sinks, and statistics owners are gone. The worker then returns reservations and clears the running pointer, and only afterward makes the terminal result visible. A caller whose wait() returns can rely on query memory/descriptor teardown being complete. Later work may already have consumed the returned allowance; a global used counter need not be zero while unrelated tasks run.

The queue does not destroy an arbitrary plan under the scheduler mutex because queued descriptors contain no plan. A worker's descriptor itself dies outside the lock at the end of the loop iteration. publish takes only the task mutex, checks that a terminal result is not being overwritten, and notifies waiters. The one worker owner supplies exactly one publication; the mutex supplies visibility, not a second ownership arbitration scheme.

The worker function is noexcept. Ordinary query exceptions must be caught by execute; an uncaught scheduler/invariant failure is not reported as a successful query. The live_threads pointer is optional test instrumentation and must outlive the executor. It is not used as a substitute for joining.

One call scope owns the query and its cancellation token

Append execute:

Read this function from the scopes inward. The outer cancellation scope borrows the still-owned request's stop flag. The admitted checkpoint happens after the scheduler's reservation but before any snapshot or workspace. Only then do we create a private Budget, result sink, isolated view, two stats owners, and the complete query plan.

The inner try owns view and plan; both disappear before its catch executes. consume_results takes the plan by value, owns its output batch, and aborts the sink on failure. The sink is outside that inner scope so we can record its cleanup status after unwinding. abort is safe after successful publication and does not remove the completed destination. The outer catch also covers failures before the inner scope exists, such as budget or sink construction.

Canceled is classified separately and carries no worker error. Other exceptions leave the default failed state and populate error. Successful consumption sets completed without rereading the stop flag. This preserves Part 1's publication rule when cancellation arrives during the masked finish region.

After the sink has left scope, copy the two fixed-size statistics values, release their charged owners, and sample the ledger. The invariant is

C_i\text{ at terminal publication}=0.

The Budget object's own small standard control allocation is outside its ledger; the ledger covers allocations requested through it, including read metadata, cache storage, and operator buffers. Exception objects and caller-held handles are also outside that ledger. Do not generalize this check to "the process uses zero memory."

If spill unlink is refused, file descriptors and working allocations still die, but disk bytes can remain. The copied statistics retain the directory, live-file count, reserved disk bytes, and cleanup errors. The runtime does not release those physical bytes by decrementing a memory counter. Nor does it automatically retry arbitrary directories after the task's owner is gone. A controller must surface the report and explicitly resolve known orphan paths; repeated cleanup failures can accumulate disk use beyond a sequence of per-query caps.

Close, cancel, wake, join

Finish src/runtime/executor.cpp:

close() rejects new submissions but keeps accepted work. finish() closes and joins, so it drains by default. cancel_all() rejects new submissions, marks queued and running requests, and wakes all resource waiters. The destructor uses that cancel path before joining. A running request that already passed the publication gate may still complete successfully; shutdown does not falsify its result.

cancel_all touches only fixed scheduler state and atomic flags while holding the mutex. It never waits for a query's private budget lock, runs a callback, or performs filesystem I/O there. Waiting for workers happens in join_all with no scheduler lock held. Otherwise the controller could block on workers that need that very lock to exit.

The diagnostic await_waiters waits for an observable count, not for an arbitrary sleep duration. Its five-second limit is a test watchdog, not a scheduling assumption or performance requirement. Production code does not need to call it.

Read the resource protocol as one trace

For a successful query, the sequence is:

A queued cancellation skips every step from private-budget construction through resource return because it acquired nothing. A running failure takes the unwind path through those owners and still returns its reservation. One failed query does not poison the executor; the next admissible request can run.

The controller must retain borrowed diagnostic contexts until the corresponding terminal result. It must stop external submissions before destroying the executor. It must not retain a mutable Database beside this immutable fixture. These are concrete lifetime and access requirements, not things a worker-count limit can enforce automatically.

Part 3 makes these traces observable with rendezvous, cancellation at precise boundaries, independent CSV answers, failure injection, and a deliberately wrong but race-free completion rule.
