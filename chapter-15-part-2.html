Chapter 15 — External sorting with bounded fan-in

Part 2 — Merge only what fits

Part 1 defined the run format, resource model, and ownership of temporary names. This part completes the same implementation file and public header. All three parts share the 6.0-hour implementation allocation. No prior chapter's source is replaced.

The important separation is between a sorted chunk, a completed run, and a sorted query stream. A chunk can be sorted without disk access. A run can be complete while other runs still contain smaller rows. Only the merge heap decides which available head is globally next.

Write a run in fixed frames

The writer borrows one output frame from the core. It owns a run reservation and an open file, in that declaration order. Constructing the run first ensures that a subsequent create or header-write failure cannot leave an ownerless name. A constructor's destructor body does not execute when that constructor fails, so the header-writing catch explicitly closes the file before member unwinding retires the run.

Append the first portion of Writer. The class continues in the next two segments.

The header knows the total number of rows before writing: an initial run knows its chunk count, and a merge sums its input descriptors. It therefore needs no final seek back to patch a count. This also makes the length reservation exact from the beginning.

append verifies nondecreasing order and enforces the promised count. It encodes one row into the available frame slot before publishing the buffered count. The previous row is an owning scalar copy; no view into a mutable frame is retained.

finish rejects missing rows before emitting a footer. It flushes a partial last frame, checks the computed final offset against the reservation, and closes the file explicitly. No synchronization barrier installs anything durably: a later process must not recover a query by guessing that a run with a footer is authority.

Returning std::move(run_) transfers the name reservation without copying a file or allocating. If the completed-run hook throws, the move never happens and the writer retains responsibility for that name. Here is the flush routine and the remaining members that close the class:

With frame capacity two, a three-row run follows this trace: write a 36-byte header; append rows 0 and 1 and write a 68-byte frame at offset 36; append row 2; finish by writing its 40-byte frame at offset 104 and a 24-byte footer at offset 144. The result ends at 168. The injected disk failure in Part 3 occurs before the write at 104, after a genuine 104-byte prefix already exists.

Validate a whole input frame before exposing its first row

A reader receives a trusted run descriptor and the configured block capacity. Its one buffer is allocated from that capacity, not from bytes just read from a file. It opens the run only after the buffer allocation succeeds. Header and footer checks compare all relevant fields with the descriptor, including total count, order ID, checksums, and expected number of frames.

The remaining_ count is initialized from the trusted descriptor only after those checks. This makes (remaining_ - 1) in the footer check safe: a run cannot have zero rows. Append the constructor and its explicit failure cleanup:

head returns an Event by value. A caller can safely advance after copying it. next decrements the total remaining count and either stays within the current frame, loads the next frame, or verifies the terminal offset and closes the file. The total count and the current frame position answer different questions; neither one can replace the other at a partial final block.

A refill knows its exact expected row count: the smaller of frame capacity and remaining rows. It therefore knows the frame length before reading. A malformed stored length cannot request a huge allocation or skip over unchecked bytes. After checking count, payload length, and CRC, walk every row in the frame to check nondecreasing order. Carry the last validated row across the frame boundary. Only then expose position zero.

Suppose one frame ends with account 8 and the next starts with account 3. Both frames could have internally sorted payloads and valid checksums. previous_ catches the cross-frame violation. Conversely, two identical records may straddle a frame boundary and remain valid because the comparison is strict, not <=.

The reader itself is an internal noncopyable object. If advancement throws, its caller terminates the surrounding sort and releases the reader; there is no public retry position that pretends a partly consumed frame was rolled back.

Keep the heap and all pass descriptors in the charged core

The core stores two fixed arrays of run owners, one fixed array of optional readers, and an index heap. An engaged optional<Reader> means a reader object exists in that slot; emplace constructs it without relocating another reader, and reset closes/releases it. The heap contains indices into those stable slots, not copied readers, spans, or owning files.

std::array::swap later exchanges current and next run owners element by element. Each run's nonthrowing move transfers its Space pointer and slot index. All readers have been closed before that exchange, so no reader retains a reference to a run object whose ownership is changing.

The explicit destructor calls cleanup while all its members still exist. It closes readers, retires names, and attempts directory cleanup. Normal member unwinding then releases scratch arrays, the reservation, Space, and shared handles. Already-reset run owners are harmless. If initialization throws after only one scratch allocation, optional-member destruction releases that allocation.

Admit the minimum useful merge before consuming input

Initialization applies Part 1's formulas with checked size arithmetic. The facade has already validated positive row capacities and a descriptor allowance of at least three. fixed_charge includes the actual allocator request for core/control storage; it is not guessed from sizeof(Core) alone.

Only after proving that the local cap admits generation and a two-input merge does initialization reserve S and allocate the exact chunk and output frame. Root budget admission may still refuse either request. No input row or temporary name has been consumed at this point.

account_workspace checks phase-specific coexistence and records the modeled peak. It runs before opening a group of readers. It includes the dynamic arrays whose allocations follow, while the root ledger independently enforces every actual request. The final streaming pass conservatively retains the output frame even though it is no longer writing an intermediate file. Removing that small unused buffer would be an optimization, not permission to increase earlier fan-in.

Delay the first spill until one more row proves it necessary

If a chunk fills exactly and the upstream ends, the query can still use the no-spill path. Do not spill merely because the chunk became full. On the next append, spill the full previous chunk before copying the arriving event into slot zero. The input batch owns that arriving event throughout the call.

For capacity three, appending rows A, B, and C creates no file. Receiving D sorts and writes A–C, then stores D. If no D exists, finish sorts A–C in memory. Empty filtered input batches never cause a flush or an end transition.

The input cap is checked before appending the row that would exceed it. The query still becomes terminal because its upstream may already have delivered that row inside an owned batch. Rejecting the row is not equivalent to restoring the whole upstream position. Likewise, a failed spill preserves neither a reusable append position nor a promise that previously generated runs remain available: abort cleans this query's temporary work.

std::sort handles only this bounded, contiguous chunk. It is not an external sorting library. In-memory comparison work is O(n\log C) over n input rows with chunk capacity C, ignoring smaller final-chunk effects. External I/O, buffering, pass scheduling, and all merging remain our implementation.

A heap of current heads is enough

For every nonempty input run, the first unread row is the smallest remaining row in that run. Therefore the smallest among those heads is the next global row. No later row can be smaller without violating the run's validated order.

Heap index i has children 2i+1 and 2i+2 and, for i>0, parent \lfloor(i-1)/2\rfloor. Maintain that a parent does not compare greater than either child. before(a,b) compares the owning values at reader slots a and b. Identical records use the reader index as an internal deterministic tie decision; this does not manufacture an input-stability guarantee.

push saves the new reader index and moves larger parent indices downward until its insertion position is reached. It never reallocates and never swaps a reader. At most the height of a heap with k elements is traversed.

For example, three reader heads keyed (account,event) might be (2,8), (1,9), and (2,3). Inserting slots 0, 1, and 2 produces a root at slot 1. Removing (1,9) may advance that reader to (4,1). The root's key increased; repair downward to choose (2,3) before (2,8), not whichever run was opened first.

take copies the winning row before advancing its reader. Advancing may reuse the frame buffer or close the file. If that reader is exhausted, replace the root index with the last heap index and shrink the heap; otherwise its new head remains at the root until downward repair. One repair covers both cases.

A refill exception can occur after selecting a row but before take returns it. The public pull catches that failure, clears the current output batch, and becomes terminal. An earlier separately owned output batch remains valid, but it is only a prefix of a failed query. Returning the selected row and silently skipping a failed refill would be a correctness bug, not graceful degradation.

Readers are inserted one by one. If allocating or opening a later reader fails, the outer terminal cleanup resets every already-engaged reader. Each still-owned run remains available until cleanup deliberately retires it. No descriptor or frame buffer is acquired for a reader beyond the computed group size.

Materialize one replacement before retiring its inputs

For a materialized group, sum its row counts, open at most k readers, then create one output run. The disk reservation still includes all inputs. Repeatedly take the minimum head and append it to the output writer. The writer checks order and count independently of the heap; a broken root repair often fails there before the final oracle comparison.

After checked output close, close/reset input readers but keep their names and run owners. Reopen and fully verify the replacement using one buffer. Only then move the output into the next-pass array and retire the old names. This deliberately adds a verification read of every materialized replacement. Its cost is counted, not hidden as a free assertion.

A singleton group is carried by moving its owner; copying its bytes would provide no reduction in run count. The row at a group boundary belongs to exactly one run and is never consumed merely to determine that the next output is full.

Let R_p be the number of runs before materialized pass p, and let k be fan-in. Grouping gives

R_{p+1}=\left\lceil\frac{R_p}{k}\right\rceil.

Because k\ge2, this strictly reduces any R_p>k. Stop materializing once R_p\le k: those remaining runs can feed the final streaming merge directly. For 25 rows, chunk capacity three, and fan-in two:

Stage Run row counts Newly written files
Initial generation 3,3,3,3,3,3,3,3,1 9
Materialized pass 1 6,6,6,6,1 4
Materialized pass 2 12,12,1 2
Materialized pass 3 24,1 1
Final streaming merge 25 rows delivered as consumer batches 0

merge_passes counts the three completed materialized passes, not the final pull merge. merge_groups counts the seven materialized multi-input groups; singletons are not counted as rewritten groups. A failed partial pass can create completed files without incrementing merge_passes. Those definitions matter when reading failure statistics.

With k inputs, each merged row performs at most O(\log k) heap work. More passes increase total reads and writes. Larger fan-in can reduce passes, but its simultaneous buffers, open files, and replacement space must be admitted together.

Seal once, then stream according to consumer capacity

finish distinguishes the in-memory path from the spill path. No-spill sorts only the visible chunk and releases the unused output frame. Spill mode writes the remaining nonempty chunk, destroys the chunk allocation, materializes necessary passes, and opens the final group. The sealed_ flag is set only after that preparation succeeds.

At no point does the merge collect all output rows in an owning vector. The output consumer can choose capacity one or a larger batch without changing run contents, heap membership, or the sequence of values. The later join will rely on that property when its own batch fills in the middle of a hot account's events.

Cleanup closes readers before retiring either pass's run owners. It may run after a normal end, an error, explicit abort, or destructor abandonment. Run reset is idempotent, and pending cleanup is retried without throwing.

A last nonempty output is still Pull::batch. A subsequent call returns an empty, absorbing Pull::end and releases temporary runs, buffers, and the stack allowance. Abandoning before that call still triggers destructor cleanup. Fixed core/control storage and the observation object remain charged while their owners remain alive.

output_rows advances only after a successful nonempty pull. Rows assembled in a refill that later throws are cleared and do not count as delivered. The lower-level read counters may nevertheless increase: useful output and transferred bytes are different measurements.

The facade validates public options before allocation. It rejects a missing ledger, a missing or previously used report, impossible row capacities, fewer than three run descriptors, a zero disk allowance, or an undersized stack policy allowance. The minimum stack allowance is a policy floor of 16 KiB, not a derived guarantee about every standard-library build.

This closes external_sort.cpp. allocate_shared uses the owning allocator for the actual core/control storage. Its constructor performs no other charged allocation; the difference in allocated() therefore identifies H under the current synchronous, nonreentrant contract. initialize allocates dynamic buffers after that observation. If it throws, constructor unwinding releases the partially built core through the same allocator.

Adapt a progress-producing source to a blocking operator

A sort is a blocking operator: before returning its first correctly ordered row, it must finish consuming the input. After sealing, its output is streamed in bounded batches. These two facts are compatible. Incremental output does not mean we can emit a row before learning whether a smaller key appears later.

Append the remaining header segment. The source is owned by value, as in Chapter 14. The input batch shares its budget and must satisfy that source's required capacity. The consumer output may use any positive capacity on the same ledger.

The loop ends only on Pull::end, which must have an empty batch. An empty Pull::batch causes another upstream step; the source contract requires that step to represent progress. There is no arbitrary "three empty batches means EOF" shortcut. An invalid source that returns empty progress forever can still keep this synchronous call busy; a concept checks the expression shapes, not semantic termination.

built_ becomes true only after finish succeeds. An exception anywhere during input consumption, run generation, merge preparation, or output refill clears current output, marks the adapter failed, and aborts the sort. Calling it again cannot retry consumed input. Incorrect outer capacity or ledger is rejected outside that execution catch and is therefore retryable without losing a sentinel output row.

The defaulted adapter moves use the compiler's member-dependent exception specification. We do not assert that every type satisfying PullSource has a nonthrowing move. The provided source types do, and SortBuffer itself moves by transferring shared ownership. A future throwing source must preserve its own move contract; the concept alone does not provide one.

The source and input batch remain owned until adapter destruction, even after sorting finishes. Thus a storage-backed plan can retain its snapshot throughout output consumption. This is conservative, not free: its source owners and column capacity remain in the common ledger and retention registry. Releasing the upstream early would require an explicit optional-source lifetime change, not a dangling borrow to save a few members.

Count the I/O the implementation actually performs

For the nine-run example, initial output is 1,444 bytes. Materialized passes write 4(264)=1056, 2(468)=936, and 876 bytes. Total successful writes are

W_{\mathrm{io}}=1444+1056+936+876=4312\text{ bytes}.

Each created run is eventually read once as a merge input or a final input. That accounts for another 4,312 bytes. Every materialized replacement is also fully verified, adding 1056+936+876=2868. Therefore successful read transfers are

R_{\mathrm{io}}=4312+2868=7180\text{ bytes}.

Headers and footers are read once per open, and each data frame once per traversal; the verifier does not reread a frame for each row. The independent native fixture checks these totals against the actual file lengths and values. It does not infer SSD traffic or elapsed-time performance from them.
