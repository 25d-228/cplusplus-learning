Chapter 23 — Profiling, optimization, and the final demonstration

Part 3 — Verify, repeat, and explain the result

The optimized recurrence is only useful if it preserves existing data. The query variants are only comparable if they return the same complete answer. This part supplies both checks, runs the final demonstration, and describes the limits of the observed measurements. Keep Parts 1–2 and Chapter 22 source.

Test the recurrence independently of its table

Create tests/measurement.cpp. The reference CRC retains a bitwise expression and does not consult the generated lookup array. Check every prefix of a 1,024-byte pattern under three initial checksums, every possible one-byte input, and the known "123456789" vector. Split each prefix at a third of its length to verify chaining: this catches an incorrect initial/final xor even when a single buffer happens to pass.

The tiny source below makes empty progress observable before a selected row. Its separate failing mode appends a partial input and then throws. This checks state transitions, not merely cleanup at process exit.

A too-small output must be rejected before consuming the source. After that rejection, the first legal call still sees the first row. A failed refill clears output and makes later calls fail rather than retrying the consumed prefix. The final budget check includes the destruction of both good and failed plans.

Compare outputs and work, not just checksums

Create scripts/check_measurement.py. It prepares 123 events and 17 accounts and runs all four plans against a selective interval, an empty interval, and the entire unsigned day domain. The analytical formula and bounded mutation replay must agree before either is used to check CSV. This is 12 complete query executions, not a hash of output produced by the same query implementation.

The early variants must have identical sort traffic and run counts. Moving a predicate later must increase first-sort spill writes in the selective fixture. Those assertions distinguish physical work from elapsed-time noise. A rejected configuration must leave an already completed answer unchanged.

Append these targets and options to the existing root CMakeLists.txt. The checksum table is on by default, while timing instrumentation is off. The compile definitions are public so the linked measurement executable reports the same choices as its core library. There is no download, database dependency, or benchmark framework.

Build matching baseline and candidate binaries

Use the native compiler selected in Chapter 1. The commands below intentionally do not require one compiler version or fabricate an LTS designation. Both builds use the same build type; only the checksum option differs. Keep profiling and sanitizer flags out of these performance builds.

A separate memory-sanitized build remains a correctness experiment. Its allocator, layout, and instrumentation costs cannot establish optimized throughput.

Now run the actual comparison. raw is portable as an unconverted observation; use kib on Linux after confirming its documented units, or bytes when the installed Mac manual specifies bytes. Record the chosen interpretation.

Avoid other builds or deliberate stress processes while collecting comparison samples. The harness runs all samples sequentially; it does not reserve exclusive hardware or make a shared machine quiet. Keep rejected or noisy trials separate rather than selecting the best repetitions after seeing their times.

A separate instrumented build can locate CRC work without contaminating that comparison. The reset/read operations concern the current synchronous query thread only. Thirty repetitions make small regions easier to inspect while opening the master input just once.

Its crc_calls, crc_bytes, and crc_seconds expose execution count, processed volume, and elapsed scope time. A real parser rejects a profile counter that saturated. The main harness refuses these records even if the result is correct.

Observe admission at a controlled pause

At the live scenario's existing two gates, both requests are admitted and cannot complete until their gates are released. Add these observations to apps/scenario.cpp. This changes no scheduling or storage decision. The fixed source upper bound and both sort allowances require 29 descriptor slots per task; two tasks hold 58. A reservation is an admission promise, not a claim that 58 native descriptors are open or 4 MiB have been allocated.

The joined executor must return both admission counters to zero. Its recorded peak is separate from query-local charged peaks and resident memory. Calling stats() at an arbitrary moment would not establish the same boundary; the already-implemented gates make the observation repeatable.

Run the combined demonstration

Create scripts/final_demo.py. It orchestrates the existing mechanisms; it does not introduce another recovery algorithm or hide missing synchronization inside a shell sleep. First, the controlled live scenario holds the old sequence while writes and maintenance advance the engine. It rejects excess retention, cancels a spilling query, then releases owners and collects obsolete files.

Independently check the old and new files. The reopened query runs in a separate process against the same live-scenario database, after the original engine has finished. Cancellation must preserve the previous complete output verbatim.

The persistence model, parent-controlled SIGKILL campaign, and resource-pressure campaign are separate experiments with separate assumptions. Run all of them, then rerun the variant boundaries. A failed stage keeps its diagnostic files and leaves complete=false. No automatic deletion or blind retry is performed.

The default live workload has a base at sequence 5 and a delta at sequence 6. It forces both query sorts to spill, retains the old answer across ingestion and compaction, preserves canceled output, and checks the reopened fresh answer. The recovery stage explores Chapter 22's 2,754 selected crash images, its native 26 stop-point kills, and pressure failures. This script does not turn those bounded campaigns into exhaustive interleaving or physical power-loss tests.

Observations from an executed run

The following are observations from Clang 17, Linux x86_64, using matching RelWithDebInfo builds (-O2 -g -DNDEBUG), the 20,000-event fixture, seed 23, batch capacity 256, chunk capacity 512, block capacity 64, and fan-in four. Each pair had one excluded warmup and five measured fresh-process samples. OS caches were not cleared. No deliberate build or profiling job ran during this final comparison. These are not M4 measurements or production tail estimates.

The bitwise batched median was slightly slower than its one-row median in this run. That is retained rather than recast as a batching success. The candidate batch and fused timings are close and their ranges overlap; five repetitions do not establish a stable timing advantage for fusion. The batch checksum comparison was about 2.68 times faster by the ratio of these sample medians. That number applies to this workload/build/environment, not to CRC implementations generally.

The separate instrumented baseline executed 2,832 CRC calls over 5,571,838 bytes per query. Across 30 in-process repetitions, median accumulated CRC scope time was 72.69 ms and median query elapsed time was 99.35 ms. These are elapsed instrumented regions, not reliable CPU percentages or uninstrumented latency. Together with the format-preserving toggle, they support CRC as a consequential cost in this fixture. The warning-bearing sampling profile was not used for quantitative attribution.

All plans returned 40 groups from the same 10,000 joined events at sequence 80. The second sort had 20 initial runs; both sorts made two materialized merge passes. Fusion removed exactly 9,216 bytes from the observed charged peak here. It did not change spill traffic. Late filtering increased first-sort writes from 796,240 to 1,694,448 bytes. The number of passes remained two, but the first sort processed twice as many rows and generated more frames/runs. A pass count alone would conceal that increase.

Every plan recorded 20,194 table bytes during isolated capture, then 1,053,396 table bytes and 259 block loads during query reads. Its private cache recorded 259 misses and one hit. These are engine counters, not physical disk traffic or processor cache statistics. They are consistent across the controlled plans.

The workload contained 603,598 logical input bytes. Generation took 1.323 s, load-and-settle 0.310 s, explicit base repacking 0.107 s, and reopening/verification 0.039 s as parent-observed command intervals. The named ingestion rate was about 1.94 million logical bytes/s, including the costs listed in the report. These single phase observations are not repeated throughput estimates. The explicit compaction process reported one job: 1,073,590 bytes read and the same number written. Its output/logical-input ratio is approximately 1.78; it is a ratio for that one explicit base repack, not cumulative lifetime write amplification.

Candidate process high-water observations ranged from 98,787,328 to 99,180,544 bytes after Linux KiB conversion, despite query charged peaks below 0.6 MiB. That difference is not an unexplained ledger leak: the two measurements cover different objects and intervals. In particular, Linux resource observations survive exec, and process launch/opening history can influence this high-water value (getrusage notes). It is not query-only resident memory. Phase-specific resident-memory sampling with the native profiler is needed to attribute that value; do not subtract it from the query ledger or claim a 32 MiB process cap.

In the controlled live demonstration, the paused old and cancelable queries hold 4,194,304 reserved bytes and 58 descriptor slots together. After joined shutdown both admission counts return to zero. The old sequence-5 query produces 16 groups; sequence 6 produces 24. Each completed query makes five materialized passes in each sort. Cancellation preserves its previous completed output, reopening preserves sequence 6, and the final collection removes two obsolete files. Reserved allowance, charged allocations, observed resident memory, and retained disk files are four distinct quantities.

Both optimized builds passed all 39 CTest entries. The candidate also passed all 39 in a Debug AddressSanitizer/UndefinedBehaviorSanitizer build. The canonical listings reconstruct 124 learner source/build files. The independent variant and final-demo checks passed. The empty-means-end diagnostic below failed the intended assertion in optimized and memory-sanitized builds without a sanitizer memory report; the correct implementation remains in these listings.

Limits: native M4/macOS execution, Apple full-device synchronization, hardware power-loss durability, larger-scale throughput, and representative tail latency remain unverified. No speedup is required when repeating the experiment.

Make one deliberate defect visible

Temporarily change the fused operator's successful return from Pull::batch to output.size() ? Pull::batch : Pull::end. Rebuild only strata-measurement-tests and run it. The expected failure is filtered empty is not end, before memory safety tools need to report anything. Restore the correct return and rerun the unit and native checks. This is a semantic defect in a valid-memory program.

The checksum optimization has a different failure mode: an incorrect recurrence can make both writers and readers agree with each other while disagreeing with the prior format. Retain the independent bitwise oracle, known vector, split checks, and the existing Python/native file decoders. A self-consistent roundtrip alone is not compatibility evidence.

Diagnose discrepancies before tuning another parameter

Observation Check next
Different sequence or CSV between variants Stop timing; inspect capture and predicate placement.
Early-plan spill bytes differ Verify equal chunk/block settings and projected fields; batching alone should not change this fixture's runs.
A profile shows nearly no samples or warns about its timer Treat percentages as unusable; use another collector or the scoped experiment.
Charged peak falls but resident maximum does not Check measurement lifetime, opening peak, allocator retention, and RSS units.
CPU time is much smaller than elapsed Inspect scheduling, filesystem delays, and wait states; do not infer one cause from the difference alone.
maximum initial runs or workspace rejection Check the late plan's unfiltered count, \lceil n/C\rceil, and simultaneous memory before increasing a limit.
Result is correct but cleanup checks fail Preserve the diagnostic; a published answer does not imply reclaimed temporary disk.
A failure run appears much faster Exclude it from success latency; compare only completed, independently verified answers.

A useful variation is to change the predicate to select almost every day while keeping the data, chunk, and batch settings fixed. Predict the first-sort run counts before executing. As selectivity approaches one, the early predicate's spill-volume advantage should disappear. The fused path can still remove an intermediate copy. If timings regress, retain the observation and explain the additional operator or cache effects instead of changing the answer definition.

What is now complete

Strata connects explicit record encodings, lifetime-safe ownership, a prepared skip-list batch, WAL-backed publication, immutable indexed tables, pinned cache entries, manifest authority, snapshot retention, streaming compaction, bounded external sorts, a many-to-one merge join, checked aggregation, cooperative cancellation, and a supervised live runtime. The demonstrations exercise these as one system rather than isolated feature names.

The scope remains deliberately single-node, fixed-schema, and single-writer. There is no general SQL parser, arbitrary many-to-many join, distributed commit, lock-free index, or unbounded disk-backed run catalog. The measured fixture is smaller than the roadmap's exploratory 512 MiB–1 GiB scale; it does not establish that larger scale. Increasing data requires checking table, catalog, disk, retention, and admission bounds while preserving spill and dimension-streaming conditions. The implemented difficult mechanisms are not replaced with a wrapper to avoid those constraints.

On the M4, rerun correctness first, then record the actual compiler, flags, local memory units, workload, and measurements. Do not transfer the Linux times or a CRC speedup ratio to that hardware. A useful result is an independently correct answer accompanied by a defensible explanation of its work, costs, and failure boundaries—not a required performance number.
