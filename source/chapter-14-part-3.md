```cpp title="tests/query_pipeline.cpp — complete file, segment 2"
public:
    TemporaryDirectory() {
        char pattern[] = "/tmp/strata-query-XXXXXX";
        const auto path = ::mkdtemp(pattern);
        if (!path) { throw std::system_error(errno, std::generic_category(), "mkdtemp"); }
        name_ = path;
    }
    ~TemporaryDirectory() noexcept {
        std::error_code ignored;
        std::filesystem::remove_all(name_, ignored);
    }
    TemporaryDirectory(const TemporaryDirectory&) = delete;
    TemporaryDirectory& operator=(const TemporaryDirectory&) = delete;
```

Append the plan constructor and consumer:

```cpp title="tests/query_pipeline.cpp — complete file, segment 3"
const std::vector<Event> day_three{
    {100, 10, 3, 500}, {101, 10, 3, 250}, {102, 20, 3, 700}, {103, 99, 3, 50}};
const std::vector<Event> day_four{{104, 10, 4, 100}};
Plan plan(ReadView view, std::size_t capacity, DayRange days) {
    return Plan{EventFilter<EventScan>{EventScan{std::move(view)}, days, capacity}, capacity};
}
struct Observed {
    std::vector<Event> rows;
    std::vector<std::size_t> batch_sizes;
};
Observed drain(Plan& pipeline, EventBatch& output) {
    Observed result;
    for (std::size_t calls = 0; calls < 100; ++calls) {
        if (pipeline.next(output) == Pull::end) {
            check(output.size() == 0, "end has no rows");
            check(pipeline.next(output) == Pull::end && output.size() == 0, "end is absorbing");
            return result;
        }
        result.batch_sizes.push_back(output.size());
        for (std::size_t i = 0; i < output.size(); ++i) { result.rows.push_back(output.row(i)); }
    }
    throw std::runtime_error("fixture stream did not end");
}
Observed run(ReadView view, std::size_t capacity, DayRange days) {
    auto pipeline = plan(view, capacity, days);
    EventBatch output{view.budget_owner(), capacity};
    return drain(pipeline, output);
}
```

`drain` checks `Pull::end` before reading rows. A zero-row `batch` is recorded and
followed by another pull. Its hundred-call guard is a fixture diagnostic against
an accidentally nonprogressing source, not an arbitrary production query limit.
After end it calls once more with valid output to verify absorbing completion.

The consumer copies each event into a test-owned result vector before refilling
`output`. That vector is an oracle convenience only. A bounded production sink
would process rows incrementally; it must not collect an entire query merely
because this tiny fixture does.

## Test the complete ownership state, not only the values

Begin the first check. A capacity-three `EventBatch` charges exactly 84 bytes.
An injected failure at each of its four replacement allocations must leave the
original capacity, rows, and existing borrowed spans unchanged.

```cpp title="tests/query_pipeline.cpp — complete file, segment 4"
void check_batch_ownership() {
    auto budget = std::make_shared<memory::Budget>(1024 * 1024);
    {
        EventBatch batch{budget, 3};
        check(budget->allocated() == 84 && batch.capacity_bytes() == 84, "charge all four columns");
        batch.append({100, 10, 3, 500}); batch.append({101, 20, 4, 250});
        const auto before = batch.columns();
        check(before.days.size() == 2 && before.days[1] == 4, "borrow only initialized rows");
        check(&before.event_ids[1] == before.event_ids.data() + 1, "unit column stride");
        for (std::size_t allocation = 1; allocation <= 4; ++allocation) {
            budget->fail_allocation_on(allocation);
            expect<std::bad_alloc>([&] { batch.replace_capacity(7); });
            budget->clear_failure();
            check(budget->used() == 84 && batch.size() == 2 && batch.capacity() == 3,
                  "failed replacement preserves capacity and rows");
            check(before.amounts[0] == 500 && before.event_ids[1] == 101,
                  "failed replacement preserves old borrows");
        }
        EventBatch moved{std::move(batch)};
        check(batch.size() == 0 && batch.capacity() == 0 && moved.row(0).event_id == 100,
              "move transfers complete row shape");
        // Deliberately reacquire from the new named owner instead of using before again.
        const auto after = moved.columns();
        check(after.amounts[1] == 250, "reacquired columns after move");
        batch.replace_capacity(1); batch.append({9, 9, 9, 9});
        batch = std::move(moved);
        check(moved.capacity() == 0 && batch.size() == 2 && budget->used() == 84,
              "move assignment releases destination storage");
        auto& alias = batch; batch = std::move(alias);
        check(batch.row(0).amount_cents == 500, "self move preserves batch");
        batch.clear();
        check(batch.size() == 0 && budget->used() == 84, "clear retains charged capacity");
        batch.replace_capacity(2);
        check(batch.size() == 0 && budget->used() == 56, "successful replacement installs empty storage");
        batch.append({1, 1, 1, 1}); batch.append({2, 2, 2, 2});
        expect<std::length_error>([&] { batch.append({3, 3, 3, 3}); });
        check(batch.size() == 2 && batch.row(1).event_id == 2, "full append does not overwrite");
        expect<std::out_of_range>([&] { (void)batch.row(2); });
    }
```

The test reacquires column spans after moving the owner. It intentionally does
not dereference the previous borrow after that successful move, even though the
underlying allocation transferred without changing address. A named-owner
contract is easier to reason about than relying on whichever object happens to
keep an allocation alive.

After `clear`, zero rows still cost 84 bytes. After successful replacement with
capacity two, the cost becomes 56 and the rows are empty. Filling both slots and
attempting a third append must preserve the two existing rows. These tests would
catch “increment the count first” errors that an address sanitizer need not find.


A scan batch has five allocations, so failing its fifth acquisition must destroy
all four already-built event columns. The account replacement fails at its second
acquisition while the first candidate column is live. Both paths return charges
without losing the previous batch's values.

The cross-ledger move is important. The destination initially owns storage charged
to `other`; afterward that ledger is zero and the destination owns the source's
arrays under `budget`. Moving a pointer without its matching allocator would make
one ledger leak charges and the other underflow at destruction.

The overflow case passes a capacity one greater than `SIZE_MAX / 36`. It must fail
before acquiring a partial five-column batch. A zero-capacity or null-ledger owner
is rejected rather than introduced as a special uncharged output mode. A moved-from
batch can have zero capacity internally, but cannot serve as a valid pull target
until reconfigured.

## Make an empty first result observable

The next check first selects day 4 at capacity three. Its first result must be a
zero-row **batch**, followed by the event 104. Only afterward do we compare the
one-row and three-row day-3 executions.

```cpp title="tests/query_pipeline.cpp — complete file, segment 6"
void check_pipeline_boundaries() {
    TemporaryDirectory path;
    auto budget = std::make_shared<memory::Budget>(8 * 1024 * 1024);
    {
        Database db{budget, path.name(), DatabaseOpen::create, tiny_options()}; seed(db);
        auto view = db.snapshot();
        const auto late = run(view, 3, DayRange{4, 5});
        check(late.rows == day_four && late.batch_sizes == std::vector<std::size_t>{0, 1},
              "empty filtered batch must not end the stream");
        const auto scalar = run(view, 1, DayRange{3, 4});
        const auto batched = run(view, 3, DayRange{3, 4});
        check(scalar.rows == day_three && batched.rows == day_three, "scalar and batch match explicit rows");
        check(scalar.batch_sizes == std::vector<std::size_t>{1, 1, 1, 1, 0}, "one-row baseline steps");
        check(batched.batch_sizes == std::vector<std::size_t>{3, 1}, "final short batch");
        const auto none = run(view, 3, DayRange{8, 9});
        check(none.rows.empty() && none.batch_sizes == std::vector<std::size_t>{0, 0}, "all filtered steps");
        check(run(view, 3, DayRange{3, 3}).rows.empty(), "empty day interval");
        AccountScan accounts{view}; AccountBatch out{budget, 1};
        for (const auto expected : {Account{10, 1}, Account{20, 2}}) {
            check(accounts.next(out) == Pull::batch && out.size() == 1 && out.row(0) == expected,
                  "accounts retain unique primary order");
        }
        check(accounts.next(out) == Pull::end && out.size() == 0, "account end");
```

The same test checks two empty filtered steps when no days match, an empty day
interval, and ordered account scanning. A source that stops on the first empty
filtered result loses event 104; a source that crosses the relation bound may try
to decode account bytes as events.

Before the first pull, a capacity-three plan and output must add exactly 300
column bytes. Reserve all remaining ledger headroom, then execute: the lazy cursor
cannot allocate. The current output stays empty and the outer plan becomes
terminal. Releasing the reservation does not authorize retrying that plan.

The fourteen deterministic construction failures are ten scratch-column
allocations plus four output-column allocations. They do not assume the size or
allocation count of an implementation-defined shared-pointer control block: the
cursor has not been created yet. Every failed construction returns to the same
baseline of retained storage.

The final two misuse cases are different from execution failure. An output that
is too small, or belongs to another budget, is rejected by the outer preflight
without changing its sentinel row or consuming upstream input. A subsequent
valid output still receives the complete expected relation.

## Exercise true emptiness and exact exhaustion

An empty relation must end directly, rather than repeatedly return empty batches.
A relation containing only accounts must not appear as event data. Six live
events with capacity three must give exactly two full batches and then end.
The maximum day must fit a half-open interval without overflow.

```cpp title="tests/query_pipeline.cpp — complete file, segment 8"
void check_empty_exact_and_days() {
    TemporaryDirectory path;
    auto budget = std::make_shared<memory::Budget>(8 * 1024 * 1024);
    {
        Database db{budget, path.name(), DatabaseOpen::create, tiny_options()};
        auto empty = db.snapshot();
        check(run(empty, 3, DayRange{0, std::uint64_t{1} << 32}).batch_sizes.empty(), "empty relation ends directly");
        AccountScan accounts{empty}; AccountBatch out{budget, 3};
        check(accounts.next(out) == Pull::end && out.size() == 0, "empty account relation");
        const std::array only_account{Mutation::put(Account{10, 1})}; commit(db, only_account);
        check(run(db.snapshot(), 3, DayRange{0, 10}).rows.empty(), "event scan cannot cross into accounts");
        std::array<Mutation, 6> rows{};
        for (std::size_t i = 0; i < rows.size(); ++i) {
            rows[i] = Mutation::put(Event{i, 10, std::numeric_limits<std::uint32_t>::max(), i});
        }
        commit(db, rows);
        const auto result = run(db.snapshot(), 3,
            DayRange{std::numeric_limits<std::uint32_t>::max(), std::uint64_t{1} << 32});
        check(result.rows.size() == 6 && result.batch_sizes == std::vector<std::size_t>{3, 3},
              "exact exhaustion and maximum day");
        for (std::size_t i = 0; i < result.rows.size(); ++i) {
            check(result.rows[i] == Event{i, 10, std::numeric_limits<std::uint32_t>::max(), i},
                  "every maximum-day row matches");
        }
        check(run(empty, 3, DayRange{0, 10}).rows.empty(), "empty snapshot stays empty");
    }
    expect<std::invalid_argument>([] { (void)DayRange{4, 3}; });
    expect<std::invalid_argument>([] { (void)DayRange{0, (std::uint64_t{1} << 32) + 1}; });
    expect<std::logic_error>([] { (void)EventScan{ReadView{}}; });
    check(budget->used() == 0, "empty/exact fixture cleanup");
}
```

The original empty snapshot remains empty after writes. That check distinguishes
a query over an immutable read state from a query that silently asks the mutable
database for a new view on each pull. The 64-bit interval endpoint includes every
possible 32-bit day; the rejected endpoint above that bound is a configuration
error, not a wrapped predicate.

## Pause queries while storage changes beneath their owners

This is sequential interleaving, not a concurrency test. The first plan reads
from a retained memory source and pauses after three output rows. A second plan
later pauses over table sources. Between pulls, the database accepts updates,
flushes, compacts, and tries to collect obsolete files.

```cpp title="tests/query_pipeline.cpp — complete file, segment 9"
void check_snapshot_interleaving() {
    TemporaryDirectory path;
    auto budget = std::make_shared<memory::Budget>(8 * 1024 * 1024);
    {
        Database db{budget, path.name(), DatabaseOpen::create, tiny_options()}; seed(db);
        {
            auto old = db.snapshot(); auto old_plan = plan(old, 3, DayRange{3, 4});
            EventBatch held{budget, 3};
            check(old_plan.next(held) == Pull::batch && held.size() == 3, "pause old query");
            const auto borrowed = held.columns();
            const std::array changes{Mutation::put(Account{10, 3}),
                Mutation::put(Event{101, 10, 3, 900}), Mutation::erase({Relation::events, 102})};
            commit(db, changes); auto newer = db.snapshot();
            check(db.flush_oldest() && db.flush_oldest(), "flush both histories");
            auto disk_view = db.snapshot(); auto disk_plan = plan(disk_view, 1, DayRange{3, 4});
            EventBatch disk_first{budget, 1};
            check(disk_plan.next(disk_first) == Pull::batch && disk_first.row(0) == day_three[0],
                  "pause disk query");
            db.compact_prefix(db.manifest().table_count, {{128, 256, 32, 4096}, 16, 65536});
            check(db.collect_obsolete().retained >= 4, "paused plans retain old WALs and tables");
            check(borrowed.amounts[1] == 250 && borrowed.event_ids[2] == 102,
                  "batch owns rows independently of maintenance");
            EventBatch tail{budget, 3};
            check(drain(old_plan, tail).rows == std::vector<Event>{{103, 99, 3, 50}}, "old stream resumes");
            const std::vector<Event> changed{{100, 10, 3, 500}, {101, 10, 3, 900}, {103, 99, 3, 50}};
            check(run(newer, 3, DayRange{3, 4}).rows == changed &&
                  run(db.snapshot(), 3, DayRange{3, 4}).rows == changed, "new views agree after compaction");
            EventBatch disk_tail{budget, 1};
            check(drain(disk_plan, disk_tail).rows == std::vector<Event>(changed.begin() + 1, changed.end()),
                  "old table stream survives reclamation attempt");
            AccountScan before{old}; AccountScan after{newer}; AccountBatch account{budget, 1};
            check(before.next(account) == Pull::batch && account.row(0) == Account{10, 1}, "old account snapshot");
            check(after.next(account) == Pull::batch && account.row(0) == Account{10, 3}, "new account snapshot");
        }
        check(db.collect_obsolete().retained == 0, "releasing plans permits reclamation");
    }
    check(budget->used() == 0, "interleaved snapshot cleanup");
    std::cout << "paused memory/table queries survive writes, flush, compaction, and collection\n";
}
```

The older query still sees event 101 at 250 cents and event 102 alive. The newer
query sees event 101 at 900 and no event 102. Old and new account scans observe
regions 1 and 3 respectively. The result does not combine one snapshot's account
row with another snapshot's event row.

The borrowed `held.columns()` view survives maintenance because its batch is
neither mutated nor destroyed during those operations. It does not borrow the
memtable or table storage. Separately, source ownership keeps the old WALs and
tables protected from collection until their read states disappear. Owning decoded
output and retaining snapshot inputs are different lifetime obligations.

After the inner scope releases all plans/views, reclamation reports no retained
obsolete files. An exhausted plan can still retain its view until destruction;
end-of-stream is not an implicit promise to release the snapshot's entire lifetime.

## Let the database and root handle disappear first

A plan can escape the database's scope because its scan owns the read state. A
completed output batch can then outlive the plan because it owns its fields and
its budget handles. Use a weak pointer only as a test observation of when the
last owning handle disappears:

```cpp title="tests/query_pipeline.cpp — complete file, segment 10"
void check_escaped_owners() {
    TemporaryDirectory path;
    std::weak_ptr<memory::Budget> weak;
    std::optional<Plan> pipeline;
    std::optional<EventBatch> output;
    {
        auto budget = std::make_shared<memory::Budget>(8 * 1024 * 1024); weak = budget;
        Database db{budget, path.name(), DatabaseOpen::create, tiny_options()}; seed(db);
        pipeline.emplace(plan(db.snapshot(), 3, DayRange{3, 4}));
        output.emplace(budget, 3);
        budget.reset();
    }
    check(!weak.expired() && pipeline->next(*output) == Pull::batch, "query works after database destruction");
    const auto columns = output->columns();
    pipeline.reset();
    check(!weak.expired() && columns.amounts[1] == 250 && output->row(2) == day_three[2],
          "output survives all source owners");
    output.reset();
    check(weak.expired(), "last column releases root ledger after deallocation");
    std::cout << "escaped plan and output release the final budget owner cleanly\n";
}
```

The first pull occurs **after** the database and caller's budget handle are gone.
After releasing the plan, output still contains the three decoded events. At that
point it needs no file or directory lock, only its own column allocations and their
ledger. Resetting the final output releases storage before the last budget owner;
the weak pointer then expires. A dangling borrowed `Budget&` would not satisfy
this destruction order.

## Reject malformed rows and abandon a failed refill

Start the final check with invalid visible-entry shapes. The decoder rejects an
unsupported record version, a disagreeing key, a tombstone, a zero sequence, and

For an actual pull failure, write eight events to a table and successfully consume
one row. Then alter one byte in a later data frame. The frame is not retained by
the deliberately undersized cache. This is a controlled fixture violation of the
engine's immutable-file assumption, not permission for applications to edit open
tables.

Each event entry uses 22 bytes of table entry framing plus 30 bytes of encoded
payload. A 128-byte data payload holds a four-byte count and two such entries.
The complete frame therefore occupies

$$
12 + 4 + 2(22 + 30) = 120\text{ bytes}.
$$

The header occupies 24 bytes. The third frame starts after two 120-byte frames;
its payload begins after its eight-byte frame prefix. The injected byte offset is

$$
o_{\mathrm{damage}} = 24 + 2(120) + 8 = 272.
$$

Those are this fixture's verified format/layout choices, not arbitrary offsets to
use on a differently configured table. Finish the test file:


The defective branch has no invalid memory access. It gives the caller a false

Other symptoms point to different boundaries. A nonzero ledger after an allocation
failure suggests a partially constructed column owner or a mismatched allocator.
Old output changing after a storage advance suggests that encoded bytes escaped
instead of being decoded and copied. A full final batch repeating forever suggests
that the scanner did not advance or did not preserve its ended state. A different
answer after compaction suggests a source-lifetime or snapshot-selection error,
not a reason to patch the filter predicate.

For a small variation within the implementation allocation, use capacity two.
The day-3 batch sizes should be `2, 2, 0`; the day-4 sizes should be `0, 0, 1`.
The same plan plus output then holds 200 column bytes, not a smaller capacity
charge when only one row passes. Predict these results before adding the checks.
Do not turn this logical call-count comparison into an unsupported throughput
claim; useful timing and workload controls come later.

## Boundary reached

The engine now has owning charged column batches, a synchronous pull protocol,
event and account snapshot scans, stable filtering, and narrow projection.
Output owns its values independently of the current storage cursor; operators
retain the source generation for their lifetime. Empty progress and permanent
completion have different results. Refill failure clears the candidate batch and
requires a fresh query rather than guessing how much input to retry.

These operators do not sort, join, aggregate, schedule threads, or provide a
whole-query success artifact. They establish the data and ownership contracts
those mechanisms need. **Next is Chapter 15 — External sorting with bounded
fan-in**, where bounded in-memory chunks become spill runs and a multi-pass merge.
