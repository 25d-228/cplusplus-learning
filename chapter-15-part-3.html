Chapter 15 — External sorting with bounded fan-in

Part 3 — Pressure, corruption, and the native run oracle

This is the final part of the same 6.0-hour chapter. Complete Part 1 and Part 2 first. The remaining files exercise the implementation, not a simplified replacement. Keep every earlier CTest entry.

A sorted output alone is not enough. We need to distinguish input exhaustion from empty progress, account for input/output coexistence, observe failure after a successful prefix, and establish that a retained output batch owns its values. The fixture deliberately keeps its reference vectors outside the engine budget: they are an oracle, not workspace silently available to the algorithm.

Construct a source with observable empty progress

Create tests/external_sort.cpp. The test-only outer directory removes everything it owns when the test ends. That broad fixture cleanup is not the engine's cleanup policy: assertions inspect live names, counters, and directory emptiness before the fixture disappears. The engine removes only its registered names.

The independent comparator constructs value tuples rather than calling EventOrder. A shared ordering bug should not make the implementation and its oracle agree by construction. Small reference vectors may use std::sort; the code under test still generates and merges actual files.

Source alternates an empty batch with a data batch. It may also emit empty progress immediately before end. Once ended_ is set, it never returns a batch again. Its borrowed fixture span is safe because every test's rows owner outlives the plan. This is a fixture-specific borrowing contract, not permission for the query engine to retain arbitrary caller buffers.

drain accepts only nonempty output batches from this particular sealed sort. That is stronger than the general upstream protocol: consuming all source input has already happened before the first sorted batch is exposed. The second end call checks absorption rather than assuming it.

Check boundaries before large inputs

With chunk capacity three, counts zero through three must create no run files. Count four must spill. Counts six and seven distinguish an exact chunk boundary from a partial final chunk. Count 384 fills exactly 128 initial-run slots without requiring a 129th descriptor. Output capacities one and seven cut across all of those boundaries independently.

For 25 rows, assert the exact nine initial runs, three materialized passes, seven merge groups, and sixteen completed files. The read total includes verification of intermediate outputs; it is not simply twice the write total. After drain, all temporary names and descriptors must be gone even though the plan and report are still alive. Their fixed object storage can remain charged until destruction.

Separate misuse from a failed execution

A call before finish() is misuse. A destination belonging to another ledger is also rejected before consuming a row or clearing that destination. Neither needs to poison an otherwise usable sort. A genuine execution failure after input has been consumed is different: the source position cannot be reconstructed by simply trying the same call again.

Moving the facade preserves the stable Core address. Move assignment first releases the destination's previous owner; it does not overwrite raw pointers to live files. The rejected options exercise initialization before disk effects.

The workspace test measures the current implementation's fixed allocation, then chooses an allowance that fits exactly two or four input frames. The descriptor allowance is deliberately generous, so bytes, rather than descriptor count, select the fan-in. For block capacity two, F=12+28(2)=68 bytes. At fan-in four, the nine runs require one materialized pass: 9\to3, followed by streaming output. At fan-in two, they require three: 9\to5\to3\to2.

One byte below H+S+3F cannot support two inputs and one output. Rejection must happen before a row is consumed. Exact duplicate records and maximum unsigned fields check both equivalence and the codec's endpoint behavior; no signed subtraction is used to determine their order.

Make file failures concrete

The hook is a synchronous diagnostic seam, not a scheduler or callback framework. Its context is borrowed and must outlive the plan. The hook sees the complete private-directory path and the current operation's file ID and offset. It may throw before an operation or alter a just-completed file for the next reader. It must not reenter the sorter.

The disk failure occurs before the operation at offset 104: the 36-byte header and one 68-byte data frame already exist. This checks preservation of an actual successful write prefix, not a fictitious rollback to an empty file. Chapter 6 already tests short system transfers within File::write_all; this seam tests how the enclosing owner handles a later operation's failure.

The huge-header and wrong-order cases recompute their CRCs. They must therefore be rejected by structural and semantic validation, not accidentally by an earlier checksum mismatch. The copy mode is only for the independent small-file oracle; these extra test copies are explicitly outside engine disk accounting.

Each early failure must clear the current output and retire every owned run. A missing run counts as confirmed absent during cleanup; the descriptor owner must not treat a failed openat as an acquired file. In the injected disk failure, write_bytes remains 104 and completed_files remains zero. Those are different facts: partial bytes transferred are real even though no usable run exists.

The terminal-state assertion follows the first exception. It prevents a seemingly successful retry that silently omits input already consumed before failure.

Fail after returning a valid batch

Use a five-row first run with two-row frames. Returning event zero advances that reader to event one without reading its second frame yet. Arm the mutation only after that first output. The next take copies event one, then advancing the reader reaches offset 104 and discovers corruption. That call does not publish its partial output: it clears it and terminalizes the stream. The separately owned earlier batch still contains event zero.

Cleanup failure is not the same as a wrong query result. With unlink deliberately refused, a correct result can finish while two files remain registered and charged. The report retains the first error, live-name count, directory path, and disk reservation. After removing the refusal, retry_cleanup() confirms deletion and releases the charge. Destroying the sort also attempts bounded cleanup; it cannot promise that the operating system will grant permission.

Charge coexistence, not just completed input

A 1,500-byte disk allowance admits the initial 1,444 bytes but cannot admit the first 264-byte replacement alongside them. Deleting an input early would hide that shortage by sacrificing failure safety. Instead the operation fails and owned temporary files are cleaned up.

Allocation injection walks charged acquisition ordinals until the first complete success. This includes construction, column buffers, chunks, and merge-reader frames. Every failed attempt is followed by zero outstanding run files and zero remaining budget charge after its scope ends. The number of failure boundaries is observed, not fixed as a portable ABI requirement.

Connect the actual storage scan

The integrated plan uses an immutable database view, then EventScan -> EventFilter -> EventProject -> ExternalSort. The first four events have day zero; the remaining 25 have day three. With upstream capacity two, the first two scan batches produce no matches. A sorter that mistakes either empty batch for end would create no useful output and never exercise spilling.

No intermediate vector of all query rows is passed to the engine. Only the test fixture and the independent expected result use vectors outside the ledger. The plan's input and output batches, snapshot, and sort all share the same budget.

Pausing after one output leaves the final two input runs live. Destruction must close readers before retiring those names. The next case consumes all remaining root-budget headroom before final merge initialization. The sort-local plan may fit, but the shared budget can still reject a reader. Releasing that pressure must not revive a failed stream.

Finally, reset the caller's budget handle before finishing a spill. The sort, output, report, and allocator controls still own the ledger. A weak observation expires only after their final releases. This catches a lifetime error that a numerically correct charge counter alone cannot detect.

Keep completed native files for a separate decoder

The special fixture invocation copies each completed file to the caller's test directory before ordinary engine cleanup. It checks the query result independently and prints only deterministic transfer counters for the Python harness. Normal invocation runs every test group, including exact no-spill boundaries and the largest permitted initial-run count in this tiny configuration.

Create scripts/check_sort_fixture.py. This script uses Python's struct and zlib, not the C++ codec, to inspect actual files. Loading these tiny test images into memory is an oracle convenience; the engine reader remains block-bounded.

The decoder checks the independently derived exact file length before walking frames. It requires canonical full blocks except the last, checks every CRC, then checks record order and the footer's counts. A checksum alone would not prove that the run contains the intended rows.

IDs 1 through 9 are initial runs. IDs 10 through 13 merge adjacent initial pairs; run 9 is carried forward unchanged. IDs 14 and 15 merge those four replacements, and ID 16 merges 14 and 15. Final output merges 16 with the carried run 9.

The harness verifies each relationship using decoded values, then adds actual file lengths to check the 4,312-byte write counter. It does not merely compare a second formula with the first formula. Completed-file copies remain test artifacts and are removed by Python's temporary-directory owner.

Build and run the cumulative checks

Append the following targets to the existing root CMakeLists.txt. Python was already discovered by earlier chapters; do not add a second incompatible Python configuration or remove prerequisite tests. No third-party sort, queue, or storage library has been introduced.

From the learner source root, configure separate build directories. The compiler must support the already-used C++20 features; no new tool version gate is added. On the target Mac, inspect the selected native compiler and SDK as in Chapter 1. Equivalent maintained toolchains are acceptable.

The complete tree now has 22 CTest entries. The normal sort program should finish with external sort: all checks passed. Its 25-row trace must report nine initial runs, three materialized passes, fan-in two, 4,312 write bytes, and 7,180 read bytes. The native oracle should report sixteen files and verified rows/CRCs. The fixed object charge and allocation-failure count can differ with the compiler, standard library, and ABI; the tests derive their needed allowance rather than hard-code those values.

Break the heap, not the allocator

Temporarily remove only sift_down(); from Core::take. Keep the copy-before-advance and reader-lifetime code intact. Rebuild and run strata-sort-tests in all three configurations. The authoring runs exited with status 1 and:

There was no sanitizer memory-error report. The pointers and bounds can be legal while the returned sequence violates ordering. For a two-reader example, heads (account 1, event 5) and (account 2, event 3) initially choose reader zero. After reader zero advances to (account 9, event 7), failing to repair the heap would choose account 9 before account 2. The invariant concerns current heads, not the initial insertion order.

Restore the call and rebuild before continuing. The canonical listings contain the correct implementation. Do not leave this diagnostic edit in a learner branch that serves as the next chapter's prerequisite.

Exercises and diagnosis

  1. With 25 fixture rows and block capacity two, raise the descriptor allowance and choose a workspace that admits four inputs. Predict 9 -> 3 before running; compare pass count and transfers, not elapsed time from one tiny invocation. Then reduce the workspace by one byte below the two-input minimum and confirm rejection before any file is created. The complete test above is the executable acceptance criterion.
  2. Keep unlink refused through destruction while retaining the report. Observe a nonzero cleanup-error count and the exact private directory path. Perform any manual removal only after the owner is gone and only inside that test directory. A zero memory charge is not evidence that filesystem cleanup succeeded. The ordinary test removes the refusal and retries so it leaves no deliberate debris.
  3. Explain why replacing the stored row count or block capacity with a file-provided allocation size would undermine the workspace proof. Point to the checks against the in-memory run descriptor and configured block capacity, then repeat the checksummed huge-header case. The expected failure is validation, not an attempted enormous allocation.

An unexpected sort workspace cannot make progress means the configured local allowance cannot hold fixed state plus either generation buffers or a two-way merge. BudgetExceeded after a previously valid local plan instead suggests other charged owners consume the shared allowance. A disk-cap failure after initial runs succeed means replacement coexistence was not budgeted. A CRC error at offset 104 is not EOF, and a cleanup error is not permission to silently zero the disk ledger. Inspect the first causal error before changing limits.

References and the next boundary

The implementation uses the existing explicit codec, file boundary, and charged allocator chapters. Relevant external contracts read for this chapter are the C++ working draft's ordering requirements, sort complexity, object construction, destruction, member initialization order, and shared allocation. The draft is a living reference, not a promise that all newer facilities are available in C++20; this implementation uses only the named C++20 facilities. Apple's archived mkdtemp manual and unlink manual explain private-directory creation and the distinction between a name and an open file. The OpenBSD open/openat manual and unlink/unlinkat manual supply additional concrete system-call contracts; they are not evidence of execution on macOS.

The exit criterion is a correctly ordered, owned event stream that stays within its explicit workspace/run/descriptor limits, spills through multiple passes, and makes cleanup failures visible. Keep all values needed by the next chapter: account ID for matching, event ID for deterministic ordering, day, and cents. Chapter 16 will implement the many-to-one merge join; Chapter 17 will add grouped reduction. This chapter has not added those operators, parallel execution, or cancellation checks.
