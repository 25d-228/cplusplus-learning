Chapter 18 — Synchronization and thread lifetime

Part 2 — Join before destroying shared state

A stop flag, a wakeup, and a join answer different questions. The state decides whether another operation is allowed. The wakeup gives a blocked thread a chance to inspect that state. The join establishes that the thread has finished and will no longer use its references. Omitting any one can leave a different bug.

This part completes the files begun in Part 1. It shares the chapter's 3.0-hour allocation. Keep all engine code at Chapter 17 unchanged. The only cumulative build change is an appended group of standalone targets.

A thread owner needs a policy for incomplete construction

SumWorkers owns its queue and every worker handle. It is deliberately not a general callable executor: each job either contributes a checked integer value or raises a deterministic error. That narrow operation keeps attention on lifetime and failure rather than task type erasure.

Multiple callers may submit using independent job handles. request_cancel may overlap submission and worker processing. The controlling thread alone calls finish and destroys the owner; those lifecycle operations must not run concurrently with each other, and destruction requires external submitters to have stopped using the object. Workers never call finish. A live object is not made safe to destroy by holding a pointer to it in another thread.

Create the complete workers.hpp:

The mutex protects the totals and first recorded worker exception together. The thread vector is controlled only by the owner thread. ThreadCounts is optional external diagnostic storage: if supplied, it must outlive construction, all worker execution, and destruction. Tests declare it before the owner. Atomic counters do not extend the lifetime of their containing object.

fail_before is a zero-based launch index. Passing 2 simulates failure just before starting the third worker. The default maximum size_t disables the injection. No attempt is made to exhaust real system thread resources.

The class is nonmovable because worker lambdas capture its this pointer. Moving its fields would not retarget those pointers, and mutexes themselves are not movable value objects. Shared ownership is not needed when one controlling scope already owns the entire lifetime.

Start workers.cpp with construction and cleanup:

All members are initialized before the constructor body starts launching threads. An early worker may run while later workers are being constructed, but uses only the already-initialized queue, result state, and diagnostic pointer. It does not access the thread vector. The vector reserves handle storage before any thread starts, so later launch attempts do not trigger vector growth. emplace_back constructs a std::thread directly in that reserved slot from the lambda.

If the third launch throws, the SumWorkers object was not successfully constructed. Its destructor will not run. Relying on that destructor for cleanup would leave two joinable member handles to be destroyed during unwinding. The constructor's catch must cancel the queue, join the existing workers, and only then rethrow the original start error. A real thread-constructor exception reaches the same catch. The simulated system_error uses the standard resource-unavailable error category rather than claiming an actual operating-system failure. See the thread creation failure contract.

With failure before launch index 2, the sequence is:

Controller Existing workers
Reserve three handle slots None yet
Start worker 0, then worker 1 May reach empty-queue wait
Inject failure before worker 2 Still own references to this object
Cancel queue and notify Observe canceled state, return from pop
Join workers 0 and 1 Complete; no later access to members
Rethrow start error Member destruction is now safe

Neither worker is guaranteed to have reached its wait before the failure. If cancellation wins first, their first pop sees canceled and returns immediately. Both schedules are correct. Tests inspect started/exited/joined counts after constructor unwinding, without depending on sleep durations.

The normal destructor uses cancellation, not implicit draining. Call finish explicitly for a completed sum and an observable worker error. During caller exception unwinding, destructor cleanup discards queued jobs, lets already-owned jobs finish, and joins. It cannot throw a worker error while another exception is already unwinding.

Never join while holding a mutex a worker needs

Append submission, observation, and joining:

submit preserves the queue's ownership contract. totals returns a coherent copy under the result mutex; callers do not borrow mutable internal fields. request_cancel changes queue policy and wakes waiters, but does not join. The controller must still finish or destroy the owner.

join_all holds neither queue nor result mutex. Joining while holding a mutex needed by a worker's final accounting would produce a cycle: the controller waits for the worker, while the worker waits for the controller's lock. The controller never calls this routine from a worker, which would attempt to join itself. A joined handle is skipped on subsequent calls.

join_all is noexcept for cleanup. Under the stated ownership contract every join is on a valid, distinct, controller-owned joinable handle. Should a join still throw a system error, this implementation fails fast through termination; it does not detach and then destroy storage still in use. Failure of the underlying synchronization primitives during destructor cleanup is likewise not modeled as a recoverable job error. Normal job exceptions and injected launch failures are handled; arbitrary synchronization-system failure is a different boundary. See the possible errors in thread::join.

Deliver an exception only after cleanup can no longer race

Append finish:

Closing first stops admission while preserving accepted work. Joining then waits for all workers. Only afterward do we copy the outcome and rethrow any captured error. The rethrow happens outside the result mutex, so the caller's error handler cannot run while that lock remains held. Repeated finish returns the same totals or rethrows the same first recorded error; it does not start another execution.

The return value is the sum of completed contributions. After explicit cancellation it may be partial. This exercise has no per-job completion records or canceled-result discriminant, so a caller that requested cancellation must not interpret the returned pair as proof that every accepted job ran. The next runtime chapter supplies explicit task states; adding arbitrary callables here would not supply those semantics by itself.

Complete the worker loop and implementation file:

while (auto job = queue_.pop()) declares an owning handle whose Boolean conversion determines whether the body runs. Each successful pop gives this worker exclusive job ownership. The body-local lock guard is destroyed before the iteration's job owner, so releasing the job happens outside the result lock. If processing throws, normal unwinding releases both before entering the catch.

Let n be the existing count, s the existing sum, v the job value, and M the maximum uint64_t. An admissible contribution requires

n < M,\qquad v \le M-s.

Only after both checks do we publish the new pair (n+1,s+v). The subtraction is safe because s is already representable. For s=M and v=1, the check fails before either field changes. This is Chapter 4's failure-safe state transition inside one mutex, not a durable transaction or rollback of earlier jobs.

The catch stores only the first error to acquire result_mutex_. With several workers, that is not necessarily the earliest submitted failing job. Recording it precedes queue cancellation, and the result lock is released before acquiring the queue lock. No path nests these two mutexes. Other workers may already own jobs; they may finish their contributions before their next pop notices canceled state. Partial totals are therefore not generally deterministic after concurrent failure. The single-worker failure fixture below fixes the relevant ordering so that its expected partial sum is exactly 10.

A bare std::thread destructor invokes termination if its handle is still joinable, even when the underlying function has already returned. Joinable is a handle state, not a synonym for “currently executing.” Explicit joining is not optional housekeeping. See thread destruction. C++20 std::jthread supplies stop-request-and-join behavior during destruction, but a stop request does not itself change this queue's predicate or notify its ordinary condition variables. Replacing the handle type alone would not fix a join-before-wakeup deadlock. Its behavior is specified under jthread construction and destruction.

Make test failures clean up threads too

Tests need the same lifetime discipline as application code. A require that throws while an unguarded test thread waits in pop could terminate the program or hang cleanup, obscuring the original assertion. The small harness below cancels its associated queue and joins during destruction.

Begin main.cpp:

expect_error<Error> checks one specified exception family; an unrelated error continues outward instead of counting as success. It takes its callable by value, a pattern from Chapter 5. require remains active with NDEBUG defined.

Append the test-only thread guard:

The fixed six-slot arrays are enough for three producers and three consumers. Default-constructed thread handles are not joinable. Each worker writes only its own errors_[index]; the controller inspects those slots after joining. Distinct ordinary array elements are distinct storage, unlike packed vector<bool> proxy bits. Only the controller changes used_.

The lambda's task = std::move(function) is an initialization capture: the closure owns the passed callable. mutable permits invoking a callable with a non-const call operator. Its references, if any, are still borrowed. Capturing a closure by value does not turn references inside that closure into owning values.

Declare every object borrowed by these closures before QueueThreads. Reverse destruction order then runs the guard, wakes the threads, and joins before those objects disappear. If starting a later harness thread fails, the already constructed guard supplies the same cleanup. The worker catch records its own error and cancels the queue so other threads do not wait forever for work that will never arrive.

finish intentionally does not close the queue: tests must first arrange that their operations can finish. A producer-only test frees a slot; a consumer-only test supplies an item or closes; the mixed fixture joins its producers and then closes. The destructor is the fallback on assertion failure, not a substitute for testing each normal protocol.

Distinguish correct synchronization from correct queue semantics

Append the single-thread ring and shutdown check:

This checks exact FIFO order through repeated wraparound, not just a sum. identity records the address owned before a rejected submission; equality proves that rejection did not consume or replace that job. Calling close twice must not discard the already-accepted value 42.

For a logical mutation, change pop's return-empty condition from state_ == QueueState::canceled || count_ == 0 to state_ != QueueState::open || count_ == 0. All accesses remain protected, but the test must report close discarded accepted job. This is a protocol error, not a data race. Restore the original line before continuing.

Establish blocked waiters, then change state

Append the empty-consumer scenario:

The controller waits until all three pop operations are registered on an empty queue. It sends an extra notification and waits for another predicate check without adding work. Output handles are read only after joining. Close and cancel are both tested; each must wake all three consumers to return empty. A five-second sleep followed by inspecting results would be both an unreliable scheduling assumption and an unsynchronized access.

Append the full-producer scenario:

Here one queued job fills the single slot, while two producers each own a pending job. The controller never reads or resets those handles until the producers are joined. It can inspect the ring through the locked probe meanwhile. Both close and cancel reject waiters without moving their handles. Close still delivers the initial 10; cancel does not. Close after cancel must not reverse the state.

The pair of tests distinguishes waking “at least one” from waking every shutdown waiter. They also exercise nonproductive notifications. A passing run establishes these controlled executions, not fairness for every scheduler.

Append the ordinary resource-change wakeup checks:

The first removes 10 from a full queue and waits for the blocked producer to transfer 20. The second supplies 12 to an already-waiting consumer. Joining in these two cases is legitimate because the controller has already performed the resource change allowing the worker to finish. Shutdown alone is not the only path that must notify correctly.

Check each job, not just the aggregate total

Append the multiple-producer/multiple-consumer fixture:

Three producers generate disjoint ID intervals 1..200, 201..400, and 401..600. Each of three consumers owns its own histogram row. No two consumers write the same row, and the controller reads all rows only after joining. The arrays exist before any thread starts; they are test-oracle storage, not a production result container.

For each ID i, let h_{c,i} be the count recorded by consumer c. The actual coverage check is

\sum_{c=0}^{2} h_{c,i}=1\quad\text{for every }i\in\{1,\ldots,600\}.

Only after checking every ID do we compute the fixture sum

\sum_{i=1}^{600}i=\frac{600\cdot601}{2}=180{,}300.

A sum alone could conceal one missing ID and a compensating duplicate. We do not expect a particular consumer to receive a particular ID, nor a deterministic interleaving between producers. FIFO orders accepted ring transitions, not the wall-clock time when independent producers began constructing their jobs.

The controller first joins producers, which can finish because consumers are already running. It then closes the queue and joins consumers. Joining consumers first on an open, empty queue would never finish: no operation would tell them that production had ended.

Run the promised result and retain the rejected owner

Append the sum fixture:

The three successful submissions empty the caller's handles. Closing and joining through finish yields three contributions totaling 42; the exact split across the two workers is irrelevant. The later 99 remains owned by the caller. Reading an atomic counter in comparisons such as counts.started == 2 invokes its atomic value conversion; these checks happen after joins, not as a polling protocol. The counter is diagnostic, not the reason the worker lifetimes are safe.

Append processing failure, overflow, and explicit cancellation checks:

With one worker, FIFO fixes the order: 10 contributes first, the failing 20 raises an exception, and 99 cannot contribute. The 99 may have been admitted before cancellation or may still belong to the caller; both schedules are allowed. accepted == !trailing checks the appropriate ownership in either case. The partial total remains (1,10), and finish rethrows the recorded failure even on a second call.

The overflow fixture completes the maximum representable value, then rejects adding 1 before changing either total. The cancellation fixture has no jobs, so it makes no timing assumption about whether a worker was already waiting when cancellation occurred. Waiting-state shutdown itself was covered separately with explicit rendezvous.

Append construction and unwinding checks:

Failure before launch indices 0, 1, and 2 verifies cleanup of zero, one, and two started workers. The observer outlives the failed construction. Throwing a CallerFailure after starting three workers verifies destructor cleanup during ordinary stack unwinding. At the end, every owner scope has ended and every started thread has been joined, so the final live-job count must be zero.

Isolate the data race instead of normalizing it

Create racy_counter.cpp exactly as this separate diagnostic:

Both closures own a copy of the shared_ptr, so the counter's lifetime is not the bug. The arrival counter and start gate are atomic; they arrange for both workers to reach a controlled starting phase. The accesses to Counter::value after that gate are plain, conflicting increments with no ordering between workers. Joining both afterward does not repair those earlier accesses.

The atomic arrived.wait(count, acquire) waits for a change from its last observed value; the loop then loads the current count again. This prevents notification counting from becoming a second bug in the diagnostic. A partial thread-start failure releases the start gate and joins any existing worker before rethrowing. That cleanup does not make the normal two-worker increment legal: the program intentionally has undefined behavior and belongs nowhere in the passing suite.

Build a separate race-diagnostic configuration:

The normal tests should pass without a race report. The deliberately wrong program should report conflicting accesses at ++shared->value, with worker creation stacks. A nonzero exit by itself is not enough: a runtime load error or unsupported environment is not a detected race. Read the diagnostic. Its address, thread identifiers, stack formatting, and exit code are not portable expectations. Even printing 200,000 would not validate this program; undefined behavior has no required numerical result.

Clang documents ThreadSanitizer support for Darwin ARM64 and compilation/linking with -fsanitize=thread; -g retains source locations, and modest optimization is appropriate for its diagnostic use. Consult the ThreadSanitizer documentation for the installed runtime's limitations. Use a working compatible native toolchain, not an invented required version. Do not combine ThreadSanitizer with AddressSanitizer in the same executable. GCC's instrumentation options also document that incompatibility; GCC is an additional testing option where available, not a macOS installation requirement.

A sanitizer substantially changes execution and resource behavior. Its passing run is evidence about exercised accesses, not a proof of race freedom, scheduling fairness, absence of deadlock, or production throughput. The controlled rendezvous tests and explicit state reasoning remain necessary.

Diagnose the missing relationship

Symptom Inspect first Concrete correction
Shutdown hangs with several consumers Close/cancel state and both waiter classes Set state under the mutex, notify all, then join
Close loses accepted jobs Pop's return-empty branch Drain until count is zero unless canceled
A rejected push empties the caller Location of the pointer move Move only after deciding to accept under the mutex
Exception during startup terminates Constructor catch and joinable members Cancel and join existing workers before rethrowing
A job exception terminates immediately The thread callable boundary Capture the exception, clean up, rethrow in the controller
Pair totals sometimes disagree Whether all fields use the same lock Protect and inspect the whole invariant together
Race despite shared ownership Accesses to the pointed-to payload Add appropriate synchronization; reference counting is not that lock
Rendezvous times out Predicate counters and actual thread startup Diagnose the blocked operation; do not treat a longer sleep as a fix

A missing notification may leave the controller blocked in join, while a worker waits in pop or push. A debugger's all-thread backtraces can reveal that wait relationship; the waiting stack alone is not evidence that the mutex was forgotten. The relevant question is which operation can make the predicate true, and whether that operation can still run. Assertions made before releasing a required test resource can themselves create a hang, which is why test cleanup is also owned.

The five-second rendezvous watchdog can expire while a debugger has paused threads. That is a test-environment interruption, not a successful synchronization result. For interactive stepping, adjust only the diagnostic watchdog in a scratch copy; never remove the production predicate or rely on scheduling delays.

What has and has not been established

The new normal programs were executed with Clang 17 on Linux in Debug, Release, and AddressSanitizer/UndefinedBehaviorSanitizer configurations. A separate GCC 14.2 ThreadSanitizer build ran the normal programs without a race report and reported the deliberately shared-counter race. These are execution observations, not required compiler versions. Native M4/macOS execution remains unverified.

The queue fixture transfers 600 distinct jobs exactly once, deliberately wakes waiters without supplying permission, closes and cancels with producers and consumers registered, retains rejected ownership, propagates job failures, preserves totals on checked overflow, joins partially started workers, and reaches zero live jobs. None of those observations proves arbitrary scheduler fairness. The exercise also does not promise prompt interruption of a blocking filesystem operation or a bound on whole-process memory.

Most importantly, the engine is still synchronous. An immutable database fixture can still use a mutable cache, accounting ledger, retirement registry, or counters on its read path. Before multiple query workers share those objects, each mutable access needs synchronization or genuine isolation. A shared_ptr<ReadView> alone would not supply it. The next chapter adds bounded execution and cooperative cancellation to complete queries; it must preserve these lifetime rules while introducing explicit task completion and admission semantics.
