Chapter 23 — Profiling, optimization, and the final demonstration

Part 1 — Define the operation before timing it

A faster query is not useful if it observes a different snapshot, silently skips validation, or reports success before its output is complete. A lower charged peak is not automatically a lower resident-memory peak. Finally, doing less work and doing the same work faster are different improvements. This chapter makes those distinctions executable.

We retain the complete Chapter 22 engine. Four equivalent query plans expose batch size, intermediate copying, and predicate placement. A separately selectable checksum implementation changes no stored bytes. A measurement program runs the real two-sort join/aggregation pipeline, records its work, and verifies every result using Chapter 21's independent answer. The final driver then exercises the live and recovery scenarios together, without confusing a controlled schedule with a throughput benchmark.

Learning objectives Define timer and ownership boundaries; distinguish charged allocation from resident memory; compare semantically equivalent plans; derive a byte-at-a-time CRC update; interpret sampling and scoped instrumentation; retain a baseline; and report measured improvements, regressions, and unverified behavior.

Prerequisites: all source through Chapter 22, including the Chapter 21 generator, analytical and replay references, strata driver, Chapter 20 live engine, and Chapter 17 completion-aware result sink. The engine should pass its existing correctness checks before measuring it.

Implementation: 4.0 hours across all three parts. Allocate 1.0 to the harness, 1.25 to profiling and the selectable optimization, 1.0 to repeated comparisons, and 0.75 to final integration. The course allocation remains 86 hours plus the 6.5-hour debugging/integration reserve, excluding reading. Record actual time; no additional implementation hours are inferred from the length of this chapter.

One answer, four controlled plans

All variants use the same captured sequence, day interval, account relation, join rule, grouping order, checked arithmetic, and CSV completion protocol. Only the named decision changes:

Variant Event-side work before the join Batch capacity
row Scan → filter → project → external sort 1
batch The identical operators and predicate Configured, initially 256
fused Scan → combined filter/project → external sort Same configured capacity
late Scan → project → external sort → filter Same configured capacity

The second joined-row sort and aggregate remain the same algorithms. The row comparison sets capacities throughout the pipeline to one; it does not shrink the sort chunk or spill block to one. Otherwise changing run count and system-call granularity would be mistaken for the effect of operator batching.

The late predicate selects by event day and does not depend on account values. Removing rows after sorting preserves the order of the rows that remain. It is therefore legal for this fixed query, although more expensive when many rows are rejected. This is not a rule that arbitrary predicates can cross arbitrary joins. The native check compares every variant against both independent references.

A versioned scan row has 28 event-field bytes plus an eight-byte sequence. Its column storage is 36 bytes per slot, independently of padding in a C++ aggregate. For capacity b, the original filter input, project input, and sort input need

M_{\mathrm{separate}} = 36b+36b+28b=100b.

The fused operator keeps one versioned input and appends projected values directly into the sort's input batch:

M_{\mathrm{fused}}=36b+28b=64b,\qquad \Delta M=36b.

At b=256, this removes 9,216 simultaneous column bytes and one copied versioned intermediate. Other operators, sort chunks, readers, cache entries, and control objects still consume memory. The global peak need not fall by exactly 9,216 because its maximum may occur in another phase. Both paths still write the same 28-byte event encoding to spill files. The native test requires identical early-plan sort traffic; fusion is not credited with fictional on-disk record compression.

Fuse copying without weakening the pull protocol

The following first block creates selection.hpp. Source is constrained using Chapter 5's concepts and Chapter 14's PullSource: it must supply versioned ScanBatch values. Member declaration order matters: source_ is constructed before input_, so the latter can obtain the moved-in source's budget. check_output runs before any source consumption. Its rejection leaves the input position unchanged.

input_.events().row(i) produces the event value, not a borrowed reference into an output that will be refilled later. The sequence remains in the scan buffer; the query does not need to copy it after the storage layer has resolved versions. An empty selection returns Pull::batch. Only an upstream Pull::end ends this operator. On a refill exception, both partial outputs are cleared and the stream becomes terminal. Reusing its already-consumed source would not constitute retry.

For the late-filter experiment, the source supplies EventBatch instead. Append the following complete operator and header closing lines. It has the same failure and empty-progress behavior, but its input has already passed through the first sort. Neither operator is a new asynchronous task.

The classes own noncopyable batch members, so they cannot accidentally copy an entire plan. Their implicit moves use the already-defined batch/source moves. There is no custom destructor or worker to join here. Upstream owners remain part of the plan and are released when that plan is destroyed.

Observe private readers, not a shared mutable cache

Chapter 20 gives each query isolated readers and a private cache. Add a small measurement snapshot to ReadView. It is deliberately not an API for reading counters concurrently with another thread mutating those same readers.

The added include supplies checked counter addition. metrics() rejects a normal nonisolated view rather than suggesting that arbitrary parent-cache observations are safe. It sums file-transfer and block-load counters across the current isolated source set, then copies that isolated cache's statistics. table_bytes counts bytes delivered through the file boundary, not physical device reads. block_reads counts block loads, not hardware cache misses.

We retain an extra measurement view until the plan finishes so those counters remain readable. This also retains its readers/cache longer than the minimal production query might. Every compared variant pays that observation cost. Do not silently compare these peaks with a run that omitted the observer.

Capture itself can read headers and metadata. Record a before snapshot after capture, then after after consumption. Their difference isolates subsequent query reads. The full query timer still includes capture and teardown. These are two different boundaries, intentionally named rather than reconciled by hiding one of the costs.

Measure elapsed time, CPU time, and resident memory separately

Create apps/measure_query.cpp. steady_clock measures a monotonic interval; duration<double> expresses its result in seconds rather than assuming the clock's native tick unit. The clock contract requires nondecreasing values unaffected by clock adjustment. It does not promise nanosecond measurement accuracy merely because a duration can represent nanoseconds.

getrusage supplies cumulative process CPU time and a resident-memory high-water mark. CPU time is a difference of user-plus-system time; maximum resident memory is not a quantity to subtract between two samples. Its peak can come from earlier opening work. The program outputs its raw value and leaves unit selection to the harness.

The join/second-sort/aggregate suffix is shared literally, not reimplemented for each benchmark. Function parameters take owning plans by value and then move them into the next operator. consume_results remains responsible for publishing only complete output. The group counter is a staged result count, not a claim that partially written CSV has been committed.

The dispatch below changes only the event-side composition. Class-template argument deduction selects the concrete source types from constructor arguments; this is the same composition technique used in Chapters 16–17. A copy of the ReadView shares its immutable owner, not the contents of the database.

The statistics handles do not own spill files. Inspecting them after the plan's destruction reveals whether its cleanup completed. Reject saturated counters: a wrapped or saturated byte total cannot support a quantitative comparison.

Validate parameters before opening inputs or touching a result. Set all pipeline capacities together, but keep merge work limits, block rows, and descriptor allowances fixed. Five sort descriptors allow at most four input readers plus one output writer, subject also to the memory calculation from Chapter 15. The 128-run catalog bound remains in force.

FrozenInputs reopens and verifies the compacted database once, with its default 64 MiB opening allowance. Each query gets a separate 32 MiB budget and fresh private cache. These are admission limits, not preallocated arrays or a combined process-memory cap.

The query timer starts before isolated capture and ends after owners and the result sink leave scope. It therefore includes metadata opening, query work, CSV close/publication, and cleanup. The database's earlier reopen interval is reported separately. An optional same-thread CRC timer is reset here; Part 2 implements it. Normal measurement builds disable that instrumentation.

inputs remains alive across optional repetitions for profiling. The main harness uses one repetition per child, so each timed sample opens a new process. Repeated in-process profile runs instead amortize that process's opening interval; do not mix those samples into the fresh-process comparison.

The complete output record follows. It contains counters and parameters, not paths interpolated into unescaped JSON. All numeric sizes are bytes unless their field explicitly says rows, runs, passes, seconds, or raw RSS.

event_read includes reads used to verify intermediate replacements, not merely one final scan. event_peak_disk and group_peak_disk are separate per-sort high-water marks; adding them does not prove that both peaks occurred together. A result with zero final charged bytes must still pass the spill-name and cleanup checks. Conversely, zero live query owners says nothing about the master FrozenInputs, stack, stream, allocator, or operating-system memory.

On Linux, getrusage's manual defines ru_maxrss in KiB, so conversion to bytes multiplies by 1024. On the Mac, inspect the installed man 2 getrusage before choosing the conversion. The harness accepts raw, bytes, or kib and defaults to raw; an unconfirmed unit must not become a convincing but wrong memory figure. An archived manual for a different SDK is not evidence of the currently installed interface. The native M4 execution and local unit observation remain tasks to run on that machine.
