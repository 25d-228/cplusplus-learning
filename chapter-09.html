Chapter 9 — Memory budgets and a pinned block cache

Part 1 — Charge allocation, not logical contents

A block size limit does not bound a process. Chapter 8 limits each table cursor, but a hundred cursors can still allocate a hundred buffers. A cache introduces another distinction: the cache may stop retaining a block while a reader still needs its bytes. Eviction policy and allocation lifetime cannot be the same thing.

We will give the engine's dynamic storage a common byte ledger, then build a synchronous cache whose readers share immutable blocks. A full cache is not an I/O error. It may return a separately charged block without retaining it. A full memory budget, however, must reject an allocation; bypass is not permission to allocate outside the ledger.

Learning objectives Reserve before allocating; charge vector capacity and allocation-control storage; implement a stateful standard-library allocator; share immutable buffers through owning pins; maintain explicit recency links; evict only unpinned entries; connect cache misses to the real table validator; diagnose logical and memory failures separately.

Prerequisites: all code through the three parts of Chapter 8, especially its TableReader::Cursor::load, and the ownership, exception-safety, and template material in Chapters 3–5. Keep the eleven passing CTest entries. The code remains in the same work/strata tree. There is no log, database manifest, or thread pool in this chapter.

Implementation allocation: 3.5 hours for all three parts together. Allocate 1.0 hour to the ledger, allocator, and existing allocation boundaries; 1.5 to pins, recency, admission, and reader integration; and 1.0 to pressure tests, debugging, and the deliberately incorrect recency variation. Reading is separate.

Part 1 implements the ledger and charges arenas/builders. Part 2 implements the cache. Part 3 updates the table reader and supplies the complete test program and CMake changes. Decide exactly what a byte limit promises

Let L be the ledger limit in bytes, R the bytes reserved but not yet allocated, and A the bytes charged to live allocations. Define admitted usage U by

U = R + A, \qquad 0 \le U \le L.

An allocation request of n bytes is admitted only when n \le L-U. Test that subtraction, rather than computing an unchecked U+n first. Once admission succeeds, adding n is safe because the result is at most the representable limit L.

A lease owns a reservation. Its destructor returns that reservation unless the allocator has converted it into an allocation charge. A lease is move-only: there must not be two destructors returning the same reserved bytes. An allocator-owned charge instead lives until the matching deallocate call.

Operation Reserved bytes Allocated bytes Admitted usage
Start, with a 16-byte limit 0 0 0
Reserve 12 12 0 12
Attempt to reserve 5 12 0 12; rejected
Allocate the admitted 12 successfully 0 12 12
Deallocate those 12 0 0 0

If the underlying allocation throws, the lease returns the 12 reserved bytes. No allocation charge was installed. The high-water mark records admitted usage, including such temporary reservations, not merely successfully allocated memory.

The accounting domain is specific. We will charge every allocation made through our allocator: full arena chunks, builder workspaces, reader metadata, cached and bypass frame capacity, cache slot storage, and the storage requested for each shared block's object/control state. A node inside an already charged arena chunk is not charged again. A second pin to an existing block is not another block allocation.

This is not a cap on the operating system's process-memory measurement. Allocator bookkeeping and size-class rounding outside requested object storage, fixed stack objects, file-system/error-message internals, runtime libraries, and the operating system's file cache are outside this ledger. Test fixtures and caller-owned input arrays are outside it too. Later subsystems must join the ledger explicitly; a naked allocation does not become charged by proximity. Leave headroom for excluded storage and measure process memory separately.

Teach the ledger to own a reservation

A budget outlives every lease and allocation that refers to it. It is neither copyable nor movable: copied limits would create competing ledgers, and moving its address would invalidate allocator pointers. Put a budget before its users in an enclosing scope so reverse destruction releases their allocations first.

The error type below derives from std::bad_alloc, the allocation-failure family introduced in Chapter 4. Its what() returns a fixed string; constructing this particular error does not need a dynamically allocated explanatory message. A caller may catch BudgetExceeded specifically, or catch std::bad_alloc to handle both admission refusal and underlying allocation failure.

Lease is nested to keep its relationship to the ledger explicit. Its default state owns nothing. friend class Budget permits the budget to create a nonempty lease, while the template friend permits an allocator specialization to commit one. Neither operation is public to an arbitrary caller. Friendship grants access; it does not extend an object's lifetime.

There are two different release paths. Lease::reset subtracts from reserved_; release_allocation subtracts from allocated_. Mixing them would make a plausible total briefly hide an invalid state. Invariant failures in nonthrowing cleanup terminate instead of underflowing a counter or throwing a second exception.

The failure seam is deliberately small. fail_allocation_on(2) rejects the second nonempty, successfully admitted allocator request after arming. Rejected budget reservations and zero-size requests do not consume an ordinal. The injected failure clears itself, and clear_failure() also cancels an unconsumed ordinal. This counts our allocator calls, not all allocations performed by a process.

A budget destructor with outstanding usage is a lifetime error. It cannot safely "fix" the situation by freeing other objects' memory. The explicit termination check catches that incorrect destruction order before later deallocators follow a dangling budget pointer.

A manually held lease is not a credit automatically consumed by a vector. The allocator below reserves for its own request. Holding another lease while allocating the same planned bytes would count both reservations. Manual leases can hold headroom for a separate operation or, as in our tests, create pressure; only the allocator's private commit transfers its lease into its allocation.

Put the accounting boundary where capacity is chosen

Suppose a vector has two elements but capacity ten. Charging two elements misses eight allocated slots. Worse, charging before calling reserve(10) with an assumed growth policy can disagree with the implementation's actual allocation request. A stateful allocator intercepts that request instead.

An allocator is a small object describing how to acquire and return typed storage. Allocator<T>::allocate(n) returns storage for n objects of type T; it does not call their constructors. Containers perform construction separately. deallocate(pointer,n) must use an allocator equal to the one that allocated the storage and the matching count. These are caller/container contracts, not bounds the deallocator can reconstruct from an arbitrary pointer. See the C++20 draft's allocator requirements.

Our state is one borrowed Budget*. The converting constructor accepts Allocator<U> and preserves that pointer when the library needs a different internal storage type. The value_type alias identifies the requested element type. std::allocator_traits supplies standard defaults, including rebinding Allocator<T> to Allocator<U>; we do not specialize a standard-library template.

The propagate_on_container_* aliases are compile-time Boolean types. std::true_type has a static value equal to true. They tell a container to move/copy/swap allocator state along with the allocation ownership when the named operation needs that state. is_always_equal is false because two different budgets cannot deallocate each other's charges. Equality compares budget identity, not the numeric limits. The relevant rules are in allocator traits and the allocator-aware container requirements.

The allocation sequence has four steps. First, reject an overflowing count * sizeof(T). Second, reserve the checked byte count. Third, run the failure seam and ask std::allocator<T> for suitably aligned storage. Finally, commit the reservation and return the pointer. If either operation in the third step throws, stack unwinding returns the reservation. There is no effect to undo in the container because it never received a pointer.

The wrapper delegates raw storage acquisition, not budget policy, to the standard allocator. This also avoids accidentally losing support for over-aligned types by calling a mismatched raw operator new/operator delete pair. The standard allocator's allocation interface specifies storage for its element type; the test uses an alignas(64) object.

For observed capacity c and element size s=\operatorname{sizeof}(T), the retained element-storage charge is c s, not values.size() * s. While a vector grows, its old allocation and candidate allocation may coexist; both are charged. Clearing elements does not itself release that capacity. The standard's vector capacity rules distinguish size, reserve, and reallocation; the implementation must not rely on a particular growth factor.

There is intentionally no default Allocator() constructor. A default-created charged vector without an explicit allocator therefore fails to compile. This is useful friction: a new engine buffer should choose its budget, not escape it.

Predict the next allocation before running it

Consider a vector that owns 80 charged bytes under a 100-byte ledger. It needs a new 160-byte allocation to grow. The request fails: there are only 20 admitted bytes available, and preserving the old allocation requires coexistence during preparation. Even an eventual 90-byte replacement would fail under these exact conditions. A final state that fits does not prove that its transition fits.

A cache has the same issue. Evicting first could free enough space, but then a read or validation failure would have already discarded useful data. In Part 2 we deliberately choose prepare before eviction, account for that peak, and make failure preserve the old cache contents.
