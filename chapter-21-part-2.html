Chapter 21 — Reproducible workloads and independent answers

Part 2 — Parse bounded input; drive the existing engine

The input boundary should be smaller than the engine it drives. We need no SQL parser, general CSV importer, or network service. We need strict unsigned fields, a bounded batch buffer, and a clear answer to this question: after a failure, which batches might already be committed?

Prerequisite code: Chapter 20's complete source state plus the generator and reference from Part 1. All files below are new. Engine::write takes a borrowed mutation span and finishes its preparation and commit before returning. Executor accepts an owning request and returns a handle whose terminal result contains no running query owner. We reuse these contracts rather than introducing a second writer or bypassing cancellation in the driver.

One buffer owns every input borrow

Input owns the file stream, a 255-byte line array, six token views, and a fixed array of 256 Mutation values. tokens() returns views into the line array. The next call overwrites them, so the parser converts every field into an owning numeric mutation before reading another line. next() returns a span into the mutation array; the importer must finish the write before asking for another batch.

The stream's buffering, path string, diagnostic strings, and fixed adapter arrays are host-side costs, not engine-budget charges. Their bound is useful, but it does not turn the ledger into a process-memory cap. In particular, the standard stream may allocate its own implementation-specific buffer.

unsigned_number uses integer std::from_chars. Its result has a pointer to the first unconsumed character and an error code. Structured binding names those two members end and error. Both must be checked: parsing the numeric prefix of 12tail is not a successful field conversion. The integer conversion contract specifies out-of-range and invalid-input results and does not throw; our wrapper turns rejection into an exception. No null terminator is needed for a view. The leading-zero rule is additional format policy.

Keep stream_.get() in its integer return type. Narrowing it to char before checking EOF could lose the distinction between a character and the sentinel. Check the content bound before writing the next byte, and reject controls, non-ASCII bytes, tabs, and carriage returns. Thus CRLF is intentionally not an alternate serialization of this format.

Tokenization returns at least one nonempty field or throws. Six views are enough for the five-field event form and a bounded rejection of excess fields. No token can point into a temporary std::string: every view points into line_bytes_.

The constructor consumes the header once. An exception closes its already constructed stream member automatically. During operation decoding, the small narrow lambda checks the range before converting to 32 bits. A cast alone would not reject an oversized day or region.

Puts and tombstones are different mutation kinds. In particular, an account tombstone must not become Account{id, 0}: region zero is valid, and that mistake would retain join matches under a new region instead of deleting them.

next() saves the batch sequence and count as integer values before reading operations. Saving token views instead would leave them referring to the next line. The duplicate scan is quadratic in batch size, but the size is at most 256: at most 256\cdot255/2=32640 key comparisons. This avoids an uncharged hash table and keeps the boundary deterministic. It is a deliberate small-batch tradeoff, not a proposed algorithm for an unbounded import batch.

The END case checks totals and then requires EOF. The successful empty span therefore means a validated end of input, not an empty batch. After a parsing exception, discard the Input object; its running counters may include part of the rejected batch. The engine has not seen that batch because next() has not returned it. No parser-level rollback is needed to protect the database.

For a useful failure trace, place a valid sequence-1 batch before B 2 1, a valid event, and C 99. Sequence 1 can commit. Sequence 2 never reaches Engine::write; the adapter reports its line number and the importer reports last_acknowledged=1. Reopening must return sequence 1's answer. A missing final END is different: all preceding terminated batches might already be committed.

Presets should force mechanisms without hiding limits

A preset is an explicit configuration, not a promise to accept arbitrarily large input. The tiny preset keeps batch capacity, spill chunk size, fan-in, cache, and table blocks small. The stream preset raises workspace granularity but preserves the existing maximum of 128 initial run descriptors per sort.

Let C be sort chunk rows, R maximum initial runs, and n selected input rows for that sort. Run generation needs \lceil n/C\rceil descriptors. Its current bound is therefore

\lceil n/C\rceil\le R,\qquad n\le CR.

For tiny, C=3 and R=128, allowing at most 384 selected rows. For stream, C=2048, giving 262144. These are per-sort row limits, not just byte limits. Input exceeding them is rejected; do not describe this implementation as an unbounded external sort. A broader disk-backed run catalog is outside this chapter. The test workload is chosen to exercise multiple passes within the implemented bound.

With two input readers and one output writer, the tiny merge allowance is three file descriptors, so fan-in is two when memory also fits. Twenty initial runs then shrink as

20\rightarrow10\rightarrow5\rightarrow3\rightarrow2.

Those are four materialized passes. The final two-way merge streams to the next operator rather than writing one more run. The stream preset allows eight input readers and one output writer. Ninety-eight initial runs become 13 and then 2: two materialized passes, followed by the streaming final merge.

The adapter declarations gather presets, import, result checking, and scenario entry points without adding another core abstraction.

The preset implementation follows. The stream case retains Chapter 20's default storage and maintenance options. Tiny maintenance has its own 4 MiB allowance, separate from each 2 MiB query reservation. That separation allows maintenance to finish while a held query consumes its entire reserved slot.

Important limits are visible rather than inferred from the machine's 16 GB:

Setting Tiny Stream
Rows per sort chunk 3 2048
Rows per spill block 2 128
Sort descriptor allowance 3 9
Maximum initial runs 128 128
Per-query reservation 2 MiB 16 MiB
Required currently available disk 64 MiB 768 MiB

The tiny 256 KiB per-sort spill allowance covers the intended small scenario, including input/output coexistence during replacement. Stream keeps the existing 256 MiB per-sort disk allowance. Neither preset's free-space check reserves that space. Table metadata bounds, log slots, retained snapshots, and other engine limits still apply independently of these numbers.

Preflight observes; admission owns

filesystem::space(...).available reports currently available space; an unknown value is represented by uintmax_t(-1). See the filesystem space contract. The driver rejects unknown or insufficient availability, but another process can consume disk immediately afterward. Runtime write errors still matter.

For descriptors, read the soft RLIMIT_NOFILE value with getrlimit. Apple's archived manual describes the call, rlim_cur, and the open-file limit; the installed man 2 getrlimit is the place to inspect the target system's details. This adapter requires at least 256 as explicit headroom, not as an asserted macOS default. It does not change either limit. Query admission still applies its separate conservative descriptor allowance.

A preflight failure is a configuration diagnosis, not evidence of a core algorithm failure. Inspect ulimit -n and the selected directories; choose a permitted limit or a different filesystem explicitly. Do not raise a process limit blindly or interpret an admission estimate as a kernel reservation.

A successful batch advances one acknowledged boundary

The importer first compares the database's current sequence with the file's base. It then alternates next() and write(), so no future batch overwrites the borrowed mutations while a write is using them. A committed result must have the sequence declared by the input.

A definitely rejected batch and an uncertain write both stop import. For an uncertain result, reopen before deciding what is present: the log might contain a complete batch whose caller did not receive success. Do not skip ahead based only on the last acknowledged value. The driver intentionally supplies no automatic retry, deduplication, or partial-file resumption command.

The exception wrapper records the seed, input line, and last acknowledged sequence. It does not claim that all later batches are absent after an uncertain write. The seed helps reproduce the fixture; the sequence identifies the boundary whose success the caller actually observed.

settled seals the active data and waits for maintenance. An explicit compaction request then runs through the existing worker. Collection is also explicit. These are ordinary graceful operations, not fault injection or a physical power-loss test. Counters returned by stats() are copied under the engine's coordinator lock.

The printed labels intentionally distinguish current-process counters from persistent state. sequence comes from the database history. flushes and compactions count work in this engine object's lifetime; reopening does not reconstruct historical totals. last_job_read and last_job_write describe one maintenance job, not all compaction traffic. Query peak_charged is the ledger peak, not resident memory; final_charged=0 means those charged owners were released. Streams, paths, thread stacks, allocator bookkeeping, and the operating system remain outside that statement.

A terminal task can report completion while also reporting a cleanup problem. require_completed checks both. If publication succeeded but removing a spill file failed, the answer may be valid while the command exits with a cleanup error. Do not replace that diagnostic with an unconditional success message.

The five-minute wait is a watchdog, not synchronization or a performance target. On timeout the caller unwinds through the executor owner, which requests stop and joins. Cooperative cancellation cannot instantly interrupt a blocked file operation. The scenario's ordering will use explicit gates, not elapsed time.

Dispatch commands without reimplementing the engine

The first half of main validates input or imports it. load requires a new database directory; apply recovers an existing one and checks the input base. The input header is opened before creating a new database, avoiding an empty database for an immediately invalid header. A later failure deliberately leaves the directory available for inspection. Never remove a possibly committed prefix merely because the command returned an error.

inspect is an ordinary recovery open followed by manifest observations. It is not a forensic no-write mode: recovery can repair a permitted active-log tail and synchronize. compact uses Engine so it follows the same maintenance path as the concurrent scenario. Neither command bypasses the directory lock.

query uses one worker and one queue slot. It copies the handle before submission transfers request ownership. All paths, output naming, query admission, cancellation semantics, CSV staging, and final publication remain the existing implementations. A rejected submit cannot be disguised as an empty answer. finish() joins before we inspect completion and stop the engine. The command's day upper bound may be 2^{32} even though a stored day is at most 2^{32}-1; Chapter 17's DayRange uses the wider representation needed for an exclusive endpoint.

Inspect a complete small history

After appending Part 3's CMake targets and building, these commands run from the learner source root. mktemp gives the run a fresh parent directory; load creates its db child. Do not start an additional query process against the same open writer. The database directory lock intentionally prevents that model.

The base query has 60 filtered events, 60 joined rows, and eight groups. The updated query has 55 filtered and joined rows and twelve groups. Both sorts make four materialized merge passes in both queries. The latter CSV includes 2,4,1,1785, the moved event traced in Part 1. Base region 1, day 4 instead contains twelve events totaling 5516 cents. The complete reference compares all rows; these examples are not a substitute for it.

Running apply again on the same delta must fail the base-sequence check and report last_acknowledged=6. It must not replay the updates as new sequences. A simple absence of a crash is not the expected check.

The final part keeps one process open while these operations overlap, then verifies that the answers still name coherent committed histories.
