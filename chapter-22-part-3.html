Chapter 22 — Recovery and resource-pressure experiments

Part 3 — Kill the process; retain the observer

Keep Part 1's boundary/model and Part 2's fixtures and campaigns. This part adds a native executable, its independent Python controller, the build entries, pressure checks, and a deliberately broken barrier experiment. It completes the same 4.0-hour chapter.

Stop at an observed boundary, not after a guessed delay

The child opens its own database, prints acknowledgements only after committed writes, and stops at an exact named hook. STOP is flushed before it waits on standard input. The parent keeps that input pipe open but sends nothing. Once it reads the expected marker, it kills the child and waits for its termination. No sleep is used to guess whether rotation or compaction has reached the target.

stop is [[noreturn]]: either the parent terminates the process or unexpected input/EOF triggers _Exit(94). That fallback must not be confused with the requested signal. The Python controller checks the actual termination code. A watchdog detects a missing rendezvous; it is not an ordering mechanism.

The fixture acknowledges sequences 1 and 2 before arming maintenance hooks. Append has two explicit stop points: after the batch has committed but before printing acknowledgement 3, and after acknowledgement 3. The first must allow both histories according to the external ledger; this particular native path will normally recover the complete third batch. The second requires it.

For compaction, flush the first and second batches separately so there are two delta tables to replace. For collection, install the compacted base before arming the deletion hook. Otherwise a test called “cleanup” might actually be stopping during the setup flush.

Dumping opens a new Database, prints its sequence, checks every fixture-domain key from 0 through 30 in both relations, and prints authoritative file references. Python compares exact field tuples rather than trusting a C++ “passed” message. The L and T lines locate required files for separate offline damage tests; they are not the oracle for expected logical values.

Like the normal driver, this command performs normal recovery and may sync or repair a permitted tail. It is not a forensic read-only inspection command. The corruption campaign works on closed copies so this behavior is explicit.

Pressure the real spill cleanup path

Reuse Chapter 19's executor and Chapter 21's tiny query preset. The input database is frozen for these focused query-pressure tests; Chapter 20/21's separate live scenario remains the test of concurrent ingestion. A spill hook throws ENOSPC on the fourth write attempt, after earlier writes have had effects. Another hook can refuse every unlink with EACCES. These are injected errors at a specified boundary, not an experiment that fills the user's filesystem.

The cancellation callback owns a TaskHandle and requests stop at a spill-pass checkpoint. Both callback state objects outlive the executor. Their fields are only mutated by that query's worker; the controller inspects results after completion and joined shutdown.

Create 60 events with amounts 1 through 60 on day 3. Event index i targets account 20 when i\bmod 3=0, otherwise account 10. Account regions are 2 and 1. The independent expected groups are therefore:

\begin{aligned} \text{region 2 count}&=20,\\ \text{region 2 cents}&=\sum_{k=0}^{19}(3k+1) =3\frac{19\cdot20}{2}+20=590,\\ \text{region 1 count}&=60-20=40,\\ \text{region 1 cents}&=\frac{60\cdot61}{2}-590=1240. \end{aligned}

The tiny run capacity of three forces 20 initial runs in each sort for a successful query. Each mode starts with an old completed-output marker. Disk quota 200 permits some work but rejects subsequent admission; no-space fails inside spill writing; cancellation stops at a pass boundary; cleanup refusal leaves residual files reported; and the final normal query proves successful work can proceed after the pressure cases.

A terminal result must retain no live charged query workspace, resource-admission bytes, descriptors, or running task slot. That does not imply that every disk name disappeared. In the cleanup-denied case, copied statistics retain a positive residual-file count and its first cleanup error after live query owners are gone. The failure path must also keep the original exception: quota exhaustion is a length_error, while the injected write failure retains ENOSPC.

Only the test controller removes intentionally stranded spill files, and only after finish has joined every worker. This is confined to the new fixture's spill directory, never its database directory. The result is checked before that cleanup; otherwise the test could erase evidence and falsely attribute the work to the engine. Then drop the frozen-input owner, reopen the database, and verify all 60 acknowledged events survived every query failure.

Give the parent an independent ledger

The Python controller uses only the standard library. Commands are argument lists, not shell strings. A nonzero exit from a damaged-database open must be the native program's caught-error path, not any arbitrary crash or missing executable. Run the script without Python's -O option: its assert checks must remain active.

The Python subprocess reference documents POSIX kill, negative signal return codes, pipe handling, and reaping. The controller below drains standard output while waiting and sends standard error to a temporary file so an unread error pipe cannot block the child.

DefaultSelector waits for pipe readiness; os.read then supplies arbitrary byte chunks. A chunk may contain half a line or several lines, so pending retains the unconsumed suffix. The parser advances acknowledged only for sequential ACK lines and accepts BEGIN 3 only after observing acknowledgement 2. The selector interface supports this readiness-plus-timeout protocol on Unix pipes.

Cleanup covers success, malformed output, premature exit, and watchdog failure. An exception does not leave the child running. communicate finishes pipe handling and reaps it after the signal; the parent verifies -SIGKILL, rather than accepting _Exit(94) or normal return as equivalent.

The expected rows are repeated here intentionally, as a small independently written oracle. This code neither imports the C++ fixture nor decodes its WAL to learn what the answer ought to be. The sequence selects one of two explicit states, and the external acknowledgement/attempt pair limits which selection is legal. Table and log descriptions are allowed extra diagnostic lines, not rows.

Run separate native crash and damage campaigns

The native campaign has 26 stop points: two acknowledgement boundaries, seven rotation boundaries, seven flush boundaries, eight compaction boundaries, and two collection boundaries. Each has a fresh child-created directory. Both reopens must produce identical logical and manifest descriptions. A missing requested hook causes a failure, not a skipped test.

Copy only closed, already-recovered fixtures for corruption checks. Remove a referenced table, flip a table byte, damage the manifest checksum, or remove the entire second batch from a sealed WAL. The sealed WAL originally has 362 bytes; truncating to 32+172=204 leaves a valid first batch but violates its required sealed end. The test checks that the failed open did not silently repair this file or rewrite the deliberately damaged table/manifest.

An invalid temporary file 900 is different: it is unreferenced, so reopening must keep the logical answer and leave the file alone. Collection and its identity fence were tested in Part 2. Normal recovery must not adopt the orphan merely because its identifier is high.

Verify the completed answer after pressure

Python checks the successful CSV independently against the arithmetic above, checks all four old-result markers, and inspects final directory contents. There must be no hidden partial-result files. The spill directory is empty only after the controller's explicitly documented cleanup of the refusal case. This final check does not erase or reinterpret the earlier residual-file report.

Build and run the complete experiments

Append this block to the existing CMakeLists.txt. It reuses the already-found Python interpreter, strata-core, strata-workload, and their thread linkage. It adds no new runtime dependency. Keep the Chapter 21 tests and earlier entries.

Use the same compatible C++20 compiler, CMake, and Python setup as the earlier chapters. On the M4 Mac mini, build natively with your installed compiler; do not assume a particular macOS release or require a branded compiler version. The native controller requires POSIX process signals and Unix pipe selection.

For direct diagnosis, the commands behind the three new tests are:

The model should report 2,754 selected crash images, 173 append prefixes, and zero surviving tracked owners at each checked boundary. Native output should report 26 controlled SIGKILL cases and the required-file checks. The pressure fixture reports failed quota/no-space tasks, canceled cancellation tasks, and one completed task. Numeric task-state values are diagnostic enum values; assertions compare the named states. The refusal case reports 20 residual event runs, while the ordinary canceled case reports none. Both preserve the previous completed output.

Keep memory and race sanitizers in separate build directories. A normal sanitizer run must use the correct implementation, not the deliberate defect below.

ThreadSanitizer support depends on the compiler/runtime/host combination. Diagnose a startup or mapping failure as a tool-environment failure, not a race report or a passing test. Chapter 18 explains that distinction. The synchronous model is not a thread-interleaving test. The focused pressure test exercises worker and controller ownership; it does not enumerate every concurrent schedule.

Remove one barrier and predict the first failure

Make one temporary diagnostic edit inside Database::install in src/storage/database.cpp: remove only the first context_->directory.sync() after encode_manifest. Leave the later directory sync after rename in place. The deliberately incorrect fragment is:

The hook's label is not a persistence guarantee. Rebuild and run recovery-model. The selected failing trace is rotation, cut 28, image 7, effect 4 (rename): the new manifest's synchronized bytes and renamed binding survive, but the new active log's binding does not. Opening that required log raises ENOENT. The database must not invent an empty replacement or choose a different manifest merely to make the test pass.

In the verified Linux run, this defect failed the model in Debug, Release, and AddressSanitizer/UndefinedBehaviorSanitizer builds without a sanitizer memory error. The same defective installer passed all 26 native SIGKILL cases. That contrast is the point: killing a user process does not ask the live kernel to roll back arbitrary unsynchronized names. Passing a native crash campaign alone is not evidence that the missing persistence barrier is harmless.

Restore the first directory sync, rebuild, and rerun the complete suite. Do not retain the diagnostic fragment as an optimization. The correct implementation used for the final checks contains both directory barriers.

Interpret failures before retrying

Observation Required interpretation and next check
Recovered sequence is below the external acknowledgement Lost acknowledged history; inspect the selected image and missing dependency, not just frame validity.
Correct sequence, wrong values or tombstone visibility Atomicity or version-resolution failure; compare the exact expected state.
Valid incomplete active tail is repaired Permitted replay behavior; verify synchronized repair and the second reopen.
Complete corrupt frame or shortened sealed WAL rejects Fail-closed behavior, not permission to discard acknowledged data.
Budget admission rejects before append Definite rejection; resources release and the old database remains usable.
Append/sync returns an I/O error Uncertain outcome; stop using that writer and reopen before deciding how to reconcile the attempted batch.
Canceled query reports residual files and a cleanup error Cancellation completed, cleanup did not; retain that evidence and remove only verified temporary fixture data after owners die.
Watchdog expires before STOP The rendezvous was not established; inspect child errors and hook placement rather than increasing a sleep.

Do not delete a WAL, table, MANIFEST, or LOCK merely because it appears old. This chapter's controlled damage helpers operate only on disposable closed fixtures. SQLite's corruption guide, Sections 1.2–1.4 and 3 illustrates why recovery dependencies and synchronization assumptions need to be considered together. Strata's own manifest and retention graph remain the specific authority for its files.

What these checks establish—and what they do not

The verified authoring runs used Clang 17 on Linux: all 37 cumulative CTest entries passed Debug, Release, and AddressSanitizer/UndefinedBehaviorSanitizer builds. A separate GCC 14.2 ThreadSanitizer build passed the focused recovery-pressure test. The independent parent compared native recovered states and completed CSV answers. A process killed with SIGKILL cannot run a sanitizer's normal exit-time cleanup report; host-side cleanup is checked separately by the model's owner assertions and ordinary pressure completions.

These are actual Linux checks, not native M4/macOS results. The native tests use the existing default file-sync mode. Apple's archived fsync(2) manual distinguishes host flushing from the stronger F_FULLFSYNC request. Consult the installed system's manuals and the Chapter 6 implementation on the target Mac; this model treats both modes as ideal file barriers and cannot validate their hardware behavior. No physical power-cut experiment, device-cache certification, or universally safe filesystem assumption follows from these tests.

The experiments also do not add an automatic corruption-repair utility, a production exactly-once client protocol, or unlimited resource capacity. They establish reproducible allowed-history, fail-closed, and cleanup behavior within the stated model and fixtures. The next chapter measures the existing mechanisms, changes one demonstrated performance decision, and assembles the final correctness-and-resource demonstration.
