Chapter 17 — Grouping, checked aggregates, and complete queries

Part 1 — Preserve the joined row through a second sort

A join can be correct without placing equal groups next to one another. Chapter 16 emits events in account order. Accounts 10 and 30 can belong to region 1 while account 20 belongs to region 2. Their joined regions are then 1, 2, 1. Flushing a regional total whenever the region changes would emit region 1 twice.

This chapter completes a fixed query: select events in a half-open day interval, join each to its visible account in the same snapshot, then count events and sum integer cents by region and day. We sort the whole joined row into group order, keep one unfinished group, and stream completed groups into an output sink. A successful row is not a successful query: only valid end-of-stream followed by successful sink publication produces a complete result.

Learning objectives Reuse an external-memory algorithm through a small compile-time schema; preserve every joined field across spill; derive checked count/sum updates; implement key-change and final-group emission; distinguish progress, completion, and failure; and publish a completed result without exposing a partial replacement.

Prerequisites: all code through the three parts of Chapter 16, including Chapter 15's complete sort, spill ownership, counters, and native-file checks. Keep all 23 existing CTest entries. Chapters 5, 6, 9, 12, and 14 supply templates, checked arithmetic, charged allocation, snapshot ownership, and the pull protocol.

Implementation allocation: 3.5 hours for all three parts together. Allocate 1.0 hour to checked aggregation, 1.25 to joined-sort/query/output integration, and 1.25 to tests, debugging, and independent answers. The integration reuses your existing spill and merge mechanisms. Reading is separate from the implementation allocation.

Create the files named by the listings. Replace only src/query/external_sort.cpp in full with the segments in this part. Keep its existing public header, tests, and event-sort interface. All other query files below are new; Part 3 appends CMake targets. Repeated filename segments concatenate in reading order. They are complete files, not patches with omitted helpers.

Part 2 implements grouping, the completed-query API, and the file sink. Part 3 provides all tests, the independent decoder, commands, and failure exercises. No concurrency, SQL parser, query optimizer, cancellation, or durable query restart is introduced here.

Derive the new ordering

For joined row x, let r(x) be its region, d(x) its day, e(x) its event ID, a(x) its account ID, and v(x) its nonnegative amount in cents. A group key is g(x)=(r(x),d(x)). Sort by the lexicographic tuple

K(x)=(r(x),d(x),e(x),a(x),v(x)).

The first two components make each group contiguous. Event ID orders rows within a group; account and amount are deterministic tie breakers for otherwise identical IDs in an arbitrary test stream. Visible database event IDs are unique, but the sort itself does not deduplicate or discard equal rows. Each occurrence must still contribute to the aggregate.

Suppose account-order input contains (region, day, event, cents) values (1,3,100,500), (2,3,102,700), (1,3,103,250). The second sort produces (1,3,100,500), (1,3,103,250), (2,3,102,700). Now one region/day accumulator suffices: the transition to region 2 proves no later region-1/day-3 row remains. Do not sort only by day or only by region; either omits part of the group key.

Tuple comparison uses ordinary ordered unsigned fields rather than subtraction. It preserves the strict-weak-order requirements developed in Chapter 5; the C++ ordering requirements explain why a comparison used by std::sort must have that property. The comparator is nonthrowing and carries no mutable state.

A compile-time schema, not a second copy of the algorithm

A schema policy here is a small type that supplies nested Row, Batch, and Order types, two constants, and row codecs. It does not allocate, own files, or schedule work. TypedCore<EventSchema> and TypedCore<JoinedSchema> instantiate the same run generation, reader, heap, and merge-pass code for different row types. There is no virtual call per comparison or decoded row.

In a template, typename Schema::Row says that the dependent name is a type. Without that information, a dependent qualified name can be parsed as something other than a type. See the draft's template name-resolution rules. An alias such as using Row = typename Schema::Row; then allows local declarations like std::optional<Row>. A function definition outside the class must still write typename Schema::Row TypedCore<Schema>::take() because that return type appears before the member's scope has been established.

These policies are private to one implementation file. We do not expose an unbounded plugin interface or claim a concept proves that the codecs preserve fields. Tests must establish byte order, row widths, ordering, and round trips. The existing PullSource<Source, JoinedBatch> concept remains the public adapter's syntactic contract; it cannot prove correct EOF behavior or ownership either.

Start the new public header with the row comparator and a move-only facade. A forward-declared JoinedCore keeps implementation details out of the header; shared ownership inside the facade is for lifetime/allocation management, not permission to copy the facade or use it concurrently.

The replacement implementation starts with both comparators and common format constants. Keeping EventOrder unchanged is important: the merge join still requires (account_id,event_id,...) order, not regional order.

Distinguish row layout from row representation

Event runs retain width 28 and order ID 1. Joined runs use width 32 and order ID 2. Both use the same 36-byte header, 24-byte footer, and checksummed frames. Header version stays 1 because that format already contains row width and ordering ID. The existing reader accepts only its own pair; version 1 never meant “every possible row has the same interpretation.”

Joined-row byte offset Width Meaning
0 8 Event ID
8 8 Account ID
16 4 Day
20 8 Amount in cents
28 4 Region ID

The event prefix reuses its existing explicit codec. The final four bytes cannot be reconstructed from an event after the account snapshot is released, so they must be written. Neither sizeof(JoinedRow) nor native struct padding defines this representation. The in-memory chunk, in contrast, allocates sizeof(Row) per element; its padding is real allocated storage and must be charged.

The header checksum covers the ordering ID as well as the width. A valid checksum alone is insufficient: Part 3 changes the joined order ID to 1 and recomputes the checksum. The joined reader must still reject that header. Checksums detect byte changes; schema validation prevents a well-checksummed misinterpretation.

For n>0 rows, encoded width w, and b>0 rows per frame, let L(n,w,b) be the complete run length. Each frame adds eight prefix bytes and four CRC bytes:

L(n,w,b)=36+nw+12\left\lceil\frac{n}{b}\right\rceil+24.

For three joined rows with two rows per frame, the file is 36+3(32)+2(12)+24=180 bytes. The same event run is 168 bytes. A single joined-row run is 104 bytes. Passing the trusted schema width to Space makes disk reservation include the region bytes instead of silently undercharging them.

Keep the existing ownership boundary

The next segments retain Chapter 15's mechanisms. Scratch<T> charges actual array storage and frees it through the owning allocator. A Run is a move-only claim on a Space slot, not an owning path string. Each slot remembers expected rows/bytes and whether a name was created, completed, or retired. Capacity remains fixed: at most 128 initial runs and 32 input readers. Those are explicit scale limits, not permission to buffer all input.

Space now receives row_width once from the policy. It is not selected by an untrusted file. The destructor retries retired names and attempts directory removal after the run owners have been destroyed. Persistent unlink failure is still recorded in caller-held statistics; destruction cannot force success.

An input name remains protected until its Run is reset. Directory creation is lazy, so an in-memory sort never needs a spill directory. The private parent must exist and be trusted; the engine creates a unique child and uses the directory handle for run operations. A slot and disk allowance are acquired before file creation, preserving the partial-create cleanup contract from Chapter 15.

Opening and closing a run also update the descriptor ledger. Exclusive creation must not overwrite a prior run; size verification on open rejects a shortened or extended file before interpreting its frames. Explicit close can throw; destructor cleanup cannot. These are the same distinctions used by table and WAL owners.

Retiring means “this owner no longer needs the run,” not “the file is definitely gone.” Only confirmed absence releases its disk charge. An output replacement and all of its inputs can therefore coexist during a merge, and denied cleanup can make a later disk reservation fail. Do not unconditionally decrement disk usage in a destructor.

The read/write counters measure bytes successfully transferred through the file boundary, including partial effects before an exception. Completed-file counters are separate. A verification reread costs real read bytes and is counted. Hooks are borrowed synchronous test callbacks; their state must outlive the operation, and they must not reenter the sorter.

Parameterize the frame writer

Writer<Schema> changes the row type, comparator, width, order ID, and codecs; it does not change the protocol. The constructor reserves the complete file, opens it, and writes the header. append validates nondecreasing order and the promised count before encoding a row. This catches an algorithmic merge defect before publishing a completed replacement.

A full frame flushes; a final partial frame flushes in finish. Finishing checks the row count, writes and checks the forecast footer position, closes the file, and only then records completion. Query temporaries are not recovery authority: there is deliberately no fsync here. Run retains responsibility for a partial file if any step throws.

Validate before exposing typed rows

The reader compares both header width and order ID with its compile-time policy. It also checks count, block size, footer, and checksums. A row decoder cannot repair a wrong header or an out-of-order run. Its single charged frame buffer limits resident encoded data regardless of run length.

head returns a value, so advancing the reader cannot invalidate the caller's copy. next enforces exact end coverage. Each refill verifies frame size/CRC and row order before handing the first row to the heap; previous_ spans frame boundaries. The final remaining_ transition also detects trailing bytes.

One core, two instantiations

The core owns generation storage, one output frame, bounded run descriptors, readers, and heap indices. Space is declared before the Run arrays: reverse member destruction keeps it alive while runs retire themselves. cleanup also closes readers before retiring their names. stack_ is an allowance reservation, not a dynamically allocated replacement for the C++ call stack.

Let W be this sort's workspace allowance, Q its measured fixed control charge plus stack allowance, F=12+wb one frame, C its chunk row capacity, and D its run-file-descriptor allowance. Generation needs Q+C\operatorname{sizeof}(Row)+F. Merging needs Q+(f+1)F for f input frames and one output frame. Therefore

f=\min\left(32,D-1,\left\lfloor\frac{W-Q-F}{F}\right\rfloor\right),\qquad f\ge2.

The initialization check requires enough space for both generation and a three-frame merge. Checked arithmetic precedes subtraction. The root ledger independently enforces simultaneous allocations across both sorts and storage; one sort's configured allowance is not a reservation that bypasses that ledger.

Generation sorts only the filled chunk and writes it directly. Input beyond chunk_rows * max_runs is rejected rather than growing metadata without a bound. An exactly full first chunk stays in memory until another row arrives: small queries need neither a file nor a merge. The cap applies independently to both sorts; an inner join cannot increase event cardinality here.

Preserve the heap algorithm

The heap stores reader indices, not copied runs. For equal complete rows, reader index breaks ties deterministically. push moves a new head up the parent chain. After consuming the smallest head, sift_down repairs the root against its smaller child. Replacing EventOrder with Order in all of these operations matters: a regional chunk sort combined with an account-order heap is not a regional sort.

take copies a row before advancing its reader. An exhausted reader is removed from the heap, and a changed nonexhausted head is repaired by the same operation. open_group checks the simultaneous frame allowance before constructing readers. A failure partway through construction is handled by the core's cleanup path.

A merge pass reads at most the chosen fan-in, writes one output, closes readers, then rereads the entire replacement before retiring inputs. A leftover singleton moves its existing run owner instead of copying its bytes. The fixed next_runs_ array owns completed replacements if a later group fails.

After generation, finish releases the row chunk before opening merge buffers. Materialized passes stop as soon as the remaining runs fit one final merge; that last merge streams directly into consumer batches. EOF releases run owners and charged buffers. Any failure clears the current output and makes the sort terminal; retrying a partially consumed stream would be incorrect.

For the 25-row joined fixture, use chunk capacity 3 and fan-in 2. Nine initial runs reduce as 9 → 5 → 3 → 2. Only the three intermediate passes materialize; the final two-way merge does not create a seventeenth file. Eight full initial runs and one singleton write 8(180)+104=1544 bytes. The three passes write 1152, 1032, and 972 bytes, respectively: 4700 write bytes in total. Input reads plus replacement verification and final delivery total 7856 read bytes. Part 3 checks those mechanics against actual native files, not timing estimates.

The next two concrete classes inherit the template constructors with using Base::Base. That syntax makes the corresponding base constructors available for constructing the derived type. It does not add virtual dispatch. We allocate and destroy each concrete type through its actual owning control block, never through a raw nonvirtual base pointer.

The new facade performs the same validation and charged allocation as the old one. The fixed allocation is measured separately for each concrete instantiation; optional<JoinedRow> and optional<Event> need not occupy equal space. The measurement assumes synchronous construction with no interleaved ledger writers, as did Chapter 15. Chapter 18 must introduce synchronization before concurrency can rely on a revised accounting protocol.

Stop retaining the upstream plan after generation

Complete the new header with JoinedExternalSort. Its optional Inputs owns the entire upstream join and one joined batch. The first pull builds the second sort; it does not promise a short wall-clock response. Empty upstream batches mean progress, not EOF. Nonempty EOF is a protocol error.

Once every joined value has been copied into the second sort's chunk or runs, inputs_.reset() destroys the first sort, join, scans, snapshot, and their columns before second-sort merge readers are opened. The result remains snapshot-consistent because joined rows already contain the account's region. No later database lookup is required. The second sort's control object and statistics can still outlive its data files.

Checkpoint. Build the existing targets after this refactoring. All 23 earlier tests must still pass, including event-run byte decoding. On a three-row joined in-memory input, inspect that all five fields survive and that the region/day prefix determines order. Do not temporarily reinterpret joined rows as events: that discards precisely the dimension value whose snapshot lifetime we just released.

The two sorts have separate disk/workspace/descriptor allowances. During second run generation, first-sort runs can still be live. The shared root budget limits covered simultaneous memory, but there is not yet one combined query-wide disk or descriptor broker. Choose allowances that fit the machine and remember the sink, database files, and standard runtime consume additional descriptors. The recorded allocation ledger is not an operating-system resident-memory cap.
