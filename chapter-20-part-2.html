Chapter 20 — Concurrent readers, ingestion, and maintenance

Part 2 — Build outside the lock; install against current authority

The output files from Part 1 are prepared but not authoritative. A writer can have advanced both the active log and the manifest while they were built. Installation must prove that the selected inputs still mean what the job assumed, then retain every unrelated newer dependency.

This part completes maintenance.cpp and supplies the whole Engine. It has no additional hour allocation. All source files and small declaration changes in Part 1 are prerequisites.

Revalidate the inputs, not just the clock

Let E_c be the manifest epoch captured during preparation and E_n the epoch now. An equality test E_n=E_c is sufficient to show the manifest has not changed, but it is unnecessarily restrictive: a new active log does not invalidate a compaction of existing tables. Conversely, accepting every changed epoch without checking source identities would permit a stale output to replace a different prefix.

For flush, require the exact same oldest sealed LogRecord and one free table slot. For compaction, require the same base coverage, the same selected table records in the same positions, and enough capacity for the replacement plus the current unselected suffix. Comparing records checks IDs, interval endpoints, and encoded file lengths; comparing counts alone is insufficient.

After validation, start from database.next_manifest(), which copies the latest manifest and advances its epoch. Never begin with captured_. The owner arrays are likewise prepared from current owners before the authority transition.

Suppose a flush captured logs [L1(0,1], L2(active after 1)]. Before installation, the writer commits sequence 2 and rotates, producing [L1(0,1], L2(1,2], L3(active after 2)]. The flushed L1 is still valid. The candidate must retain L2 and L3, not resurrect the captured active-log entry. The first regression test in Part 3 checks exactly this case.

For compaction, consider tables [T1, T2] captured through sequence 2 and a later table T3 covering sequence 3. Replacement [B1] produces [B1,T3], not just [B1]. If compaction removes every row in its prefix, base_count becomes zero but base_end retains the eliminated coverage. A future older source must not be allowed to resurrect a deleted value.

A stale result returns false without changing authority and consumes the job. The coordinator may prepare a new job from current state. It must not call build again on the stale object or reuse the old file identities.

The authority and serving-state boundary

database.install performs Chapter 11's dependency, manifest, and namespace synchronization. From that call onward, failure poisons the database until reopen. The next table/log arrays already exist. Swapping their owners after a successful install allocates nothing.

The engine mutex spans installation and both swaps. A new capture cannot see the new manifest with old owner arrays. An existing capture needs no such lock: it owns its previous immutable source set. “Atomic publication” here means one indivisible observation through the coordinator, not a bitwise atomic store of an entire manifest or a new std::atomic<shared_ptr<...>> design.

Destruction of an old array may decrement shared ownership counts, but snapshots still retain their own sources. Their final release is safe because Part 1 synchronized the ledger and registry. Physical removal comes later, after the job itself has died.

Define the coordinator's public contract

Engine implements QueryInputs, so the Chapter 19 executor can hold either a frozen fixture or a live engine. final prevents further derivation of this coordinator. An application may call write, capture through the executor, and request maintenance concurrently. It must not destroy the engine while another thread is executing an API call without owning its lifetime.

stop requests shutdown and wakes writers; finish is a controller-only stop-and-join operation. Do not call finish concurrently, from the maintenance thread, or from a hook. Calling it again serially is harmless except that a stored error is rethrown again. Explicit shutdown exposes worker failure; destruction joins but cannot throw it to an absent caller.

The header uses an incomplete nested State held by unique_ptr. The state contains mutexes and is never moved. Define the destructor out of line after State is complete, so destruction sees the actual owned type. This is simply a way to keep synchronization details out of the public header, not a second allocation layer for each query.

Add the explicit stopped-writer reason. A known closed engine rejects before appending the submitted batch; this differs from a write whose synchronization outcome is uncertain. An existing stored engine error is rethrown instead of being mislabeled as ordinary closure.

Build state before starting its thread

Start src/runtime/engine.cpp. Configuration validation rejects descriptor allowances that cannot support the declared fixed upper bound. Memory capacity is enforced by the allocators, rather than guessed from a platform-dependent sizeof total. The low-capacity test will fail visibly when even a job cannot fit.

database is constructed before the thread. Recovered active contents set the batch threshold as already reached, so the next write seals them before growing that generation again. Fresh engines count committed batches; the threshold is neither a byte limit nor a timer. Arena and WAL limits still apply.

Declaration order gives destruction order in reverse. The thread is declared last but is explicitly joined before state destruction starts. If thread creation throws, the unique state owner destroys a fully constructed database with no started worker. We do not detach and hope the borrowed State* remains alive.

counts, batches, pending flags, and the database require mutex. The stop flag is also read while building outside the lock, so it is atomic. Relaxed loads suffice for that Boolean request: no manifest or error object is published through it. Those objects are still observed under the mutex. The distinction between relaxed atomics and cross-object synchronization is described in data races.

Admit work that can actually free a slot

The worker prefers a requested or pressure-triggered full-prefix compaction, otherwise the oldest sealed log. Base-only repacking at a full table set is allowed, as in Chapter 13. It may create the slot needed by a waiting flush. If a completed repack still leaves all 16 slots occupied with sealed logs waiting, fail instead of scheduling the same ineffective work forever.

A writer reaches backpressure when it must rotate and all four log slots are occupied. It increments the diagnostic waiting count and calls wait with the engine lock. Waiting atomically releases that mutex; returning reacquires it. The loop rechecks both capacity and terminal state, including spurious wakeups. This is the condition-variable contract in the standard library specification.

Holding the mutex while polling or sleeping would prevent the maintenance installer from removing the oldest log. Notification is not the resource: manifest.log_count < max_logs is the resource predicate.

Failure stores the first exception and requests stop. Cleanup refusal is visible as either failed deletion or failed synchronization; it is not silently declared successful because the serving manifest is valid. Old snapshots can still read their isolated sources after the engine stops accepting work.

There is no automatic busy retry of a failed I/O operation. A failed install may already have replaced the manifest name, so reopening—not replaying the same mutation on a poisoned object—decides authority.

One worker, two critical sections, one private build

The next function is the worker state machine. Follow the ownership of job: creation under the lock, build outside, validation/installation under the lock, then destruction outside the lock. Collection starts only after that last owner has gone. This ordering is what protects names during off-lock reads.

The shared job control block is charged to the maintenance budget. It has only one controlling worker owner; shared ownership here is used for the existing allocator facility, not to permit concurrent build and stats calls. Engine statistics are copied only after building stops.

CancellationScope is thread-local. The build observes the engine stop token, not an unrelated query's token. Installing a completed candidate has cancellation masked: a cancellation exception must not split the durability sequence. If stop wins the engine mutex before installation, the prepared job is abandoned. If installation wins first, that valid installation may finish before shutdown returns. Both outcomes preserve acknowledged writes.

On a build exception, the job dies before the engine stores the terminal error. Temporary buffers and input readers disappear; incomplete files remain nonauthoritative. On an installation exception, the database may be poisoned, and the same visible error policy prevents further writes or captures. Do not collect questionable artifacts through that old object.

await_idle is a controller observation, not a way to seize the worker. It means no pending work and no active job at the observed point. Another writer can create new work immediately afterward. Tests use controlled pauses when a stronger ordering is required.

Own the thread through every public exit

Constructing the state completes before its pointer is captured by the worker. The destructor always stops and joins. A serial explicit finish additionally rethrows the stored error after joining. It does not flush the final active log: committed data is already represented by the WAL, and normal reopen replays it.

To drain already accepted queries normally, call executor.finish() before engine.finish(). To cancel them, request the executor's cancellation and join its workers, then finish the engine. Stopping the engine first can cause an accepted but not yet captured query to fail capture; already captured views remain usable. No contract promises an immediate stop of a blocked filesystem call.

The application must also join its own writer threads. The engine owns the maintenance thread, not every caller that happens to invoke write. The backpressure test uses an explicit guard that requests engine stop before joining its external writer.

Keep write outcomes distinct

Writes are serialized through the engine mutex. When the committed-batch threshold is reached, the next write waits for a log slot and rotates. A write that is rejected by the underlying WAL does not increment the batch count. A committed write increments it once. An uncertain outcome stops future engine activity but returns that original uncertainty to its caller.

The submitted span is borrowed for the duration of write; it must remain valid even while the caller waits for a log slot. Concurrent callers each keep their own stable input buffers. The coordinator does not queue an unbounded copy of their batches.

With one batch per log, the shutdown fixture holds three sealed logs and one active log containing batch 4. A fifth writer cannot rotate. Stop changes the predicate and wakes it; it returns rejected/engine_closed with sequence zero. Batches 1–4 remain in the authoritative logs, even if their pending flush is abandoned.

seal is a controller convenience for a nonempty active log. The worker does not periodically flush a mutable memtable. Explicit sealing, a snapshot capture, or the next threshold-crossing write produces immutable maintenance input.

Capture under the mutex; construct readers outside it

Capture first produces and registers one immutable parent view under the engine mutex. Snapshot pressure is rejected before rotation by the existing database admission check. A full log set or retained-source limit is not bypassed by allocating an extra generation. This implementation rejects a pressured capture rather than sleeping inside capture; the executor will release its query permit when that request fails.

After the parent exists, the mutex is released. Private file opens, metadata reads, and cache allocation then happen outside it. Parent retention protects every name during those opens. A caller's cancellation cannot interrupt the rotation/authority mutation, but ordinary query checkpoints remain active during private reader construction and execution.

There is a deliberate asymmetry: a waiting writer releases the engine lock and can resume when maintenance frees a log slot; a capture under retention pressure fails immediately. Neither operation waits while holding the lock needed to relieve its pressure. A caller that chooses to retry must use an external policy tied to released resources, not an unbounded busy loop in this API.

The remaining methods request maintenance, observe completion, expose a test rendezvous, and copy statistics. await_writers has a watchdog so a broken test fails rather than hanging the entire suite; production progress never depends on its timeout.

Check the lock order against actual call paths

An executor releases its scheduler mutex before invoking the provider. Engine operations may acquire the registry or budget mutex briefly. The registry and budget do not call back into the engine. Private cache operations acquire their budget ledger only while accounting; no shared cache lock is added.

The registry lock is not held while the owned sources are destroyed. The allocator's ledger lock is not held while arbitrary query code executes. Do not introduce a callback from either bookkeeping layer that acquires the engine mutex; it would create the reverse edge of the lock order.

EngineStats coherently reports database sequence/epoch/counts while holding the engine mutex. Its ledger observations are individually protected but not one atomic global RSS sample; query releases can change charges between observations. last_job is a completed-or-failed job report, not a race-prone live pointer into an active builder.

The stopped engine and its maintenance thread can be gone while a captured query still owns its parent context. That is intentional. Source files and the directory lock remain alive until that last snapshot ends. The next part tests both that retention and the final release on a different thread.
