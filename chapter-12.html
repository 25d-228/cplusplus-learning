Chapter 12 — Immutable snapshots and merged reads

Part 1 — Own a complete read boundary

An atomic write batch prevents half of a batch from becoming visible. It does not make two separate current-state reads repeatable. Read account 10, commit a batch, then read event 101: Chapter 11's Database::get can legally combine the old account with the new event. Each call is individually correct; their combined answer belongs to no single committed state.

A read view changes that contract. It captures one sequence and the exact owners needed to answer all reads at that sequence. Later writes use a different active memtable. A later flush can change the database's serving set without replacing anything inside an existing view.

Learning objectives Build ownership that survives database destruction; distinguish shared ownership from frozen contents; admit a bounded immutable source set before rotation; implement ordered point and range reads with a hand-written heap; and make failed cursor advancement terminal rather than silently skipping data.

Prerequisites: the completed Chapters 7–11, including Chapter 9's charged constructors and pinned table reader, and Chapter 11's sealed-log checks and manifest installation. Keep the language-foundation programs and all existing tests. This chapter has 4.5 implementation hours across its three parts: 1.25 for ownership/capture, 2.0 for merged lookup/scan, and 1.25 for retention and visibility tests. Reading is not included. Nothing in this chapter starts threads.

Part 2 implements the merge. Part 3 supplies the runnable checks and build changes. Finish all three parts before building the new executable. They form one chapter, not three separate projects.

What the view promises

Use the roadmap's batch. Account 10 changes from region 1 to region 3, event 101 changes from 250 to 900 cents, and event 102 is deleted. The changes share sequence 2.

Read boundary Account 10 Event 101 Event 102
View captured at sequence 1 Region 1 250 cents Present
View captured at sequence 2 Region 3 900 cents Absent
Sequence-1 view after both generations are flushed Region 1 250 cents Present

A view returns owning point results and creates independent range cursors. A cursor keeps the view alive even after its original handle is reset. Both may outlive the Database facade. They cannot be used concurrently yet: the cache, counters, budget, source readers, and capture protocol remain synchronous and nonreentrant. Reference counting is not a replacement for the synchronization chapter.

There is no arbitrary snapshot_at(old_sequence) API and no read-write transaction. Capturing freezes the currently published boundary; retaining that handle preserves it. The distinction between committed visibility and a stable read snapshot also appears in SQLite's isolation explanation. Here the implementation is our own immutable-generation protocol, not SQLite's page/WAL mechanism.

Draw every ownership edge, including the ledger

Chapter 11's table reader owns its descriptor and metadata, but borrows its cache and budget. Keeping only a shared_ptr<TableReader> after destroying the database would therefore leave two dangling dependencies. Keeping an arena's node address is even less sufficient: an address does not retain its allocation.

The new lifetime graph is:

The last line matters during destruction. State can be the last owner of its context. Destroying its members may destroy that context; only afterward does the shared-pointer implementation finish releasing storage for the state itself. An allocator that merely borrowed Budget* would not, by itself, keep that final deallocation safe. We give the allocator its own shared budget owner.

There is no cycle: neither Budget nor Context owns a view or a scan. The retention registry stores identities and counts, not owning pointers back to states. Table-reader borrows remain valid because the state retains the context, and a scan destroys positions and pins before dropping its state.

The directory lock also belongs to the context. Destroying the database while a view exists does not release the lock. This intentionally prevents another cooperating process from reopening and modifying files while escaped readers are still using them. Release the final view/cursor before reopening that directory. This conservative lifecycle is part of the interface, not a surprising leak.

Let the allocator retain its budget

std::shared_ptr<T> copies an ownership handle; it does not copy T. A shared_ptr<const T> denies mutation through that access path, but cannot stop a separate mutable alias from changing the same object. We will combine const state ownership with actual sealing. See the standard draft's shared-pointer constructors for ownership-sharing conversions; do not manufacture a second independent shared pointer from an existing owner's raw pointer.

Create include/strata/memory/shared_allocator.hpp. The new allocator delegates allocation sizes, failure injection, and ledger updates to Chapter 9's allocator. It changes only who retains the ledger. The complete file is:

The converting constructor permits rebinding from SharedAllocator<T> to SharedAllocator<U> while retaining the same ledger. allocate_shared may allocate an implementation-defined control/object type rather than exactly T; its creation requirements use a copied, rebound allocator. Consequently the ledger records the real request, not a guessed sizeof(T) plus an invented control-block constant.

Copying the allocator copies a shared pointer without allocating another budget. deallocate still has a live owner_ when it returns storage and subtracts the charge. Only afterward can releasing the allocator's own copy destroy the budget. The null-owner check prevents constructing a context with an unusable ledger.

The caller creates the small root ledger with std::make_shared<Budget>(limit). That bootstrap object/control storage is outside its own accounting. Context, view, scan, source-owner controls, metadata, cache frames, and arena chunks are charged. Call-stack space, filesystem caches, allocator overhead outside recorded requests, and fixture containers are still outside the ledger. It remains an engine allocation budget, not a process-resident-memory limit.

Lower-level MemTable, TableReader, and BlockPin APIs retain their Chapter 9 borrowed-budget contracts. Only the database-level lifetime boundary is changing; we are not adding a hidden global budget or duplicating the accounting algorithm.

A source set has a fixed shape

Create include/strata/storage/read_view.hpp. Append its following blocks in order. The source cap is the manifest's existing table-plus-log cap, not an unbounded vector of every file ever created. A source contains exactly one owning pointer: a sealed WAL/memtable owner or an immutable table reader.

Source::identity() is an in-process complete-object identity used only while that object is retained. It is neither the durable file ID nor the cache binding ID. Once its final registry reference disappears, that address may be reused. We never carry the raw identity across reopening or use it to locate a file.

The memtable path is shared_ptr<const WalMemTable>: read code cannot call its writer methods. The disk path remains shared_ptr<TableReader> because reading updates block-read counters and cache state. Its underlying table bytes are immutable even though its bookkeeping is not. Constness is not transitive through a pointer member; the sealed-owner invariant is what protects stored rows.

Append the context and state declarations:

Context owns its budget before constructing the directory and cache. The member declaration order makes cache destruction precede directory/lock release, which in turn precedes releasing the budget member. State declares the context before its held sources, so source destruction happens first. These are concrete uses of reverse member destruction order. The owning allocator separately protects the later control-storage deallocation.

A state is prepared privately with active == false. It is not admitted to the registry until the freeze/install step succeeds. Destruction of an unactivated candidate releases its source copies without decrementing counters that were never incremented. An activated state unregisters once, when its final shared owner disappears—not once for every copied ReadView handle.

The array has 20 slots with the current manifest caps. Its unused shared pointers are empty. The actual count bounds every traversal. No state stores a borrowed span into the caller's source array; the constructor copies the owning handles.

Separate a repeatable view from a mutable cursor

Finish the header with the public handles:

A default or moved-from view is empty. Copying a view intentionally shares one state and one admission slot. reset() releases that handle; another copy or cursor can keep the state alive. get returns a small owning OwnedEntry, so it needs no rvalue restriction. scan also owns what it needs, allowing a temporary view to create a longer-lived cursor.

A cursor has one mutable position and is move-only. Its internal shared_ptr is used for the allocator-backed factory and lifetime cleanup; the public API does not let clients copy the traversal position. The forward declaration of Scan keeps the heap/position layout in the implementation file. Shared-pointer handles can be declared with an incomplete pointee type; the allocation is performed later where that type is complete.

entry() returns a borrow into the cursor's owning row. The reference-qualified accessor rejects a direct borrow from a temporary cursor. A previously returned span must still not outlive the cursor or a call that advances/resets/replaces it. Qualifier restrictions are useful, not a complete lifetime proof.

Count the union, not the number of pointer copies

Let V be the number of admitted state objects, S_i the set of source identities held by state i, and R the number of distinct retained source identities. The limits apply to:

V \leq V_{\max}, \qquad R = \left|\bigcup_{i=1}^{V} S_i\right| \leq R_{\max}.

Copies of a view do not add another S_i. Capturing a fresh view over the same sources adds one state but no new source identity. A cursor retains its state's slot even after reaching end-of-range; reset or destruction ends that retention.

Suppose view A holds memtable M1. The database flushes M1 into table T1, then writes M2. A new view would hold T1 and M2, while A still owns M1. With a retained source cap of two, the union would contain three identities, so capture must fail. After A's final owner disappears, capturing T1 and M2 fits. Replacing A's source with T1 behind its back would hide retention rather than implement it.

The registry has at most 128 slots. Checking admission scans this bounded array; it does not allocate a map. Its cost is bounded by the small configured source caps, and it is not advertised as constant-time hashing.

checked_owner returns an owning handle after checking it, rather than returning a reference to a nullable pointer's target. own copies at most the 30-byte event payload into an inline result. It is also the lifetime boundary used later when a cursor is about to advance and invalidate its source span.

Open the internal namespace and implement admission:

Each source must select exactly one alternative. A null/null source or a memory/disk pair is a programming error; duplicate source identities inside one state are also rejected. That makes the registration loop's reference counts unambiguous. added counts only identities absent from the existing union.

The subtraction test avoids unchecked addition. Existing invariants guarantee counts_.sources <= limits_.retained_sources, so comparing added with the remaining slots cannot underflow. Capacity rejection performs no allocation, file operation, source freeze, identifier consumption, or serving publication.

A raw pointer comparison here tests identity only; it does not dereference a stale address. The state still owns every source while the registry contains its identity. There is no weak-pointer polling or use_count()-based synchronization.

Append registration, release, and state construction:

retain runs only after a successful preflight and with no intervening reentrant operation. Therefore a free registry slot is guaranteed. Its termination guards mark internal invariant failures, not ordinary admission errors; ordinary pressure was already reported by check_admission. The maximum reference count for a source is the maximum admitted state count, 32, not the number of handle copies.

activate additionally verifies that every captured memtable is actually frozen. A conversion to shared_ptr<const WalMemTable> did not freeze it. This guard catches a capture implementation that forgets to rotate before publication.

A state's destructor unregisters while it still owns its sources and context. The member destructors then release those owners. Because no callback or thread can observe this intermediate cleanup, counters and ownership change as one synchronous operation from the caller's perspective. The cache may retain its own blocks after a source dies; those blocks remain charged under the context.

Capture before the effectful rotation, publish after it

Add the following complete method immediately before the closing strata::storage namespace in src/storage/database.cpp:

First inspect the active table. An empty active table contributes no records and need not be rotated or captured. Every sealed predecessor is retained. If the active table is nonempty, the pending state includes that owner but remains private until rotation has made it immutable.

The fixed array copies owning handles on the stack. It does not copy row payloads. Preflight counts the union before allocating a state; the state itself is then allocated and populated before rotation. Chapter 11's rotate prepares the replacement WAL/memtable owner before sealing the old one, synchronizes the required files, installs authority, and publishes the replacement by nonthrowing owner moves. The data sequence does not change during this maintenance.

The replacement owner is prepared, not a promise of unlimited future write capacity. Its empty arena allocates chunks lazily; a subsequent batch can still be definitely rejected for lack of charged memory. This distinction keeps "prepared replacement" separate from an invented guarantee about future loads.

After rotate succeeds, activate and the conversion/move into ReadView need no allocation, I/O, or user callback. Thus there is no late state-allocation failure after a successfully installed freeze boundary. Part 3 arms the next allocation at manifest-closed to check that property directly.

Failure location Returned view Database behavior
Retention cap or no spare log slot None No change; remains usable
State allocation before rotation None No change; remains usable
Rotation after entering its effectful region None Poisoned; destroy and reopen
Successful rotation and activation Complete immutable view New active writer is usable

An existing view remains readable when a later database operation is poisoned: it owns an earlier sealed source set. It is not allowed to consult that database's possibly stale current owner arrays. If a view still holds the directory lock, release it before reopening. An error does not implicitly revoke another caller's read handle.

This capture operation may perform durable log rotation and therefore is not an O(1), allocation-free snapshot promise. Repeated captures without intervening writes avoid rotation but still allocate distinct states and consume view slots. Batching read requests or reusing a view can amortize that explicit cost later.

The full on-disk formats are unchanged. No obsolete file is deleted here, no concurrent reader/writer safety is claimed, and no new power-loss guarantee is inferred from ownership. Continue with the actual merge in Part 2.
