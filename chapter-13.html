Chapter 13 — Streaming compaction and safe reclamation

Part 1 — Replace a complete history prefix

A snapshot can keep a file alive after the database stops using it. That is a correct lifetime property, but it does not by itself tell us when to delete the file. Nor does merging several sorted files tell us which versions can safely be omitted. This chapter connects those two decisions to the manifest's recovery authority.

We implement a deliberately bounded policy: compact the whole oldest table prefix, including any existing compacted base, into one or more size-capped files. Newer tables and all logs remain outside the operation. This is an actual streaming rewrite, not a map built from all records. The existing heap merge selects live values; the builder decides exactly when the next row needs a new file. After durable installation, an explicit collector removes only unreferenced numbered files that no retained view needs.

Learning objectives Prove when an obsolete version and a tombstone may disappear; encode a multi-file or empty base without inventing sequence gaps; forecast complete output size; preserve old readers across replacement; fence file identities before deletion; and distinguish transferred bytes, logical file sizes, and physically reclaimed space.

Prerequisites: the complete Chapter 12 implementation, including the Chapter 9 charged containers/cache, Chapter 10 WalFileOps test backend, Chapter 11 manifest installation and directory lock, and Chapter 12 owning views and heap merge. Keep all existing tests. This chapter allocates 4.0 implementation hours across all three parts: 1.5 for selection/merge, 1.25 for installation/reclamation, and 1.25 for interaction tests and counters. Reading is not included. Reuse the earlier mechanisms rather than reimplementing the heap or encodings. The engine remains single-threaded and nonreentrant.

Part 2 implements installation and lifetime-aware cleanup. Part 3 contains the complete test executable, independent native-file decoder, and build instructions. Finish the changes in all three parts before building.

Why a prefix, not an arbitrary selection?

For a user key k, let an entry's sequence be s. A put supplies a value; an erase is a tombstone. Chapter 12 orders entries by user key ascending and sequence descending, then consumes the whole key group. For a read boundary e, its answer comes from the largest eligible sequence:

s^*(k,e)=\max\{s : \text{an entry for }k\text{ exists and }s\leq e\}.

An empty set means absent. A tombstone at s^*(k,e) also means absent. This formula says nothing about entries in a source we forgot to select.

Consider a put at sequence 1 in table A and an erase at sequence 2 in table B. Compacting B alone and discarding its tombstone would leave A's put visible again. Even a perfectly sorted, checksummed output would be semantically wrong. Instead, select all installed table history through boundary e=2. There is now no unselected older put to resurrect. The selected output can contain no row for that key.

Our manifest makes the proof mechanical. Before the first compaction, tables cover consecutive sequence intervals beginning at zero. After compaction, one base represents all history in (0,e], possibly using several key-partitioned files. Later delta tables cover consecutive intervals starting at e. A legal selection includes every base file and zero or more entire following delta tables; without an existing base, select at least one table. Repacking just the base is useful when larger output files can free table slots. Every omitted table or log is newer than the selected end. Thus a tombstone that wins within the selected prefix can be omitted along with all of its older puts.

An already-held sequence-1 view does not start using this sequence-2 base. It continues owning table A. New views capture the current sources at a boundary at least as new as the base. There is still no API that asks the current serving set to reconstruct an arbitrary discarded historical sequence.

Object Before prefix replacement After replacement
Current database Old prefix, newer deltas, logs New base, same newer deltas, same logs
Earlier view Its captured source owners Exactly the same owners
Uninstalled output Not authoritative Still not authoritative after a failed install
Collector No deletion during replacement Checks current authority and retained sources

This policy is intentionally not a general leveled or tiered compaction picker. It gives us a small, complete correctness argument while still requiring real merge execution, bounded outputs, failure-safe installation, and delayed reclamation. Rewriting a large oldest prefix repeatedly can be expensive. We will measure that work rather than call the policy optimal.

Give a compacted base an explicit format

Chapter 11's table record is {id, base, end, bytes}. Its interval describes coverage, not just the minimum and maximum sequence physically left in the file. For an ordinary flushed delta, both endpoints are witnessed by its rows. After compaction, the newest live value for every key might come from sequence 1, although the prefix also contains later deletions. Requiring an actual row at the compacted end would either reject valid output or tempt us to invent a dummy row.

Introduce base_end and base_count. The first base_count table records are ordered, disjoint user-key partitions of one base; each record has base == 0 and end == base_end. Their rows are puts with original sequences in that interval, one row per user key. Remaining table records retain the old contiguous-delta rules. A base whose last values were all deleted has a positive base_end, zero base files, and no dummy table.

Keep the family magic STRAMAN1; the explicit version field selects the layout. Version 1 remains byte-for-byte unchanged when base_end == 0. Version 2 uses the former reserved field and appends one eight-byte header field:

Offset Width Version 1 Version 2
0 8 Family magic Same family magic
8 4 Version 1 Version 2
12 4 Table count Total table count, base files included
16 4 Log count Log count
20 4 Zero Base-file count
24, 32, 40 8 each Epoch, next ID, flushed boundary Same meanings
48 8 First record begins here Compacted base end
56 Variable Already inside records First record begins here

All integers remain little-endian. There is still one trailing CRC-32 over all preceding bytes. Let T be total table records and L log records. Each table uses 32 bytes and each log 24. Including the checksum, exact lengths are

N_1=52+32T+24L,\qquad N_2=60+32T+24L.

At T=16 and L=4, N_2=60+512+96=668 bytes. An empty version-2 base with one active log uses 60+24=84 bytes. Counts are checked before they determine subspans or loops. Bounds on directory key ranges require opening the files; manifest checks alone cannot prove their contents.

Replace this header in full. The old constants, records, and codec declarations remain available; max_bytes grows by eight, not by an unbounded variable header.

Replace src/storage/manifest.cpp with the following four segments in order. The first retains the family magic and the common rejection helper. A version change is explicit data, not a guess made from file length.

The validator advances boundary only for temporal delta intervals. It must not advance once per base file: all those files describe the same temporal prefix, partitioned by key. The shared take_id lambda still rejects duplicate identities across tables and logs.

For a base through sequence 3 split into five files, each of those first five records says (0,3]. A following delta says (3,4]; flushed is 4. The active log begins at 4 unless sealed logs extend the boundary. For an empty base through 2 followed by no delta, boundary begins and ends at 2 even though the table loop has zero iterations. That is why absence of files is not absence of history.

The encoder allocates one charged, exactly sized byte vector. Its emit lambda captures the current offset by reference, just as in Chapter 11. No table row or pointer representation is copied into the manifest.

The decoder first establishes the version-dependent minimum length, then verifies the checksum and exact count-derived length. A checksummed version-2 image with base_end == 0 is rejected rather than becoming an ambiguous second spelling of version 1. Semantic interval checks run after bounded decoding.

This change is forward use of a new format by the updated reader. An old Chapter 11 reader is not expected to open version 2. Do not remove its version check to make it do so. The updated reader still opens all valid version-1 directories.

Stop before the next row exceeds the whole-file cap

Chapter 8's builder detects file-size failure, but discovering it in finish() is too late for a streaming splitter. The row that caused the excess may already be in the builder, and the input cursor may already have advanced. We need a nonmutating question: would appending this row and immediately finishing fit?

Use these symbols for the existing builder fields. u is used_, including the four-byte count of the current data block. b is the number of already flushed data blocks, o the offset immediately after them, B the block-buffer capacity, f the Bloom-filter bytes, and \ell=22+v the encoded row length for v value bytes. A data frame adds 12 bytes. Metadata with n directory entries has payload length 12+46n+f, also wrapped in a 12-byte frame. The footer uses 40 bytes.

When u+\ell\leq B, finishing after this row needs n=b+1 blocks and

S=o+(u+\ell+12)+12+(12+46n+f)+40.

Otherwise the current block must flush, and the row starts a new block with its own four-byte count. Now n=b+2 and

S=o+(u+12)+(4+\ell+12)+12+(12+46n+f)+40.

The 24-byte file header is already included in the initial o. This is a forecast of actual framing, not a safety percentage. Event values use 30 bytes, so \ell=52. With a 128-byte block and 32-byte filter, two event rows have u+\ell=108 and one directory entry. Their whole file is

24+(108+12)+12+(12+46+32)+40=286\text{ bytes}.

A third event needs a second block and produces 400 bytes, not merely another 52 bytes. A cap of 286 therefore admits exactly two such rows; a cap of 285 does not. The minimum block size is 64, so a validated maximum-sized row fits into a fresh block: 4+52\leq64. That fact prevents an empty-block special case in the forecast.

In table.hpp, make the following exact declaration changes. In these small unified diffs, lines beginning with - are removed, + lines are inserted, and unprefixed context is retained; the markers are not C++ source. All algorithmic functions appear in complete listings below.

Add these functions inside namespace strata::storage in table.cpp, after its existing definitions and before the final namespace-closing brace. They use the existing validate_entry, metadata_size, and format constants from that same translation unit; do not create duplicate helpers.

can_append checks the builder state and the same strict internal ordering as append. Invalid entries throw without modifying the builder. A valid entry that would exceed either the block count or file cap returns false, leaving it ready to finish. The caller retains the unconsumed row and offers it to the next file. The arithmetic is bounded by the validated format limits: at most 4,096 blocks, 64 KiB block payloads, and 256 KiB metadata. It does not multiply attacker-provided unbounded counts.

The endpoint getters expose authenticated directory keys, not proof that every row is correct. Reopening a compacted base will first fully verify each table, then require strictly increasing user keys inside it and strictly separated ranges between files. Empty tables return nullopt; they are not admitted as base partitions.

Count work where successful transfers occur

File length and traffic answer different questions. Rewriting a 1,398-byte output creates 1,398 logical bytes, but a failed operation may write a 24-byte header and never finish any file. Reading a table may hit the block cache or may reread a block. Metadata validation during reopen is not the same phase as input merge traffic. Counters must have narrow names and precise boundaries.

Add per-File counters at Chapter 6's successful partial-transfer boundary. They count bytes returned by read_at and write_at, including successful prefixes before a later error. They do not count zero-progress errors, EINTR, or synchronization requests, and they are not measurements of physical device I/O. Overflow saturates at the largest unsigned 64-bit value and sets a flag, rather than wrapping into a deceptively small number.

IoBytes::add tests count > maximum - total before addition, so the overflow check cannot itself overflow.

Replace read_up_to and write_all with the following complete functions. Notice that accounting follows backend-contract validation and successful progress, but precedes the next system call. With a nine-byte request, two successful two-byte transfers followed by failure leave written == 4, not zero and not nine.

Boundary reached

The table layout has not changed. We added a nonmutating forecast and small observability accessors. The manifest now distinguishes a temporal delta from a key-partitioned base, including an empty one. Part 2 connects those definitions to source ownership, streaming output, manifest installation, and explicit cleanup. No deletion belongs in a TableReader destructor.
