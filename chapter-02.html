Chapter 2 — Values, references, containers, and views

A query operator will eventually receive a buffer, examine part of it, and hand results to another operator. Before doing that, it must answer three questions: who owns the elements, which access path may change them, and what operation ends the validity of a borrowed range? A pointer and a length cannot answer all three. Neither can a modern-looking type used without its lifetime contract.

This chapter makes those questions executable. A value parameter changes its own copy of {3, 5, 8} without changing its caller. A mutable view changes the caller's middle element to 7. A read-only view then observes a sum of 18. A growing vector and a text field show why a view is neither an owner nor a snapshot.

Starting code: keep the complete five-file exercise from Chapter 1, including its final subrange checks. Keep foundation-01-stats, foundation-01, and cxx20-probe in the root CMake file. This chapter adds a separate executable; it does not change those sources or require any engine code.

Learning objectives

Distinguish an owning value from a reference and a copied view; use const, auto, and range-based loops deliberately; explain array and vector storage; write mutable and read-only span interfaces; preserve an owner's lifetime; predict invalidation before changing a container; distinguish text length from null termination; use a focused diagnostic without putting undefined behavior into the normal test suite.

The implementation allocation is 2.0 hours: 1.0 for the programs, 0.5 for the interface variations, and 0.5 for invalidation diagnosis and tests. Reading is separate. There is no speed target for these tiny fixtures.

A fixed array is an owning value

std::array<std::uint32_t, 3> is a library type containing three unsigned 32-bit integers. The angle brackets supply arguments to a library class template: the element type and the element count. Using this existing type does not require writing a template. Chapter 5 will develop that separate skill.

Unlike a C array parameter, a parameter of this std::array type does not silently turn into a pointer. Passing it by value gives the function its own three-element value. The count is part of the type, so an array of four elements is a different type. The elements are contiguous, and the array's .size() is always three; see the array overview.

using Triple = ...; gives the existing type a shorter name; it creates no object and adds no runtime layer. An object declared as Triple values{3, 5, 8} contains those three integers. Triple zeros{} instead initializes all three to zero. Do not infer that a bare Triple uninitialized; initializes its integer elements: keep initialization explicit.

The helper check is the same active-control-flow idea as Chapter 1. A failed condition prints a label and returns false; later callers propagate that to main. It is not disabled by a Release build. <limits> and the view/string headers will be used below, after their interfaces are explained.

with_middle receives an owning value. Its assignment changes its parameter, not the caller's array. Returning that array gives the caller an owning result, not a pointer into a dead local object. For an input named original, the semantic trace is:

Moment original Function's value / returned value
Before the call {3, 5, 8} No parameter yet
Parameter initialized {3, 5, 8} {3, 5, 8}
After replacing index 1 {3, 5, 8} {3, 99, 8}
After return {3, 5, 8} Caller owns {3, 99, 8}

This is an explanation of observable values, not a promise that machine code performs two physical copies. An optimizer may remove unnecessary copying while preserving those observations. Three copied integers are also a very different cost from copying a million-element vector. Avoid turning “pass by value” into either a universal mistake or a universal optimization.

A reference names the caller's object

An & in a parameter declaration changes the relationship. Triple& is an lvalue reference: it binds to an existing Triple, and uses of the parameter access that same object. There is no separate array payload for the parameter. A normal reference must refer to a live suitable object; it is not a nullable optional argument. The reference rules specify the language relationship, without promising a particular reference representation.

const Triple& also refers to the existing array, but it disallows modifying its elements through that reference. It does not promise that no other access path can change a non-const owner. Append these functions:

The call syntax is set_middle(original, 7), not set_middle(&original, 7). The declaration supplies the reference binding. Inside the function, ordinary values[1] accesses the caller's element; there is no explicit dereference. This differs from a C pointer interface while preserving the ability to mutate a caller-owned object.

read_middle returns an integer value. That returned integer does not borrow from the array and remains usable after the array is gone. Returning a const Triple& or a span would be a different lifetime promise.

auto deduces a type, not an ownership policy

In a local declaration, auto asks the compiler to deduce the type from the initializer. It does not mean dynamically typed, and it does not universally mean reference. For the array original, the following spellings express different relationships:

Declaration Relationship
auto copy = original; A new Triple, with its own three integers
auto& alias = original; A mutable reference to original
const auto& observed = original; A read-only reference to original
const auto copy = original; A new, non-mutable Triple value

For these ordinary value initializers, plain auto does not carry over an initializer's reference or its top-level const. The explicit & and const in the declaration matter; the placeholder deduction rules give the full specification. We are not using decltype(auto) or forwarding references here.

Assignment through a reference does not rebind it

A reference is bound when it is initialized. Later assignment through it assigns to its object; it does not select a new referent. The reference initialization rules make this distinction explicit. Predict which array changes in the following variation, then append the complete check:

A range loop still chooses between values and references

A range-based loop visits the elements of a range in order. In for (auto value : values), the loop variable is a new value for each iteration. In for (auto& value : values), it is a reference to the current element. The colon separates the loop variable's declaration from the range expression.

Append this experiment:

The first loop produces local values 4, 6, and 9, but the array remains 3, 5, and 8. The second loop writes 4, 6, and 9 into the array. The final loop borrows each element read-only. 1U is the unsigned literal one. These three small values make every increment and sum exact; no overflow behavior is being used.

Copying a small integer for reading is normally appropriate. const auto& is also a useful spelling for reading a larger record without copying it, but it is not inherently faster for every type. More importantly, auto applied to an element that is itself a view copies that view, not its referenced payload. The type being copied determines the copy's meaning.

The range-for specification describes iteration using a beginning position and an end position obtained before the loop. An iterator is a position used to traverse a container; for contiguous storage it behaves in many ways like a pointer, though its actual type need not be a pointer. end() denotes the position after the final element and is not itself an element. Do not structurally modify a vector inside a loop over that vector: even an append without reallocation invalidates the old end iterator. Element assignments, such as the second loop above, do not change the range's size or storage.

A span combines an address and an element count

std::span<T> describes a contiguous sequence of T objects owned elsewhere. The spelling without a second template argument uses a count stored at runtime. It is useful to reason about the descriptor as a start address plus an element count, without assuming a particular binary representation or sizeof(span). The span overview defines this non-owning relationship.

Constructing std::span<std::uint32_t>{owner} from our array derives the range from the array itself. It avoids manually repeating a possibly wrong count. Copying the span copies the description, not the integers. Destroying the span does not destroy its owner's elements. A span does not pin storage, extend an owner's lifetime, or repair an invalid raw pointer supplied to a constructor.

The element type controls write access. std::span<const std::uint32_t> reads integers but cannot assign them through its subscript. A mutable-element span can be converted to a read-only-element span; the reverse conversion is not a way to obtain write permission.

Read the position of const

These types make two distinct choices:

Type Can the descriptor be assigned a different range? Can an element be assigned through it?
std::span<std::uint32_t> Yes Yes
const std::span<std::uint32_t> No Yes
std::span<const std::uint32_t> Yes No
const std::span<const std::uint32_t> No No

A const span is a fixed descriptor; it need not describe const elements. Span's subscript operation is const-qualified for the descriptor while returning access to the declared element type. In contrast, a const array or const vector gives read-only access to its owned elements. Do not generalize a container's const behavior to every handle-like type.

For a read-only input range, pass std::span<const T> by value. A const std::span<T>& only makes the descriptor read-only and still permits writes to its elements. Passing a descriptor by reference is not necessary to avoid copying the whole payload: that payload was never copied by span.

Check an index before modifying an element

std::size_t, supplied by <cstddef>, is an unsigned size type. It is the natural type for a span's element count and index. An index is not a byte offset. For a valid index i, values[i] names one element. In the C++20 interface used here, operator[] does not provide a portable checked-error result for an invalid index. The current draft also describes newer facilities; this program does not depend on later span::at or library hardening modes.

Preserve the accumulator's range proof

Chapter 1 used 32-bit elements and a 32-bit count to prove that a 64-bit sum fits. A span's count is std::size_t, so adopting a span must not silently discard the count bound. We will reject counts above the original bound and keep the output unchanged on rejection. The return value reports success; a mutable reference carries the numeric result. This also distinguishes an empty sum of zero from a rejected call.

std::numeric_limits<T>::max() returns the greatest representable value of the numeric type T; see numeric limits. Here ::max() calls a type-associated function; no limit object is needed. Append the reader and its complete test helper:

Let n be the accepted count and x_i the unsigned value at index i. The loop's accumulator after k iterations is the sum of the first k elements. The guard enforces n \leq 2^{32}-1, and the element type enforces x_i \leq 2^{32}-1. Therefore

0 \leq \sum_{i=0}^{n-1} x_i \leq (2^{32}-1)^2 < 2^{64}.

All terms are nonnegative, so every partial sum also fits. total is already 64-bit when an element is added. A failed count check returns before assigning result. An accepted empty range performs no reads and assigns zero. Read-only here means the input elements cannot be changed through this interface; the separate result reference is intentionally mutable.

This is a bounded 32-bit-element exercise, not the later engine's general 64-bit-amount aggregate. Do not claim to exercise the large-count rejection by constructing a fake span over a tiny array: the span would already violate its valid-range precondition. The guard is directly inspectable; the runnable fixtures test empty, ordinary, and wide-element sums using real storage.

Slicing changes the description, not the owner

A span's subspan(offset, count) returns a new view. Let n be the original length, o the offset, and c the requested length, all measured in elements. The required inequalities are

o \leq n, \qquad c \leq n-o.

Using c <= n - o after checking o <= n avoids an overflowing o + c validation expression. It also prevents unsigned subtraction from wrapping. For {3, 7, 8}, choosing o=1 and c=2 describes {7, 8}. Its sum is 15. Choosing o=2 and c=2 violates the second inequality and must not be executed. At o=n, the only permitted count is zero. The subview specification gives this contract; subspan is not a replacement for validating untrusted offsets.

On the verified four-byte element layout, a view starting at address A with length three describes elements at A, A+4, and A+8. The suffix starts at A+4 and contains two elements. It does not allocate another eight-byte payload. Neither descriptor owns those bytes.

An empty range is identified by a zero length, not by an assumed null address. A default empty span and an empty suffix are both valid inputs. No element may be accessed in either. The owner remains alive until this function returns, and none of its borrowed descriptors escapes.

A vector owns storage that can move

std::vector<std::uint32_t> owns a dynamically sized contiguous sequence. The vector object and its element allocation are distinct: a local vector can own a buffer elsewhere in memory. Copying this integer vector creates independent elements; copying a span of it does not. The standard library manages the allocation and releases it on normal destruction. Do not delete the address returned by .data(). The vector overview describes automatic storage management and contiguous storage for this element type. We are not using the specialized vector<bool> representation.

Three quantities must remain distinct:

Quantity Meaning
size() Number of current elements; valid subscript indices are below it
capacity() Number of elements that fit before an append needs reallocation
max_size() A container limit, not available physical memory or an allocation promise

reserve(8) asks for capacity of at least eight; it does not create eight elements. Writing v[7] into a vector of size three is invalid even when its capacity is eight. resize(8) changes the element count to eight. With this integer type and the default allocator, newly appended elements are initialized to zero. Shrinking removes the trailing elements. The capacity operations specify these different effects.

Brace and parenthesis initialization also express different requests here: std::vector<std::uint32_t> a{3} contains one element equal to 3; std::vector<std::uint32_t> b(3) contains three zero-valued elements. The initializer-list form describes element values, while the count constructor creates that many elements. Neither is universally the “safer spelling”; choose the constructor that means what the program requires. The vector constructor specification describes the count forms.

Size is not allocated payload

Let n be the size, c the capacity, and e the bytes per element. The logical element payload is ne bytes; capacity accounts for ce bytes of element storage. If an observed vector has n=3, c=8, and e=4, those quantities are 12 and 32 bytes. They exclude the vector object, allocator overhead, and any other process memory. This is a capacity illustration, not a claim that a particular reserve(8) must report exactly eight.

In the engine, charging only size would let retained spare capacity escape the memory budget. Here, it also explains why a successful reserve is not a hard cap: appending past capacity can request another allocation. A bounded builder must enforce its own admission limit.

A successful allocation is not guaranteed. Vector construction, copying, and growth can throw if resources are unavailable. This foundation executable has no recovery handler for allocation failure; such an uncaught exception is a failed run, not a passing ownership test. Chapters 3 and 4 teach owned-resource cleanup and explicit error boundaries. No manual resource-release code is hidden in these container examples.

A live vector object can still invalidate its views

A borrow can expire before its owner object is destroyed. Reallocation replaces the element storage and invalidates references, pointers, and iterators into the old allocation. Appending without reallocation preserves existing element access, but does not enlarge a previously created span and does invalidate the old vector end iterator. Erasing elements can invalidate positions even without reallocation. See the vector modifier rules.

Use the following distinctions when predicting a mutation:

Operation Consequence for earlier access paths
Assign an existing integer element Existing views remain valid and observe the new value
Append with spare capacity Existing element references remain valid; an earlier span keeps its old length
Grow beyond capacity or reserve above capacity All earlier element access paths expire
Insert without reallocation Positions before insertion survive; those at or after it do not
Erase or shrink Removed elements cannot be accessed; earlier prefix elements can remain valid
Destroy the owner No nonempty view into its elements remains usable

A span spanning removed elements is not safe just because its first element survives. An unchanged numeric address is not proof of a valid object or a still-correct logical record. Our default discipline is simple: finish borrowing, perform a structural mutation, and then construct fresh views from the live owner. Use a narrower exception only when its actual invalidation rule is part of the interface.

A string view is a borrowed character range, not a C string

std::string owns a character sequence. std::string_view describes a read-only character range owned elsewhere. Think of the latter as the text counterpart of a read-only span: copying it does not copy the characters, and its .size() is a length, not a search for a terminating zero. Its elements are char units; a byte count is not generally a count of human-readable Unicode characters. Our fixtures use ASCII and one explicit zero byte.

We will return the part of a line before the first =. The input is borrowed for the call. The result continues borrowing from the same character owner. No separator means the entire input; a leading separator or empty input yields an empty name. No allocation is required for that extraction.

find('=') returns an index or the special value std::string_view::npos when there is no match. Test that sentinel before treating it as an index. substr(0, separator) on a string view returns another view, not an owned string. Its position is valid here, and its length comes from the successful search. The searching and substring contracts describe these operations.

Returning a copied descriptor from a function is not itself a bug. The parameter line dies on return, but the characters were not owned by that parameter in the first place. The caller must keep their actual owner alive and avoid invalidating its storage for as long as it uses the result.

A six-character view need not end at a zero byte

For the owner "amount=7", the field view has length six. The next character in the owner's sequence is =, not \0. Printing the view with std::cout << view uses the view's length, as specified by its stream insertion operation. Passing view.data() alone to an interface requiring a null-terminated C string loses that length and can consume unrelated characters or read beyond the owner. The string-view data contract explicitly does not promise null termination.

To pass an ordinary text field to a C-string API, create an owning std::string from the view and use that string's .c_str() while it remains alive. That addresses termination, not arbitrary binary input: an embedded zero still terminates a C string early. Prefer pointer-plus-length APIs when zero bytes are meaningful data. Do not read view[view.size()] to check termination; it is outside the view's element range.

The useful expected observation is an AddressSanitizer heap-use-after-free report at the stale read, with allocation and release stacks involving the vector. The exact address, line layout, and status number are not portable constants. A loader failure, unsupported sanitizer runtime, allocation failure, or the explicit status 2 guard is not that observation. The Clang AddressSanitizer documentation describes instrumentation and linking; its report-symbolization section discusses readable source locations. On macOS, xcrun dsymutil build/diagnostics/dangling-span can help produce source-location information when the report lacks it; it is not a repair for the memory error.

There is no defined “old value” that this invalid program must print. A run that seems to print 5 does not establish correctness. Sanitizers are diagnostics, not the definition of validity; the invalidation rule already determines the bug. Reacquiring a span from owner after reserve, as the normal program does, is the repair. Increasing an earlier reserve only postpones the problem unless the interface also enforces a no-growth borrowing interval.

Diagnose the relationship, not just the line that crashed

Symptom Likely misunderstanding Useful next inspection
A loop's changes disappear Its element variable is a value Compare auto with auto&, then inspect the owner after the loop
A supposed read-only parameter permits writes const applies to a descriptor Read the span's element type, not only its outer qualifiers
An older span misses a new vector element A view's length was mistaken for a live subscription Inspect its creation time and reacquire the intended range
A reserved vector rejects or crashes on indexing Capacity was used as size Establish index < size(); create elements before indexing them
A string field contains extra text in a C API A counted range was treated as terminated Preserve the length or create a suitable owning terminated string
A view fails after a function returns The actual owner was local or temporary Trace the character/element owner, not merely the returned descriptor
A view fails after growth Storage was reallocated while borrowed End the borrow before mutation and reconstruct from the live owner
Failure appears only under memory diagnostics Invalid behavior happened to look plausible before Follow the invalidation/lifetime rule; do not suppress the report

Bounds, lifetime, and meaning are separate checks. A range can be in bounds inside its old allocation yet dead. A live, in-bounds element can also hold a different row after a buffer is reused. A future operator contract will need to state both how long its batch is valid and what advancing that operator does to previous views.

What carries forward

Keep all three new sources and the appended CMake target. Only values.cpp belongs to foundation-02; the other two remain named diagnostic examples. Keep Chapter 1's sources and targets unchanged. The normal code now demonstrates owning copies, mutable and const references, returned values, range loops, array/vector storage, borrowed spans, text views, and safe reacquisition after structural mutation.

For each future borrowed interface, state the owner, permitted mutation, valid interval, and invalidating operations. A span makes range boundaries visible; it does not enforce those lifetime promises. A value type's copy can provide independent contents, while a copied descriptor still aliases its original contents. That distinction is the bridge to the roadmap's next chapter: Lifetime, RAII, and move-only owners. It will implement an owner and trace resource release rather than merely using ownership supplied by a container.
