Chapter 7 — An arena-backed skip-list memtable

Part 2 — Prepare, publish, and verify

Continue from Part 1. The arena, entry types, memtable declaration, search, and height generator are already written. We now finish src/storage/memtable.cpp, construct the complete test executable, and append its build target. Both parts share the chapter's 4.5 implementation hours. Keep the eight earlier tests.

A prepared batch is not a second visible index. It is an exclusive owner of unpublished objects and a rollback point. Its lifetime creates a useful boundary: all validation and allocation happen before publication; no ordinary recoverable failure remains once publication begins.

State Searchable entries Arena storage Height-generator state
Before preparation Committed versions Committed chunks and prefixes Committed seed
Prepared token alive Still only committed versions Old storage plus candidate nodes/values Committed seed; token holds a private candidate
Token abandoned or construction throws Same committed versions Original chunks and prefixes restored Original seed
Token committed Entire batch added Candidate storage retained Candidate seed installed

This is a failure guarantee within exclusive execution. It is not a transaction-isolation implementation, an atomic CPU instruction, or a persistence protocol. A caller must not read from another thread during either preparation or publication.

Validate and sort before constructing nodes

Each batch has one positive sequence number, greater than the table's previous committed sequence. It contains 1–256 mutations with distinct storage keys. Multiple versions of a key across batches are allowed; two changes to the same key inside one batch are rejected. This avoids an undeclared “first or last operation wins” rule.

The fixed array order stores indices into the input, not copies of its encoded values. Sort only its active prefix. The comparator from Chapter 6 is a nonthrowing strict order over the validated numeric keys; it does not call user code. Sorting and duplicate detection still belong to preparation, before we publish anything.

The factory returns Prepared{...} directly even though Prepared is neither copyable nor movable. A same-type class prvalue initializes its destination directly under the C++17-and-later rules; C++20 supports this. In auto prepared = table.prepare(...), there is no intermediate token that needs a move constructor. Do not rewrite the factory as a named local followed by return local;: named-return optimization is a different rule and cannot be assumed for this immovable type. See class initialization.

Continue the source namespace left open in Part 1:

Member initialization precedes the constructor body. Thus transaction_ already owns the arena checkpoint when a size, sequence, format, or duplicate check throws. Its destructor restores the transaction flag even though no node was allocated. A second outstanding preparation fails while constructing that transaction member; it does not reset the first token's guard.

checked_size_add computes the future version count now. Committing must not perform an overflow check that could throw after linking some nodes. Input validation also precedes span::first(change.length) in the entry validator, so an invalid length cannot create an out-of-bounds view.

Capturing changes by value in the sorting lambda copies a span, not its rows. The span remains valid throughout this synchronous constructor call. The next step copies every accepted payload into the arena; the completed token does not retain the span or refer back to the mutation array.

Register each lifetime before the next failure point

Node construction is nonthrowing for this exact Node type, as checked in Part 1. The allocation immediately before it can throw. After construction, put the node on a pending chain before allocating its value. If that value allocation fails, the new node must already be reachable by cleanup.

pending_next is not one of the skip-list links. While a token owns a node, all of its searchable next slots are still null. The pending chain has its own head and tail and cannot be reached by begin, lower_bound, or find.

Finish the constructor:

A put copies 30 event bytes or 14 account bytes. An erase has no value allocation and retains the default empty span. Mutation factories construct the usual well-formed values, but preparation still checks the public mutation fields: a caller can edit those fields directly.

Notice the order inside the loop: allocate storage, begin node lifetime, register cleanup, set scalar metadata and height, allocate value storage, then copy bytes. The potentially failing operations are before publication and are covered by the pending chain plus arena checkpoint. Scalar assignment, span assignment, and the byte-copy loop do not allocate.

The catch-all handler performs cleanup and immediately rethrows the original exception. It does not convert all failures into “not found.” When a constructor body throws, the class's own destructor is not called; fully constructed members are destroyed. We therefore need explicit pending-node destruction in the catch, followed by the transaction member's ordinary rollback during unwinding. The constructor-unwinding rules are the reason for this division, not an optional defensive convention.

Saving the next pointer must happen before destroy_at. Accessing a destroyed object to find the next node would violate the lifetime boundary. Node destruction currently releases no separate heap allocation: its payload is a borrowed span into the same arena. We still end its lifetime explicitly and keep the trivial, nonthrowing destruction restriction visible in the type assertions.

On ordinary token abandonment, the destructor body first destroys pending nodes. Only afterward are members destroyed, including transaction_, which rewinds or releases their storage. On constructor failure, the catch does the first part and member unwinding does the second. On successful commit, the pending chain is empty and the transaction is disarmed, so neither cleanup path destroys the published entries.

Trace a failed preparation

Assume an existing chunk has a committed prefix of u_0 bytes and the arena has reserved R_0 bytes. A preparation may consume the rest of that chunk, acquire another chunk, and then fail while acquiring a second new chunk. The following sequence is independent of the platform's node size:

  1. Destroy every node on the pending chain, including one whose value allocation failed. The previously committed nodes are not on that chain.
  2. Release each chunk newer than the saved chunk. Restore its cursor to u_0.
  3. Restore the saved aggregate used count and clear the active transaction flag.

Reserved storage returns to R_0 because every newly acquired chunk is released. Bytes beyond the restored cursor need not be cleared: they are outside the live allocation prefix and will be overwritten or constructed before reuse. Committed links and the committed height-generator seed were never changed.

The failure countdown is deliberately diagnostic state, not committed database state. A triggered injection disarms itself. Retrying without rearming can succeed; we do not promise to roll back a log counter, diagnostic counter, or allocator's hidden bookkeeping.

Publish against the current list, not stale predecessor paths

Preparation knows the nodes' keys, heights, and payloads. It does not save a predecessor path for each node. Those paths could become stale as earlier nodes in the same batch are linked.

At level zero, consider this initial chain and two prepared keys:

Before either publication, both keys have predecessor 10. Reusing that predecessor for 25 after publishing 20 can either overwrite the new path or create the wrong order, depending on how the outgoing link is assigned. Sorting the batch alone does not repair a stale predecessor array.

Instead, search the current index afresh for each node. At every level, record the last node strictly less than the new internal key. nullptr means that the incoming link is the table's head at that level. link(previous, level) returns a reference to that precise pointer slot.

For a participating level, first set the new node's outgoing link to the old successor, then redirect the incoming link to the new node. Other links are unchanged. If the level did not previously contain a node, its head simply becomes this node. A node of height h participates in indices 0 through h-1; higher slots stay null.

There is no recoverable failure in this function: the predecessor array is fixed stack storage, comparison is the built-in numeric policy, and the rest is pointer assignment. It neither allocates nor invokes callbacks. The earlier uniqueness checks and strictly increasing batch sequence ensure there is no identical internal key already in the table. The function therefore does not need to replace or destroy an existing node.

Correctness here is not a hardware atomicity claim. During these pointer writes, a concurrent reader would have an unsynchronized access and could observe an incomplete structure. External exclusion is part of the API contract, not an optimization that callers may omit.

Commit the entire prepared chain

After each node is linked, remove its pending-chain pointer. Install the already checked count, sequence, and candidate generator seed only after the chain has been exhausted. Finally tell the arena transaction to retain the allocations.

The first call commits; later calls see an empty chain and do nothing. There is no “empty prepared batch” ambiguity because empty input was rejected before construction succeeded. An already committed token may remain in scope without blocking a later preparation: its arena guard is disarmed.

An exception-safe operation is not automatically crash-safe. A later write-ahead log will have to record the same accepted batch and complete its required synchronization before this commit. In particular, it must not prepare copied bytes and then log a caller buffer that has been changed in the meantime. Here we establish the in-memory boundary only: no log record, disk table, or restart recovery exists yet.

The noexcept declaration expresses an obligation. If a future edit adds a throwing operation to commit, termination would replace rollback; it would not magically preserve the contract. Keep all allocation, checked arithmetic, fallible I/O, and extensible callbacks outside this path.

Freeze without pretending to reclaim versions

A frozen memtable accepts no further preparation. Freezing while a token exists is rejected so that “frozen” cannot later acquire hidden new entries. Repeated freeze calls are harmless.

The height histogram reports the number of nodes with each exact height: element zero counts height one, not all members of level zero. It is a diagnostic walk, not a cached concurrent metric.

All versions, including tombstones, remain until the table is destroyed. There is no per-key deletion of old nodes and no recycling of committed arena space. When a cap prevents preparation, a later engine layer will rotate or flush the table; this layer neither evicts silently nor exceeds its cap. freeze alone provides neither shared ownership nor synchronization for readers in other threads.

Verify the structure, not only successful lookups

A corrupt upper level might leave small level-zero scans looking correct. We need a stronger check than “the last inserted key can be found.”

First traverse level zero. Require strictly increasing internal keys, legal heights and sequences, no pending links on visible nodes, and no links above a node's height. The published count bounds traversal: reaching an additional node when seen == size_ detects an overlong chain, including a cycle, before another iteration. At the end, the count must match exactly.

Now fix an upper-level index i. Its complete chain must equal the level-zero subsequence whose nodes have height greater than i. Merely checking that an upper-level node also appears somewhere below would miss absent eligible nodes. Compare pointers to the required subsequence in order, then reject extra tail nodes:

With n versions and a height cap H, the diagnostic performs at most a constant multiple of nH steps. Here H=16. It is intended for tests and deliberate inspection, not every production read. It assumes pointers refer to live nodes owned by this table; it cannot safely validate arbitrary corrupted addresses. Sanitizers and the semantic checker answer different questions.

height_counts and this checker use ordinary pointers. Call them under the same exclusive-access rule as the rest of the mutable table. Do not mistake a const member function for a thread-safety guarantee.

An object can own a lifetime without owning its storage

Tracked increments a live-object counter during construction and decrements it at destruction. Its bytes belong to the arena, so an ordinary delete would be wrong. DestroyOnly is a custom unique_ptr deleter: it ends the object's lifetime with destroy_at but does not free the chunk containing it. The unique pointer owns the destruction obligation, while the arena owns the allocation.

The second template parameter of std::unique_ptr<T, D> is the deleter type. On destruction of a non-null owner, it calls that deleter. This is the same unique ownership mechanism from Chapter 3 with a different cleanup operation; see the unique-pointer destructor contract.

Declare the lifetime guard after the arena transaction. Reverse local destruction order then destroys the tracked object before the transaction rewinds its storage. This is an ownership relationship expressed through scope, not through a comment that cleanup “should happen eventually.”

The test casts an address to std::uintptr_t only to inspect its alignment on our native target. reinterpret_cast here exposes the address representation; it neither begins an object lifetime nor makes an arbitrary pointer safe. The allocator itself uses byte-array offsets, not integer-to-pointer fabrication.

Follow versions, borrowed values, and the preparation boundary

Start with three deliberately unsorted mutations: event 30, event 10, and account 10. Their storage keys differ even when their numeric primary keys match. The next batch inserts events 25 and 20 and writes a tombstone for event 10.

While the token is alive, neither the size nor a lookup of event 20 changes. A nested preparation and freeze both fail. Then overwrite the caller's mutation for event 25 after preparation. Committing must still install the copied put, not the caller's new erase:

The next block checks the complete order, not just the newly inserted keys. For event 10, sequence 2 comes before sequence 1. An unrestricted lookup returns the tombstone; a lookup at visible sequence 1 returns the old put with its original payload address. At visible sequence 0, no version qualifies.

Returning a tombstone is different from returning nullopt. A future lookup across multiple tables must stop when it finds a visible tombstone, rather than continue into an older table and resurrect a deleted value. This chapter does not implement that multi-table lookup, but it provides the information needed for the correct decision.

The borrowed old value survives insertion because its allocation is not moved or freed. It does not keep the table alive. Destroying the table still invalidates it, and retaining a cursor while committing does not create a consistent scan snapshot. Reacquire a cursor after a commit unless an external protocol guarantees that its iteration semantics are acceptable.

Reject malformed requests before allocating

The public Mutation representation makes explicit validation essential. The next function checks duplicate keys, empty or oversized batches, a zero sequence, a disagreement between metadata and encoded key, an excessive value length, and an invalid row-format version.

Continue with malformed tombstones, unknown enumeration values, repeated sequences, and maximum unsigned fields:

UINT64_MAX is a valid key and sequence value. Accepting the maximum sequence does not permit the next sequence to wrap to zero; the engine will eventually need a terminal sequence-exhaustion policy. This table enforces strict increase without computing last_sequence + 1, so the validation itself cannot wrap.

No test fabricates an enormous span to exercise overflow. Scalar limits and the bounded batch array provide valid objects throughout. Earlier codec tests already cover exact row lengths and all truncated prefixes; these tests add the mutation boundary rather than duplicating every decoder case.

Fail after some preparation work has already succeeded

A failed first allocation is useful but insufficient. It says little about cleanup after a partially built candidate. Keep one committed event, save its payload address and arena charges, then prepare 64 new events. The batch is large enough to need multiple chunks for this fixed node layout.

Finally exercise ordinary cap exhaustion, which is a different error from the injected allocator failure:

The histogram and charge comparison check that retries do not consume the committed height sequence or retain padding from an abandoned attempt. A matching histogram alone would not prove every node received the same height; the stronger reason is visible in the implementation: preparation changes only next_seed_, and only commit assigns it to table_.seed_.

These failures are deterministic test seams. They do not claim to reproduce all system allocator failures or operating-system out-of-memory behavior. Their role is to execute real cleanup paths at controlled points, including after partial success.

Compare against an independently expressed order

The oracle uses std::map with a tuple key. A tuple stores a fixed heterogeneous sequence of values; std::get<0>(t) and std::get<1>(t) select its first two components at compile time. Tuple comparisons are lexicographic. A map maintains one value for each ordered key and provides ordered iteration and lower_bound. See tuple element access, tuple comparisons, and the map interface.

Do not give the map our InternalLess. Sharing that comparator could let the implementation and oracle agree on the same mistake. Instead, represent an internal key as

(\text{relation},\ \text{primary},\ M-\text{sequence}), \qquad M=2^{64}-1.

Each component uses ordinary ascending comparison. For unsigned sequences s_1>s_2, we have M-s_1<M-s_2, with no underflow because both sequences lie between zero and M. Thus newer versions sort first without reusing the memtable's comparator code.

The map owns a copy of every expected byte sequence. Reference::value_type names its element type, a pair containing a const key and its associated value. Comparing it with an EntryView tests metadata, value length, and each byte:

A reproducible mixed workload

Use 300 batches with three distinct storage keys each. There are 64 possible keys: events 0–31 and accounts 0–31. Offsets 0, 13, and 26 modulo 64 make the three keys within a batch distinct. Every fifth operation by the stated arithmetic pattern is an erase; other operations alternate between the two row types according to the key's relation.

The unsigned 32-bit recurrence deliberately wraps modulo 2^{32} on the target. It is a deterministic fixture generator, not a claim about statistical quality. The skip-list's height seed is separate, so record selection does not depend on how many height bits the index consumes.

map::emplace constructs an entry from its key and value. The vector in RefValue uses the iterator-range constructor to copy the encoded bytes; it does not borrow the batch array. Continue the test file:

After every batch, compare the entire ordered iteration and every key at three visible-sequence bounds: zero, halfway to the current sequence, and the current sequence. A map lower bound is only a candidate: its relation and primary must still match, or the requested key is absent.

The final table contains 300\times3=900 versions, not necessarily 900 live user rows. The point checks total 300\times64\times3=57{,}600. Iteration comparisons and structural checks are additional work. Reusing a row's encoded bytes in the oracle does not independently test the codec; Chapter 6's Python decoder covers that separate boundary.

For those measurements, 48 chunks cost 48\times4112=197{,}376 charged bytes. The difference between reserved and used is 7{,}374 bytes. It contains chunk metadata/padding and unconsumed payload suffixes. Used bytes already include node-internal padding and inter-allocation alignment gaps, so “used” is not synonymous with application payload.

The fixed tower alone stores 16 pointers per node. It pays for transparent, ordinary object layout even when a node participates in only one or two levels. A future compact layout would need a separate, correct lifetime and allocation design; indexing past a one-element member is not that design. The native target may report different sizes. Compare invariants and printed observations, not a hard-coded ABI assumption. This fixture is a correctness and accounting check, not a throughput benchmark or a 16 GB whole-process measurement.

Force both height extremes

Generated mixed heights exercise typical paths, but they need not produce the maximum tower in a small run. Explicitly run the same insertion/lookup checks with all heights equal to one and then all equal to 16. The latter makes every level contain every node; the former reduces the index to one linked list.

Before main, understand its two compile-time checks. The _v type-trait helpers from <type_traits> expose Boolean properties. The first rejects accidental movability of the prepared token. The second uses noexcept(expression) to ask whether calling commit can propagate an exception according to its declaration. std::declval<T>() supplies an expression with type T in this unevaluated context; no token is constructed or function executed. It must not be called as ordinary runtime code. See type properties and declval.

The static assertion checks the declared contract, not the function body's semantic safety. The failure tests and the audit of operations inside commit are still necessary. Adding noexcept to code with hidden allocation would not be a substitute for preparing that allocation earlier.

Symptom Inspect first Reason
Newest lookup returns an older put InternalLess, then the visible-sequence lower bound User keys ascend, but sequences descend; a tombstone is still an entry.
A batch loses one of two nearby keys Predecessor search inside each publish call Earlier nodes in the same batch change later predecessor paths.
Failure restores entries but keeps extra charges Pending cleanup followed by the arena checkpoint Unpublished nodes must die before their chunks are released or their cursor is rewound.

What is now available

The engine now has a capped, aligned, rollback-capable allocator and a real ordered in-memory index. It stores multiple versions, preserves tombstones, performs lower-bound and visible-sequence lookups, iterates internal order, and retains stable payload addresses until generation destruction. A prepared token owns all candidate work; committing it performs only nonthrowing link and scalar updates under exclusive access.

The tests cover object lifetime and charge restoration, malformed input, borrowed payload stability, interacting inserts, maximum sequences, deterministic chunk failures, abandoned preparations, cap exhaustion, forced tower shapes, and an independently expressed reference order. None of this supplies durable commits, snapshot ownership across generations, concurrent mutation, or compaction yet.

Chapter 8 will turn this ordered entry stream into an explicitly encoded sorted table with a sparse index and Bloom filter, and implement the corresponding checked reader. It will consume the interfaces just built rather than substitute an opaque storage library. Keep this chapter's restored source and all nine passing tests as its starting point.
