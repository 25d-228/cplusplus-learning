Chapter 16 — A streaming many-to-one merge join

Part 3 — Skew, invalid streams, and snapshot checks

The engine code from Part 1 and Part 2 now composes with the existing storage and sorter. This part supplies the complete tests/merge_join.cpp, the CMake append, and runnable diagnosis. It shares Chapter 16's 5.0-hour allocation; it is not a separate project.

The reference implementation in the tests deliberately uses a map lookup and a separate tuple comparator. It may materialize small fixture data because it is a test oracle, not the production join. The engine path must still consume the account relation through AccountScan, with its configured bounded batch.

Keep fixture ownership separate from engine ownership

Start the test file with imports, active checks, exception expectations, and an isolated temporary directory. Fixture directory removal is restricted to the unique directory this fixture created; it is not a database reclamation policy. All objects using its path live inside its scope.

The following source can return a deliberately empty progress batch before each real batch. A SourceProbe can count calls or inject a malformed end or exception. The source borrows the fixture's row span; the enclosing test owns those arrays or vectors until the plan is destroyed. Only this fixture adapter uses that borrow. The database factory owns its read-view handles instead.

Type aliases instantiate one fixture source for each row/batch pair. The static assertions check the expected interfaces and output move properties; they are not substitutes for the ordering tests.

Use an oracle with different failure modes

The oracle builds a dimension map, sorts facts by independent value tuples, and looks up each account. It does not call EventOrder, either head loader, or the join state machine. Its own duplicate-dimension check catches invalid test fixtures rather than choosing one value arbitrarily.

drain is a test collector, not the production output API. It accepts empty progress, gathers copied rows, bounds fixture calls to detect a stuck loop, and checks absorbing end. A production sink should process each batch without building an unbounded result vector; complete result publication comes later.

Test the output type before the join

A capacity-two joined batch has 64 column bytes. Five different failure ordinals cover construction of its replacement's four event columns and region column. Every failed replacement must preserve the old row, the exact borrowed region address, its value, and the old charge. The remaining checks exercise whole-owner moves, self-move, cross-ledger assignment, moved-from reuse, and overflow before allocation.

Moving the destination across ledgers is particularly useful here: returning memory through the wrong allocator could otherwise be hidden by two budgets with the same numeric limit. The assertions require the old destination ledger to return to zero and the destination object to expose the source ledger. The surviving output owns decoded columns, not any table block.

Vary boundaries without changing the answer

The event fixture below has 31 rows, including a 27-row group for account 10. Missing accounts 1 and 11 remove two rows. Accounts at zero and the maximum 64-bit ID test unsigned endpoints. Fourteen dimension rows are larger than every account batch used by this test.

The Cartesian product of three event capacities, three account capacities, three output capacities, three work limits, and two empty-progress modes contains 3\cdot3\cdot3\cdot3\cdot2=162 cases. Each compares every returned field against the oracle. The test also checks all four empty/nonempty input combinations.

The test's budget->used() == output.capacity_bytes() after draining is an ownership assertion. The fixture sources have no engine-owned dynamic data of their own. Once Inputs is reset, only the consumer's column storage should remain charged. End-of-stream alone would not have released those inputs if the join retained both source objects forever.

Separate retryable preflight from execution failure

A wrong output ledger must leave its sentinel row and both source call counts unchanged. A paused move must preserve the current account head after event one has already been returned. Replacing an already-owning destination join must release its old input columns rather than leak them.

Six charged input-column acquisitions occur during simple join construction. The final block reserves all remaining root allowance and arms the next allocation to fail. The already constructed join still drains fixture sources: its kernel does not allocate. The oracle/test vector allocation is outside this engine ledger; this is not a claim that the whole process performs no allocation.

Reject broken input contracts, including unused tails

Run duplicate and descending dimension keys both inside and across batch boundaries. Duplicate keys in the tail must fail even with no events. The same reasoning applies to decreasing event keys after the account side has ended. Exact duplicate events remain legal because they represent repeated input rows, not a uniqueness violation in the dimension.

The final two loops distinguish malformed end from an ordinary upstream exception. Both sources are tested as the failing side. Previously returned output remains unchanged; the current refill is empty; removing the injected fault cannot revive the terminal plan.

Make the seven-comparison trace executable

The first call returns events 100 and 101 after exactly one account-source call. A second call returns event 102. Input counts are five and three, matched and unmatched counts are three and two, and the comparison count is seven.

The second block deliberately supplies a duplicate account after one useful row has already been staged during the failing refill. A separate earlier batch retains event 100. The partial current batch disappears, even though the internal match counter includes its discarded event 101.

This test distinguishes three facts that are often conflated: the operator may have consumed a row, counted a match, and still not have returned that row in a successful batch. A later result writer must use query completion, not a positive match counter, to decide whether a result is authoritative.

Reuse the existing native storage and sort configuration

The small sort uses three-row chunks, two-row run blocks, and three run-file descriptors. Chapter 15's fan-in calculation therefore selects two input readers plus one output writer. The database uses small table blocks so scans cross real file-frame boundaries. A 64-byte total cache allowance for one slot leaves too little room for these frames; reads exercise the charged bypass path rather than relying on an indefinitely warm data cache.

All setup helpers are given here. The seed_small rows are the roadmap's example; commit requires an acknowledged committed result rather than silently accepting an uncertain write in a test fixture.

Keep the old region with the old amount

The old day-three join has three rows. Pause after event 100, then atomically change account 10 to region 3, change event 101 from 250 to 900 cents, and delete event 102. Flush, compact, and collect while the old plan still exists.

The old plan must retain event 101 with 250 cents and region 1, plus event 102 with 700 cents and region 2. A new plan must return only events 100 and 101, both in region 3, with 500 and 900 cents. No aggregation is required to observe whether the two relations shared a snapshot.

retention().snapshots == 1 demonstrates that the two source handles share one admitted state, rather than acquiring independent views. After the old query ends, its inputs are gone even though the old facade and its statistics still exist. Collection can then reclaim formerly retained names. The earlier output batch is independent and remains readable throughout.

The fixture also proves the factory uses the real spill path: four qualifying events exceed a three-row chunk, creating two initial runs. There is no map-based shortcut for the native query.

Stream a dimension larger than the buffers

The larger fixture stores 128 accounts and 100 events, then deletes account 20. Only events with IDs 4 through 99 have day 3, leaving 96 facts. Of those, IDs 4 through 70 contribute 67 matches for account 10. Ten later facts use other existing accounts. The remaining nineteen refer to deleted account 20 or missing account 999. Thus J=67+10=77 and the visible dimension has 127 rows.

With chunk capacity three, initial run count is \lceil96/3\rceil=32. Two-way materialized passes reduce that count as 32\to16\to8\to4\to2. The last two runs are merged directly into the join, so there are four materialized passes, not five. While the query is paused, these final run owners coexist with the account scan and output columns.

The account input holds two rows, not 127. Changing the hot account's region to 99 during the pause cannot affect the old query. Subsequent compaction and collection also must not revoke its original sources. The independent map oracle compares every returned event and region; counts alone would miss a correct-cardinality join with wrong regions.

This is a native-file functional fixture on the machine running the tests. The reported counts are not throughput measurements, process-memory measurements, or a claim about how long the workload takes on an M4.

Let a right-side failure destroy left-side spill owners

For 25 input events, the tiny sorter creates sixteen files over run generation and materialized merging before its final output begins. Now make the account source throw on its first pull. The join has already invoked the left source; its failure cleanup must therefore destroy a fully built, partially consumed sort, not merely an unstarted placeholder.

The next block creates common-budget pressure after plan construction. The local sort workspace plan remains valid, but another reservation consumes the root headroom. Failure is terminal even after releasing that reservation. The last loop injects charged allocation failures at successive boundaries through sort construction, run processing, join columns, and output creation, then checks that the first successful plan matches the oracle.

SortStats stays alive after the failing plan so file and descriptor cleanup is observable. The allocation ordinal is a deterministic seam, not a portable count of all library allocations in a process. This fixture observed 41 failing ordinals before success in the Linux authoring environment; another compatible standard-library layout can change that number without changing the contract. Every tested scope still requires zero covered charge and no private temporary names once its owners have been destroyed.

Abandon output, then let ownership escape the database

A caller need not drain a stream. Destroying a paused join must release its remaining final runs and snapshot handles. Conversely, a caller may destroy the database while retaining a plan: the copied read-view handles keep its sources, lock context, and ledger alive.

The final scope reopens the same fixture database, creates a plan and output, then releases both the database and the caller's budget handle. The plan can still return event 100. Destroying that plan removes its spill files but cannot destroy the output columns. Only releasing the final output makes the weak budget observation expire.

The fixture directory objects outlive these escaped owners. Reversing that scope order would intentionally remove files while a query still needed them; RAII only works when the owning relationships represent the intended lifetime. Finish the test file with its namespace closure and entry point:

The chapter's completed boundary is an owning, bounded many-to-one merge over a spilled event stream and streamed accounts. The account value can survive refills without retaining a borrow; end and failure release the upstream plan; returned columns remain independently owned. Output is still in event-account order. Chapter 17 will establish grouping order, implement checked aggregates, and connect a complete synchronous query result.

References used in this chapter

PostgreSQL, Table Expressions, Joined Tables provides the matching-pair definition of inner joins. Our unique-dimension contract deliberately excludes many-to-many expansion and null semantics.

PostgreSQL, nodeMergejoin.c introductory notes describes ordered synchronization and why a general repeated-key join needs mark/restore behavior. This chapter implements its restricted state machine independently; PostgreSQL is not an executor dependency.
