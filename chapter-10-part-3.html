Chapter 10 · Part 3 — Failure images, pressure, and native checks

The code from Part 1 and Part 2 now has a concrete claim to test: no partially replayed batch becomes visible, and no allocation is needed between successful synchronization and publication. A round trip alone cannot test either claim. We need controlled partial effects, a completed but unacknowledged frame, and failures that occur after useful preparation work has already happened.

This final part completes the same 4.5-hour chapter. It supplies every test helper, the native-file driver, an independent decoder, and CMake additions. No separate engine solution or future database layer is needed to run them.

Model a byte image, not an imaginary durable disk

Create tests/wal_file_ops.hpp. Its fixed 64 KiB array is test fixture storage, not an engine allocation and not a simulated hardware cache. The backend keeps bytes written even when a later synchronization reports an error. That gives one permitted complete-unacknowledged image; it does not model which unsynchronized bytes a real power failure would preserve. The truncation loop below installs other byte images explicitly.

The double permits one live handle, transfers at most three bytes per call, and can interrupt individual operations. write_allowance counts successful bytes remaining before an injected write error; zero means fail the next write. A positive fail_read_on counts backend calls, not records. These are test controls, not production interfaces.

set_image requires the prior handle to have closed. The tests never silently replace the bytes underneath an active writer. The observed pointer is a short-lived diagnostic borrow: at each write/sync boundary the double checks the writer still exposes the preceding sequence and node count. close clears that pointer before the owner can disappear. No fixture callback mutates the writer.

Append the two transfer functions. Both obey Chapter 6's Transfer convention: a nonzero error is paired with zero successful bytes for that backend call. Earlier successful calls have already changed the image.

For a 17-byte allowance, the writer accepts 3, 3, 3, 3, 3, and 2 bytes, then returns EIO on the next call. File::write_all sees those successes separately and advances its offset each time. The double therefore checks the real transfer loop, rather than replacing write_all with an unrealistic all-or-nothing mock.

The offsets are converted to size_t only after being compared with the bounded fixture size. A zero read at or beyond length is EOF. An injected EIO is not EOF and must escape recovery.

Append the remaining methods and close the class/header:

A successful sync can arm the budget to reject its next allocation. The normal commit must finish without consuming that failure. The test then deliberately allocates one byte and requires that allocation to fail. This is stronger than checking only that the final byte charge is unchanged: an allocate-then-free mistake after sync could leave the same charge while still being unsafe.

fail_allocation_on(1) receives a valid positive ordinal and does not itself allocate. The test backend's methods are noexcept; do not add a throwing test assertion inside them. observe instead records a Boolean that the calling test checks afterward. The backend accepts either synchronization mode as a logical operation; it supplies no hardware guarantee for either one.

The truncate double supports only shrinking. Its injected truncate error leaves the image unchanged; its sync error can occur after a successful shrink. These are two explicit failure cases, not a general promise about native errors.

Resource-pressure tests will constrain it explicitly rather than depend on incidental allocator behavior. expect_error<Error> catches only the named error family. An unrelated exception fails the test through main instead of being counted as success.

Add the record builders, value checks, and initial-image generator:

The conditional expression in batch selects 500 for the initial event and 700 for its update. check_values checks both relations at the same visible sequence. Checking only the event would let an implementation silently omit the account. At sequence 3 the event entry must be a tombstone; absence of a version would be a different result for a versioned index.

Observe publication order and allocation timing

Append the first test. It samples the old view before the update and keeps that view only while the same owner is alive. Its observer checks both sequence and node count, so moving link publication earlier while delaying the sequence scalar would still be detected.

The first commit retries interrupted write and sync calls. Before the second, the observer's expected state becomes sequence 1 with two stored versions. Synchronization arms the failure seam. A successful second commit followed by a failed one-byte test allocation establishes that publication did not allocate through the engine budget. This does not instrument every C++ runtime allocation; the source-level commit path supplies the corresponding no-allocation argument.

The old view continues to decode 500 because these committed arena bytes were not overwritten by the update. This is sequential version access, not a complete snapshot-lifetime API. After the third batch, the table has six stored versions, although only the account remains live in the latest logical state. Reopening checks all three visible sequence choices again.

Reject before append, including late preparation failure

The next test first rejects malformed/empty batches, reserves the whole available budget, and checks a zero-cap arena. None may write another log byte or poison the otherwise usable writer. It then sweeps allocation-failure ordinals for a 48-operation batch until one whole write succeeds.

The 48-operation batch needs more than one arena chunk. A later ordinal therefore fails after earlier chunk acquisitions, not merely before any work began. The token must destroy pending nodes and return every newly acquired chunk's charge. The empty table's charge returns to zero, and the file stays at its 32-byte header.

The sweep's upper bound prevents an accidentally nonterminating test. Reaching a successful ordinal means every earlier allocator request was individually rejected once in a fresh writer. The observed count was four in the tested Clang/libstdc++ build; the assertion intentionally requires at least the frame and arena boundaries, not a particular ABI's node/chunk packing.

A definite rejection does not consume sequence 1. The subsequent valid small batch commits at sequence 1 without reopening. That is different from poison.

Keep an uncertain writer stopped

Append the partial-write and synchronization-error checks. The three write allowances exercise no reported successful bytes, a partial header, and a frame missing its final byte. The complete-tail sweep comes afterward.

The rollback check compares arena used bytes as well as the shared budget charge. A failed preparation could consume room inside an already charged chunk without changing that chunk's charge; checking only the ledger would miss that leak of arena capacity. The prior borrowed row also remains readable.

After an uncertain return, another request is rejected without any new backend write calls. Only after the old owner is destroyed does recovery trim a permitted tail and resume. With a synchronization failure the file contains a complete second frame, while the live writer still exposes only the first batch. Keeping the sync failure enabled makes opening itself fail. Disabling it allows opening to accept and synchronize both batches.

This is a complete-but-unacknowledged test image, not a process killed at an instruction boundary. It exercises the parser's permitted answer without pretending to model physical power loss or lost interprocess messages.

Cut the final batch at every byte boundary

A 100-byte final batch has 101 retained-prefix lengths, from zero through 100. The first 100 are shorter than the frame; zero leaves no tail bytes at all. For every incomplete prefix, recovery must expose exactly the preceding two rows, not one or both rows from the new batch. The complete prefix exposes both new versions. Then write again and reopen again, so stale suffixes cannot hide behind a one-time successful read.

At kept == 0, EOF is exactly at 132 and repaired_tail() is false. At lengths 1 through 23 the header is incomplete; 24 through 99 leave an incomplete body or trailer. These nonempty permitted tails are physically removed. At 100 the final frame is complete, no repair occurs, and sequence 2 is accepted.

This exhausts byte cuts of this small valid final frame. It is not exhaustive over payload contents, device failures, or all file sizes. The maximum-batch test below separately exercises the format's operation and frame-size bounds.

Corruption is not permission to discard a frame

Add helpers that require failed opening to release all charged resources and leave the physical image unchanged. rewrite_checksums is a test-only tool for making structurally checksummed but semantically invalid records; otherwise a CRC failure would prevent us from reaching inner validation.

The following test flips one chosen bit in each of the fixture's 232 bytes. It therefore covers both the complete final batch and earlier required data. It also tries every short file-header prefix; those are all fatal rather than accepted batch tails.

The structured mutations then repair their checksums after introducing a sequence gap, zero count, unknown operation, or key/row disagreement. The last case builds two account operations and changes the second key in both its envelope and its row image, so only the duplicate-key rule can reject it after codec checks.

For the duplicate fixture, each account operation is 28 bytes. Its second operation starts at relative offset 24 + 28 = 52; its envelope key is at 54 and its encoded row key at 52 + 14 + 2 = 68. Both must change to construct a true duplicate rather than an easier envelope/row mismatch. Those offsets derive from the explicit format, never from a C++ member address.

The length-bound case contains a complete final header and no body, but its repaired header checksum describes a payload one byte above the cap. It must fail before treating the absent body as a tolerated tail. The short X prefix likewise contradicts the magic and is rejected rather than removed. Complete checksums are never an excuse to ignore semantic constraints.

Opening can fail after useful replay work

A partially recovered table must not escape when reading, repairing, synchronizing, or allocating later state fails. The next test first exercises read error, truncate error, and truncate-success/sync-error cases. It then sweeps recovery allocations, including failures after earlier batches have already been replayed inside the unfinished constructor.

For the first two failure variants the deterministic image stays 149 bytes. For the third it has already shrunk to 132 before the injected sync error. Every failure closes the handle and returns all charged allocations. A later opening uses the actual remaining image, not a cached assumption about the failed call. The enabled truncate interruption is retried when repair is still needed.

In the allocation sweep the file is complete, so there is no reason to modify it. Failure may destroy a table containing replayed first-batch nodes, but their bytes still exist in the log and are replayed on the next attempt. A cleanup success is not permission to return those partial nodes to an application.

Add the format and sequence-boundary checks:

The 257-operation request is rejected, while 256 maximum-size event puts produce 11264 payload bytes and an 11292-byte frame. The final test starts a standalone log at base UINT64_MAX - 1, writes exactly one maximum-numbered sequence, and rejects the next request before addition can wrap. Reopening with the correct expected base succeeds; reopening that same file with the default zero base fails. This is arithmetic and log-generation validation, not a database with all earlier sequence history.

Exercise real files across ordinary process exits

The same test executable has a thin native mode. Add it and main to finish tests/wal.cpp. --write uses exclusive creation. --recover-append expects a permitted tail after two complete batches and appends the deletion batch after repair. --inspect opens again and checks the resulting three sequences.

No-argument execution runs the deterministic checks. Supplying --full as the fourth argument selects the existing full-device synchronization branch; otherwise the explicit choice is file synchronization. A failure remains a failing exit, not a silently downgraded success. All command modes own their file and memtable inside a budget scope; ordinary scope cleanup closes them before process exit.

The Python check supplies independent byte interpretation and invokes these modes in separate processes. It is not the storage or recovery implementation. Create scripts/check_wal_fixture.py with the following imports and decoder:

struct's leading < requests explicit little-endian standard-width fields without native alignment. The formats correspond directly to the tables in Part 1. Python's zlib.crc32 is an independent implementation from our bitwise C++ checksum. The decoder deliberately requires complete frames; it does not reimplement the engine's permissive-tail rule and then use that same rule as an oracle for itself.

After reading each batch, the reference checker applies its operations to a small Python dictionary. This is a test-only expected-state calculation, not the learner's storage implementation or an unbounded query substitute. Add it now:

Finally add the driver. It verifies the initial 232-byte file and refusal to create over it, appends a 13-byte third-header prefix, runs native recovery, and requires a 302-byte result with its original 232-byte complete prefix unchanged. The corruption case flips the final checksum and requires the native diagnostic rather than accepting any unrelated failing exit.

The temporary directory isolates every run. Only tiny fixtures are read into Python memory. The success checks remain active under Python optimization because require uses an explicit conditional rather than assert. A command timeout is a test-driver bound, not an engine performance assertion.

The tail is written by a normal Python append and the engine is reopened after normal process exits. This validates native offset/truncate/sync plumbing and file-format compatibility. It is not a crash-kill experiment, a namespace persistence test, or a physical power-loss test. Those distinctions should remain visible when interpreting a green test run.

Break the ordering without breaking memory safety

Make one temporary edit in WalMemTable::write: move the existing prepared.commit(); line from after the inner I/O try to immediately before file_.write_all(end_, image); inside that inner try. Do not move the replay commit, and do not leave a second writer commit call behind. Rebuild and run only the WAL test in both Debug and Release:

The observer sees new nodes during append even though the sequence scalar has not yet advanced. No out-of-bounds access is needed for this defect. The temporary version produced the same logical failure in the instrumented build without an AddressSanitizer or UndefinedBehaviorSanitizer report. Restoring commit to its post-sync location made the tests pass again. Restore it and rerun the complete suite before continuing.

A second useful variation needs no engine edit: change the test-only partial write allowance from 17 to 50. Predict the effect first. The header is now complete and valid, but the body/trailer is incomplete. The writer still returns uncertainty and preserves its old memtable; recovery still truncates to 132. Then change only fail_sync instead of limiting writes: all 100 bytes remain, and the reopened sequence becomes 2. Restore the published fixture afterward.

Diagnose the boundary that failed

Symptom Inspect first
A rejected batch changed file length A write happened before encoding/preparation completed, or an I/O exception reached a pre-append rejection handler
Account/event states disagree after replay Operations were published during parsing rather than after full-frame and whole-batch validation
An old view changes after an uncertain write Preparation overwrote committed bytes, or rollback used the wrong arena checkpoint
Reopen silently loses a corrupt complete final batch A checksum/schema error was converted to a tolerated EOF case
Reopen after repair fails on stale bytes The physical tail was not truncated, or the next append used physical length instead of verified end
Replay fails with a budget error Count retained arena chunks plus both temporary vector capacities; do not bypass the ledger or skip records
The first read error becomes a successful short log An I/O exception was mistaken for EOF
--full fails while the normal run passes The two runs requested different synchronization modes; inspect platform support and the actual error

The chapter ends with a log-backed memtable that encodes whole batches, exposes explicit uncertain outcomes, repairs only permitted incomplete tails, and refuses to publish an incompletely opened state. It has not installed any sorted table or chosen between log generations. The next chapter adds flush installation, authoritative manifest state, directory ownership, and database reopening; do not bolt an untracked table file onto this log and assume its bytes are now safe to discard.
