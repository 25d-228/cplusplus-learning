Chapter 22 — Recovery and resource-pressure experiments

Part 2 — Recover an allowed history, not a convenient answer

Part 1 supplies the optional directory boundary and synchronous persistence model. Keep those edits and both model files. This part adds the fixtures and the complete model test executable. All parts share the chapter's 4.0-hour implementation allocation.

Make the answer distinguish all-or-nothing behavior

Use three short batches rather than random traffic. The first establishes both relations. The second updates, deletes, and inserts. The third changes both relations again. An atomicity failure therefore has several independent ways to become visible: wrong cents, an old account region, a resurrected event, a missing account, or a value carrying the wrong sequence.

These mutations reuse the real Mutation::put encodings; they do not bypass the WAL. Expected values below are handwritten from their meanings. The table limits keep files small enough for the model's 16 KiB inode capacity. The arena, cache, and output caps remain real engine limits, not test-only replacements.

After sequence 2, event 1 has value (10,3,11) at version 2, event 3 has (20,4,5) at version 2, account 10 has region 4 at version 2, and account 20 still has region 2 at version 1. After sequence 3, event 1 has cents 13 at version 3, event 4 and account 30 exist at version 3, while event 3 and account 20 are absent. Account 10 remains at version 2. Event 2 remains absent in both states.

Ledger::permits admits only the acknowledged state, plus the single explicitly attempted successor when it has not been acknowledged. It does not allow an arbitrary lower sequence merely because recovery managed to parse it.

Seed the shape of storage, not just its rows

The same logical sequence 2 can reside in an active WAL, a sealed WAL, two delta tables, or a compacted base. Different representations stress different failure chains. seed creates each representation through real database operations and checks that all charged owners and handles are gone before returning the model.

authority decodes manifest bytes only to locate fixture files for controlled damage. It does not determine the oracle's allowed sequence or expected rows. on passes the shared model owner into the newly added boundary; the string "model" is a nonempty diagnostic path and does not name a native directory.

For the repair seed, append exactly the first seven bytes of a valid encoded batch 3 and make that incomplete tail persistent. Chapter 10's 32-byte WAL header plus the first two frames has length

32+172+158=362\text{ bytes}.

The damaged tail makes it 369 bytes. Recovery must retain sequence 2, truncate back to 362, and sync the repaired file. It must also survive a second cut during that repair. Seven zero bytes are a different experiment: once enough header bytes exist to reject the magic, the decoder reports corruption. Calling every short suffix “a valid torn append” would weaken the recovery contract.

Keep the ledger outside the crashed owner

The ordinary append sets third_attempted before entering write. Only a committed result advances acknowledged; the following checkpoint represents a cut after that observation. If the model cut causes an uncertain result, the still-live but poisoned database must reject another write. We do not retry the same batch automatically.

An exception from construction, maintenance, or the acknowledgement checkpoint passes through the same outer cleanup check. The catch runs after the local Database has unwound, so it can require zero charged bytes, zero handles, and an unlocked model. That checks host-side exception safety separately from the frozen disk image.

Recovery is also allowed to fail while constructing owners, so it needs the same cleanup check. On successful open, compare the external ledger first, then the exact logical values and versions. Returning a sequence number alone would leave most atomicity defects undetected.

Enumerate cuts in a reproducible trace

An uncut probe records the number of persistent effects in one operation. For each effect index, clone the same closed seed, arm that cut, and execute again. A non-crash system_error is not accepted as a successful injection. Require that the requested cut was reached and that no later persistent effect occurred. Then choose one of nine survival profiles and reopen twice.

The nine profiles are (stable,current) combinations for bytes and names, a five-byte append prefix with current names, two alternating-inode profiles, and two rename-only profiles. They are intentionally enumerated, not randomly chosen. A failure reports scenario, cut index, image index, and effect category. This is sufficient to reproduce one failing chain without storing a large execution log.

For the shown implementation, effect counts are 30 for append, 31 for rotation, 139 for flush, 94 for compaction, 8 for collection, and 4 for tail repair. Therefore the selected campaign contains

9(30+31+139+94+8+4)=2754\text{ crash images}.

Each is reopened twice. A changed implementation may alter the effect count; the test discovers it from its probe rather than hard-coding these totals. The effects array only checks that all eight listed effect categories occur somewhere in these traces. It is not coverage of every possible crash schedule.

The second reopen matters. The first may repair a tail or stabilize a manifest. Those changes must themselves yield the same logical answer when opened again. A recovery routine that succeeds once but leaves a differently interpreted image has not completed its job.

A failed sync can still have persisted the batch

Batch 3 is 172 bytes. After injecting a failed sync, enumerate every correct append prefix from zero through 172 bytes. For prefix p<172, the active tail is incomplete and the recovered state must be D_2. For p=172, the full valid frame survives and recovery must produce D_3, although no success was returned to the writer. The number of prefix cases is 172+1=173.

Separately, corrupt the complete final frame. Its length is no longer evidence that its payload is valid. Require FormatError, not a successful rollback that silently erases an arbitrary complete frame. Finally, make a failing file-sync call either copy to stable storage or leave stable storage unchanged. Both calls return the same error, yet the next boot can legitimately recover different complete histories.

This distinction separates availability under the stated valid-prefix model from detection of damaged data. A complete corrupt required frame deliberately prevents automatic opening. A repair tool would need a separate policy and explicit data-loss decisions; widening this chapter's normal replay to skip it would conceal rather than solve the failure.

Preparation pressure is not write uncertainty

Exhaust the charged budget before constructing a new batch: the write is definitely rejected, the old state remains readable, and the database is not poisoned. In contrast, an error once the append boundary is entered is classified as uncertain. The generic byte boundary does not promise that an error implies zero side effects, even when this particular injected case used allowance zero.

The 19-byte allowance forces multiple successful short writes before ENOSPC. Recovery of the current image must still exclude the incomplete batch. Allocation failure during reopening is different again: construction fails, all partial owners disappear, and retry without the allocation fault can recover the same acknowledged state.

The allocation sweep advances the failure ordinal until construction succeeds; its numeric count can depend on implementation details. It covers 34 failing allocation positions in the tested implementation. The initial fixture uses two delta tables so reopening allocates real metadata, readers, and recovered state. The final clean retry is as important as the thrown bad_alloc.

Required-file damage is not an invitation to search for any older file that happens to parse. A manifest has one authority. Corrupt its magic, corrupt a referenced table, remove a required log, or shorten a sealed log by an entire complete batch. Each must fail closed. A sealed file's expected final sequence comes from the manifest; “the shorter file ends on a valid frame boundary” is not sufficient to accept it.

Reclamation can succeed logically while cleanup remains uncertain

First deny every unlink. The collector must report a refusal rather than claiming removed bytes. Then permit unlink but make the following directory sync fail. Select both possible persistence outcomes: the deleted names return on restart, or they remain absent. In either case the installed database state must still be D_2, because those names were obsolete before deletion.

A surviving orphan is safe to ignore as authority, but its identity is still important. Create invalid temporary file 900, synchronize its contents and name, and reopen. The database counts the orphan without replaying it. Collection must persist a next_id fence greater than 900 before deleting the only directory evidence of that identity. After another restart, rotation must not reuse 900. This tests the protocol from Chapter 13 rather than replacing it with a counter inside the test.

Trace the failure chain across three owners

Consider rotating after sequence 2. The old manifest names the old active WAL. Rotation creates and synchronizes a new empty WAL, and prepares a candidate manifest that seals the old WAL and names the new active one. At this point:

Object Contents Namespace or authority
Old WAL Acknowledged batches 1 and 2 Required by the old manifest
New WAL Valid synchronized header, base sequence 2 New name may still be volatile
Candidate manifest Old sealed log plus new active log Not yet installed as MANIFEST

The dependency directory sync makes the new WAL name stable. Only afterward may the installer create, sync, and rename the candidate manifest. A crash after the rename may keep old or new authority; either authority has all dependencies needed to recover the acknowledged state.

Now omit just that first directory sync. The candidate's bytes can be stable, and its rename can survive, while the new WAL's binding disappears. Recovery reads a perfectly checksummed manifest but receives ENOENT opening its new active log. There is no memory error or data race. The defect is a missing persistence dependency. The rename-only profile is what makes this chain visible.

Part 3 turns this trace into a controlled diagnostic edit and contrasts it with a real process kill, where already-created names ordinarily remain in the live kernel filesystem state.
